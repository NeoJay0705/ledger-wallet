# Ledger request batch Tokio benchmark results

## Run conditions

All eight full cases completed exactly 10,000,000 replies with 50,000 users, 50,000 closed-loop coroutines, one outstanding request per coroutine, a 50,000-slot bounded channel, one batch worker, and three Tokio runtime worker threads. Each coroutine mapped to `user_id = coroutine_id % users`. The handler only echoed request IDs and deterministic opaque values.

The release-profile command for the required 2,048/5 ms case was:

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_request_batch_tokio -- \
  --iterations 10000000 --users 50000 --coroutines 50000 \
  --repetitions 1 --batch-size 2048 --batch-timeout-ms 5 \
  --sample-stride 1024 \
  --csv target/ledger-request-batch-2048-5ms.csv \
  --preflight-path target/ledger-request-batch-preflight \
  > target/ledger-request-batch-2048-5ms.log 2>&1
```

The 4,096/5 ms case used the same command with `--batch-size 4096` and the corresponding `4096-5ms` CSV/log names. Remaining timeout cases used:

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_request_batch_tokio -- \
  --iterations 10000000 --users 50000 --coroutines 50000 \
  --repetitions 1 --batch-sizes 2048,4096 --batch-timeouts-ms 1,10,20 \
  --sample-stride 1024 \
  --csv target/ledger-request-batch-timeout-matrix.csv \
  --preflight-path target/ledger-request-batch-preflight \
  > target/ledger-request-batch-timeout-matrix.log 2>&1
```

Environment: 2026-09-29, Linux 6.17.0-35-generic x86_64, rustc/cargo 1.98.1, AMD Ryzen 7 3700X with 8 cores / 16 logical CPUs visible, ext4 on `/dev/sdb2`. The GCC 13 include path supplies `stdbool.h` to RocksDB bindgen; it is needed by this workspace's native dependency build. Every strict preflight passed on its first 3-second observation. Across cases, observed CPU busy was 1.044–1.630%, target-device busy was 0.033–0.567%, available memory was about 47.0 GB, and free space was about 98.0 GB.

Every case had one final 1,664-request timeout batch. All earlier batches flushed at the configured size; the final partial batch waited for its first-dequeue timeout while its clients awaited replies. Therefore these saturated closed-loop runs did not exercise the configured timeout for full batches. The observed 1/5/10/20 ms differences are run-to-run variability, not evidence of a timeout effect.

## Stage detail for the 5 ms cases

All stage means use all ten million completions. Percentiles use 9,893 deterministic samples (request ID 0 plus IDs selected by `splitmix64(ID) % 1024 == 0`) with nearest-rank. Values are milliseconds; the tiny enqueue values are capacity-reservation waits. For every request the five stage durations added exactly to end-to-end latency before aggregation.

The mean queue wait accounts for most of the roughly 18 ms mean request latency. With 50,000 closed-loop requests outstanding and measured throughput around 2.7 million requests/s, sustained queueing is a plausible explanation; this is an inference from the workload and measurements, not a separately isolated cause. The handler interval is per-batch shared wall time copied to each request, not per-request CPU consumption.

Process `read_bytes` and `write_bytes` deltas were zero in all cases. Target-device reads were zero; target-device writes varied from 98,304 to 5,128,192 bytes and busy time from 2 to 19 ms. Those device-wide counters can include unrelated host activity and should not be attributed to this in-memory handler. The process character-read counter was about 11.5 KB; process character-write delta was zero.

The 4,096/5 ms case recorded about 2.6% more completed RPS than 2,048/5 ms in this run. Since each setting has one repetition, this is a single-host observation without an uncertainty estimate or a significance claim. It does not establish a generally faster batch size or production capacity. Raw per-stage CSVs and full logs are under `target/` as listed in the design document.

Each reply also triggers one atomic bitmap update in the ID verifier after its response-observation timestamp. That work does not enter that request's latency, but it is inside the process CPU bracket and delays the same coroutine's next request; the reported throughput and CPU include this validation cost. The verifier was identical across cases, and this benchmark did not separately measure its overhead.
