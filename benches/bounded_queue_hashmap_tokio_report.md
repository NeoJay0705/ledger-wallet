# Tokio 有界佇列 HashMap 基準測試報告

執行日期：2026-09-26。預設矩陣共完成 128/128 個情境，每個情境處理 N=10,000,000 筆請求並執行 1 次。每列都通過程式內的 ID／計數、map、各延遲指標資料流的計數與樣本數、階段總和、batch 數量及 flush 原因檢查。

執行環境：Ubuntu 24.04.2 LTS、x86_64、AMD Ryzen 7 3700X 8-Core Processor、16 個邏輯 CPU。Rust 1.98.1、Cargo 1.98.1、Tokio 1.53.1。基準測試使用 `cargo bench` 的最佳化建置設定。

## 執行命令

```sh
cargo fmt --check
cargo check --benches --locked
cargo check --locked --bench bounded_queue_hashmap_tokio
cargo bench --bench bounded_queue_hashmap_tokio -- --iterations 10000 --coroutines 8192 --latency-sample-stride 97
cargo bench --bench bounded_queue_hashmap_tokio -- --iterations 200001 --coroutines 4096 --map-state all --batch-size 2048 --batch-timeout-ms 1 --latency-sample-stride 257
cargo bench --bench bounded_queue_hashmap_tokio -- --iterations 128 --coroutines 1000 --map-state empty --batch-size 4096 --batch-timeout-ms 1
cargo bench --bench bounded_queue_hashmap_tokio
```

前三個短測試分別涵蓋高 C 下的 16 種組態、empty 與 prefilled map 下每個 key 多次出現時的回應計數，以及設定 C=1,000 時程式會採用 effective C=128。最後一條命令產生下方連結的完整預設結果。

## 測試方法與指標解讀

完整測試依序執行設定的 coroutine 數量：100000、50000、25000、12500、6250、3125、1562、781。每個 C 下，組態依序為 empty／prefilled map、batch 大小 2048／4096、timeout 1／5／10／20 ms。各情境依固定順序執行一次，沒有隨機排序。下表記錄的是這次執行結果；同一個 C 的中位數是 16 種不同組態的描述性摘要，不是重複測量的統計量。

吞吐量與延遲是不同指標：所有 RPS 欄位的單位都是百萬請求／秒（M requests/s），延遲欄位的單位都是毫秒（ms）。`completed RPS` 是 N 除以最早的 t0（開始送出）到最晚的 t6（收到回應）之間的時間。詳細表的 RPS 順序為完成、enqueue、dequeue observed、dequeue active、post-dequeue；每項都是 N 除以其對應的時間窗。enqueue 的時間窗從最早 t0 到最晚 t1；dequeue observed 從第一個 dequeue 呼叫開始到最後一筆 dequeue；dequeue active 則以所有 dequeue 呼叫內累積的 active 時間作分母。`post-dequeue RPS` 是 N 除以第一筆請求 dequeue 到最後一筆回應送達之間的時間窗；此窗涵蓋 dequeue 後的剩餘流程，且多筆請求會彼此重疊。它是整段時間窗的吞吐量，不是單筆請求延遲。每筆完成延遲則是 t6-t0；post-dequeue 延遲是單筆請求的 t6-t2。

CPU 秒數與 CPU wall 秒數使用對齊的 ProcessTime 和 `cpu_measured_at` 樣本。CPU 時間樣本在取得最晚 t6 的 coroutine 完成本地延遲與計數處理後擷取，所以 CPU 時間窗會比完成時間窗稍長；CPU wall 分母與 ProcessTime 樣本使用相同終點。核心等效數為 CPU 秒數除以 CPU wall 秒數；單核心使用率為核心等效數乘以 100%。ProcessTime 包含主協調執行緒與 Tokio worker 執行緒。

每個 request coroutine 同一時間只送出一筆尚未完成的請求。當 C 小於 batch 大小時，請求數可能不足以填滿 batch，因此 batch timeout 會明顯影響等待時間與逾時 flush 數量。滿批與逾時 flush 都是設定行為的一部分；佇列關閉時也支援尾批 flush，而這個 closed-loop 工作負載通常不會出現尾批。

各階段欄位是所有 N 筆請求的平均值，單位為 ms，依序為 `t2-t0 / t3-t2 / t4-t3 / t6-t4`：送出至 dequeue、batch 等待、batch 處理、回應送達。預設 latency sample stride 為 1024：依請求 ID 的 hash 確定性抽樣，p50／p95／p99 以抽樣資料計算；各延遲平均值則使用全部 10,000,000 筆請求。原始 CSV 另含精確的整數奈秒總和、各項樣本數與 batch duration 分位數。

## 主要觀察

- 以每個 C 的 16 種組態之完成 RPS 中位數來看，C=100000 為 1.489M requests/s，C=6250 為 3.179M requests/s。C=100000 的 CPU 核心等效數中位數約為 2.7。
- C=3125 時，batch=2048 的完成 RPS 約為 3.1–3.5M requests/s；batch=4096 且 timeout=20 ms 時約為 0.145M requests/s。因 C 小於 4096，單一 outstanding request 的工作方式無法湊滿 batch，觀察到 batch_wait 約 20.6 ms。
- C=781 且 timeout=20 ms 時，完成 RPS 約為 0.037M requests/s，batch_wait 約為 20.9 ms。低 C 下每批請求不足以填滿設定的 batch 大小，timeout 等待成為主要階段之一。

以上比較來自每種組態僅一次、依固定順序執行的結果，可描述這次量測中的差異，不能據此判定某個設定造成效能變化。
