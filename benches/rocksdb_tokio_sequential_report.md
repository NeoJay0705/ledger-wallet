# Tokio sequential RocksDB ledger benchmark 實測報告

**執行日期：** 2026-09-26。完整預設矩陣成功完成 15/15 trials；每個 trial 完成 10,000,000 筆同步寫入、關閉後重開 DB，再完成並驗證 10,000,000 次 shuffled lookup。

## 執行摘要

跨 batch size 64 到 4,096 的三輪中位數，觀察到寫入 RPS 約提升 10.4 倍，交易加權 mean latency 由 1.054 ms 增至 6.509 ms；查詢 RPS 約提升 1.06 倍，交易加權 mean latency 由 0.298 ms 增至 18.014 ms（約 60.4 倍）。這是同一固定 workload 的觀察結果，呈現吞吐量與 batch 完成延遲的取捨；不據此推論造成差異的單一原因。

| Phase | batch 64：median RPS / mean latency | batch 4,096：median RPS / mean latency | 比率 |
|---|---:|---:|---:|
| 寫入 | 60,733 RPS / 1.054 ms | 629,185 RPS / 6.509 ms | RPS 10.4×；latency 6.2× |
| 查詢 | 214,591 RPS / 0.298 ms | 227,342 RPS / 18.014 ms | RPS 1.06×；latency 60.4× |

原始產物：[stdout CSV](rocksdb_tokio_sequential_results.csv)、[preflight 與 stderr log](rocksdb_tokio_sequential_preflight.log)。指標定義及 workload 設計見 [benchmark 設計文件](../docs/01-11.development-design-rocksdb-tokio-sequential-benchmark.md)。

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench rocksdb_tokio_sequential \
  > benches/rocksdb_tokio_sequential_results.csv \
  2> benches/rocksdb_tokio_sequential_preflight.log
```

預設矩陣是 batch size 64、256、1,024、2,048、4,096，各 3 次；每輪有 10M 筆交易、10M write 與 10M lookup。每個 batch 以一個 RocksDB `WriteBatch` 原子更新 ledger、受影響 user balances 及 global sequence；WAL 啟用且 `sync=true`，依序 await blocking-pool 寫入。查詢以固定 seed shuffle ID，使用 batched multiget，並比對每筆完整 ledger value。CPU core equivalents 是整個 benchmark process 的 CPU time 除以同一 phase wall time。

## 完整性與 strict preflight

CSV 有 200 欄、15 筆資料列，每列寬度均為 200 欄。15 trials 都記錄 10M write 和 10M query transaction。每個 phase 的 batch 數等於 `ceil(10,000,000 / batch_size)`；`write_rocksdb_wal_file_synced_delta` 在所有 trials 都剛好等於 write batch 數，query phase sync delta 全為 0：

| Batch size | Write / query batches | WAL sync ticker Δ |
|---:|---:|---:|
| 64 | 156,250 | 156,250 |
| 256 | 39,063 | 39,063 |
| 1,024 | 9,766 | 9,766 |
| 2,048 | 4,883 | 4,883 |
| 4,096 | 2,442 | 2,442 |

Strict idle preflight 共 30 個 phase runs，log 有 79 筆觀察：30 次 ready、49 次 wait；所有 phase 最後均 ready，沒有失敗或調整門檻。write preflight 15 次全在 attempt 1 ready。49 次 wait 全由 `/dev/sdb2` busy 高於 5% 門檻觸發；CPU、可用空間與記憶體沒有觸發 wait。Query 預設最多等待 60 秒、每次觀察 3 秒。各輪 attempts（括號內 waits）如下：

每筆 CSV row 只在寫入狀態驗證、重開 DB 後完整 lookup 驗證、關閉 handles 並清除該 trial 唯一 DB directory 後產生。執行後 `target/rocksdb-tokio-sequential/` 沒有 `trial-*` 目錄。

## 解讀限制

- 「關閉後重開 DB」沒有清除 RocksDB block cache 或 OS page cache，不是 OS cold-cache 查詢；本次 query 的零 `read_bytes` 與可能的 cache residency 相符，但無法辨認命中哪一層 cache。
- `WalFileSynced` 是 RocksDB software ticker。本報告沒有做斷電、拔除電源或裝置 volatile-cache 驗證，因此這個計數不是物理斷電後持久性的證明。
- Flush/compaction 是非同步背景工作；計數器差值和 phase-end gauges 會涵蓋取樣視窗內的背景工作，可能影響不同 trial 的時序。idle preflight 的裝置 busy 也是整個 `/dev/sdb2` 的活動。
- Query RPS 約為 214k–232k/s；較大的 batch 對應較長的交易加權 batch latency。這些是觀察到的關係，本報告不從此單一 workload 推論其成因。
- 這是單一 host 上、固定 workload、順序寫入與 shuffled multiget 的 benchmark，不是服務端到端 latency 或 SLO 測量。

## 後續平行查詢實驗（2026-09-27）

後續另以 batch size 2,048、4,096，各設定 1、2、4、8 個在途 query batches，進行每情境三輪的平行查詢實驗。每輪仍先寫入 10M 筆交易、關閉並重開 DB，再完成 10M 次 shuffled lookup。下表列出三輪中位數；完整方法與結果見[平行查詢報告](rocksdb_tokio_parallel_query_report.md)、[設計文件](../docs/01-13.development-design-rocksdb-parallel-query-benchmark.md)及[原始 CSV](rocksdb_tokio_parallel_query_results.csv)。

本次測得最高查詢吞吐量為 batch 2,048、並行上限 4 的 733,227 RPS。該 batch 的上限 8 測得 712,442 RPS，CPU 用量升至 7.560 cores，batch p99 為 29.175 ms。batch 4,096 從上限 4 提高到 8，吞吐量約增加 2.3%（678,194 至 694,035 RPS），CPU 從 3.919 升至 7.642 cores，batch p99 從 31.921 升至 50.931 ms。
