# Bounded Queue HashMap Benchmark 實測報告

## 測試方式

本次於 2026-09-26 執行預設完整矩陣：每情境 10,000,000 筆、100,000 個循序輪替 key，request/response bounded queue 容量各為 50,000。Producer、Worker、Collector 固定為三個 thread role；每情境獨立建立 map、queues 與 threads。空 map 的建立與 prefilled map 的 100,000 個 key 初始化都在同步起跑前完成；空 map 首次 insert 與擴容列入 batch active time。

涵蓋空 map / 預填 map、batch size 2,048 / 4,096、timeout 1 / 5 / 10 / 20 ms 的完整 16 組矩陣，每組一輪。每輪都驗證收到 10,000,000 筆 response，逐筆檢查 ID 與 count，並檢查 final map 長度及 key count。四段 latency count 均為 N，四段 `total_nanos` 之和逐輪精確等於 pipeline `total_nanos`；16 組全部通過。

## 指標說明

- `enqueue latency` 是 producer 每次 blocking `send` 呼叫耗時，作為獨立指標保留。`sync_channel` 沒有精確成功入列 timestamp，receiver 可能在 sender 的 `send` 返回前取到 request，因此不能將 send 返回時刻當成無重疊的 t1；enqueue 呼叫耗時不會加入四段。
- 同一 request ID 的時間點為 t0=producer 開始嘗試 send（`Request.started_at`）、t2=worker 成功 `recv` / `recv_timeout` 返回、t3=batch map update 開始、t4=batch 所有 map update 與本地 response staging 完成且 response send 尚未開始、t6=collector 收到 response。`submit_to_dequeue=t2-t0` 含 blocking send 與 request queue wait；`batch_wait=t3-t2`；`batch_service=t4-t3`，每筆都承擔整批處理耗時；`response_delivery=t6-t4` 含 response send 阻塞、response queue wait 及 collector 取出。
- 四段 mean 使用所有 N 筆 duration 的整數 nanoseconds 總和除以 N，完整精度下可相加為 pipeline mean。各段 p50/p95/p99 是各段獨立排序後的 nearest-rank 分位數，雖使用相同 sample plan 和相同 ID，不能直接相加。`batch_service` 每筆都計入整批耗時；舊 `map_update_avg_ns_per_item` 是 batch active nanoseconds / N，定義不同。
- Enqueue latency、dequeue call latency、pipeline latency 的 p50/p95/p99 依 ID 以 `splitmix64(index) % 1024 == 0` deterministic hash sampling；sample plan 在起跑前建立。本次每個 latency stream 抽得 9,892 筆；四段 mean、count 和 total 涵蓋全部 10,000,000 筆。
- `dequeue_observed_rps` 是 N / 首次成功 recv 呼叫開始至最後一次成功 recv 返回的 wall span；其中含兩次 recv 間的 map update 和 response send。`dequeue_active_rps` 是 N / N 次成功 recv 呼叫耗時總和，呼叫耗時包含等待。Completed RPS 使用 pipeline 首筆嘗試至末筆 response 到達的 wall span。各階段 active RPS 不可相加或視為完整 pipeline throughput。
- Batch active time 累加每批 map update 與本地 response staging，不含 response channel send；batch duration 分位數涵蓋各批 active 區間。ProcessTime 是程序 CPU time（Producer、Worker、Collector）；CPU window 從 main thread barrier 返回至 collector 收到最後一筆 response。

原表 latency 欄依序為 mean / p50 / p95 / p99。Pipeline latency 單位是毫秒，batch duration 單位是微秒；四段 latency 表使用微秒。Flush 欄依序為 full / timeout / tail；batch size 欄依序為平均 / 最大筆數。

## 主要觀察

16 組平均而言，`submit_to_dequeue` 約佔完整平均 latency 的 96.8%（四段平均：26.389 ms、0.697 ms、0.077 ms、0.103 ms；完整 pipeline 平均 27.266 ms）。worker 成功 receive 前、包含 blocking send 與 request queue wait 的區間是主要等待來源；此 benchmark 無法再把兩者拆開。Enqueue send call 平均約數百 ns、成功 dequeue call 平均約數百 ns，兩者都只描述呼叫範圍，不能代表 request 在 t0 到 t2 的完整等待。Batch map update/staging 的 active ns/item 也遠小於每筆 `batch_service` 與整體 pipeline latency，因為每筆 batch_service 都包含整批處理時間，且前後仍有排隊與 response delivery。

加入 t2/t6 timestamps、四段 latency accumulator 與 t4 傳遞會改變量測成本；新版結果不能直接與舊版 benchmark 數值比較。

## 限制

本報告每情境只有一輪，沒有輪間變異或顯著性估計；跨輪中位數等於單輪值。Latency 分位數使用 deterministic hash sample 的 9,892 筆而非全部 10,000,000 筆，mean 和 total 涵蓋全部逐筆觀測。四段可加平均值，不能加各段分位數。`submit_to_dequeue` 合併 blocking send 與 request queue 內等待；`response_delivery` 合併 response send 阻塞、response queue 等待及 collector 取出，無法再拆分。CPU 是程序整體用量，one-core CPU 高於 100% 表示多個 thread 可同時消耗 CPU。這是本機同步通道與 HashMap pipeline，不模擬網路、磁碟持久性或外部到達率。
