# Tokio 單一 in-flight Account Store benchmark 設計

## 目的與工作負載

`ledger_account_store_tokio` 是獨立的 benchmark-only 帳戶交易與 RocksDB durability driver，用來比較每批同步保存餘額與背景版本化餘額 checkpoint 的成本。它直接依序 `await handle_batch(Vec<Transaction>)`，任一時刻只有一個前景交易 batch；不建立 request mpsc queue、batch coroutine、oneshot reply pipeline、projector、watermark、mock DB 或 application-data GC。Checkpoint writer 是唯一的 application-level 背景工作，可與前景交易同時執行，使用有界 queue 並以單一 writer 順序持久化。RocksDB 自己的 flush/compaction background threads 仍由 RocksDB 管理。

預設 runtime 有 3 個 Tokio worker threads。RocksDB 開啟、交易批次處理、recovery、integrity scan 及 checkpoint 寫入都放到 `spawn_blocking`；非同步 handler 等待這些工作完成，Tokio event-loop worker 不執行同步 RocksDB 操作。帳戶數預設 50,000，每帳戶 200 個 request，合計 10,000,000 個 logical requests。預設 `--workload baseline` 保留原有 40/40/10/10 mix：每個 10-operation pattern 有 4 credit、4 debit、1 refund 和 1 balance query；pattern 依帳戶 deterministic shuffle、以 credit 開始、debit 不會透支，refund 全額退回該 pattern 中最近一筆尚未退款的成功 debit。可用 `--workload credit-debit-50-50` 選擇新增 profile；每個 10-operation pattern 含 5 credit 和 5 debit，不含 refund 或 balance query，以 credit 開始，任何 prefix 都不透支，並以零餘額結束。新 profile 的兩個固定互補 pattern 保證帳戶數至少為 2 時，pattern 中間八個 wave 都同時包含 credit 與 debit；其第一個 wave 必然全是 credit，最後一個 wave 必然全是 debit，這是初始餘額為零、pattern 以 credit 開始且最後餘額為零的直接結果。其他帳戶使用依 account ID deterministic seed 產生的有效 pattern。兩個 profile 每筆金額均為 1，所有交易都應成功套用。每個 wave 每帳戶恰有一個操作：先將該 wave 的交易操作分批並逐批同步提交，再以記憶體餘額執行存在的 balance queries。這保留每帳戶時間順序，並讓 batch 保持較大。

預設交易 batch size 是 2,048 或 4,096，balance mode 各跑一次，checkpoint sequence 間距為 100,000。Baseline 預期 9,000,000 筆新交易、1,000,000 次 balance query、1,000,000 次成功 refund，以及 90 個 checkpoint snapshots；`credit-debit-50-50` 預期 10,000,000 筆新交易、5,000,000 credits、5,000,000 debits、沒有 query/refund，以及 100 個 snapshots。兩種 mode 使用相同預先建立的 pattern 和 wave account order，`tx_id`、`transaction_at` 也相同。Baseline 維持既有 ID 序列；新 profile 每位使用者每 cycle 的 10 筆交易使用連續 deterministic offsets，跨 mode 和 repetition 固定。Workload plan 及其生成時間在 trial 前建立；前景期間仍會依 plan 組成 `Transaction` batch。

## 交易與 durable commit

複合 idempotency key 是 `(account_id, tx_id, transaction_at)`，synthetic `transaction_at` 對同一 request 固定且跨 balance mode 相同。精確重複回傳先前結果，不新增 sequence；同 key 不同 body 回覆 conflict；新交易，包括 insufficient funds、無效退款、重複退款、零金額或 credit overflow 等業務拒絕，都取得遞增 ledger sequence。無效 account 是 handler error。餘額 query 直接讀取記憶體，不進交易 handler、transaction index 或 RocksDB。

交易索引提供複合 key 的精確查詢；同一 batch 的暫存索引則處理 batch 內重複 key。Refund 必須指向同帳戶、已套用且金額相同的 debit；每個 debit 最多退款一次。退款成功時 refund marker 與退款交易記錄一同提交。

每個含有新交易的 batch 只使用一個 RocksDB `WriteBatch`，原子寫入 transaction index、sequence ledger、適用的 refund marker 及 latest sequence。Per-batch mode 也在該 batch 寫入已變更的帳戶餘額；checkpoint mode 不在交易路徑寫入餘額 key。WAL 保持啟用並設定 `sync=true`。只有 RocksDB write 成功後才發布記憶體餘額與 sequence；寫入錯誤會使 handler/trial 失敗，不會回覆成功。Ledger 在此階段保留供 restart replay，沒有 application-data GC。

## 餘額保存與 recovery

| Balance mode | 交易 batch 同步保存 | 重開時恢復 |
| --- | --- | --- |
| `per-batch` | index、ledger、refund marker、latest sequence 與變更餘額 | 讀取每個帳戶的 balance key |
| `checkpoint` | index、ledger、refund marker 與 latest sequence | 讀取最新 valid manifest/chunks，再重播其後 ledger；若沒有 manifest，從 sequence 1 重播 |

Checkpoint mode 在每個新 sequence 越過 `--checkpoint-quantity` 的倍數時，於 batch commit boundary 複製一致的完整 50,000-account memory snapshot。若單一 batch 跨越多個 threshold，會各排入一個 snapshot，snapshot sequence 可高於精確 threshold。Queue capacity 為 2；滿載時前景 handler 在 enqueue 上 backpressure。Checkpoint worker 順序工作，每個 generation 先將最多 1,024 帳戶一 chunk 的所有 chunks 寫進同一個 `sync=true` WriteBatch，再用第二個同步 WriteBatch 發布帶 checksum、sequence、帳戶數及 chunk 數的 manifest，並刪除前一代 chunks。Manifest 發布前中斷的 orphan chunks 不會被 recovery 當成已發布資料，recovery 會清除它們。Manifest 若存在但格式、chunk 或 checksum 無效，recovery fail closed；不會靜默改以完整 ledger replay 掩蓋已發布 checkpoint 損毀。

Benchmark 在前景 request window 結束後先讀取一次 foreground I/O counters，再 drain checkpoint queue。Settled wall 從前景開始到 drain barrier 完成計時，因此包括 foreground 結束後的 I/O 觀測間隔；`checkpoint_drain_wall_s` 只計 I/O 觀測後的 barrier/drain 時間，所以 settled wall 不等於 foreground wall 加 drain wall。Settled ProcessTime 從前景開始到 drain 完成，也包括該觀測間隔；foreground CPU 在前景結束點停止。Settled I/O counters 在 settled wall/CPU endpoint 後取樣。接著明確停止並 join checkpoint worker，關閉 DB，再計時 close/reopen recovery。Recovery 後另以獨立計時執行完整 index/ledger integrity scan，檢查 contiguous sequence、唯一 index sequence 及每筆 index payload 與其 ledger payload 相同。最後驗證所有帳戶餘額與最新 sequence，取得 DB directory bytes 後才清理由每個 trial 擁有的 DB directory。

## 參數與量測

主要 CLI 參數為 `--workload baseline|credit-debit-50-50`、`--users`、`--waves`、`--iterations`、`--batch-sizes`、`--modes`、`--repetitions`、`--checkpoint-quantity`、`--output-dir` 與 `--preflight-*`。`--iterations` 必須能被 users 整除，換算後 waves 必須是 10 的倍數。Time-based checkpoint trigger 在此 isolated 比較中停用。每個 trial 先建立 workload plan 及新 DB，再對該 case DB 執行 committed idle preflight；preflight 通過後立刻開始 foreground measured window。Preprocessing 不計入 RPS，plan generation 秒數另列。每 case 使用唯一 DB directory；成功或失敗都由 cleanup guard 嘗試移除。

Idle preflight 每 case 執行一次，預設觀察 3 秒、最長等待 60 秒、CPU busy 上限 10%、target device busy 上限 5%、可用記憶體至少 128 MiB、預留空間至少 1 GiB，並額外依 logical requests 數量估算資料庫空間。可用 `--preflight-observation-ms`、`--preflight-timeout-ms`、`--preflight-max-cpu-pct`、`--preflight-max-disk-busy-pct`、`--preflight-min-mem-bytes` 和 `--preflight-free-reserve-bytes` 調整。Preflight、workload plan 與 DB 初始化都在計時前完成；每 case 若 preflight 失敗就不執行 workload。

CSV 同時報告 workload name、operation totals、foreground completion window 與包括 checkpoint drain 的 settled window：all-request/transaction RPS、ProcessTime CPU 秒與 core equivalents、process `rchar/wchar` 和 storage read/write bytes、target block-device I/O、RocksDB WAL sync/bytes、flush/compaction/stall ticker delta。交易 handler 與存在的 balance query 分開報告 latency mean/p50/p95/p99；mean/count 納入所有對應 requests，percentile 用 account/request ID hash 決定的 deterministic sample。沒有 query 的 `credit-debit-50-50` CSV row 將 `query_handler_latency_status` 寫為 `not_applicable`、sample count 寫為 0，latency 欄留白，避免把零誤讀成量測延遲。交易 handler latency 是每一批共用的 request wait wall span（包含同步 commit、memory publish 和 checkpoint enqueue backpressure），不是每 request CPU 使用量。Balance latency 是直接記憶體查詢的實際 wall span。

Batch phase mean 以 batch 數為分母。`batch_read_build_mean_ns` 包含 RocksDB index/refund lookups 與 ledger/index record construction，不含最後 latest-sequence/餘額 key staging；`batch_wal_sync_mean_ns` 包含後者及 `DB::write_opt` 的同步 WriteBatch wall time，不應解讀為純 fsync 時間；`memory_publish_mean_ns` 只計 memory balance/sequence update，不含之後的完整 checkpoint snapshot copy。Checkpoint snapshot、queue wait、chunk sync、manifest sync 與 checkpoint wall duration 分別輸出；queue wait 和 checkpoint wall duration 可能與前景/其它階段重疊，這些 phase mean 不可相加當成不重疊的端到端分解。

結果另列 checkpoint 數量、enqueue 數、最後 checkpoint lag、checkpoint 累計工作時間、recovery 秒數、integrity scan 秒數及 cleanup 前 DB bytes。Checkpoint failure 會讓 trial 失敗；不會把 foreground completion 的 RPS 當成包含背景持久化成本。Settled RPS 將同一 request count 除以從前景開始至 drain barrier 完成的 wall time，當中包含 foreground I/O 觀測間隔；它不以 foreground wall 與 drain wall 的算術和作分母。CSV 與 run log 寫在 `target/ledger-account-store-trials/` 內的唯一 run directory；preflight 要求 benchmark 路徑位於可辨識的非 volatile block device。

Default full matrix 是 batch sizes 2,048/4,096 乘上 per-batch/checkpoint 四個 case，各執行一次 10M requests。新增 profile 使用同一 matrix，且同樣每 case 建立 10,000,000 筆新 durable transactions。短 smoke 範例如下；它仍執行 idle preflight，但以較短觀察與較寬鬆門檻縮短驗證時間：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_account_store_tokio -- \
  --users 10 --waves 20 --batch-sizes 32 --modes per-batch,checkpoint \
  --checkpoint-quantity 10 --preflight-observation-ms 50 \
  --preflight-timeout-ms 5000 --preflight-max-cpu-pct 100 \
  --preflight-max-disk-busy-pct 100 --preflight-min-mem-bytes 16777216 \
  --preflight-free-reserve-bytes 1048576 \
  --output-dir target/ledger-account-store-smoke
```

新增 profile 的 smoke 以相同參數加上 workload selector：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_account_store_tokio -- \
  --workload credit-debit-50-50 --users 10 --waves 20 \
  --batch-sizes 32 --modes per-batch,checkpoint \
  --checkpoint-quantity 10 --preflight-observation-ms 50 \
  --preflight-timeout-ms 5000 --preflight-max-cpu-pct 100 \
  --preflight-max-disk-busy-pct 100 --preflight-min-mem-bytes 16777216 \
  --preflight-free-reserve-bytes 1048576 \
  --output-dir target/ledger-account-store-smoke-50-50
```

RocksDB build 需要 libclang 與 C/C++ toolchain。上方 GCC 13 include 路徑是目前開發環境的 bindgen workaround；其他主機應改成當機 GCC toolchain 對應的標準 include path。
