## 目標與比較範圍

本 case 量測每個帳戶固定路由到專屬 DB worker 時，使用固定 48 條 data connections 的服務吞吐、延遲、資源與錯誤行為。

ScyllaDB 固定為三個 node，每 node 使用 4 個 shards。每 node、每 shard 使用 4 條 PerShard pool connections。因此目標資料連線總數為 `D=3*S*P=3*4*4=48`，每 node 為 16 條。控制連線另行分類，不計入 D。

服務使用 `C=50,000` 個 DB workers。這些 workers 與 50,000 個 users 一一對應。每個 `account_id` 固定路由到同 index 的 worker。這個 case 使用明確 per-user routing；舊 worker round-robin routing 保持為既有模式。

本 case 中，`C` 表示 DB workers 及其交易／CQL in-flight 上限。`D` 表示 Scylla driver pool 的目標資料連線數。兩者獨立設定和稽核。Shared `Session` 可在資料連線上 multiplex requests；每個 worker 不獨占一條實體 connection。

唯一性能參考為既有 `S4/C48/P4` case 的前兩次有效結果：median RPS `9176.983178`，median p99 `25.425870847` 秒。新 case 的 C 從 48 改為 50,000，routing 從 round-robin 改為 per-user。這不是只改 worker 數的受控比較，不得將差異歸因於單一因素。

本 case 不比較 RocksDB、不增加 LWT、不改 CQL batch、不改 consistency level、不改 fsync 模式，也不改 deadlines。

## Workload

每個 trial 使用 50,000 users。每個 user 對應一個 account，並依序送出 200 筆交易，共 10,000,000 筆交易。

每個 account 的交易為 amount 1 的 Credit 與 Debit 交替。每個 account 有 100 筆 Credit 與 100 筆 Debit。每個 caller 必須 await 當前 request 的 reply 後，才送出下一筆 request。

每個帳戶仍由 account owner lock 保護。相同帳戶的交易依序執行。Per-user worker routing 不取代 owner lock，也不提供跨服務程序的 writer fencing。

Seed 和完整驗證都在計時窗外執行。兩者的最大並行工作數為 `min(C,D)=48`。每個帳戶初始 balance 為 100。完整驗證須檢查 50,000 個帳戶及全部 10,000,000 筆 ledger rows。

## 固定交易與耐久契約

每筆交易維持既有 wallet schema 與 idempotency key `(account_id, tx_id, transaction_at)`。服務先讀取 static account state 與既有 ledger，再依序計算並提交。每筆交易仍使用兩個 SELECT 和一個 single-partition UNLOGGED BATCH。Batch 保持兩個 statements，原子保存目前 balance/version/write clock 與完整 immutable ledger row。

Wallet read、write、replay 及 verify 一律使用 `CL=THREE`。Keyspace 使用單一 DC、RF=3 和 `durable_writes=true`。三個 node 使用既有固定 release 與 `commitlog_sync=batch`。成功 reply 必須符合既有 fsync 後 acknowledgement 契約。

Driver retry 和 speculative execution 維持關閉。不得降低 CL、改用 periodic commitlog、增加 retry、改變 2 SELECT + 1 BATCH，或調整既有 driver/server deadlines。

相同 key、相同 body 必須安全 replay；相同 key、不同 body 回傳 conflict。Insufficient funds、overflow 及 invalid amount 的拒絕結果仍須持久化。任何 write 產生未知提交結果時，freeze 該帳戶並 fail closed；不得假裝交易未提交或自動重試。

每個 worker queue 容量為 1。全域 admission 上限為 50,000 個 accepted/outstanding jobs，並包含 queued 與 active jobs。超過上限的 request 明確拒絕或等待 admission，且不得造成未受限的 pending-job 記憶體成長。

## 主機與 server profile

沿用三個 pinned ScyllaDB node、image 與 source evidence、strict formal preflight、必要監控、ownership labels、資料驗證和 cleanup。Image 維持 `scylladb/scylla@sha256:333b9ab3a3214c7f98af100711c51df7f58964e8227e6d26050e889ebb216df1`。

S4 node CPU affinity 固定如下：

| Node | CPUs |
| --- | --- |
| A | 0,1,8,9 |
| B | 2,3,10,11 |
| C | 4,5,12,13 |
| Service、load 與 monitoring pool | 6,7,14,15 |

S4 使用每 node 兩個 physical cores 的四個 SMT threads。三個 Scylla nodes 共用同一 host 和 SSD。報告必須說明這個資源邊界，並記錄 node、service、load 與 monitor 的 CPU 及記憶體成本。

50,000 個 worker tasks、per-account owner state 和 50,000 個全域 admission slots 可能增加 service RSS、CPU、queue latency 和 scheduling cost。這些成本是本 case 的觀察對象，不得移除 worker 或縮小 workload 以掩蓋成本。

## 單次執行與結果分類

完成單元測試、build、CLI dry-run、source/binary 對照及 root review 後，只執行一次完整 10M request custom formal case：

```text
--mode formal
--shards 4
--workers 50000
--per-shard-pool 4
--worker-routing per-user
--users 50000
--requests-per-user 200
--repeats 1
--skip-build
```

此命令只執行單一 custom case。即使 trial 通過，也只能報告 case pass；runner run 狀態仍是 `formal_partial`，exit code 為 1，不能稱作完整 27-case formal pass。不得另跑九-case matrix，也不得把此 case 合併進舊矩陣統計。

Trial 通過須同時符合：10,000,000 requests 全部完成；沒有未知結果；required metrics、driver pool readiness 與連線稽核有效；沒有 driver retry、speculation 或 timeout；50,000 個帳戶和 10,000,000 筆 ledger 完整驗證；owned resources cleanly cleanup。

若遇到 overload、timeout 或其他錯誤，保留 error kind、原始 driver error text、driver/server metrics、service latency/resource samples、ledger verification 和 cleanup evidence。不得因未知結果重跑，不得調高 timeout、放寬 gate 或降低 workload。錯誤 case 不納入有效性能結果。
