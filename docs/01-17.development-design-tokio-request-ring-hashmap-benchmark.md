# Tokio Request Ring Buffer HashMap benchmark 設計

## 目的與比較範圍

新增 `bounded_queue_request_ring_tokio` 作為獨立的 in-process HashMap pipeline benchmark。既有 per-request `mpsc` 與 batch-pool benchmark 保持原狀。新測試採用一個固定容量 ring，容量為 50,000 個 `Request` slot；不建立每筆 dequeue，也不把批次的 Request 搬到暫存 `Vec`。

預設每種情境處理 10,000,000 個 ID，key 為 `id % 100000`，map 初始狀態為 empty 或 prefilled。C 為 100000、50000、25000、12500、6250、3125、1562、781；B 為 2048 或 4096；timeout 為 1、5、10 或 20 ms；每情境一輪，共 128 種組合。使用 3 個 Tokio runtime worker threads、一個 ring batch worker，以及 C 個 closed-loop coroutine。每個 coroutine 同時只保留一筆 outstanding Request，並等待 oneshot 回傳原 ID 和 map count。

## Ring 索引、發布與批次處理

Ring 是固定配置的 50,000 個 `UnsafeCell<MaybeUninit<Request>>` slot；建構後不擴充或重新配置。唯一的 `Metadata` token 綁定 ring identity，且由 ring 一次性簽發。所有 producer append、seal、consumer claim 與 reclaim 的索引狀態都在同一把 Tokio async metadata mutex 下更新。

Producer 在 metadata mutex 下檢查 `tail - head < 50000`，把 Request 寫入 `tail % 50000`，初始化 live flag，然後增加單調遞增的 `tail`。寫入不含 await；取消發生在發布前時不改 tail，Request 隨 future drop。發布後，worker 必須處理它一次，即使 response receiver 已被取消。超過 capacity 時 producer 等候 slot reclaim，Notify future 會在讀取 occupancy 前註冊，並以 RAII waiter counter 追蹤取消；reclaim 最多對已註冊 waiter 發出與釋放 slot 數相同的 `notify_one`，避免 C 個 coroutine 一起被喚醒。

Ring 的 `seal` 以 `sealed_tail..tail` 產生不允許複製或偽造的 FIFO range token。唯一 worker 依 ready queue 順序 claim range，metadata 記錄正在處理的結尾位置。worker 在 mutex 外依實體 slot 順序直接更新 map 與 staging count；環繞時以陣列尾端和起點的至多兩個 slice 遍歷，不複製 Request。Producer 可同時 append 到不相交的空閒 slot。容量以 `tail - head` 計算，active、sealed、processing 都仍佔用容量。

批次達 B 時立即 seal；active 第一筆 admitted request 起算 T，到期後由 timer task seal partial batch。所有 N 個 ID 已送出不會觸發提前 partial flush。成功關閉時會明確檢查 active tail，必要時以 `tail` reason seal，但 closed-loop 正常情境應由 timeout 或 full seal 完成所有批次。

handler 完成並記錄 `t_done` 後，worker 逐 slot 嘗試所有 oneshot send。之後重新取得 metadata mutex，在沒有 await 的臨界區 drop 整批 slot、再推進 head 並釋放 claim。回覆可能先喚醒 coroutine；在 head 前進之前，tail-head 仍保護原 slot 不被覆寫。若 task 錯誤或取消，ring final Drop 依 live flag 清理所有尚未 reclaim 的 Request。Live flag 在 drop value 前清除，避免 unwind 時重複 drop；benchmark Request 欄位的 destructor 不會 panic。

Unsafe 操作只封裝在 `benches/support/request_ring.rs`。`FixedRing` 對每個 slot 使用 release/acquire live flag；其 `Sync` 不變量依賴唯一 metadata token、producer 對 tail 的 mutex 序列化、worker 的單一 range claim，以及 `tail - head < capacity` 保證 producer 和 batch slot 範圍不重疊。Safe API 驗證 ring metadata/range identity、range FIFO、單一 claim、slot 初始化狀態與完整 reclaim 順序。

## 計時邊界與輸出

逐筆 timestamp 使用和 batch-pool 相同的邊界：

- `t0`：開始 admission wait 前。
- `t_admit`：Request 寫入 slot 並發布 tail 後。
- `t_seal`：整批 range 被 seal 時。
- `t_start`：worker 開始更新 HashMap 時。
- `t_done`：整批 map 更新/count staging 完成、response send 開始前。
- `t6`：client 收到 oneshot response。

五段 latency 為 `t0→t_admit`、`t_admit→t_seal`、`t_seal→t_start`、`t_start→t_done`、`t_done→t6`。每段 mean、count、sample count 和 total nanoseconds 均輸出；mean 與 total 使用全部 N 筆，p50/p95/p99 使用依 request ID 透過 `splitmix64(id) % stride == 0` 選出的 deterministic sample，預設 stride 為 1024。程式逐輪確認五段 total 精確等於 end-to-end total。

另輸出 completed/admission RPS、ProcessTime CPU seconds、CPU measurement wall seconds、core equivalents、batch active duration/size、full/timeout/tail flush 數、ring full wait time/events、peak occupancy、wrapped-batch count 與檢查數、response count verifier、final HashMap verifier 及 map length。`t_start→t_done` 僅計 map update 和 count staging；response dispatch 位於 `t_done→t6`。CSV 寫到 stdout，scenario progress/error 寫到 stderr；失敗情境不輸出成功 row。

Ring full wait 表示 tail-head 已達 50,000 後，等待 worker 完成某批並 reclaim slots 的時間。與 batch-pool semaphore acquisition、reserved-but-unadmitted、buffer availability 等欄位不相同；兩個 benchmark 的 backpressure 機制不同，結果只作描述性比較。兩者亦可能在不同日期量測，單次執行無法隔離環境與執行順序的影響。

## 驗證與命令

Ring storage 測試涵蓋固定小容量多次環繞、滿載拒絕、處理中 producer append 到不相交 slot、ring identity/one-shot metadata、確定性反向 producer admission 順序、取消 full waiter 後計數釋放、按 reclaim slot 數限制喚醒，以及錯誤/取消後 Drop 清理。

基本命令：

```sh
cargo bench --bench bounded_queue_request_ring_tokio
```

短測可用以下命令覆蓋 N 大於 ring capacity、不同 map state、完整批次和 timeout partial batch：

```sh
cargo bench --bench bounded_queue_request_ring_tokio -- \
  --iterations 60001 --coroutines 60001 --map-state all \
  --batch-size 2048 --batch-timeout-ms 1 --latency-sample-stride 257
```

`C=1,N=1,B=4096` 可驗證有限 timeout 下的單筆 partial batch。完整預設 128 情境執行一次，輸出保存在 `benches/bounded_queue_request_ring_tokio_results.csv`，執行資源檢查與進度記錄保存在同名前綴的 log，結果彙整於 `benches/bounded_queue_request_ring_tokio_report.md`。
