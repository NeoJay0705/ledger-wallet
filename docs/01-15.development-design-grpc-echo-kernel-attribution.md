# Tokio 同機 gRPC Echo Kernel 層監測與瓶頸歸因

## 目標與範圍

本設計擴充 `benches/grpc_echo_loopback.rs`，在既有 parent trial 的 `PHASE_START` 至 `PHASE_END` 量測窗中，以 opt-in 方式收集 kernel 層與 socket 層資料。既有 96-case 基準矩陣預設不啟用密集採樣或 perf；一般執行的新增成本只包含設定值與 metadata 記錄。

此工具只描述兩個 Tokio 程序經 `127.0.0.1` loopback 進行 unary gRPC echo 的結果。HTTP/2 會在單一 TCP channel 上多工多個 RPC，因此 TCP 與 kernel 數值以程序、socket endpoint 或整條 TCP flow 為範圍，不能換算成單次 RPC latency，也不能據此宣稱實體網路或 NIC 行為。

## CLI 與輸出

- `--kernel-sample-ms 100` 啟用密集 socket 採樣；`0` 關閉，預設為 `0`。週期採樣在收到 `PHASE_START` 後開始，目標 server port 的 client/server 兩側都獨立輸出。另在收到 `PHASE_END` 後做一次邊界快照，該快照只用於 TCP counter delta，不列入 phase 內的 queue maxima。
- `--perf-mode off|stat|record` 控制 perf。`off` 預設不呼叫 perf；`stat` 對 client/server 分別量測 task-clock、user/kernel cycles、user/kernel instructions、context-switches、CPU migrations；`record` 限定 closed-loop C=256，兩個程序各輸出 49 Hz CPU call stacks 與 `perf report` 摘要。
- `--perf-bin PATH` 指定 perf 執行檔，預設 `perf`。指定 `stat` 或 `record` 時，先以相同事件集附加到 parent process 做權限 preflight。未通過即在 `perf_preflight.log` 記錄命令、版本、核心限制和錯誤並停止該次 perf run，不靜默改成別種指標。
- 每個啟用 socket sampler 的 trial 產生獨立 `*.kernel_tcp.csv`。其中快照列保存 CLOCK_MONOTONIC 時間、phase 起訖 offset、client/server endpoint、兩端 Send-Q/Recv-Q、skmem、TCP_INFO raw string 與常用欄位；counter-delta 列保存每條 flow、每個 endpoint 的 TCP 累積計數首末值與差值。
- trial diagnostic log 記錄 `ss -tinmH` 命令、採樣次數與失敗數、樣本牆鐘總時間、parent process CPU 與已回收 ss subprocess 的 CPU 時間、最久單次命令時間、monitor wall-time 比例、各 endpoint 的已觀察 queue maxima，以及 perf 命令、輸出、狀態與相對 phase 邊界 offset。
- parent 的 `results.csv` 保留既有 RPS、E2E latency 分位數、client/server CPU core equivalent 等欄位。密集採樣原始資料獨立保存，避免把 TCP counters 或 queue 快照當作逐 RPC 指標。

## Socket 與 TCP_INFO 取樣

採樣器以設定間隔執行 `taskset -c 6,7,14,15 ss -tinmH 'sport = :PORT or dport = :PORT'`，將 monitor subprocess 固定在未分配給 benchmark worker 的 CPU，並只要求本次 trial server port 的 sockets。若 socket local port 是 server port，歸類為 server endpoint；若 peer port 是 server port，歸類為 client endpoint。每條 channel 預期各有一個 client 與 server endpoint，並以雙端 tuple 作 flow key。CSV 將 socket 的送出方向與接收方向明確標成 client-to-server 或 server-to-client。

快照列中的 Send-Q、Recv-Q、`skmem` 與 TCP_INFO 欄位是取樣當下值。`kernel_snapshot_max_*` 僅表示已觀察快照的最大值；採樣間隔內可能出現未被觀察的尖峰，不能由零或低 maxima 推論整段測量從未積壓。TCP_INFO 的 bytes、segments、delivered 等累積 counter 則另外以同 endpoint 的 phase 內第一個樣本及 phase-end boundary 樣本計算 `end - start`，並保留 start、end 與 delta 三值。Counter delta 的 boundary offset 會揭露樣本相對 `PHASE_END` 的延遲。

TCP_INFO 欄位包括可用時的 RTT、RTO、cwnd、ssthresh、MSS、unacked、notsent、bytes sent/acked/received/retransmitted、segments、delivered、retrans、busy、rwnd/sndbuf limited、delivery rate 與 pacing rate。`busy`、`rwnd_limited`、`sndbuf_limited` 另以 first fully in-phase sample 與 phase-end boundary sample 的 millisecond delta 輸出為 `busy_ms`、`rwnd_limited_ms`、`sndbuf_limited_ms`；比例分母使用兩個 snapshot 的 monotonic observation interval，不使用 `ss` 括號中的 connection-lifetime 百分比。TCP_INFO 的 `busy` 是 socket 的累積 busy 狀態時間，不是 CPU busy time；不能與 `/proc/stat` CPU busy 或 process `task-clock` 混用，也不能據此歸因 CPU 瓶頸。核心 `ss` 版本若沒有提供某欄位，raw string 與 CSV 空欄可供辨認，不能把缺欄補成零。

## Perf 與權限

`perf_event_paranoid`、目前 effective capability、perf 版本與 preflight 結果會寫入 run artifacts。`stat -v` 會記錄各 event 的 time enabled/time running；若有 multiplexing，報告應以此比例限定 cycles/instructions 比較。工具不改 `perf_event_paranoid`、不調整其他全機 sysctl，也不假設 `CAP_PERFMON` 可授權 bpftrace 或 tracefs 讀取權；此設計不執行 bpftrace。Perf sampling 以 `--perf-bin` 指向明確路徑，讓管理者可把 CAP_PERFMON 設在專用 perf 複本上，不必改系統共用的 perf 檔案。

此主機的 `/usr/bin/perf` 是 shell wrapper；實際 ELF 為 `/usr/lib/linux-tools/6.17.0-35-generic/perf`（perf 6.17.13）。本次以其專用複本 `target/grpc-echo-perf` 執行；`getcap` 顯示 `cap_perfmon=ep`，並且實際 perf preflight 成功。若複本需重建，可執行：

```sh
sudo install -Dm0755 /usr/lib/linux-tools/6.17.0-35-generic/perf target/grpc-echo-perf
sudo setcap cap_perfmon=ep target/grpc-echo-perf
getcap target/grpc-echo-perf
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --bench grpc_echo_loopback -- --payload-sizes 128,4096 --concurrencies 256 --channels 1,8 --modes closed --repetitions 3 --warmup-seconds 5 --seconds 20 --perf-mode stat --perf-bin target/grpc-echo-perf --kernel-sample-ms 0 --output-dir benches/grpc_echo_kernel_data/perf_stat_verbose_targeted
```

執行時 `perf_event_paranoid=4`、`unprivileged_bpf_disabled=2`；專用 ELF 的 perf permission preflight 對 task-clock、cycles:u/k、instructions:u/k、context-switches、cpu-migrations 都讀到有效值，無 permission/access denied。Perf stat 輸出每個 event 均有 100% time-running 比例。原本無 CAP_PERFMON 時的拒絕紀錄也保留於 `benches/grpc_echo_kernel_data/perf_preflight/`。此主機的 `perf list` 雖能列出 syscall/sched tracepoint，對 target PID 執行 `perf stat` 時仍因無法讀取 `/sys/kernel/tracing/events/...` 失敗；未掛載或 remount tracefs，也未更動 sysctl。故 syscall 次數與 `sched_switch` 無法歸因。

`stat` / `record` monitor 在 parent 收到 `PHASE_START` 後附加於 client 與 server PID，觀察到 `PHASE_END` 後立即送 SIGINT；所有 `/proc`、TCP_INFO 與 ss 邊界樣本在等待 perf finalize/report 前完成。Client 的 completion timestamp 和 ProcessTime endpoint 不受 parent 的 perf wait 延長；client 持有 channel 至 ACK，使 parent 能在 phase-end 擷取 socket 後收結果。附加與停止並非原子地與 worker 時鐘邊界同時發生，故每個 monitor 的實際 start/end offset 與總觀察時間都必須保留；短窗口或 offset 較大的結果不作精確 phase counter 解讀。Record 使用 DWARF call stacks，負擔高於 stat，故僅對 128/4096 B、C=256、ch1/ch8 各一個代表 trial 收集，並獨立於效能比較。

本次 `perf record` 的 `.perf.data` 均非空、`perf report --stdio` status 為 0 且沒有 lost samples；stderr 提示 `/proc/kallsyms` 受限，kernel samples 可能無法解析。報告可討論有符號的 user-space 樣本，但 `[unknown]` kernel 地址不得猜成特定核心函式，也不要求 CAP_SYSLOG。

若 perf preflight 失敗，仍可用 `--perf-mode off --kernel-sample-ms 100` 完成 socket、`/proc`、loopback 與 per-core softirq 歸因。Kernel CPU cycles、task-clock、instructions 和 context-switches 則標示為未取得；不得以 TCP_INFO、softirq tick 或程序 CPU core equivalent 取代這些 perf 指標。

## 實驗矩陣與控制

正式測試沿用 strict idle preflight：每 case 至少觀察 3 秒，CPU busy 不高於 10%、目標 block device busy 不高於 5%、可用記憶體至少 512 MiB、loopback 背景流量不超過既有門檻，並確認 trial port 閒置。不因採樣或 perf 權限問題放寬門檻。本次所有正式 socket/proc 與 perf trial 都通過原門檻，沒有縮短 idle observation。

Kernel diagnostic 組使用 128 B 與 4096 B payload、100 RPS low-load baseline、closed-loop C=256 的 1、4、8 個 channel，每組三次重複。另對每個飽和 payload/channel 組執行相同配置且 `--kernel-sample-ms 0 --perf-mode off` 的 kernel-off 3-repeat 對照。另在主診斷前後以相同 kernel-off 設定執行 payload 128/4096 B、ch1/ch8 的 rep1 bracket，用於觀察時間漂移；診斷與 control 分批執行，不能將 RPS 差當成精確監控因果效應。Perf stat 對 128/4096 B、C=256、ch1/ch8 各執行 3 次；record 對四個代表組各執行一次。Perf 結果獨立報告，不能與無 perf 組直接作因果比較。

執行前後均保留 `preflight.log`、`perf_preflight.log`、完整命令與環境 metadata。輸出使用唯一 run directory，不覆寫 `grpc_echo_loopback_report.md` 或既有 bench 結果。

## 歸因規則

先比較同 payload、併發、channel 和 repeat 的 kernel-on/off RPS、latency p50/p95/p99 與兩端 CPU core equivalent，再對照分端 queue snapshots、TCP_INFO counter deltas、loopback counters 與 per-core softirq。只有量測窗一致且時間 offset 足夠小的直接指標才用於歸因。Queue maxima 是快照 maxima，TCP_INFO counters 是整條 TCP flow 的累積差值；兩者皆不代表每個 RPC。

若 perf 權限不足，報告可以描述 socket queue、RTT snapshot、TCP counters、loopback 流量、程序 CPU 與 per-core softirq 的變化；仍無法把未拆分的 `t0-t1` / `t2-t3` framework-plus-scheduler-plus-loopback 時間歸為純 HTTP/2 或純 kernel CPU 成本。缺少 perf 時，這個 H2 與 kernel CPU 的區分必須列為未判定。

本次結果新增 `benches/grpc_echo_kernel_report.md`，原始 run 目錄與後處理 CSV 位於 `benches/grpc_echo_kernel_data/`。診斷密集 sampler 每 trial 約 200 個 phase 內 100 ms ss 樣本；ss 子程序使用約 0.21–0.26 核心，monitor wall duty 約 22–26%。同設定 kernel-off 組與前後 bracket 顯示監控差值混有時間漂移，報告以同設定參考對照表述。
