# Tokio sequential WAL benchmark 設計

## 目標與工作量

此 benchmark 與 `wal_sync` 使用相同 deterministic 128-byte records、batch 設定、segment/frame 格式、preflight、recovery 驗證及 trial 目錄清理方式；差異是 writer 以 `tokio::fs` 完成檔案建立、寫入、flush 和 sync。預設每輪寫入 10,000,000 筆，每個 batch 都必須等到 durability acknowledgement 後才提交下一批，只有一批在途。

預設 batch size 為 64、256、1,024、2,048、4,096，各搭配 1 GiB rotation threshold；另有 batch size 4,096 搭配 256 MiB threshold。每種情境重複 3 輪，共六種情境。CLI 與同步 benchmark 相同，可用 `--iterations`、`--repetitions`、`--batch-sizes`、`--rotation-bytes` 縮小工作量或選擇情境。輸出 CSV 到 stdout，預設 WAL 暫存位置是 `target/wal-tokio-benchmark/`。

## Runtime 與 durability

Benchmark 使用帶 time driver 的 current-thread Tokio runtime。Async writer 對 segment 使用 `tokio::fs::OpenOptions` 與 `tokio::fs::File`；Tokio 將一般檔案系統工作交給 blocking pool，使 runtime event loop 能繼續 poll heartbeat task。每批依序執行 `write_all().await?`、`flush().await?`、`sync_all().await?`，三者都成功後才回覆 durable acknowledgement。明確 flush 可讓 write error 傳回呼叫端；`sync_all` 等候進行中的寫入本身不一定會傳遞 write error。

Writer 重用同步 WAL 的 frame encoder 與 segment naming。整批 records 組成一個 frame，絕不跨 segment 拆分。新 segment 用 `create_new` 建立，接著 async sync run directory 以持久化檔名，再寫入 frame。累計 segment bytes 在整批完成後若**大於** threshold，下一批開始前才建立下一個 segment。建立、directory sync、write、flush 或 file sync 失敗後 writer 進入 failed 狀態，不再接受會產生 acknowledgement 的操作。

每批 CSV 分別記錄 frame encode、`write_all().await`、flush、file sync、directory sync、segment open 與 rotation 的耗時。`batch_latency` 與 durable RPS 的量測窗從第一批 handoff 到最後一次 durable acknowledgement；RPS 的分子是完成的 records。ProcessTime、程序 I/O counters 與 target disk busy time 也沿用同步 benchmark 的計量方式。Recovery 在量測窗外同步讀取所有 segments，檢查 frame、checksum、LSN 順序與記錄內容；成功後只刪除該 trial 的 WAL 檔和空目錄。

## Event-loop heartbeat

同一個 current-thread runtime 另執行 1 ms heartbeat task。第一批 handoff 時啟動 heartbeat 時程；最後 durable acknowledgement 時結束統計窗。每次 event loop poll heartbeat 時，程式記錄相對於預期 tick 時間的 scheduling lateness，輸出 tick 數、missed tick 數，以及 lateness 的 p50、p95、p99 和最大值。分位數採 nearest-rank。

Lateness 顯示 event loop 在預期時間後多久才 poll heartbeat，不會單獨指出延遲來源。它可能受檔案工作以外的 event-loop 工作、frame encoding、runtime 排程、作業系統負載或計時器粒度影響；async filesystem 操作由 blocking pool 執行的安排也不保證每個裝置或 filesystem 的實際等待特性。因此這是 WAL 測量期間的排程觀察值，不是檔案 I/O latency 的因果歸因。

## Preflight 與 smoke run

每輪仍檢查非 volatile filesystem、free space、memory、CPU utilization 和 WAL target block device busy；tmpfs、ramfs、devtmpfs 會被拒絕。預設門檻、等待方式與 `--preflight-*` CLI 選項沿用 `wal_sync`。Base directory 逐層建立時同步每個新目錄的 parent；每輪建立自己的唯一目錄並同步其 parent。這些準備作業在第一批 handoff 前完成。

短 smoke command：

```sh
cargo bench --bench wal_tokio_sequential -- \
  --iterations 10000 --repetitions 1 --batch-sizes 1024 \
  --rotation-bytes 104857600 \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --preflight-max-cpu-pct 100 --preflight-max-disk-busy-pct 100 \
  --preflight-min-mem-bytes 16777216 --preflight-free-reserve-bytes 1048576
```

預設完整矩陣包含 18 輪 durable storage 測量，短 smoke run 不代表預設工作量的效能結果。

Async integration tests 驗證 awaited append 後的 recovery、strict post-batch rotation 與 append error 後 fail-closed 行為。和同步 writer 的測試一樣，它們沒有執行實際斷電或 power-cycle。
