# Fixed connections, batch sweep (ledger-fixconn) — Requirements (user-confirmed)

Goal: with the connection count fixed, sweep batch-max upward until RPS saturates, for PG and TiDB; and measure TiDB at CPU=8 when tidb-server is given the remaining CPUs.

## Decisions (user)
1. Curves (ONLY these 5), 2 M requests (50,000 accounts x 40), queues 256, TiDB 256 regions/table (one queue = one region), no RF, same workload/semantics/monitoring/idle gate/stall rule as ledger-connsweep:
   - PG CPU4, 16 connections
   - TiDB CPU4, 16 connections (standard placement)
   - PG CPU8, 16 connections
   - TiDB CPU8+, 16 connections
   - TiDB CPU8+, 32 connections
   CPU8+ = TiDB CPU8 with tidb-server given the remaining CPUs: TiKV 0-7 (unchanged), client + PD + sampler together on 8-9, tidb-server 10-15 (6 logical CPUs). No standard-placement TiDB CPU8 curves are run (existing connsweep batch 50/100 points of the standard placement may be shown as reference only).
2. Batch grid 50, 100, 250, 500, 1000, 2000, 4000, 8000 ascending (8000 is the cap: a queue has ~7,800 requests, so 8000 = one window per queue). Stop rule: stop after 2 consecutive points whose RPS is each < 105 % of the best RPS so far. A non-sampler failure (e.g. 30 s window timeout) ends that curve, recorded as the limit. Saturation point = smallest batch with RPS >= 95 % of the curve's max.
3. Existing 2 M connsweep points for batch 50 and 100 at 16 connections (PG CPU4, PG CPU8, TiDB CPU4) are reused (imported, marked); everything else is measured fresh. Replicates after the curve: saturation point and its next-lower grid point, once each. Flush rerun rule as before.
4. Monitoring and report identical in content to ledger-connsweep (RPS, p50/p95/p99/max, CPU, memory, disk sdb, network, TiKV durability, region distribution, tidb-server % with `*` >= 85 % of its cpuset), plus for CPU8+ the CPU used by client, PD and sampler on the shared 8-9 (to show they are not saturated).
5. Report: docs/07-03.development-analysis-ledger-txn-fixed-connection-sweep.md.

## Disclosures
CPU8+ cpus are SMT siblings of TiKV cores (as before); client/PD/sampler share two logical CPUs (sampler measurement may be perturbed slightly); tidb-server cpuset 6 vs 4 elsewhere.

## Out of scope
Other connection counts, standard-placement TiDB CPU8 curves, CPU4 tidb-server enlargement, TiKV per-thread profiling.
