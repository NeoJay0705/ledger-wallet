# Tokio 單 shard Ledger 完整 Pipeline 基準測試

## 目的與範圍

`ledger_pipeline_tokio` 將已完成的 bounded request queue、帳戶儲存、durable projection、time boundary 與 safe-GC 模組接成單 shard、benchmark-only pipeline。每筆新交易經 admission gate、容量有界佇列、批次 worker 和同步 RocksDB 寫入，再由背景 projector 套用到記憶體 mock destination。Watermark、餘額 checkpoint 和 GC 與前景流量並行。

此測試比較每批同步保存餘額與背景 checkpoint 兩種模式，並觀察 GC 和歷史請求負載造成的成本。它不改變各個已提交獨立 benchmark 的行為，也不代表正式服務部署或真實外部投影儲存。

## 固定負載與案例

每個完整 case 建立 50,000 個使用者，每個使用者一個 coroutine、依序等待前一筆回覆後才送下一筆，共 200 筆，合計每 case 10,000,000 筆 request。Runtime 使用 3 個 Tokio worker threads；request queue 容量 50,000；batch 最多 2,048 筆，第一筆入批後最多等待 5 ms。新交易一律為 amount=1，Credit 和 Debit 精確各半。

每位使用者在計時前寫入三筆種子交易：Credit 100、Credit 1、Debit 1，初始餘額為 100。後兩筆 amount=1 交易也作為歷史精確命中目標。每個 200 筆區塊用 multiplier 37 的排列和使用者 offset 排出操作與歷史類別，因此 5% 歷史 case 中每位使用者有 10 筆舊 request：5 筆命中、5 筆未命中；兩種歷史操作合計 Credit／Debit 各 5 筆。其餘 190 筆新交易為 Credit／Debit 各 95 筆。歷史未命中使用不重複且不存在的交易 key。歷史查詢套用可調的 10 ms async mock delay。

| 餘額模式 | GC | 歷史 request 比例 | 歷史命中 | 歷史未命中 | 新交易提交 |
|---|---:|---:|---:|---:|---:|
| 每批保存餘額 | 關 | 0% | 0 | 0 | 10,000,000 |
| 每批保存餘額 | 開 | 0% | 0 | 0 | 10,000,000 |
| 每批保存餘額 | 開 | 5% | 250,000 | 250,000 | 9,500,000 |
| 背景餘額 checkpoint | 關 | 0% | 0 | 0 | 10,000,000 |
| 背景餘額 checkpoint | 開 | 0% | 0 | 0 | 10,000,000 |
| 背景餘額 checkpoint | 開 | 5% | 250,000 | 250,000 | 9,500,000 |

5% case 中，歷史 request 合計 500,000 筆；歷史與新交易子集合各自維持 Credit／Debit 50/50。退款和餘額查詢不進入效能負載；其他模組的測試負責驗證這些 API。

## Pipeline 與背景工作

前景只把新交易送入 commit queue。Worker 以固定最大 batch 和 timeout 呼叫共用 `AccountStore`，只有 RocksDB 同步 WAL 寫成功後才回覆成功。歷史命中或未命中由已投影的 mock destination 回答，不增加 source sequence。

計時前會把所有種子投影至 mock destination，並將初始 durable watermark 設在種子時間之後。預設 retention 為 500 ms，watermark 每 100 ms 嘗試推進，GC worker 每 100 ms 喚醒；GC batch 上限 256 筆。這些短 retention 和頻繁 tick 是壓力測試設定，不是正式服務設定。GC 僅刪除已投影、已有足夠餘額 checkpoint 覆蓋且位於 durable watermark 前的連續 ledger prefix，遇到第一筆不合格記錄即停止；前進時 yield，無進展時休眠。RocksDB 邏輯刪除使用同步 WAL batch，不強制 compaction。

Durable projector 每批讀取最多 256 筆 source ledger、原子套用至 mock destination，再同步保存 projection progress。背景 checkpoint 預設每 100,000 個 sequence 觸發。任一 commit worker、projector、watermark、GC 或 checkpoint 背景錯誤都會使 case 失敗。

## 計時、指標與樣本

Client wall window 從釋放 client start barrier 前開始，至最後完成 coroutine 的最後一筆 `route_request` 回覆為止。最後回覆的 coroutine 立即記錄 `Instant` 與 `ProcessTime`；wall RPS 和 CPU 秒使用同一個最新回覆端點。之後的 request count 驗證、樣本向量合併、JoinSet 收尾不進入 client wall 或 CPU 窗口。CPU sample 與 endpoint 的微秒偏移也輸出。

Request latency 依 `splitmix64(logical_request_id) % sample_stride == 0` 決定樣本，預設 stride 為 64，分位數用 nearest-rank。輸出 admission、enqueue、queue、batch、handler、response、完整 request，以及歷史查詢、歷史命中和歷史未命中的 p50／p95／p99。Background CSV 保留量測窗口內完成的 projection、checkpoint、GC 和 watermark event，以及其分段耗時和進度。

Projection／GC／checkpoint 進度快照、Process I/O、目標 block device I/O、RocksDB ticker 與 DB bytes 都在最後回覆後取樣，並輸出相對該回覆的取樣偏移。I/O、RocksDB 與 DB bytes 在所有 coroutine 被 JoinSet 收集後取樣，因此它們的 delta 可能包含回覆後的 coroutine 收尾和統計合併時間；offset 可用來判斷它們和 client window 相差多少。RPS 不包含最後 projector catch-up、watermark 推進、GC sweep、integrity scan、source 關閉與重開恢復。

完整預設負載只有在六個 case 全部成功後才寫入 `benches/data/ledger_pipeline/run-<run_id>/`：

- `ledger_pipeline_summary.csv`：每 case 負載、throughput、CPU、I/O、RocksDB、進度、GC、checkpoint、recovery 和 preflight 指標。
- `ledger_pipeline_stages.csv`：逐階段 p50／p95／p99 和樣本數。
- `ledger_pipeline_background.csv`：計時窗口內的背景工作 event samples。
- `ledger_pipeline_run.log`：參數、量測語意與逐 case 摘要。

## 前置檢查、驗證與清理

開始建立資料庫前、每個 case 建立資料庫前，以及完成種子設定且即將開始量測前都會執行 strict idle preflight。預設觀察 3 秒、最多等待 60 秒，CPU busy 上限 10%、目標磁碟 busy 上限 5%、額外保留記憶體 768 MiB、額外保留磁碟 1 GiB。可用資料庫記錄數估算額外記憶體為每筆 256 bytes、磁碟為每筆 768 bytes；可用 CLI 調整 preflight 門檻和保留量。

每個 case 成功前會檢查 request、Credit／Debit、新交易、歷史命中／未命中數；最終 sequence 必須等於種子加新交易數；所有帳戶餘額必須回到 100；destination、source durable projection 與 GC prefix 必須遵守進度不變量。GC 開啟的 case 必須回收至少一筆合格記錄，GC 關閉的 case 不得推進 prefix。測試會驗證 source integrity、歷史種子 key、缺席 key 和所有餘額，將 RocksDB 關閉後重開，再次檢查 durable watermark、sequence、GC prefix、integrity 和餘額。成功 case 在 source 關閉後會明確刪除自己的 DB 目錄；錯誤路徑使用 RAII 嘗試清理，清理失敗會輸出 warning。

恢復測試保留同一份記憶體 mock destination，並依 mock apply 成功視為 durable 的測試契約驗證 source RocksDB reopen。它不模擬程序 crash，也不聲稱外部 projection database 的 crash durability。

## 執行

完整六 case 預設命令：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_pipeline_tokio
```

以下 smoke 命令使用較小的使用者集合，仍執行六個 case 和完整驗證。`--smoke` 預設把 checkpoint 門檻設為 100，以便 200 個使用者的 600 筆種子記錄能產生覆蓋 GC prefix 的餘額 checkpoint；程式會在 checkpoint+GC case 開始量測前確認已發布 manifest 覆蓋全部 seed。可在 `--smoke` 前或後用 `--checkpoint-quantity` 覆寫；若覆寫值令 seed 未被 manifest 覆蓋，該 case 會在量測和 GC 前失敗。它放寬 idle CPU／磁碟 busy 門檻，但仍保留記憶體與磁碟空間檢查，不可用來替代正式 benchmark 的 strict preflight：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_pipeline_tokio -- \
  --smoke --output-root target/ledger-pipeline-smoke \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --max-cpu-busy-pct 100 --max-disk-busy-pct 100 \
  --memory-reserve-mib 0 --free-space-reserve-mib 0
```
