# Connection sweep at fixed batch (ledger-connsweep) — Requirements (user-confirmed)

Goal: at a FIXED small batch-max, sweep the number of client connections upward from the CPU core count until RPS saturates, for PG R1 and TiDB R1, with latency and the same monitoring as `ledger-batchsweep`.

## Decisions (user)
1. batch-max fixed at **50** and **100** (both measured).
2. Series: {PG, TiDB} x {CPU4, CPU8} x {batch 50, 100} = 8 curves. Same hardware, bindings, DB settings, no RF, idle gate, stall rule, sampling as `ledger-batchsweep` (see its requirements/report).
3. Connection grid (power of 2, starting at core count): CPU4 = 4, 8, 16, 32, 64, 128, 256; CPU8 = 8, 16, 32, 64, 128, 256. **Upper limit is 256** (= number of queues). If 256 is still rising, report it as "observed-grid saturation" (no extension).
4. **Queues stay 256** at every point; TiDB stays 256 regions per table, one queue = one region (shard = queue). Connections < 256: each connection serves `256 / connections` queues, sending their windows round-robin, one window in flight per connection (so one in-flight window per queue at most; per-queue order and per-account order preserved; every window touches one region).
5. Requests: **2,000,000** = 50,000 accounts x 40 requests (verification unchanged: 40 rows per account). The old 4M batch-sweep points are NOT reused (not comparable); connections = 256 is re-run at 2M.
6. Saturation point = smallest connection count whose primary RPS >= 95 % of the curve's max primary RPS. Full grid is always run (no early stop; high-connection points are fast). Latency is reported per point (p50/p95/p99/max); no SLO chosen here.
7. Replicates: after a curve is done, rerun the saturation point and the next-lower grid point once each. Stall rule: flush await > 2 ms => one rerun, both kept, rerun replaces primary.
8. Report: `docs/06-03.development-analysis-ledger-txn-connection-sweep.md`, same structure as `ledger-batchsweep-report.md` (load method, monitoring method, per-curve RPS + latency, CPU/memory, disk/net, TiDB durability/region distribution, attempt list, observations, limits).

## Out of scope
Connections > 256, other batch sizes, TiKV per-thread profiling, TiDB tuning.
