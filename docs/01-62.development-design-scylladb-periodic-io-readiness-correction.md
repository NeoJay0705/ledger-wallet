## Source 行為與失敗原因

固定的 Seastar source snapshot 顯示，I/O queue 的 priority class 和統計會在首次 I/O 時建立；初始化時可以尚無某類 series。[`io_queue.cc` 的 priority class 建立路徑](https://github.com/scylladb/scylla-seastar/blob/bf882627c3f813c8cfb88cb595ceed34d6462300/src/core/io_queue.cc#L762-L800) 與 [統計/queue 初始化路徑](https://github.com/scylladb/scylla-seastar/blob/bf882627c3f813c8cfb88cb595ceed34d6462300/src/core/io_queue.cc#L859-L875) 是判讀依據。

Scylla pinned release 的 commitlog 路徑在 DMA 前切換到相應 sched group；在 periodic profile 下，首次 preseed 之前可能尚未建立 commitlog queue series。[Pinned release `commitlog.cc`](https://github.com/scylladb/scylladb/blob/0dbea6201d676548993bc5889d8f4a34dd6ef54c/db/commitlog/commitlog.cc) 記錄該同步路徑。Lazy queue/stat creation 是符合 source 行為的解釋，但第二次 attempt 在 seed 前停止，尚未證實 seed 後 series 會出現，也尚未排除其他設定問題。第三次 post-seed readiness gate 將驗證此行為。

因此，修正對象是第三次 attempt 的 readiness 時點。Gate 移到既有 1,024 account seed 完成、Wallet CLI 到達 `ready_to_measure` 之後，並在 monitor 與 measured start gate 放行前執行。Runtime profile gate、device identity gate、file hash gate 和 shard mapping gate 不放寬。也不修改 periodic 設定或測量中的 Wallet workload。

## Readiness 修正

第三個 attempt 沿用同一 pinned image、binary、budget、RF/CL、timeout、CQL pool、CPU affinity 和 workload。不得因前兩次 setup failure 改變上述設定。

先完成現有 1,024 account seed。`seed_account` 本身維持既有 LWT。Runner 到達 `ready_to_measure` 後，且在啟動監控視窗與 start gate 前，執行 bounded I/O queue readiness polling。Polling 每秒檢查一次，最多等待 30 秒。它只等待必要 series 出現，不發送額外 Wallet request，也不增加超出既有 seed 的 LWT 或 preload warmup。

| Readiness 條件 | 處理方式 |
|---|---|
| 所有預期 main/commitlog series 都存在 | 通過 readiness，啟動正常 monitor 與 start gate |
| 任一預期的 main 或 commitlog series 尚未出現 | 每秒重查，最多 30 秒；只等待缺少 series |
| 逾時後仍缺少任一必要 series | 停止 setup，保存 evidence，清理 owned resources；不放行 measured workload/start gate |
| io-properties hash 或 device identity 不符 | 立即失敗，不等待 |
| shard/device mapping 不符或出現 unexpected series label | 立即失敗，不等待 |
| argv、runtime profile、source hash 或 REST/system config 不符 | 立即失敗，不等待 |

Required series 必須涵蓋每個 shard、`main` 與 `commitlog` class，以及預期的 data mountpoint `/var/lib/scylla`。本修正只等待預期集合內缺少的 series；通過時仍要求 full coverage。不可忽略任何 class、shard 或 mountpoint。

Readiness polling 是 setup gate，不是測量的一部分。不要把等待 samples 混進 measurement samples。Gate 通過後，start gate 才可放行唯一一次 1,024,000-request workload。

## 第三次 attempt 控制

第三個 attempt 必須使用新的 fresh job、fresh owned node、fresh keyspace 與 fresh data。第一次 JSON enum parser failure 和第二次 missing commitlog queue failure 都保留原始 artifact，不覆寫、不併入 performance statistics。

執行前保存新 freeze manifest、source snapshots、歷史 hashes/change summary、image/binary/budget/config hashes、argv、offline validation 與 parser/readiness fixtures。舊 source bytes 不可用時，不宣稱完整的前後 bytewise diff。

第三次 attempt 的順序：

1. 建立 fresh job，保存新的 provenance。
2. 執行 external strict preflight，確認容量、CPU、device、memory、AIO 與三個連續 passing samples。
3. 建立 fresh node，確認 pinned image、runtime config、plain CQL periodic enum、period、`O_DSYNC` 與 pinned source evidence。
4. 完成既有 1,024 account seed。
5. 到達 `ready_to_measure` 後，於 monitor/start gate 前等待 queue series readiness，最長 30 秒。
6. Gate 通過後開始唯一的 S2/C512 periodic workload。不得 app retry 或再建立新 workload trial。
7. Drain、完整驗證 accounts/ledger、停止並 inspect，清理 ownership 確認的資源。

若任何 strict, config, source, hash, device 或 mapping gate 失敗，保存原始錯誤，停止並清理 owned resources。若 30 秒後任一預期的 main/commitlog series 仍缺失，也停止，不放行 measured workload/start gate。Readiness 通過後若 measured workload 失敗，同樣停止，不 retry。

## 不變的 workload 與 interpretation

Workload 維持 N=1、RF1、read/write CL `ONE`、serial CL `LOCAL_SERIAL`、S=2、C=512、P=3、D=6、1,024 users × 1,000 sequential requests，Credit/Debit 各 512,000。

每筆 accepted request 仍是單一 conditional `INSERT ... IF NOT EXISTS` LWT。Cache 只在 `Applied` 後更新。Unknown commit outcome 仍 freeze account 並 global fail closed，不自動 retry。Commitlog mode 仍為 periodic，period 10000 ms，`O_DSYNC=false`。

LWT 在 pinned Scylla release 的所有 commitlog sync modes 下仍同步持久化。Periodic case 不能解讀為「沒有 fsync」，也不能保證禁止 group commit。Queue readiness 只確認 metric series 已建立，不證明 queue depth、磁碟飽和或交易 durability latency。

後續性能報告必須分別保留兩次 setup failure 和第三次 attempt。只有第三次達到 measured window、完整 correctness、required metrics、hash gates 和 clean owned cleanup 後，才可列入 01-61 的 periodic result。若第三次仍未進入 workload，RPS、latency、LWT stage 和 verification 仍標示 N/A。

```text
second attempt
  strict/config/source/AIO pass -> I/O gate lacks commitlog shard 0/1
  -> before Wallet CLI/seed/ready_to_measure -> no measured requests
  -> preserve setup evidence
  -> clean owned resources

third attempt
  fresh job -> external strict preflight -> fresh node -> runtime/source gates
  -> CLI starts -> seed 1,024 accounts -> ready_to_measure
  -> wait up to 30s for missing commitlog queue series
  -> monitor/start gate -> one workload -> verify -> cleanup -> report 01-61
```
