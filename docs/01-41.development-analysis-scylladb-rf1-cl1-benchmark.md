## 固定環境與交易結果

三個隔離 ScyllaDB 2026.1.14 instances 使用相同 pinned image，並共用同一 host 與 SSD。S4 每 node 的 CPU affinity 沿用 node A 0,1,8,9，B 2,3,10,11，C 4,5,12,13；service/load/monitor 使用 6,7,14,15。每 node 使用 P4，總目標 D48。SMT 啟用。Commitlog 使用 `batch`、`commitlog_use_o_dsync=false`，保持 fsync 後 ack 和既有 timeout。

唯一 profile 差異為 RF1、wallet read CL=ONE、write CL=ONE。Workload 為 50,000 users × 200 requests，共 10,000,000 預期交易。每帳戶初始 balance=100，Credit/Debit amount=1 交替各 100 筆。服務使用 per-user owner routing、50,000 workers、單一 shared Session、每 worker queue capacity 1、global admission 50,000；seed/verify concurrency 為 48。

| 計數 | RF1/ONE/ONE 結果 |
| --- | ---: |
| 預期 requests | 10,000,000 |
| Accepted | 78,205 |
| Attempted | 78,207 |
| Replies | 78,207 |
| Applied | 77,027 |
| `CommitOutcomeUnknown` | 1,178 |
| `NotAccepted` | 2 |
| Unexpected business outcomes | 0 |

全域 fail-fast 停止新 work，並 settle 已接受的 jobs。Unknown 帳戶 freeze，不重送。兩筆 `NotAccepted` request 沒有送到 DB。

Driver query delta 為 234,615，恰為 78,205 個 accepted requests 的 3 倍。Driver errors 為 1,178；retries、request timeouts 和 connection timeouts 均為 0。代表性 server error 是 CL=ONE write timeout，`received: 0, required: 1, write_type: Simple`，原始訊息指出只收到 0/1 responses 並回報 `Operation timed out`。這是 Scylla server write timeout，不是 driver request timeout。

`requests.first_error` 顯示 `NotAccepted`，但這個彙總欄位不代表錯誤發生順序。主要 storage failure 依 `error_samples.commit_outcome_unknown` 和 driver counter 判定；不得將 first_error 誤讀成首個 storage timeout。

完整 workload 正確性驗證未通過：`accounts_verified=0/50,000`、`failures=50,000`、`complete=false`。`accounts_verified` 表示符合每帳戶完整 200 筆預期的帳戶數；0 不代表未執行逐帳戶檢查。`ledger_rows_seen=77,027` 是 `ScyllaStore::verify_account` 成功返回 rows 的累計，不是完整 DB ledger 數，也不是已 ack 資料遺失證據。

RF1 的 `db_read` mean 為 0.144028360 s，`db_write` mean 為 1.397113511 s。成功 `cql_write_batch` samples 有 77,027 筆，其 p99 為 1.994391551 s。這個成功 samples histogram 不代表全部 write attempts，亦不同於涵蓋 write errors 的 `db_write` stage。`db_write` 包含 driver、網路與 DB 等待，不是 fsync 耗時；不能用此 stage 單獨定位磁碟瓶頸。

RF1 measured-window 只有 3 個 1 Hz RSS samples；整個 Rust process peak 為 578.234375 MiB。RF3 process peak 為 752.01171875 MiB，但有 58 個 samples。RF1 樣本太少，不能據此宣稱穩態記憶體節省。

Commitlog window counters：RF1 三 node 合計 flush 472（nodea/b/c 分別 156/153/163）、bytes written 50,810,880、cycle 491、alloc 78,188；RF3 分別為 flush 109,068、bytes written 3,912,613,888、cycle 109,715、alloc 5,659,911。Windows 長度及 scrape offsets 差異很大，不能用這些 counter 精確計算每筆 transaction 或 fsync 歸屬及耗時。固定 release 註冊的 batch window 預設為 10,000 ms；本輪沒有覆寫，且該 release 的 commitlog 執行路徑未讀取它，因此不能解讀為固定等待十秒。

RF3 對照是 [run `run-20261012T071303Z-a7f4b0a6`](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261012T071303Z-a7f4b0a6/trials/trial-001-S4-C50000-P4-D48-per-user-rep1/service/result.json) 的相同 C/P/D、per-user case。該 case 收到 2/3 CL=THREE write responses 後 timeout。RF1 case binary 不同，且 RF、read CL、write CL 同時改變；兩次都 failed，window 長度和已完成 workload 也不同。這些資料不能證明 RF1 天生較慢或較快，也不能識別 RF 對結果的單一因果效果。

較早的 [S4/C48/P4/D48 round-robin n=2 full-pass](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261011T173702Z-c88fb8e8/case-summary.csv) 可作背景：RPS median 9,176.983178、E2E p99 median 25.425870847 s。該 baseline 與新 profile 的 C、routing 及 binary 不同，亦不是本次 RF1 case 的受控對照。

## 結論

RF1/R1/W1 沒有讓此 50,000 in-flight case 完成。結果未提供有效的 full-load throughput winner。不能把 replies/s 或 applied-ack RPS 解讀為已完成 10M workload 的效能，也不能將 unknown 當成未提交。

RF1 每個 partition 只有一份 replica。Replica node 暫時離線時，該 node 的 partitions 不可用；永久磁碟遺失時沒有 peer copy 可復原。Fsync 後 acknowledgement 仍只保護唯一副本，不提供 RF3 replication 的故障容忍。CL1 也不協調多個 service writers。

後續方向為保留 50,000 個 account owners，獨立限制 DB in-flight，先由 48 開始，再評估更高上限。此方向尚未實作或執行。維持明確 RF/CL profile 與既有 timeout；不拉長 timeout、不自動降級，也不以重送 unknown 使 case 通過。

```text
input
  -> run_clients
  -> run_client (per user; await reply before next request)
  -> Service::submit (account owner lock)
  -> worker_loop -> process_job
  -> ScyllaStore::load
  -> SELECT static state -> SELECT ledger key
  -> compute
  -> ScyllaStore::commit
  -> single-partition UNLOGGED BATCH
  -> RF1 / CL=ONE / unique replica commitlog fsync acknowledgement
  -> reply -> next request

write outcome unknown
  -> freeze account / global fail-fast
  -> stop new work and settle accepted jobs
  -> verify -> cleanup owned resources -> report failure
```
