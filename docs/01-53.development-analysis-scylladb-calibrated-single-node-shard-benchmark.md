## Live 測試結果

Job `calibrated-single-node-rf1-s1-s2-20261012T152629Z` 於 2026-10-12 15:53:57 UTC 結束（台北時間 23:53:57）。Job 結果是 `all_cases_passed`，3/3 階段通過，所有 case validation 都沒有問題，source、binary 和 control hash 相符，terminal resource audit 通過。Job 標記 `formal_complete=false`、`workload_class=diagnostic_only`；它不是 27-case formal matrix，也沒有多次重複。

| 階段 | 設定 | 結果 | 測量窗／吞吐 |
|---|---|---|---|
| Smoke | S=1、C=128、P=3、D=3；32 users × 1,000 | 32,000 requests 全部 accepted、applied、replied；32 accounts 和 32,000 ledger rows 全部驗證 | 10.810610 s；2,960.1 RPS。只驗證執行與監控，不納入性能比較 |
| S1 | S=1、C=128、P=3、D=3；1,024 users × 1,000 | 1,024,000 requests 全部 accepted、applied、replied；1,024 accounts 和 1,024,000 ledger rows 全部驗證 | 129.658664 s；7,897.7 RPS |
| S2 | S=2、C=128、P=3、D=6；1,024 users × 1,000 | 1,024,000 requests 全部 accepted、applied、replied；1,024 accounts 和 1,024,000 ledger rows 全部驗證 | 101.618180 s；10,076.9 RPS |

兩個 full case 使用單節點、RF=1、read/write CL=ONE、`LOCAL_SERIAL`、`durable_writes=true`。每個已接受 request 只發出一個 `INSERT ... IF NOT EXISTS` LWT，測量窗內 SELECT 為 0；driver query delta 精確等於 1,024,000。兩案的 driver errors、retries、request timeouts 和 connection timeouts 都是 0，並完整比對 memory cache 與 Scylla 狀態。沒有重試或不完整驗證。

本輪 `N=1`。`S` 是 Scylla shards，`C=128` 是 worker 數與 in-flight 上限；`P=3` 是每個 shard 的 driver pool 目標。總 data connections `D=N×S×P`，所以 S1 為 3、S2 為 6。Workload 有 1,024 個 client，採 round-robin worker routing。Node shard CPU 為 S1 `0`、S2 `0,1`；service/load CPU 為 `6,7,14,15`。Node memory 設定 8 GiB，Docker memory limit 是 10 GiB。兩案使用同一校準 budget；S2 的 pool 在測量中 1,005 次取樣皆為 6，S1 的 1,283 次取樣皆為 3。

Process CPU 由窗口內第一筆與最後一筆 Scylla process CPU ticks 差分，再除以 `sysconf(_SC_CLK_TCK)` 和窗口時間；Rust CLI process CPU 由同窗的 process CPU counter 計算。100% 代表一個 CPU。Rust CLI 數字包含服務、load clients 與同程序的內部監控，不含 Scylla 或獨立 Python monitor。裝置數字由同窗 `/proc/diskstats` 第一筆與最後一筆差分：write IOPS 使用 writes counter，weighted write await 使用 write milliseconds/writes，busy 使用 I/O milliseconds/elapsed。裝置為共享主機的 `/dev/sdb2`，這些數字不是單筆 fsync latency，也不表示 benchmark 獨占裝置。兩案 cgroup `nr_throttled` 和 `throttled_usec` 都是 0；事後容器檢查為 exit code 0、`oom_killed=false`。

Commitlog counter 是在測量窗邊界前最近一次 scrape 的近似 delta。S1 shard 0：flush 65,633、cycle 65,634、alloc 5,096,324、bytes 3,455,979,520；起點 scrape 比量測起始邊界早 54.008 ms，終點 scrape 比量測結束邊界早 641.445 ms。S2 shard 0：flush 68,162、cycle 68,163、alloc 2,534,851、bytes 1,825,841,152；shard 1：flush/cycle 67,155、alloc 2,562,998、bytes 1,840,918,528。S2 起點、終點 scrape 分別比相應量測邊界早 47.160 ms 和 590.581 ms。這些 counter 不等同交易數或 fsync syscall 數，不應除以 request 數推算每筆 fsync。

## 執行流程

```text
Deployment
  calibration on /dev/sdb2 ext4
  -> validate budget file and hash
  -> create a fresh owned single-node Scylla cluster
  -> validate running I/O, commitlog and AIO profile
  -> preload account states
  -> run 32 x 1,000 smoke; then 1,024 x 1,000 at S=1 and S=2
  -> after all replies: verify requests, accounts and ledger rows
  -> stop cluster and clean owned resources

Wallet request
  Credit / Debit
  -> run_clients -> run_client -> Service::submit
  -> account owner lock + enqueue -> worker_loop -> process_job (cache compute)
  -> ScyllaStore::commit (one conditional INSERT ... IF NOT EXISTS)
  -> batch commitlog fsync -> RF=1 / write CL ONE acknowledgement
  -> process_job publishes cache on Applied -> worker reply

After all replies / case verification
  verify_all -> verify_account / verify_one_account

Unknown commit outcome
  -> freeze account and fail closed globally
  -> retain evidence; do not retry
```

Calibration 是部署前的 profile 設定，不是每筆交易的一部分。Batch commitlog acknowledgement 不能解讀成每筆 request 一次獨立 fsync。

## 解讀限制

S1 與 S2 使用相同單 node budget、C=128、P=3 和 node memory。S2 的 D 是 S1 的兩倍，也增加 shard reactor 數；每 shard 可用 memory 會改變。兩個 case 都是單節點總吞吐，不是單 shard 吞吐。兩個 live case 各只有一次測量，不足以建立穩態或普遍的 shard 擴展結論；本次結果不觸發自動擴測。

RF1/CL1 單節點結果不能和 RF3/CL3 三節點結果直接比較。裝置上仍有其他主機工作，因此本次寫入速率、IOPS、await 和 busy counters 不是 benchmark 獨占數據。Calibration 的 sequential write deviation 為 107%，因此 calibration 不能證明 runtime 裝置能力穩定，也不能保證單次 fsync latency。舊 RF3 timeout 與本次 RF1 topology 不同，沒有證據表明 calibration 單獨解決舊 timeout。Commitlog counters 是近似邊界 scrape，不能當成每筆 transaction 的 fsync 計數。有限的單次 case 不代表 steady-state、production SLA 或 shard scaling 的一般結論。
