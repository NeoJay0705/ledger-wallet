# Tokio bounded queue HashMap benchmark 設計

## 目的與範圍

新增 `bounded_queue_hashmap_tokio` 作為獨立的非同步 pipeline benchmark；原有 `bounded_queue_hashmap` 同步 benchmark 維持原狀。這個測量只包含本機 Tokio bounded mpsc request queue、批次 worker、HashMap 更新和個別 oneshot 回覆，不包含 gRPC、網路或 response serialization。

## Runtime 與工作配置

每個程序建立一個 `tokio::runtime::Builder::new_multi_thread()` runtime，設定 3 個 runtime worker threads 並啟用 time driver。每個情境啟動一個批次 worker task，以及設定數量 C 的 request coroutine；這些 task 共用 runtime，允許在 runtime worker threads 間遷移。沒有 pinned completion task，也不為每筆 request 建立 Tokio task。程序的 main orchestration thread 在 runtime 外呼叫 `block_on`。

Request queue 使用容量 50,000 的 `tokio::sync::mpsc::channel`。每筆 request 配一個 oneshot response channel。每個 coroutine 依序送出一筆 request、等待它的回覆，再送下一筆；各 coroutine 彼此沒有全域 round barrier。設定 C 大於 N 時，有效 coroutine 數為 `min(C, N)`，並在結果輸出設定值與有效值。

Coroutine `i` 處理 ID `i, i+C, i+2C, ... < N`。Key 是 `id % 100000`。預設 N=10,000,000，因此全部 100,000 個 key 各有 100 次更新。其他 N 的每個 key 預期更新次數為 `0`（key >= N），否則為 `floor((N - 1 - key) / 100000) + 1`。

## 情境矩陣與命令列

預設 C 為 100000、50000、25000、12500、6250、3125、1562、781；每個 C 都執行下列 16 種組合，預設一輪：

- map 初始為空或預填 100,000 個 value=0 的 key。
- batch size 為 2048 或 4096。
- batch timeout 為 1、5、10 或 20 ms。

Timeout 從該批第一筆成功 `recv` 的時間開始。worker 達 batch size 或 deadline 時處理該批；request sender 全部關閉時也會送出不足一批的尾批。Closed-loop coroutine 在等待最後 response 時仍持有 request sender，因此正常完成時 worker 通常會以 full 或 timeout flush 最後批次；`flush_tail` 仍保留作為 channel 關閉時的正確處理。

可使用 `--iterations N`、`--repetitions N`、`--coroutines all|N[,N...]`、`--map-state all|empty|prefilled`、`--batch-size all|2048|4096`、`--batch-timeout-ms all|1|5|10|20` 及 `--latency-sample-stride N` 篩選。短工作量可例如執行：

```sh
cargo bench --bench bounded_queue_hashmap_tokio -- --iterations 10000 --coroutines 8192 --latency-sample-stride 97
```

## 起跑與計時

建立 runtime、map、sample plan、channels、worker staging buffers 及 C 個 request tasks 都在量測前完成。所有 task 完成必要配置後，經 watch start gate 回報 ready 並等待同一個 release。ProcessTime 起點與 release wall timestamp 在 gate 開啟前取得；每筆 request coroutine 在建立 oneshot 後，緊接著取 t0 並呼叫 `send().await`。Pipeline latency 與 completed RPS 以最後一筆 response 的 t6 結束。CPU ProcessTime 與 CPU wall span 共用另一個終點：記錄最大 t6 的 coroutine 完成自己的 latency/count 記錄後，緊接著取 ProcessTime elapsed 與 `cpu_measured_at`。因此 CPU window 比 t6 多包含少量該 coroutine 的收尾 bookkeeping；這兩個量測的 wall denominator 仍與 CPU elapsed 對齊。Main thread 呼叫 runtime `block_on` 負責情境協調與結果收集，其 CPU 也計入程序 ProcessTime；runtime 建立設定的 3 個 worker threads。

## Batch worker

worker 收到 batch 第一筆時記錄成功 dequeue 的 t2，並以 `t2 + timeout` 建立 deadline。累積達 batch size 即 full flush；deadline 到期即 timeout flush。channel 關閉時，worker 會處理已收到的尾批。每批在 t3 開始 HashMap 更新與 response staging；t4 在 staging 完成後、個別 oneshot sends 開始前取樣。所有 batch response 使用該批共同的 t3/t4。

## 輸出指標

程式輸出 CSV，每列代表一個情境輪次。

- Completed RPS = N / (最早 t0 至最晚 t6)。Complete latency 為全部 N 筆 t6-t0 的 mean，以及 deterministic ID hash sample 的 p50/p95/p99。
- Enqueue-call latency 是 `send().await` 的呼叫時間 t1-t0；enqueue RPS 是 N / (最早 t0 至最晚 t1)。這個呼叫完成時間不是 queue admission 時間，也不與其他 latency stages 相加。
- Successful dequeue-call latency 是成功 `recv` 呼叫的耗時，包含該呼叫中的等待。Observed dequeue RPS 使用最早成功 receive call start 至最晚成功 t2；active dequeue RPS 使用 N 除以成功 receive call durations 的總和。
- Post-dequeue latency 是 t6-t2；post-dequeue RPS 是 N / (最早成功 t2 至最晚 t6)。
- 四個逐筆 stages 是 `submit_to_dequeue=t2-t0`、`batch_wait=t3-t2`、`batch_service=t4-t3`、`response_delivery=t6-t4`。Mean 使用全部 N 筆，percentiles 使用相同的 deterministic ID hash sample；CSV 輸出每段的 exact integer total nanoseconds。每輪檢查四段 totals 之和等於 pipeline total，並檢查最後三段之和等於 post-dequeue total。
- Batch 輸出 active seconds、active RPS、ns/item、批次數、平均與最大 batch size、full/timeout/tail flush 計數和 batch duration quantiles。
- ProcessTime 輸出程序 CPU seconds、release-to-`cpu_measured_at` wall seconds、core equivalents 及 one-core percent。core equivalents = CPU seconds / wall seconds。

所有 latency 的 sample plan 在計時前依 `splitmix64(id) % stride == 0` 建立；stride=1 時所有 request 都納入分位數樣本。CSV 同時輸出各 latency 的 count、sample count 和 exact total nanoseconds。

## 結果驗證與限制

每個 response 的 ID 必須與該 coroutine 當前 request ID 相同。回覆 count 必須在該 key 預期範圍內；預先配置的 per-key atomic bitset 記錄每個 response count，量測後確認每個 key 都恰好收到 `1..=expected_count` 的完整 permutation。程式檢查 completion、enqueue-call、successful dequeue-call、post-dequeue 與四個 stage 都恰有 N 筆，這些逐筆串流的 sample count 也必須相同；batch duration count 必須等於 batch count，batch sizes 總和必須等於 N，flush reason 計數總和必須等於 batch count。worker map 在量測後檢查 key 數及所有最終值。此 count 驗證在每筆 response 路徑使用 atomic bitset，但 bitset 經過 key/count 緊湊配置；全量 bitmap 與 map 驗證在計時區間外完成。

此 benchmark 是 closed-loop、本機 in-memory pipeline。它不表示外部到達率、網路服務、磁碟持久性或 SLO；低 C 時每個 coroutine 一次只有一筆未完成 request，批次可能以 timeout flush。Runtime 排程、oneshot、mpsc backpressure、sampled latency bookkeeping 與 response count 驗證也都屬於此 harness 的成本。
