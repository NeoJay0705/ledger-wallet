## 2. 專案定位與需求

專案以 Rust、Tokio 與 RocksDB 建立單機帳本 library 和本機 CLI。
支援入帳、扣款、退款、餘額查詢、狀態觀測與安全關閉。
金額使用 `u64` 最小貨幣單位。第一版只支援單一幣別。
每筆交易只修改一個帳戶。同一帳戶依佇列接受順序執行。

| 必須滿足的需求 | 可檢查的契約 |
| --- | --- |
| 重試不再次修改餘額 | 相同完整 key 與內容回傳原結果，sequence 不增加。 |
| 相同 key 不接受不同內容 | 回傳 conflict。 |
| 已提交結果可恢復 | ledger、index、退款狀態、受影響餘額與 sequence 原子同步保存。 |
| 退款不重複成功 | 同帳戶的一筆成功扣款最多成功退款一次。 |
| 流量與背景工作可控 | queue、in-flight、I/O concurrency 與 metrics sample 有界。 |
| 歷史刪除不破壞重播 | GC 必須具備耐久歷史與連續覆蓋證據。 |
| 故障語意可供呼叫端使用 | 區分未接受、結果未知、業務拒絕、衝突與基礎設施錯誤。 |

需求來源：[正式核心契約](01-30.development-design-ledger-formal-core.md)。

## 3. 設計案例

### D01：交易重試與退款防重

- 需求：回覆遺失後，重試仍取得原交易結果。成功扣款最多退款一次。
- 比較選項：只記錄 tx_id；保存完整交易 key、內容與結果；由呼叫端自行避免重送。
- 現行選擇：以 `(account_id, tx_id, transaction_at)` 查詢已保存交易。相同 key/body 回傳原 status、balance 與 sequence。相同 key、不同內容回傳 conflict。
- 代價：呼叫端必須保存第一次提交的完整 key。改時間戳會形成另一筆交易。持久化索引與退款證據增加儲存成本。
- 代價處理：原子提交交易結果與索引。保存退款 marker。來源 GC 後仍要求耐久歷史提供退款防重證據。
- 錯誤處理：業務拒絕也保存成可重播結果。接受後回覆逾時回傳 `CommitOutcomeUnknown`。呼叫端以原 key/body 重試；不得改時間戳。
- 證據：[交易儲存](../src/storage/account_store.rs)、[入口與回覆](../src/pipeline.rs)、[退款及恢復測試](../tests/formal_storage.rs)、[公開 API 測試](../tests/formal_pipeline.rs)。

可呈現的能力：定義重試契約，並將業務結果與傳輸／儲存錯誤分開。
此契約不等於跨服務 exactly-once。不同完整 key 不受同一筆交易的防重保證。

### D02：同步提交與恢復一致性

- 需求：回覆已提交結果前，交易與餘額必須有一致的持久化來源。
- 比較選項：獨立 WAL 加多份進度；RocksDB 原子同步批次；非同步落盤後立即回覆。
- 現行選擇：使用單一 `WriteBatch` 保存新交易的 ledger、index、退款狀態、受影響餘額與 shard sequence。保持 WAL 啟用並設定 `sync=true`。
- 代價：同步 I/O 進入前景延遲。服務依賴本機 RocksDB 格式、路由版本與儲存拓樸。
- 代價處理：以批次攤分同步成本。同步成功後才發布記憶體狀態。重開時驗證 metadata 與資料一致性。
- 錯誤處理：storage error 不偽造成功。服務停止接受新交易並呈現健康異常。格式、拓樸或資料不一致時拒絕啟動；不猜測或自動遷移。
- 證據：[原子同步實作](../src/storage/account_store.rs)、[核心開啟與恢復](../src/pipeline.rs)、[儲存測試](../tests/formal_storage.rs)、[程序 crash 測試](../tests/formal_crash_recovery.rs)。

可呈現的能力：明確定義 durability、記憶體發布與對外成功回覆的先後關係。
程序 SIGKILL 測試支持程序中斷後的恢復案例；不支持斷電或磁碟故障保證。

### D03：有界資源與批次等待

- 需求：高並行呼叫不能讓 queue、背景 I/O 或觀測樣本無界累積。
- 比較選項：無界佇列；有界逐筆佇列；批次緩衝池；固定 request ring。
- 現行選擇：正式核心使用有界 MPSC queue、全域 in-flight permits、每 shard 批次與全域 I/O permits。Pool 和 ring 保留為歷史實驗。
- 代價：容量不足時拒絕或等待。低流量請求可能等待 flush deadline。同 shard 的慢批次會延後後續請求。
- 代價處理：queue 與 in-flight 預設全域各 50,000。每 shard 批次上限 2,048，首筆 dequeue 後最多等待 5 ms 組批。設定可調整；所有 shard 共用全程序預算。
- 錯誤處理：in-flight 耗盡回傳 `Overloaded`。入列前逾時回傳 `NotAccepted`。入列後回覆逾時回傳 `CommitOutcomeUnknown`，不能視為工作已撤銷。
- 證據：[入口與 permits](../src/pipeline.rs)、[有界批次佇列](../src/batch_queue.rs)、[設定](../src/config.rs)、[佇列測試](../tests/ledger_request_batch_queue.rs)、[歷史 pool 實驗](01-16.development-design-bounded-queue-batch-pool-tokio-benchmark.md)、[歷史 ring 實驗](01-17.development-design-tokio-request-ring-hashmap-benchmark.md)。

可呈現的能力：將資源上限、背壓與呼叫端重試行為一起設計。
容量與 timeout 是保守預設，不是已證明的最佳值或 SLA。原生儲存與動態帳戶仍有額外記憶體成本；有界 queue 不等於全程序 RSS 硬上限。

### D04：分片與受控查詢並行

- 需求：同帳戶更新維持順序；不同 shard 可並行處理；索引讀取不能改變交易套用順序。
- 比較選項：單 shard 或多 shard；shared 或 dedicated DB；逐筆 Get、整批 MultiGet 或分組 MultiGet。
- 現行選擇：以 `account_id % shard_count` 路由。每 shard 順序執行批次。正式核心預設一個 shard、shared DB、每組 256 keys 且最多 4 組查詢並行。
- 代價：同 shard 的不同帳戶仍共享批次處理順序。增加 shard／查詢並行會增加 CPU 與背景資源競爭。Dedicated DB 增加管理成本。既有資料不能直接改 shard 數或 DB layout。
- 代價處理：查詢結果先檢查群組、範圍、數量與完整性，再依原位置套用。儲存批次與 GC 共用 shard gate。Write buffer、cache 與 background jobs 依全程序預算分配。
- 錯誤處理：lookup 結果錯誤時不套用未驗證批次。重開時 shard、routing 或 layout 不符即拒絕。第一版不提供 resharding。
- 證據：[查詢與順序套用](../src/storage/account_store.rs)、[pipeline 設定與儲存預算](../src/pipeline.rs)、[lookup fault 測試](../src/storage/ledger_index_lookup_fault_tests.rs)、[schema/layout 測試](../tests/formal_pipeline.rs)、[整合查詢實驗](../benches/ledger_pipeline_index_lookup_tokio_report.md)、[分片實驗](../benches/ledger_pipeline_sharding_tokio_report.md)。

可呈現的能力：增加讀取並行度，同時維持寫入順序與資源邊界。
跨 shard sequence 不構成全域順序。第一版不提供跨 shard 原子交易。

### D05：歷史投影、時間邊界與安全 GC

- 需求：刪除來源資料後，仍能查到原交易結果與退款證據。投影進度不能超過真實已保存資料。
- 比較選項：依 TTL 直接刪除；保留全部來源資料；以耐久投影、watermark 與連續覆蓋證據控制 GC。
- 現行選擇：歷史 apply 成功後才同步保存來源 progress。發布 watermark 前先安裝 fence、排空相關請求、等待投影，最後同步保存邊界及配對 sequence。
- 代價：增加進度、目的端身分與時間邊界狀態。GC 遇到第一筆不合格記錄會停止，較後面的舊資料仍可能留存。
- 代價處理：目的端接受相同內容的冪等重播。GC 只刪除安全連續前綴，並原子更新 ledger、index、退款 marker 與 GC prefix。Durable backend 必須提供一致讀回能力。
- 錯誤處理：history 暫時失敗採有界重試；耗盡後 degraded 並凍結相關進度。永久 conflict 或 corruption 停止投影。Volatile backend 不發布 durable watermark，也不執行實際歷史 GC。
- 證據：[投影與 watermark](../src/pipeline.rs)、[fence](../src/admission.rs)、[歷史儲存契約](../src/history.rs)、[安全 GC](../src/storage/account_store.rs)、[正式歷史失敗測試](../tests/formal_history_failure.rs)、[durable fixture 測試](../tests/formal_pipeline.rs)、[GC 中斷與邊界測試](../tests/ledger_safe_gc.rs)。

可呈現的能力：以資料覆蓋證據決定刪除條件，並處理跨儲存進度的不一致。
目前 CLI 沒有真實 durable external connector，使用 volatile mock。Durable fixture 只驗證契約。Logical delete 不保證立即回收實體磁碟空間。
以已發布 watermark W 判斷時，transaction_at < W 必須查歷史；查無資料則回傳 ExpiredTime，不執行新交易。transaction_at == W 屬新交易邊界。Fence 可能先阻擋尚未完成邊界切換的請求。

### D06：取消、安全關閉與觀測

- 需求：呼叫端離開或 shutdown deadline 到期時，不能誤報已接受交易被撤銷。關閉流程須有可觀察狀態。
- 比較選項：逾時直接 abort 全部工作；由呼叫端持有交易生命週期；由核心持有已接受工作並排空。
- 現行選擇：核心 coordinator 持有批次與 gate。Shutdown 先停止入口，再排空已接受交易及已開始 I/O，join 背景工作後關閉 DB。
- 代價：呼叫端逾時後，工作可能仍執行。需要維持 runtime 與 DB handle，直到服務完成關閉。
- 代價處理：區分 `shutdown()` 與 `wait_closed()`。提供每 shard 進度、健康狀態與固定容量 metrics。每 stage 最多保留 4,096 個樣本。
- 錯誤處理：回覆 deadline 導致結果未知；shutdown deadline 回傳 `ShutdownTimeout`。繼續觀察並等待 `wait_closed()`，不提早刪除資料或釋放 runtime。
- 證據：[生命週期實作](../src/pipeline.rs)、[CLI](../src/main.rs)、[metrics](../src/metrics.rs)、[取消與 drain 測試](../tests/formal_pipeline.rs)、[SIGINT／EOF 測試](../tests/formal_crash_recovery.rs)、[metrics 上限測試](../tests/formal_history_metrics.rs)。

可呈現的能力：區分呼叫端等待期限與工作生命週期。
Metrics 的 RPS 計入已返回的 submit 和 balance 呼叫，包含錯誤；不是 durable commit RPS。不同 stage 的計時可能重疊，分位數不能相加。

## 4. 實際函式執行流程

### 4.1 交易輸入與回覆

```text
CLI stdin: credit / debit / refund
  |
  v
dispatch_line() -> number()
  |
  v
Pipeline::credit() / debit() / refund()
  |
  v
Pipeline::submit() -> submit_inner()
  |
  +-> admission.begin() + try_acquire_owned()
  |     `-> Closed / Overloaded
  |
  v
AdmissionGate::admit(transaction_at)
  |
  +-> Historical
  |     |
  |     v
  |   HistoryStore::lookup_transaction()
  |     `-> replay / Conflict / ExpiredTime / history error
  |
  `-> Commit
        |
        v
      BatchQueue::submit() -> bounded MPSC
        |  `-> timeout before acceptance: NotAccepted
        v
      run_worker() -> collect batch -> handler
        |
        v
      AccountStore::handle_batch_with_index_lookup()
        |
        v
      handle_batch_with_index_lookup_coordinator()
        |
        +-> shard batch gate + index lookup + result validation
        |
        v
      spawn_blocking(process_batch_with_index_lookup())
        |
        v
      process_batch_selected()
        |
        +-> replay / conflict / ordered business evaluation
        |
        `-> new results: DB::write_opt(WriteBatch, sync_write_options())
              |
              v
            publish memory state after successful sync
              |
              v
            RequestHandle::wait() -> TransactionReceipt
              |
              v
            print_transaction() -> CLI stdout
```

歷史分支結果亦回到 CLI 的 `print_transaction()`。
接受後的 response timeout 會回傳 `CommitOutcomeUnknown`。交易工作仍由核心持有。
只有含新交易結果的批次需要上述同步寫入。純 replay 不增加 sequence。
`balance` 由 `Pipeline::balance()` 呼叫 `try_balance_snapshot()`，不進交易 queue。
函式來源：[main](../src/main.rs)、[pipeline](../src/pipeline.rs)、[queue](../src/batch_queue.rs)、[account store](../src/storage/account_store.rs)、[admission](../src/admission.rs)。

### 4.2 耐久歷史、watermark 與 GC

```text
committed_head update
  |
  v
run_projector()
  |
  v
AccountStore::read_ledger_range()
  |
  v
HistoryStore::apply_batch()
  |
  +-> temporary error: bounded retry -> degraded on exhaustion
  +-> permanent error: stop projection
  |
  `-> durable destination acknowledged
        |
        v
      AccountStore::persist_projection_progress()
        |
        v
      ProjectionProgress::acknowledge()

watermark tick -> run_watermarker()
  |
  v
AdmissionGate::begin_fence(candidate)
  |
  v
wait_for_admitted_commits() -> capture source sequence
  |
  v
ProjectionProgress::wait_for(target)
  |
  v
AccountStore::persist_projected_before_durable(candidate, target)
  |
  v
fence.publish()

GC task loop -> spawn_gc_task() closure
  |
  v
AccountStore::collect_garbage(batch_size)
  |
  +-> first unsafe record: stop prefix deletion
  |
  `-> sync deletion + GC prefix -> update observed progress
```

本圖的 durable 分支有條件：注入符合契約的 durable backend。
CLI 的 volatile backend 可重建投影視圖，但不執行上述 durable watermark／GC 流程。

## 5. 錯誤與恢復素材

| 觸發情境 | 結果或狀態 | 處理方式 |
| --- | --- | --- |
| in-flight 額滿 | `Overloaded`。 | 呼叫端降速，稍後以原 key/body 重試。 |
| 接受前逾時 | `NotAccepted`。 | 請求未被接受，可用原 key/body 重試。 |
| 接受後回覆逾時 | `CommitOutcomeUnknown`。 | 不推論失敗，以原 key/body 查回保存結果。 |
| 相同 key 不同 body | Conflict。 | 修正呼叫端 key 使用方式，不盲目重試衝突內容。 |
| 餘額不足等業務拒絕 | 已提交的 status。 | 重播取得原拒絕。修改業務意圖時使用新交易識別。 |
| storage error | 健康異常、停止新交易。 | 不偽造成功；恢復儲存條件後重開並驗證。 |
| history 暫時失敗耗盡 | degraded、相關進度凍結。 | 修復目的端，確認覆蓋後重新啟動；不假造進度。 |
| history 永久 conflict／corruption | 投影停止。 | 修復資料一致性與目的端身分，再驗證恢復條件。 |
| metadata／shard／layout 不符 | 啟動失敗。 | 使用相符設定；第一版沒有自動遷移。 |
| shutdown 超時 | `ShutdownTimeout`，關閉仍可能進行。 | 維持 runtime，等待 `wait_closed()`。 |

來源：[型別化錯誤](../src/error.rs)、[pipeline](../src/pipeline.rs)、[正式核心錯誤契約](01-30.development-design-ledger-formal-core.md)。
呼叫端降速與資料修復是本次整理的操作建議，不是核心自動提供的控制器或修復功能。
