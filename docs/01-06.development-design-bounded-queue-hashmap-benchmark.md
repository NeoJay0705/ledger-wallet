# Bounded Queue HashMap Benchmark 設計

## 範圍

新增獨立 harness-free benchmark `bounded_queue_hashmap`，量測同步 bounded request/response queue、單一 worker batch 與 `HashMap<u64, u64>` 更新。它不使用 Tokio，也不連接正式 transaction processor。每輪只有三個固定角色：main thread 作 collector、一個 producer thread、一個 worker thread。

## 工作負載與批次

預設每個情境送出 10,000,000 筆，`id` 由 0 遞增，`key=id%100000`。Producer 持續呼叫容量 50,000 的 `sync_channel` blocking send，不等待個別 response。Worker 依 FIFO 收集 batch；batch size 為 2048 或 4096，timeout 為 1、5、10 或 20 ms。第一筆進入空 batch 時啟動 deadline；到達 batch 上限或 deadline 時處理。Producer 關閉且佇列排空後，worker flush 不足一批的尾批。

Map 可從 `HashMap::new()` 開始，或在量測前預填 100,000 個 key、value 為 0。空 map 的首次 insert 與擴容計入 batch active time；預填成本排除於計時。Worker 更新該 key 的 count 並產生每筆 response `{id,count}`。Main collector 依序檢查 response ID 與 `count=id/100000+1`。每輪結束也驗證最終 map 的長度及各 key 的 count；對小於 100,000 的 N，空 map 只需含已使用的 key，預填 map 仍有完整 key 空間。

Request 與 response channel 都是容量 50,000 的 bounded `sync_channel`。三個角色透過 barrier 同步起跑。每輪獨立建立 queue、thread 與 map；map 初始化在起跑計時前完成。預設執行 map 狀態、batch size、timeout 的完整 16 組，每組一輪。CLI 可用 `--iterations`、`--repetitions`、`--map-state all|empty|prefilled`、`--batch-size all|2048|4096`、`--batch-timeout-ms all|1|5|10|20` 選擇範圍。

## 指標定義

- **Enqueue latency**：每筆 blocking `send` 呼叫從開始到返回的實際耗時。平均值累計所有 N 筆耗時；RPS 為 N 除以 producer 從首筆嘗試到末筆成功送入的時間。
- **Dequeue latency**：worker 成功取得一筆 request 的 `recv` 或 `recv_timeout` 呼叫耗時，含該呼叫內的阻塞等待。只統計成功收到 N 筆的呼叫，並檢查成功呼叫數必須等於 N；Timeout 與 Disconnected 呼叫只用於 flush/結束判斷，不計入 dequeue latency。
- **Dequeue rates**：`dequeue_observed_rps` 為 N 除以首次成功 recv 呼叫開始至最後一次成功 recv 結果返回的 wall span，該 span 包含兩次 recv 間的 map 更新與 response send。`dequeue_active_rps` 為 N 除以所有 N 次成功 recv 呼叫實測耗時總和；其呼叫耗時包含等待。這些分階段 active rate 不能相加，也不等於完整 pipeline throughput。
- **Batch active**：所有批次 map 更新及本地 response staging 區間的耗時總和，不包含 bounded response channel send。Active RPS 為 N 除以此總和；平均 ns/item 為 active nanoseconds 除以 N。Batch duration 分位數涵蓋每一批 active 區間，另列 batch 數、平均/最大 batch size 與 full、timeout、tail flush 數。
- **Pipeline latency**：各 ID 從 producer 開始嘗試 send 到 main collector 收到相應 response 的實際耗時。平均值累計每筆耗時，不用 wall/N 代替；completed RPS 為 N 除以首筆嘗試至最後一筆 response 到達的 wall time。
- **分位數抽樣**：enqueue、dequeue 與 pipeline latency 預設依 logical index 以 `splitmix64(index) % stride == 0` 做 deterministic hash sampling，並在起跑前建立共用 bitset，避免量測迴圈執行抽樣 hash。Stride=1 時每筆都取樣；每輪報告實際樣本數與 nearest-rank p50/p95/p99。可用 `--latency-sample-stride` 調整。Batch duration 直接涵蓋每批，預期樣本量小。
- **CPU**：以 `cpu-time` 的 ProcessTime 計量 producer、worker、collector 所在程序 CPU 秒數。CPU 與其 `cpu_measurement_wall_s` 同從 main thread barrier 返回後量到 collector 收到最後一筆 response；core equivalents 為 CPU seconds / `cpu_measurement_wall_s`，one-core CPU% 為 100 × core equivalents。Completed RPS 另使用首筆 send 嘗試至末筆 response 的 pipeline wall。

## 報告與限制

每輪及跨輪逐欄中位數都輸出。報告保存完整預設矩陣的實測值、測試環境與執行命令。此測量描述本機同步通道與 HashMap 更新；它不代表網路、磁碟持久性、外部到達率或正式交易處理效能。CPU 是程序整體值，batch active time 不含 response send；平均 latency 與抽樣分位數的樣本範圍需依上述定義解讀。

逐筆完整 pipeline latency 的四段 breakdown 與量測成本變更，見 [01-07 latency breakdown subdevelopment](01-07.development-design-bounded-queue-latency-breakdown.md)。
