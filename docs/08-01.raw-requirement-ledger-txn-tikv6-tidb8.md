# ledger-tikv6 — Requirements (user-confirmed, REVISED by user correction)

**Revision (user): two fresh configurations, both measured now at 16 connections, batch 2000/4000/8000, one run each (no reuse of earlier data):**
- `tidb-k4t4-n16`: TiKV 4 CPU, tidb-server 4 CPU = the existing standard TiDB CPU4 placement (wrapper `--cpus 4`: TiKV 0-3, tidb 6-7,12-13, client 4-5, PD+sampler 14-15), measured again.
- `tidb-k6t8-n16`: TiKV 6 CPU (2 stores x 3, cpusets 0-2 / 4-6, `--cpus 3` each), tidb-server 8 CPU (3,7,10-15), client+PD+sampler 8-9 (wrapper `--cpus 8 --tidb-extended --tikv-cpus 6`).
Runs go back to back with no fixed waits added by the driver/operator (the only fixed wait is the existing wrapper PD-balance wait for 2-store layouts). The +-15 % extra-run reference: k4t4 vs artifacts/fixconn-tidb-c4-n16 (not published) effective primary (earlier measurement, reproducibility), k6t8 vs artifacts/fixconn-tidb-c8x-n16 (not published) effective primary. The text below that says 'CPU6x'/c6x means `tidb-k6t8-n16`.

Goal: add one TiDB configuration "CPU6x": TiKV gets 6 logical CPUs, the 2 CPUs freed from CPU8+ go to tidb-server. Compare with the existing TiDB CPU8+ (TiKV 8 / tidb 6) at 16 connections.
1. Placement (profile CPU6x): 2 TiKV stores x 3 CPUs: TiKV cpusets 0-2 and 4-6, each `--cpus 3`, 8g; tidb-server cpuset 3,7,10-15 (8 logical CPUs, no CPU quota, 16g); client + PD + sampler/wrapper 8-9 (same as CPU8+). no RF (max-replicas=1), 256 regions per table (one queue = one region), same PD balance gate/wait as CPU8.
2. Workload: 2 M requests (50,000 accounts x 40), 256 queues, 16 connections, batch-max 2000, 4000, 8000 only. Same semantics, monitoring, idle gate (before every attempt), flush rerun rule (flush await > 2 ms => one rerun) as ledger-fixconn. No import, no stop rule, no saturation search.
3. Runs: each batch ONCE. One extra run only if the result differs a lot: flush await > 2 ms (existing flush rerun) OR RPS differs from the existing TiDB CPU8+ N16 result (artifacts/fixconn-tidb-c8x-n16 (not published) effective primary, same batch) by more than +-15 %. Extra runs never replace the first value; both are reported (flush rerun replaces only under the existing flush rule).
4. Report docs/08-03.development-analysis-ledger-txn-tikv6-tidb8.md: per batch table: RPS, p50/p95/p99/max, windows, TiKV CPU (cores, % of 6-core quota), tidb-server cores and % of its 8-CPU cpuset (`*` >= 85 %), client/PD/sampler shared-CPU, memory, disk sdb, network, TiKV durability deltas, region distribution, extra-run info; plus comparison vs CPU8+ N16 (same batch RPS ratio, p99) and vs TiDB CPU4 N16; disclosures: TiKV quota 6 (3 per store), CPU3/7 are SMT siblings of CPU11/15 (both tidb-server), client/PD/sampler share 8-9, single runs.
