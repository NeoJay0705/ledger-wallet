# 帳戶記憶體狀態與單 CQL LWT Wallet 基準驗證

## 結果與範圍

`wallet-memory-lwt-v1` 的實作與小型正確性驗證已通過。完成兩個 64 帳戶 smoke cases；這些結果不是 10M workload，也不構成效能比較或效能改善結論。

兩個 case 各使用三個同機隔離 ScyllaDB nodes，共用 SSD、固定 image 與 ScyllaDB `2026.1.14`。每個 case 使用單一 service 與共享 `Session`，設定 `LOCAL_SERIAL`、`commitlog_sync=batch` 和既定 timeout。RF3 使用 round-robin；RF1 使用 per-user routing。交易路徑每筆送出一個 LWT CQL request。每個帳戶依序執行 200 筆交易；兩次 smoke 各有 64 帳戶、12,800 筆請求。

## 兩個 live cases

| Profile | RF / read CL / write CL | Routing | S / C / P / D | Accounts × requests | Accepted / applied / replies / errors | Driver CQL / measured SELECT | Verification | Runner / integration / cleanup |
|---|---|---|---:|---:|---:|---:|---|---|
| RF3 | 3 / `THREE` / `THREE` | round-robin | 1 / 3 / 1 / 3 | 64 × 200 | 12,800 / 12,800 / 12,800 / 0 | 12,800 / 0 | 64 accounts、12,800 ledger rows | passed / 2 tests passed / clean |
| RF1 | 1 / `ONE` / `ONE` | per-user | 4 / 64 / 4 / 48 | 64 × 200 | 12,800 / 12,800 / 12,800 / 0 | 12,800 / 0 | 64 accounts、12,800 ledger rows | passed / explicitly skipped / clean |

`S` 是每 node 的 shard 數；`C` 是 worker 數及應用層 in-flight 上限；`P` 是每 node、每 shard 的 data connection 數；`D=3×S×P` 是三個 node 的 data connections 總數。RF1 case 的 48 條 data connections 實際分布為每 node 16 條；兩個 case 的 pool、required metrics 與 workload verification 均通過。RF1 case 沒有執行 live fault integration；它的 harness 明確記錄 `integration_skipped_explicitly=true`。因此這兩個 case 只驗證指定成功路徑與資料，不比較 RF 對吞吐或故障恢復的影響。

兩個 case 的 CPU affinity 如下。Scylla nodes、服務與 load process 使用互不重疊的 CPU sets；S4 node 使用 SMT threads。

| S | Node A | Node B | Node C | Service、load、monitors |
|---:|---|---|---|---|
| 1 | `0` | `2` | `4` | `6,7,14,15` |
| 4 | `0,1,8,9` | `2,3,10,11` | `4,5,12,13` | `6,7,14,15` |

RF3 smoke 的兩個 ignored live integration tests 另外通過，耗時 8.81 秒。測試包含 owned node A 的 SIGKILL 與 restart、unknown LWT 結果 fail-closed，以及 cache 未因 unknown transaction 前進。Restart 後檢查確認節點仍帶有預期 owner 與 nonce。測試結束後三個容器、network 與 owned data 均清理完成。RF1 smoke 沒有執行這些 fault assertions。

## Build 與測試

Freeze source 的 Rust suite 通過 40 項：9 lib、17 CLI、14 service tests。Rust format 與 release build 通過。Python runner suite 通過 90 項；`py_compile` 與 dry-run 也通過。後續報告欄位修正有獨立的回歸檢查，未改變測量輸入。

常用的重現命令：

~~~bash
CARGO_TARGET_DIR=target/scylla-wallet taskset -c 6,7,14,15 cargo test --locked --manifest-path benchmarks/scylla-wallet/Cargo.toml
CARGO_TARGET_DIR=target/scylla-wallet taskset -c 6,7,14,15 cargo fmt --manifest-path benchmarks/scylla-wallet/Cargo.toml -- --check
CARGO_TARGET_DIR=target/scylla-wallet taskset -c 6,7,14,15 cargo build --release --locked --manifest-path benchmarks/scylla-wallet/Cargo.toml
taskset -c 6,7,14,15 python3 -m unittest discover -s tests -p test_scylla_wallet_runner.py -v
~~~

## 驗證歷程

第一次 RF3 live attempt [run-20261012T105014Z-f270fb97](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261012T105014Z-f270fb97/report.zh-TW.md) 的 wallet verification 失敗：`verify_account` 的 SELECT 回傳 7 欄，但 decoder 需要含 `kind` 的 8 欄。修正 SELECT 將 `kind` 放在第一欄後，retry [run-20261012T105930Z-8f821354](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261012T105930Z-8f821354/report.zh-TW.md) 的 runner workload 與 wallet verification 通過。Retry 的獨立 integration harness 隨後拒絕 fault-test 前的 ownership audit，原因是容器 ID short/full 格式不一致；network ownership check 本身通過。該 retry 沒有執行 fault tests，不能描述為 wallet case 失敗。這兩個 attempt 的 owned cleanup 都完成。

Runner 只將容器 ID 正規化為 Docker inspect 的 canonical full ID 後，RF3 run [run-20261012T110549Z-9571b9a9](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261012T110549Z-9571b9a9/report.zh-TW.md) 通過完整驗證、兩個 live integration tests 與 cleanup。RF1 run [run-20261012T110929Z-8db6ac1b](../benches/data/scylla_wallet/artifacts/target/scylla-wallet/runs/run-20261012T110929Z-8db6ac1b/report.zh-TW.md) 也通過 workload、verification 與 cleanup；其 live integration 依 harness 設定明確略過。

## 報告計數說明

兩次 live run 保留的原始 monitor artifacts 仍帶有舊三 CQL profile 註記（兩個 SELECT 加一個 batch）及其 expected count。這些原始檔沒有改寫。後續 runner 報告修正已將 contract 註記更新為每筆交易一個 LWT statement、零個 SELECT，並由 90 項 Python tests、`py_compile` 與 dry-run 驗證。兩次 live run 的實際 request count 以 CLI driver-counter delta 和 service summary 為準：每筆 accepted transaction 一個 CQL request，measurement SELECT 為零。

## 執行流程

```text
client input
  -> Service::submit
  -> account owner and cached AccountState
  -> worker_loop
  -> process_job
  -> compute next state and result
  -> ScyllaStore::commit
  -> one INSERT ... IF NOT EXISTS
  -> publish cache only after Applied acknowledgement
  -> reply

unknown write result
  -> freeze affected account and fail admission closed
  -> drain accepted work
  -> verify ScyllaDB ledger and cached account snapshot
  -> cleanup owned resources
  -> retain result and audit artifacts
```
