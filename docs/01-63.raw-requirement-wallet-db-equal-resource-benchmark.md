# ScyllaDB 與 PostgreSQL Wallet 等資源比較：原始需求

日期：2026-10-13。

目標：在固定 Wallet 交易語意和主機資源上，比較 ScyllaDB 與 PostgreSQL 的單節點吞吐、延遲、CPU、記憶體及 I/O。

需求編號：01。文件序號：63。

狀態：Workload/resource profile 已定。PostgreSQL 18.6 基礎設施資格測試、有限的 Rust Wallet live integration/32×32 smoke/runtime/catalog/monitor/process-restart qualification，以及 bounded Scylla profile qualification 均已通過；先前 Wallet live qualification 使用 CLI binary SHA-256 `b507e1f112a30ea8ffcf4bd2d185ee4ec485a858edcc8832bdafabe67b9a3fe2`。目前 formal-campaign CLI candidate SHA-256 為 `02ddf0f843ab8a7a15d2f20cc3ed35f6d7661fcbd1d4e4141250672fcba7e555`，僅含 telemetry lifecycle correction，尚未以此 binary 執行 live qualification。SQL migration 未變。上述 qualification 不是 1,024,000-request calibration 或正式比較；正式 campaign 仍須 root 完成 source、binary、SQL、runner 與資源 profile 的 final freeze review。

本需求接續 [01-54 的 ScyllaDB S2 需求](01-54.raw-requirement-scylladb-calibrated-s2-concurrency-benchmark.md) 和 [01-56 的單節點診斷結果](01-56.development-analysis-scylladb-calibrated-s2-concurrency-benchmark.md)。本文件固定新的比較條件，不沿用舊 run 的吞吐作為本輪 baseline。

## 比較目標與邊界

比較相同 Wallet service、account owner、memory cache、使用者請求與正確性要求，由 ScyllaDB 或 PostgreSQL 單獨承接每次 Wallet commit 的結果。每個 workload case 只啟動一種資料庫。兩種資料庫依序使用同一台主機、相同 CPU affinity、container memory limit、cgroup I/O caps、檔案系統和資料裝置。

這是本機固定資源下的資料庫與 transaction path 比較。它不比較多故障域、RF=3、replication、容錯、自動 failover、steady-state 容量或 production SLA。結果也不能證明裝置的物理上限。

每筆新 Wallet request 不另作資料庫前置讀取。PostgreSQL client 對預先建立的 `wallet_commit` prepared statement 發出一次呼叫；這個 statement 以單一隱式 transaction 原子寫入 ledger 和 account state。Rust 實作凍結後，SQL schema、回傳欄位及衝突處理以該 migration 的實際內容與 hash 為準。[01-64 設計](01-64.development-design-wallet-db-equal-resource-benchmark.md) 記錄已核准的 transaction shape，但不取代 frozen SQL。

## Wallet transaction contract

1. ScyllaDB 和 PostgreSQL 共用同一個 service、同一個 account owner 順序控制和 memory cache。Client response 必須等資料庫 command 已完全 drain 到 `ReadyForQuery`；新 transaction 還必須等 backend durable commit acknowledgement 後才發布 committed account state。Applied outcome 會改變 balance；insufficient-funds、overflow 或 invalid-amount 是已持久記錄的 business rejection，balance 維持不變，但 version/write_clock 前進且 cache 反映該已提交狀態。Duplicate 不得重複更新 account/cache；content conflict 不改變 cache。
2. PostgreSQL 的一次 prepared statement call 在 server 端以同一個 transaction 寫入唯一 ledger key `(account_id, tx_id)`，並更新 account。`amount` 和 `balance` 使用 8-byte unsigned integer 的 BYTEA 編碼，保留 `u64` 全部位元範圍。
3. 首次套用成功時只更新一次 account。相同 key、相同內容的重送回傳原始 ledger result，不再更新 account。相同 key、不同內容回報 conflict，不改變 account。Account 不存在時，ledger insert 和 account update 一起 rollback。
4. Business rejection（insufficient funds、overflow、invalid amount）會以 ledger outcome 持久化、保留原 balance 並推進 version/write_clock；durable acknowledgement 後 cache 同步該 committed state。Constraint/function failure 或已確認 rollback 不發布未提交 state。未知 commit 結果會 freeze 該 account 並使整個 workload fail closed；不得自動 retry、reconnect 後重送或把未知結果算為成功。
5. PostgreSQL 成功 reply 等待 `synchronous_commit=on`、`fsync=on` 的 commit acknowledgement。這是 PostgreSQL 軟體與裝置 flush contract，不是斷電保證的實測證據。Scylla 的 batch commitlog acknowledgement 不是每筆 request 各自一次 fsync；兩種 engine 的 flush counters 都不得換算成每 transaction 一次 fsync。

另需以 correctness validation 覆蓋 duplicate、content conflict、insufficient funds、overflow、missing account、rollback 和 account freeze。Owned crash/restart durability 驗證獨立記錄，不混入本次吞吐矩陣。

## Workload 與連線校準

每個 workload case 使用新資料，執行 1,024 accounts × 1,000 sequential requests，共 1,024,000 operations；Credit 和 Debit 各 512,000，每筆 amount 為 1。每個 account 同時最多有一筆未完成 request；client 收到 reply 後才送下一筆。Service 使用 C=512 workers、50,000 個 bounded queue slots。所有 case 使用相同 request order、seeded account state 與 verification 規則。

先對 PostgreSQL pool D=16、D=32、D=64 各執行一個 1,024,000-request calibration case。只納入通過完整 correctness、error、runtime profile 和 cleanup gates 的有效 case。選擇 RPS 最高有效 case 的最小 D，使其 RPS 至少為最高值的 95%。不得加跑 D=6 calibration。

接著使用固定選定 D 執行六個 fresh full cases，順序固定為 Scylla / PostgreSQL / PostgreSQL / Scylla / Scylla / PostgreSQL。Scylla 的 D 固定 6；PostgreSQL 使用上述選出的 D。每個 case 一次，不自動 retry。連同三個 D calibration case，本輪共九個 case。

## 計時、驗證與觀測

Workload RPS 時窗從第一個 client request 開始，到最後一個 client reply 完成。時窗包含 service admission、account owner、service queue、DB pool wait 和 SQL/CQL latency。PostgreSQL pool wait 另外量測，且另行報告 SQL latency 與 end-to-end latency。Pool wait 仍包含在 RPS 與 end-to-end window 內。

每個 case 全量驗證 1,024 account states 和 1,024,000 ledger rows；檢查 accepted/applied/replied、Credit/Debit totals、query/statement count、重試、timeout、unknown outcome 和 cleanup。Database setup、seed、verification、checkpoint、drain 和 cleanup 都在正式 workload window 外。Checkpoint/drain 的額外時間另外保存，不加進 workload RPS。

PostgreSQL 保存 `pg_stat_io` 中 `object='wal'` 的 writes/fsync/time、`pg_stat_wal` bytes/FPI、`pg_stat_activity` waits、`pg_stat_database` transaction counts、checkpointer 和 autovacuum stats。兩種資料庫保存 container cgroup CPU 與 memory；memory 包含 page cache。PostgreSQL process RSS 會共用 shared mappings，不得將各 backend RSS 相加當成 server 記憶體。Host diskstats 以 1 Hz 取樣，分開保存 `/dev/sdb2` partition 與 `/dev/sdb` whole-device counters；不要相加，也不要稱為 per-transaction latency。Whole-device flush await 為 host block-layer 指標，不是 Wallet commit latency。

## 舊數字與結論限制

01-56 的 Scylla C=512 case 約為 15,885 RPS，只作歷史參考。它使用不同 caps、binary 與 workload run context，不是本輪比較 baseline。新資源 caps 和凍結 binary 必須產生新的 Scylla case。

Short closed-loop cases 無法證明 steady-state 或硬體上限。即使兩種資料庫在本機裝置上的吞吐不同，也不能直接推論其他裝置、複寫數、故障域或 production workload 的勝負。本次不增加 S1、RF3、D=512、commit delay、batch size 矩陣或新的 calibration。
