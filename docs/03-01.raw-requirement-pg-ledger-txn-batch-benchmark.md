# 需求：PostgreSQL 冪等帳本交易（before/after）批次吞吐測試

程式與資料：[`benchmarks/pg-ledger-txn`](../benchmarks/pg-ledger-txn/README.md)。

## 1. 請求語意
請求為 `(tx_id, account_id, amount)`，以 tx_id 冪等：
- tx_id **已存在**：回傳原本的 ledger 記錄，不改動餘額。
- tx_id **不存在**：在同一個交易內新增 ledger 記錄並更新帳號餘額，回傳新記錄。

ledger 欄位：`transaction_id, account_id, amount, before_balance, after_balance`，`after = before + amount`；帳號餘額等於該帳號最新一筆的 `after`。

## 2. 契約（本測試採用的決定）
1. 一個 tx_id 永遠屬於同一個帳號（重送一定帶相同 account_id）。冪等鍵為 `(account_id, transaction_id)`；**不強制**不同帳號間 tx_id 全域唯一（在 ScyllaDB 上無法與餘額更新原子完成，故兩個資料庫採同一契約）。
2. 金額為正的 64 位元整數，初始餘額 0；金額 ≤ 0 → `rejected:invalid_amount`。
3. 帳號不存在 → `rejected:unknown_account`，不自動建立帳號。
4. 重送帶不同金額：回傳**原本**的記錄。
5. 保留外鍵 `ledger.account_id → accounts`。
6. 批次一定混合多個帳號；application 可先整合（去重、依帳號分組、保留帳號內輸入順序）再送。每個帳號同一時間只有一個執行者（queue 依帳號分區）；晚到的重送要查 DB，不只看當前視窗。
7. 每個請求必須有且僅有一個終態回覆。

## 3. 持久性
PostgreSQL：`fsync=on`、`synchronous_commit=on`、`full_page_writes=on`。（ScyllaDB 對應設定為 `commitlog_sync: batch`，本次未量測，見設計文件。）

## 4. 工作量與環境
PostgreSQL 18.6（pinned image digest），容器 8 CPU（cpuset 0–7）、8 GiB 記憶體、`shared_buffers=2GB`、`wal_buffers=256MB`、`max_wal_size=8GB`、`track_wal_io_timing=on`；client 綁 CPU 8–9，sampler 綁 CPU 14–15。100,000 帳號 × 40 筆 = 4,000,000 個新請求（金額 1）；256 個 queue（`queue = user % 256`）= 256 條連線；一個視窗 = 一個 statement。

| Cell | 視窗（新請求數） | 重送 |
|---|---|---|
| 4000 | 4000 | 0% |
| 8000 | 8000 | 0% |
| 8000 + retry | 8000 | 5%（每個 queue 782 或 780 筆，共 200,000 筆，於下一個視窗重送；總請求 4.2 M） |

## 5. 量測項目
吞吐（請求／秒、statement／秒、WAL 與磁碟頻寬）、延遲 p50/p95/p99、in-flight、CPU、記憶體、磁碟 util／await／IOPS，另含 WAL 位元組、fsync 大小、checkpoint 次數、`wal_buffers_full`。

## 6. 驗收（必要項）
每個請求都有終態回覆（`missing=unexpected=0`）；各帳號 ledger 筆數、金額總和、餘額、before/after 鏈（首筆 before = 0、每筆 before = 前筆 after、最後 after = 餘額）；重送回傳與原記錄相同（`replay_mismatch=0`）；拒絕案例沒有變更；生效設定與預期相同。Checkpoint、停頓、`wal_buffers_full`、fsync 次數是**診斷**，不是正確性條件。
