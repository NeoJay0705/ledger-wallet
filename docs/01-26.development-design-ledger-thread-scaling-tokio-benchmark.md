# Tokio 批次佇列與 Ledger Pipeline 執行緒數擴展效能對照測試

## 目的與範圍

本 benchmark 比較共用 Tokio runtime `worker_threads` 設為 3、4、6、8 時，固定負載下的 throughput、tail latency 與 CPU 效率。單獨量 queue echo 不能決定 storage pipeline 的執行緒設定，因此測試同時包含純 queue、前景持久化與整合 pipeline 三種 profile。

沿用現有 shared batch queue 與 `AccountStore`，不改動既有 benchmark 的預設值。完整矩陣為 3 profiles × 4 worker 數 × 3 repetitions，共 36 trials；每 trial 量測 10,000,000 requests，總量 360,000,000 requests。

## Profiles 與固定矩陣

| Profile | 量測路徑 | 背景工作 |
| --- | --- | --- |
| `queue_echo` | enqueue → dequeue batch → mock echo → oneshot response；不使用 HashMap 或 RocksDB。 | 無 storage pipeline。 |
| `foreground_persistence` | 相同 queue → Credit/Debit handler → RocksDB sync-WAL commit → response。 | 量測與 settlement 期間停用 projection、watermark、GC。 |
| `integrated_pipeline` | 前景持久化路徑，加上 durable projector、watermark 與 safe GC。 | 依下列固定 projector、watermark、GC 設定執行。 |

每個 storage profile 在量測前為 50,000 個 users 各寫入三筆 seed transactions：Credit 100、Credit 1、Debit 1；共 150,000 筆 seed，初始 balance 為 100。各 user 再送 200 筆量測請求（Credit 1、Debit 1 各半），每位 user 同時最多一筆 outstanding request。全矩陣固定 50,000 users/coroutines、每個 user 200 requests、history traffic 0%、balance mode `PerBatch`。量測後每位 user balance 應仍為 100，source sequence 應為 10,150,000。

所有 profile 的 queue capacity 固定為 50,000；foreground batch size 固定 2,048，第一筆 dequeue 後 timeout 為 5 ms。`integrated_pipeline` 的 projector batch size 為 256，GC batch size 為 256，retention 為 500 ms，watermark tick 為 100 ms。GC 有進度時 yield 並繼續；遭阻塞或沒有進度時 sleep 100 ms。Contiguous prefix 用來保護 watermark、durable projected sequence 與 durable balance coverage。

## Trial 隔離、順序與主機條件

每個 trial 使用 fresh child process 與 fresh Tokio runtime；兩個 storage profiles 各自使用 fresh DB，`queue_echo` 不建立 DB。每個 repetition 旋轉 worker 數執行順序，並交錯執行三種 profile；manifest 記錄實際順序。所有 trial 沿用相同 inherited CPU affinity，SMT 設定不變；記錄允許使用的 CPU、CPU topology、software versions 與 storage device。`runtime_workers` 僅計 Tokio runtime worker，不包含 blocking pool 或 RocksDB threads。

每個 trial 前執行嚴格 preflight：CPU busy ≤10%、target device busy ≤5%，觀察 3 秒，最多等待 60 秒，並確認可用記憶體與磁碟 reserve 足夠。完整測試不得放寬這些門檻。Setup、seed 與 preflight 不計入 client RPS。Client window 結束後，final projector catch-up、watermark 與 GC sweep 合併記為 settlement time，且在 client window 外；recovery 與 integrity 另行分項計時及報告。

## 時間窗、取樣與輸出指標

`queue_echo` 的 RPS 時間窗由最早 request t0 至最後 reply；CPU window 由 start release 至最後 reply 的 CPU acquisition，並記錄 CPU sample offset。Pipeline 的 RPS 與 CPU window 均由 barrier release 至最後 reply。兩種 window 的起點差異很小，但報告必須保留並說明，不能隱藏或混為同一個起點。

所有 profile 使用完整 deterministic sample stride 64，p50/p95/p99 使用 nearest-rank，並列出每個 stage 的樣本數。報告 stage latency、process CPU、CPU cores、每 request CPU ns、I/O、WAL syncs、flush/compaction/stall、projection/GC counts 與 progress。記錄 I/O 各 endpoint 的 sample offset。

指標解讀限制：既有 read timing 包含 decode；`sync_write` 不等於純 fsync 時間；device I/O 是整個 device 的數值，並非程序獨佔。GC backlog 包含當時不符合資格、尚不能處理的 records。本任務不收集 per-file I/O attribution；aggregate 數字不能用來聲稱每個檔案的成本，也不能據此斷言 CPU hotspot 的成因。此矩陣不 sweep batch size 或 timeout，也不測試真實 external DB。

## 正確性、durability 與失敗處理

成功條件包含 exact replies、request IDs、operation mix、balances、source sequences、integrity 與 close/reopen 驗證。`foreground_persistence` 在量測與 settlement 期間停用 projection、watermark、GC；source 與 destination 的 durable projected sequence 均維持 seed sequence 150,000，durable boundary 也維持 seed。量測期間 projection、watermark、GC background work counters 必須為零；不得把尚未 projection 的量測請求當成 worker failure。`integrated_pipeline` 必須驗證安全 progress 與 contiguous-prefix 邊界。

一般 sync-WAL commit 只有在 write 成功後才能 acknowledge fresh request。Benchmark 的 MockDB 契約把 apply success 視為 durable；close/reopen 驗證保留並使用同一個 in-memory destination。這不代表 external DB 或 process-crash durability。

任何 commit、projection、watermark、GC 或 storage error 都使該 case 失敗，且不得產生 false acknowledgement 或 false progress。Case 結束或失敗後須 drain、drop handles，再清理本 trial 擁有的 DB。Invalid CLI、0 threads 與 unknown scenario 必須拒絕。未完整跑完矩陣或有失敗時，不得標示為 36-trial full result，並保留足以診斷的 failed logs。

## CLI、產物與清理

完整預設命令會執行全部 36 trials；`--validate-only` 列出 36 個設定但不執行 trial。Smoke 仍跑 36 個設定，每 case 改為 200 users × 200 requests，即 40,000 requests；preflight observation 為 100 ms，CPU 10% / device busy 5% 嚴格門檻不變。Smoke 輸出限定在 `target/`，不得覆寫 full report。

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --locked --bench ledger_thread_scaling_tokio

BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --locked --bench ledger_thread_scaling_tokio -- --validate-only

BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --locked --bench ledger_thread_scaling_tokio -- \
  --smoke --output-root target/ledger-thread-scaling-smoke
```

可用 `--scenario all|queue_echo|foreground_persistence|integrated_pipeline`、`--threads 3,4,6,8`、`--repetitions 1..3` 篩選。任何子集合都必須標示為 partial，不得當成完整 36-trial 矩陣。

Canonical report 為 `benches/ledger_thread_scaling_tokio_report.md`；archive 存於 `benches/data/ledger_thread_scaling/run-<id>/`，目前不指定固定 run ID。保留 summary、stage 與 background summary CSV，以及精簡 logs、manifest、metadata 與 report。Trial 結束後刪除所屬 DB、preflight scratch 與大型 per-event intermediates；不得刪除或改寫無關資料。

## 結果呈現

重複輪次以 descriptive median/min/max 呈現。不可將不同輪次的 percentiles 平均後當成 pooled percentile，也不可宣稱統計顯著性。比較 CPU/RPS 與 tail latency 等資源效率；worker 數增加可能提高 contention。完成 full matrix 並取得實測結果前，不提出 empirical worker-count recommendation。
