# TiDB R1 txn (before/after) batch-queue benchmark – report

Workload: 100k accounts x 40 = 4,000,000 requests, amount 1, 256 queues = 256 connections, single run per cell, no RF
(`max-replicas=1`), TiKV CPU only counted (tidb-server/PD pinned separately, sampled). All figures from `artifacts/`.

## batch-max 8000

| Cell | result |
|---|---|
| PG CPU=4 | 167,550 rps (txnpg4-bm8000, full resources, DB CPU 3.95 / 4); re-run txnpg4-bm8000-rerun 167,725 rps (client valid; resource summary lost to the sampler race below) |
| PG CPU=8 | 262,134 rps (txn-bm8000-W256) |
| TiDB CPU=4 / CPU=8 | **FAILED, not measurable in this setup**: tidb-server memory exceeds 13.7 GB (container 16g) and TiDB's memory controller kills statements (error 8176) or connections stall (30 s timeout). See below. |

Memory investigation (`artifacts/txntidb-mem/`, `artifacts/txntidb-mem2/`): 256 connections each carrying a packet of
8000-key literal SQL (Q1/Q2 IN lists, 8000-row INSERTs) drive tidb-server heap to 13–18 GB. TiDB's per-statement tracked
memory is only a few MB (EXPLAIN ANALYZE: Q2 1.94 MB, INSERT 3.5 MB), so the memory is plausibly untracked parse/plan data held while the
statements execute (a hypothesis: no heap profile was taken to confirm the allocation source). Not fixed by: gogc tuner off, GOGC=50, memory limit 0 (OOM-killed at 15.8 GB), 32g container (18 GB, run stopped
at the first controller warning, inconclusive; host has only ~37 GB available). The batch-max 4000 runs peak at ~11.5 GB.

## Disclosed differences from PG R1
- A window is one pessimistic txn in 2 round trips (6 SQL statements, before/after computed in the client); PG is 1 statement.
- Tables carry an extra `shard` PK column (clustered, 256 pre-split regions, one queue per region); no CHECK constraints (TiDB default off); FK enforced (proved by error 1452).
- tidb-server and PD CPU not counted in "DB CPU"; at both CPU4 and CPU8 tidb-server stayed below the 85 % saturation flag (57 % / 70 %), so these are not tidb-server-bound by that criterion.
- CPU4/CPU8 pinned cpusets share SMT siblings (N / N+8).
- Single run per cell; PG CPU=8 numbers are older artifacts, PG CPU=4 are new.

## Incidents
- Two orphan `smoke` python processes (99 % CPU each, unrelated, 1 day old) were found and killed by the review before the final runs. Earlier failed attempts (`txnpg4-bm4000`, `txntidb-c4-bm4000`, `-c4-bm8000`, `-c8-bm4000`, `-c8-bm8000`, `-c4-bm8000-v2`) are kept for evidence and are not results. PG rerun of bm8000 gave 167.7k vs 167.6k under the orphans, so they did not visibly change that cell.
- `txnpg4-bm4000` stalled on the disk (util 100 %, write await 1–2 s) → client 30 s timeout; re-run is the reported number.
- `monitor.Sampler` has an exit race (`Permission denied: /proc/<pid>/io`) on the exiting client. The TiDB wrapper tolerates it (recorded in `sampler-tolerated-errors.json`); the unmodified PG wrapper hit it once (`txnpg4-bm8000-rerun`).
- Client monitor query changed to `SHOW PROCESSLIST` (the information_schema variant materialised full SQL text).
