# Ledger R1 txn on TiDB — Design (rev 3: rev 2 after independent review by review APPROVE-WITH-CHANGES, plus user decision L1 = two multi-statement round trips per window)

Requirements: `ledger-txntidb-requirements.md`. Strictly additive: no existing source/script/test is modified. Only `Cargo.toml`/`Cargo.lock` change (new dependency), and the lock diff must be additions only.

## Files

## Schema (client creates, untimed)
```sql
CREATE DATABASE IF NOT EXISTS ledger; USE ledger;   -- every connection (monitor and data) selects `ledger` explicitly
CREATE TABLE accounts(shard INT NOT NULL, account_id BINARY(16) NOT NULL, balance BIGINT NOT NULL DEFAULT 0,
  PRIMARY KEY(shard, account_id) CLUSTERED);
CREATE TABLE ledger(shard INT NOT NULL, account_id BINARY(16) NOT NULL, transaction_id BINARY(16) NOT NULL,
  amount BIGINT NOT NULL, before_balance BIGINT NOT NULL, after_balance BIGINT NOT NULL,
  PRIMARY KEY(shard, account_id, transaction_id) CLUSTERED,
  FOREIGN KEY(shard, account_id) REFERENCES accounts(shard, account_id));
```
Review experiments already confirmed on v8.5.6: both clustered composite PKs, FK enforcement (error 1452), ON DUPLICATE KEY UPDATE, `Batch_Point_Get` for 8,000 ledger tuples and locking `Batch_Point_Get` for Q1, a 672 KB / 8,000-row INSERT, 255-boundary SPLIT (`255 1`, 256 regions/table, 1 peer/region), `tidb_scatter_region='table'`, PD merge keys, the five information_schema tables, and the aggregate verification SQL. Limits seen: packet 64 MiB, txn 100 MiB, query quota 1 GiB (none blocks 4000/8000 cells). FK cost is real (8,000 rows / 400 parents: foreign-key check + parent lock ~36 ms) and is disclosed, not tuned away.
UUIDs are stored as 16 raw bytes (`Uuid::as_bytes`), sent as `x'<32 hex>'` literals. shard = queue index (every request of queue q, including injected unknown-account requests, uses shard q).

## Sharding (option B) and topology gate (client, before ready-file)
1. Connect to the URL (no database in it) with retry (<= 600 s) until `SELECT count(*) FROM information_schema.tikv_store_status` == `--stores`.
2. `SET GLOBAL tidb_scatter_region='table'`, create DB/tables, then for each table `SPLIT TABLE t BY (1,x'00..',x'00..'), ..., (255,...)` (255 boundaries => 256 shard ranges; `tidb_wait_split_region_finish` is ON by default). Verified form (demo on v8.5.6): the tuple must contain exactly the PK columns, i.e. `SPLIT TABLE accounts BY (1,x'00'*16),...,(255,x'00'*16)` and `SPLIT TABLE ledger BY (1,x'00'*16,x'00'*16),...,(255,...)`; result `TOTAL_SPLIT_REGION=255, SCATTER_FINISH_RATIO=1`, 256 regions per table, region k = `[(k,0,0), (k+1,0,0))`, shard 0 = `[table start, (1,0,0))`, shard 255 = `[(255,0,0), table end)`.
3. Bulk-load 100,000 accounts (5,000 rows per INSERT, shard = user % queues) AFTER the split.
4. Gate (abort before `ready` if violated; results saved in `topology.json`): `SHOW TABLE t REGIONS` count >= queues for both tables; for the regions of both tables every region has exactly 1 peer (RF=1; via `information_schema.tikv_region_status` join `tikv_region_peers`); with `--stores 2` per-store `REGION_COUNT` and `LEADER_COUNT` from `information_schema.tikv_store_status` each within 40–60 % (poll <= 120 s for PD scatter to settle). PD is configured with `schedule.max-merge-region-size=0`/`keys=0` so the pre-split regions are not merged back.
5. FK proof: after setup the client runs one negative insert (ledger row for an unknown account) and requires error 1452 (`fk_enforced=true` in `topology.json`).
6. Plan proof: before ready the client runs `EXPLAIN` of the real Q1/Q2 statement shape for 8,000 keys of its first window; gate: plan contains `Batch_Point_Get` and no `TableFullScan` (stored in `topology.json`).
7. `topology.json` also stores TiDB variables (`tidb_txn_mode`, `tidb_enable_1pc`, `tidb_enable_async_commit`, `foreign_key_checks`, `version()`) and the TiKV effective config subset (`readpool.unified.max-thread-count`, `storage.scheduler-worker-pool-size`, `raftstore.store-pool-size`, `raftstore.store-io-pool-size`, `raftstore.raft-write-wait-duration`, `storage.block-cache.capacity`, `raft-engine.enable`) read from `information_schema.cluster_config`; the FULL `cluster_config` table is saved as `cluster_config.tsv` and the relevant session/global variables as `variables.json`. All client-produced files live in `<out>/client/` (`result.json`, `per_second.csv`, `latency.hdr`, `topology.json`, `cluster_config.tsv`, `variables.json`); the wrapper does not copy them.

## Client (`txn_batch_tidb`)
CLI = `txn_batch_pg` CLI with `--pg-url` replaced by `--mysql-url` (default `mysql://root@127.0.0.1:14000`) and added `--stores` (default 1). `--shards` is not a flag: shards == queues (hard rule).
Protocol, outputs, `per_second.csv` columns, `result.json` fields: identical to `txn_batch_pg` (`measurement_start/end_unix_ns`, `rps_*`, `latency_us`, `batch_size`, `outcomes`, `verification`, ...) except: `effective.pg_url/postgres_version` -> `mysql_url/tidb_version`; `wal_stats` removed; new `sql_statements` and `round_trips` in `outcomes` (definitions below); `statement_retries` removed (no retry).
Connections: 1 monitor + `queues` data connections (opened and `SELECT 1` checked before ready; no prepared statements, text protocol).

Worker, per window (all on the queue's own connection; `tokio::time::timeout(30 s)` around the whole transaction = both round trips; multi-statements/results are enabled by default in mysql_async 0.34, no option needed; packets of ~700 KB are fine, server max_allowed_packet is 64 MiB):
```
d = dedupe_first(window); sort canonical by account (existing fns)
-- round trip 1: ONE text packet, 3 statements, 3 results (OK, rows, rows): use `query_iter`; consume BEGIN's empty result, `collect` Q1 and Q2 separately, then `drop_result()`; decode BINARY(16) columns as length-checked 16-byte Vec<u8>
BEGIN PESSIMISTIC;
Q1  SELECT account_id, balance FROM accounts WHERE shard=S AND account_id IN (x'..',...) FOR UPDATE;      -- distinct accounts
Q2  SELECT account_id, transaction_id, amount, before_balance, after_balance FROM ledger
      WHERE (shard, account_id, transaction_id) IN ((S,x'..',x'..'),...);                                  -- probe
-- client: classify each canonical request: in Q2 -> existing(original record); else amount<=0 -> rejected:invalid_amount;
--         else account not in Q1 -> rejected:unknown_account; else applied
--         applied rows: per account in sorted input order before = start_balance + running sum, after = before + amount
-- round trip 2: ONE text packet via awaited `query_drop()` (drains every result, surfaces a COMMIT error)
Q3  INSERT INTO ledger(shard,account_id,transaction_id,amount,before_balance,after_balance) VALUES ...;      -- applied rows, omitted if none
Q4  INSERT INTO accounts(shard,account_id,balance) VALUES (S,a,new_balance),... ON DUPLICATE KEY UPDATE balance=VALUES(balance);  -- accounts with >=1 applied, omitted if none
COMMIT;
```
Error handling (fail fast, no retry, run invalid): after a SQL error (server stops at the failing statement; the transaction may remain open) finish consuming the response, attempt a bounded (5 s) `ROLLBACK`, then abort. On timeout, I/O error or any uncertain protocol alignment, drop the connection (never reuse); packet 2 may already have committed, so the run is simply invalid. Per-window outcome counters/`completed`/latency are published only after packet 2 (COMMIT) is acknowledged. If nothing is applied, packet 2 is just `COMMIT;`.
Accounting (workload connections only; setup/monitor/cleanup excluded): `round_trips` = packets whose response was fully received; `sql_statements` = statements in those packets (6 per window with applied rows, 4 without). Successful-run invariants: `round_trips == 2 * windows`, `sql_statements == 6*windows_with_applied + 4*windows_without`. RPS(IO) stays windows/s.
Verified on v8.5.6 (demo, mysql CLI): a multi-statement packet is accepted with `tidb_multi_statement_mode=OFF` when the client sets the multi-statement flag; Q3/Q4-style client-computed windows of 8,000 rows over 400 accounts took 261–282 ms in 2 packets.
Outcome mapping, `map_outcomes` bijection check, `replay_mismatch` logic, counters, latency (one `record_us(txn_duration)` per request), batch-size stats: unchanged from `txn_batch_pg`. Probe statements must plan as `Batch_Point_Get` (enforced by the plan gate in the setup section, not by a one-off check). Single executor per account (queue = user % queues), so no lock conflicts are expected; Q1's `FOR UPDATE` makes the balance read current and is cheap (<= ~390 keys).
`server_active` (per_second.csv): `SELECT count(*) FROM information_schema.processlist WHERE command<>'Sleep' AND id<>CONNECTION_ID()`.

Verification (monitor connection, untimed, one query set):
```sql
SELECT count(*), sum(balance), sum(bad) FROM (
  SELECT a.balance, ((a.balance<>K) OR (c.n IS NULL) OR (c.n<>K) OR c.min_before<>0 OR c.max_after<>a.balance
         OR c.dist_before<>c.n OR c.amount_bad>0) AS bad
  FROM accounts a LEFT JOIN (SELECT shard,account_id,count(*) n,min(before_balance) min_before,max(after_balance) max_after,
       count(distinct before_balance) dist_before,sum(after_balance<>before_balance+amount) amount_bad
       FROM ledger GROUP BY shard,account_id) c USING(shard,account_id)) t;
SELECT count(*) FROM ledger;
```
(K = requests-per-user; with measured amount = 1 `count(distinct before)=count`, `min before=0`, `max after=balance`, `after=before+amount` prove the unbroken chain 0..K.) `valid` additionally requires the same outcome conditions as `txn_batch_pg` (completed == sent, missing/unexpected/replay_mismatch 0, applied == total, existing == retries, rejected == injected, sum == applied, ledger rows == total).

Unit tests (`#[cfg(test)]`, kept small): all PG-client pure-function tests that still apply; plus `classify_and_compute` (existing/invalid/unknown/applied precedence, running before/after per account, repeated account in window), `sql_*` builders (hex literal format, row counts, tuple list), shard == queue index.

## Wrapper (`scripts/txn_tidb_run.py`)
Args: `output_dir --cpus {4,8} --users 100000 --requests-per-user 40 --queues 256 --batch-max N --sample-interval-ms 250 [--retry-pct --inject-rejects]`. Refuses existing output dir.
Layout dict: `4: tikv_cpusets ['0-3'], tidb '6-7,12-13', client '4-5', sampler '14-15'`; `8: tikv ['0-3','4-7'], tidb '10-13', client '8-9', sampler '14-15'`. The wrapper process and PD run on the sampler CPUs (PD: `--cpuset-cpus 14-15`, no quota). Client CPUs checked against TiKV cores (SMT-sibling overlap allowed only at CPU8, disclosed).
Backing-device gate as in `batch_queue_run.py` (`/var/lib/docker` must map to physical `sdb`). Containers (all owner-labelled, own network `ledger-tt-<owner>-net`, own volumes, same collision/cleanup pattern as `batch_queue_run.py`):
- pd: `pingcap/pd:v8.5.6`, `--config` file from the output dir: `[replication] max-replicas=1`, `[schedule] max-merge-region-size=0 max-merge-region-keys=0`. Not published.
- tikv_i: `pingcap/tikv:v8.5.6`, `--cpuset-cpus <set> --cpus 4 --memory 8g`, flags `--addr --advertise-addr --status-addr=0.0.0.0:20180 --advertise-status-addr --pd --data-dir=/data --config`, config `[storage.block-cache] capacity="2GB"`; status port published to `127.0.0.1:20180+i` (metrics scrape). `docker_resource_assignment` check (quota 4, 8 GiB).
- tidb: `pingcap/tidb:v8.5.6`, `--cpuset-cpus <set>`, `--memory 16g`, `--store=tikv --path=pd:2379 --advertise-address`, published `127.0.0.1:14000->4000`. Effective cpuset/memory checked from `docker inspect`.
Images are referenced by tag as in the local image store; their IDs/digests are recorded in `inspect-*.json`. Host ports 14000/20180/20181 are checked free (`single_run.preflight_endpoint`-style bind probe; 2379 is NOT used on the host).
Flow: create resources -> start pd, tikv(s), tidb -> `cargo build --release --locked --offline` -> client under `taskset -c <client cpus>` (it waits for the cluster, builds schema/split/load, checks topology, writes ready) -> wait ready (<=600 s; fail early if client exits) -> socket census == queues+1 established sockets to port 14000 (3 stable samples) -> scrape TiKV `/metrics` (before) -> create the sampler sub-dirs synchronously (`res-tikv<i>`, `res-tidb`, `res-pd`; `monitor.Sampler` creates its dir inside its thread but `NetSampler` opens files immediately), then start `monitor.Sampler(backend='pg')` per container (tikv_i, tidb, pd; allocated cpus 4 / cpuset size / 2; same client pid, device sdb) and `NetSampler` for the tidb container and each TiKV container -> GO -> wait client exit -> stop samplers -> scrape `/metrics` (after) -> `single_run.filter_resources(subdir, parsed client/result.json dict)` for each sampler dir -> `summary.json`.
`summary.json` = client result + `resource_summary`: `tikv_cpu_cores_mean` (sum over stores) and `% of 4*stores`, `tidb_cpu_cores_mean` and `% of its cpuset size`, `tidb_saturated` (diagnostic flag: mean >= 85 % of its cpuset), memory max per container, disk/device means (from the first TiKV dir; device is shared), net rx/tx for tidb container and TiKV containers, `full_resource_intervals`, `resource_window_formal` (every container summary's `formal` is true AND >= 4 full intervals); client CPU/RSS from the first TiKV dir; PD CPU/memory reported, `durability`: for each store `raft_engine_sync_log_duration_seconds_count`, `raft_engine_write_duration_seconds_count`, `raft_engine_write_size_sum`, `raft_engine_sync_log_duration_seconds_sum` deltas; gate: per store all four counters present, finite, not reset (after >= before), write and sync deltas > 0; and `|sum(sync)-sum(write)| <= 0.01*sum(write)` (no additive allowance). Missing counter = failure, never zero.
Exit nonzero on: client invalid, sampler error, socket census mismatch, durability gate failure, cleanup residue. Raw `topology.json`, `settings.json`, TiKV metrics snapshots, `docker logs` (final) are saved in the output dir.
Pure helper with a unit test: `metric_value(text, name)` (sum over label sets) + `durability_delta(before, after)`; the test includes absent and reset counters. Disclosures in report: CPU4 tidb-server/client/PD-sampler also share SMT siblings (tidb 12-13 with client 4-5, sampler 14-15 with tidb 6-7); CPU8 as in the requirements.

## Non-functional decisions
- Closed-loop, 256 connections; no scalability/concurrency design beyond "one executor per account"; fail fast, no retries; external dependency = three pinned local images (tag v8.5.6, IDs recorded).
- The DB-side work differs from PG (several statements, client-side before/after); this is inherent to TiDB and disclosed, not compensated.
- If tidb-server is saturated while TiKV is not, results are reported as tidb-server-bound; no multi-tidb tuning in this scope.
