# Ledger account store sharding benchmark

## Purpose

Measure the account-store write path as one ledger is split across one, two, or
four independent shard sequences. The standalone benchmark reuses
`benches/support/ledger_account_store.rs`; transaction validation, synchronous
WAL commits, checkpoint writes, recovery, and index/ledger validation remain in
that support module.

The existing `ledger_account_store_tokio` benchmark keeps its current defaults
and legacy key format. This benchmark uses the new namespaced store entry point
and writes its report files under `target/ledger-account-store-sharding-trials/`.

## Fixed workload and cases

The default run offers 50,000 accounts x 200 requests, or 10,000,000
transactions, in each case. Every transaction is durable and goes through the
checkpoint balance mode with batch size 4,096. The existing deterministic
credit/debit workload gives each account five credits and five debits per
10-request cycle; its generated per-account order prevents overdrafts. Each
account is assigned to shard `account_id % S`.

Each shard has a private ledger sequence starting at 1. A shard loop sends one
batch at a time and awaits its completion. The shard loops run concurrently on
a Tokio runtime with four worker threads. The benchmark has no request queue or
gRPC layer.

| Shards | Storage layout | Case |
| ---: | --- | --- |
| 1 | One RocksDB | S1 control |
| 2 | One shared RocksDB | S2 shared |
| 2 | Two independent RocksDB databases | S2 dedicated |
| 4 | One shared RocksDB | S4 shared |
| 4 | Four independent RocksDB databases | S4 dedicated |

The shared database has one WAL. Dedicated databases each have their own WAL.
For an S/layout pair, account IDs, request identities, operation order,
per-shard batch boundaries, latency sample selection, and total offered work
match.

`--smoke-users N --smoke-waves N` explicitly selects a reduced workload for
correctness smoke runs. Both arguments are required together. The default run
cannot silently become a smoke run.

## Key namespaces and recovery

Every application key in the sharded benchmark begins with a fixed five-byte
namespace: ASCII `S` followed by the shard ID as a big-endian `u32`. This prefix
is applied to transaction-index keys, ledger-sequence keys, latest-sequence
metadata, balance keys, refund markers, checkpoint manifests, and checkpoint
chunks. The same prefix is used in shared and dedicated layouts.

The global account ID remains in transaction records and balance/checkpoint
keys. Each store is opened with the exact sorted account-ID set assigned to its
shard. Recovery replays only that namespace and maps those account IDs into its
local balance vector. Integrity scans start at that namespace's index and
ledger prefixes, then require each local sequence from 1 through the shard's
latest sequence exactly once.

At the end of a case, stores are shut down, database handles are closed, every
database is reopened, and each shard's sequence and balances are checked before
the namespace-bounded index/ledger scan. A case-specific directory guard
removes each database after verification, including error paths.

## Checkpoints

The checkpoint threshold is 100,000 local ledger sequences per shard. At the
default workload this creates 100 checkpoint generations in aggregate for S1,
S2, and S4: 100 for S1, 50 per shard for S2, and 25 per shard for S4.

The number of saved balances per generation scales with shard count. A
checkpoint for S4 contains one quarter as many accounts as an S1 checkpoint,
and the aggregate number of account-balance entries written across the 100
generations also falls with shard count. This is an intentional consequence of
local checkpoints and should be considered when comparing checkpoint I/O.

## RocksDB budgets

The benchmark configures these approximate aggregate budgets for each layout:

| Resource | Aggregate configured budget | RocksDB settings |
| --- | ---: | --- |
| Write buffers | 128 MiB | Two write buffers per DB; `write_buffer_size = 128 MiB / (database_count * 2)` |
| Block cache | 128 MiB | One LRU block cache per DB sized `128 MiB / database_count` |
| Background jobs | 4 | Shared DB: 4 jobs. Dedicated DBs: `4 / S` jobs each |

For S2 dedicated storage this assigns 32 MiB per write buffer, a 64 MiB cache,
and two background jobs to each database. For S4 it assigns 16 MiB per write
buffer, a 32 MiB cache, and one background job to each database. The shared DB
uses the full corresponding aggregate setting in one instance. S1 uses one DB
with 64 MiB write buffers, a 128 MiB cache, and four background jobs.

These settings bound the configured memtable count, cache, and background-job
limits. Actual resident memory can also include RocksDB table/filter/index
metadata, compaction and flush buffers, WAL buffers, allocator overhead, and OS
page cache. `max_background_jobs` is a configured maximum, not a reserved CPU
allocation.

## Measurements

`results.csv` contains one aggregate row per case. `shards.csv` contains one row
per shard. `run.log` records case pass/fail progress and the same aggregate and
per-shard metrics.

The benchmark records:

- Foreground completed RPS and settled RPS after checkpoint barriers.
- Per-shard transaction count, local final sequence, RPS, and handler latency
  p50/p95/p99.
- Aggregate handler latency mean and p50/p95/p99.
- CPU seconds and core equivalents for foreground and settled windows.
- Process I/O and target-device read/write/busy-time deltas for foreground and
  settled windows.
- RocksDB WAL syncs and bytes, writes with WAL, flush bytes, compaction read
  and write bytes, and stall microseconds.
- Checkpoint count, queue wait, snapshot, chunk sync, manifest sync, and total
  checkpoint work.
- Recovery and integrity-scan time, database bytes, preflight readings, and
  sampled peak RSS.

Handler latency uses the store's stable 1-in-1,024 account/request hash sample.
The same account IDs and transaction IDs select samples for shared and
dedicated layouts at a given shard count. Percentiles use nearest-rank
selection, matching the original account-store benchmark. Peak RSS is sampled
from `/proc/self/status` `VmRSS` every 10 ms from the foreground start through
checkpoint settlement; brief peaks between samples can be missed.

RocksDB counters are sampled once per database. A shared database contributes
one ticker delta; dedicated layouts sum deltas from their distinct databases.

## Preflight and invocation

Each case opens its database(s) and initializes every namespace before the
strict idle preflight. Default preflight thresholds are at most 10% CPU busy,
at most 5% target-device busy, at least 128 MiB available memory, and at least
1 GiB of free space plus the estimated database size. The smoke run may shorten
the observation interval while retaining the same thresholds.

Build or run the default matrix with:

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_account_store_sharding_tokio
```

A reduced topology smoke can be run with:

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench ledger_account_store_sharding_tokio -- \
  --smoke-users 2000 --smoke-waves 20 --preflight-observation-ms 250 \
  --preflight-timeout-ms 5000
```

The reduced smoke workload checks topology setup and recovery. At this size the
100,000-sequence local checkpoint threshold is not crossed; the default matrix
records the planned 100 generations per case.
