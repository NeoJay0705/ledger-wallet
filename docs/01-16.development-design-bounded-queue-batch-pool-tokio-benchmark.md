# Tokio bounded queue batch-pool HashMap benchmark 設計

## 目的與範圍

新增 bounded_queue_batch_pool_tokio，量測以 Vec<Request> 作為批次佇列單位的 in-process HashMap pipeline。既有 bounded_queue_hashmap_tokio 仍是獨立的 per-request mpsc 基準；本測試不把舊版 dequeue latency 當成可直接比較的同名階段，也不包含 gRPC、網路、磁碟或外部 I/O。

每個情境使用 3 個 Tokio runtime worker threads、C 個 closed-loop request coroutine，以及一個 FIFO batch worker 和一個批次 timeout task。每個 coroutine 同一時間只有一筆 outstanding request，回覆以 oneshot 傳回 ID 和更新後的 per-key count。

## 工作量與命令列

預設每個情境 N=10,000,000，每個 key 的空間為 100,000，一輪。C 為 100000、50000、25000、12500、6250、3125、1562、781。每個 C 測試 empty／prefilled map、B=2048／4096、timeout=1／5／10／20 ms，共 128 個情境。

支援 --iterations N、--repetitions N、--coroutines all|N[,N...]、--map-state all|empty|prefilled、--batch-size all|2048|4096、--batch-timeout-ms all|1|5|10|20 和 --latency-sample-stride N。例如：

    cargo bench --bench bounded_queue_batch_pool_tokio -- --iterations 200001 --coroutines 128 --map-state all --batch-size 2048 --batch-timeout-ms 1 --latency-sample-stride 257

## Active batch、FIFO ready queue 與 buffer pool

Producer coroutine 取得 request capacity permit 後，在 async state mutex 下將整筆 request append 到唯一 active Vec<Request>。append commit 後的時間是 t_admit。active Vec 的第一筆 admitted request 開始 timeout 計時。達到 B 筆時，或第一筆 admitted request 的 timeout 到期時，producer／timer 在同一個 mutex 下 seal 批次，記錄 t_seal，並把完整 Vec ownership 移入 FIFO ready-batch queue。Seal、timer 和 append 共用同一把 mutex，因此到期與滿批競爭會線性化；sequence number 由 worker 檢查 FIFO 順序。批次有效長度由 Vec 的 len 表示，沒有 ring read index。

Producer 可在 worker 處理 sealed Vec 時取得另一個 active Vec。一般情況預先配置 ceil(50000/B)+2 個 Vec<Request>，每個 capacity 為 B：B=2048 時為 27 個，B=4096 時為 15 個。若 partial batches 暫時佔用較多 buffers，pool 可按需擴充至最多 50,000 個 buffer；擴充配置在 state mutex 外進行。沒有可用 buffer 時，producer 等候 buffer 回收。worker 完成該批所有 map updates、staging 與 oneshot dispatch 後，清空原 Vec 並放回 pool。跨 ready queue 的 Vec ownership handoff 只移動 Vec header/pointer，沒有 clone 或複製 request payload。

pool 的 buffer 數和 capacity 會影響可同時存在的批次與 throughput，CSV 記錄預先配置數量、擴充次數、peak buffers、buffer wait 次數與時間。Pool buffer 等候與 request-capacity 等候分開量測。

## 容量、admission 與計時邊界

50,000 個 async semaphore permits 限制 capacity reserved、active、sealed、processing 的 request 總數；permit 在回覆 dispatch 後才釋放。正在等 semaphore 的 client 尚未取得 permit，也尚未 admitted。取得 permit 後、append commit 前的 request 是 reserved-but-unadmitted：它會佔用可用 permits，但只有 append commit 才納入 t_admit 和 admitted request 數。CSV 個別記錄這段 reserved-unadmitted wait、peak reserved-but-unadmitted 和真正 peak admitted outstanding，避免把兩種狀態混稱 50k admitted requests。若等待 buffer，會降低當下可用 semaphore permits；其等待時間和次數分開輸出。

逐筆 timestamp：

- t0：client 開始等待 capacity permit 之前。
- t_admit：request append 到 active Vec 後、仍在 state mutex 保護範圍內。
- t_seal：整個 Vec 被 seal 並放入 FIFO ready queue 的時間。
- t_start：worker 開始該批 map update 的時間。
- t_done：該批所有 map updates 和 response staging 完成、oneshot sends 開始之前。
- t6：client 收到 oneshot response。

五段 latency 為 t0->t_admit、t_admit->t_seal、t_seal->t_start、t_start->t_done、t_done->t6。t_start->t_done 只計 map updates 與 count staging；回覆 dispatch 位於 t_done->t6。五段對全部 N requests 計算精確 mean 和整數奈秒總和，以 ID hash deterministic sampling 算 p50/p95/p99。程式逐輪檢查五段總和等於 completion latency 總和。所有 latency CSV 欄位皆附 count 和 sample_count。

另外輸出：

- capacity_acquire_wait：t0 到取得 semaphore permit。
- reserved_unadmitted_wait：取得 permit 到 t_admit，涵蓋 producer admission path。
- buffer_availability_wait：只累計沒有 active/free Vec、正在配置或等候 Vec 回收的時間；另記錄發生過這種等待的 request 數量。
- completed RPS：N 除以最早 t0 到最晚 t6。
- admission RPS：N 除以最早 t0 到最晚 t_admit。
- batch handler duration、batch size、full／timeout／tail flush 數量、ProcessTime CPU 秒數、CPU wall 秒數及 core equivalents。

不同 coroutine 競爭 mutex 的順序決定 append FIFO；ID 並不保證按數值順序進入 pipeline。Map 更新與 response count 依 admitted FIFO 順序產生。

## Timeout、關閉與錯誤處理

Timeout task 從 active Vec 第一筆成功 append 的 t_admit 起等待。timeout seal 是正常 flush，可讓 C<B 時的 closed-loop client 不會等待永遠無法湊滿的 batch。所有 N 個 ID 已經提交不會觸發提前 partial flush；client 仍須等回覆。正常完成後 coordinator 明確關閉 pool；如關閉時仍有 active partial Vec，會以 tail 批次交給 worker。

任何 client、worker、timer 或驗證錯誤都會令該情境失敗，abort 並 drain sibling tasks；該情境不輸出成功 CSV row。每個 request 的 semaphore permit 使用 RAII，取消或 task failure 時隨 request drop 釋放。Worker failure 時，active、ready 和 processing requests 的 oneshot sender 會在 cleanup drop，使 awaiter 得到錯誤／取消，而不是成功結果。

## 驗證

每個 response ID 必須和 client 當前 ID 相同；每 key 回覆 count 必須恰好構成 1..=expected_count permutation。結束時檢查 final map 長度與所有值、完成 response 數、admitted 和 dispatched 數、五階段 latency 加總、batch size 總和、batch flush reason、batch count、FIFO sequence、request permits 全部歸還，以及 admitted／reserved peak 都不超過 50,000。任何錯誤都不會寫出該情境的成功 row。
