## 主要性能比較

主要比較使用九個設定共同具備的 rep1 與 rep2，共 18 個 valid trials，每個設定 `n=2`。先以每個 trial 自己的摘要值比較，再取兩次重複的中位數。`p99` 是兩個 trial 的 p99 值中位數，不是合併兩個原始 latency histogram 後重新計算的 percentile。CPU 是 Rust CLI process 每 request CPU 時間的中位數，換算為 µs。Flush ratio 是每個 trial 三節點 `commitlog_flush` counter delta 總和除以 10,000,000 requests，再取中位數。

在共有 rep1/rep2 的比較中，S2/C48 throughput 最高。它比 S1/C48 高 28.29%。S4/C48 比 S2/C48 低 14.41%。從 C12 增至 C48，throughput 分別增至原值的約 1.896、2.451、2.464 倍（S1、S2、S4）。C 同時擴大 DB worker 數與 data connection pool，這不只是 coroutine 數的效果。

S2/C48 的 throughput 最高，但 tail latency 不是每個設定都最低。S2/C24 的 p99 中位數為 23.46 秒，略低於 S2/C48 的 23.92 秒。不能把 S2/C48 稱為 latency 全面最佳。

S4 每個 node 使用 2 個 physical cores 和 4 個 threads，後兩個 threads 是 SMT siblings；S2 每 node 也使用 2 個 physical cores。這次量測不能解讀成 S4 使用了 4 個 physical cores，也不能從同一 host 的結果得出一般性的 SMT 效能退步結論。

### Queue 與服務時間

代表性 S2/C48 rep1 的 end-to-end p99 為 23.303553023 秒，`db_queue_wait` p99 也為 23.303553023 秒。`db_read` p99 為 4.513791 ms，`cql_write_batch` p99 為 10.289151 ms。這些 stage 觀察支持大量 50,000 個 closed-loop clients 排在 48 個 DB workers 前面等候。不同 percentile 不能相加；end-to-end 秒數也不能推成每次 DB write 花數十秒。

### Process CPU 與 commitlog counters

CLI CPU 包含同一 Rust process 的 service、load clients、heartbeat 與 driver gauge monitor。不包含三個 Scylla processes，也不包含獨立的 Python runner、supervisor 或外部 monitor。

`commitlog_flush_delta_total/request` 是三節點 counter delta 的比例，不是每筆交易的 fsync syscall 數，也不是 fsync latency。Counter 可能包含背景 flush 與採樣邊界偏移。不能預設每筆 request 對應三次 fsync。固定 S 時 C 增大、每 request flush ratio 下降，與 group commit 相符，但不是因果證明。

原始 Prometheus、CPU、RSS、I/O、cache、compaction、backlog 與 network samples 都保留，required-metrics validation 有效。本分析不從未列出的原始 metrics 虛構彙總數值。

## Failure：trial 023

Trial `trial-023-S4-C12-rep3` 收到 4,277,669 replies，applied 4,227,678。共有 49,991 errors：3 個 `commit_outcome_unknown`，以及儲存錯誤後 fail-closed 所造成的 49,988 個 `not_accepted`。Driver 記錄 3 errors、12,683,043 queries；retries、request timeouts 與 connection timeouts 均為零。預期 query delta 是 30,000,000。

`error_samples` 的原文指出 CL=THREE 只收到 2/3 個 write responses，`write_type=Simple`，並帶有 `Operation timed out` server error。這是 Scylla server 寫入逾時，不是 driver `request_timeout`。先前 diagnostic run 的 `deadline-runtime-evidence.json` 讀到三個 node 的 `write_request_timeout_in_ms=2000` 與 `read_request_timeout_in_ms=5000`，符合當時檢查的既有 release 設定。正式矩陣沒有另加逐 node timeout probe；不能把 diagnostic probe 說成正式 trial 的新驗證，也不能把 deadline 值當作根因證據。

Ledger scan 看見 4,227,681 rows，預期 10,000,000；50,000 accounts 的完整驗證未通過。`commit_outcome_unknown` 不代表寫入肯定未提交。缺少剩餘 rows 表示預期 workload 未完成，不能直接推出已確認的 acknowledgement data corruption。原始 `error_samples` 是可靠度證據；其餘 22 個通過的 trials 所得的性能排名不能代替整體穩定性通過。

先前歷史 run `run-20261011T163641Z-5850a603` 的 S1/C12 trial 1 曾出現 12 次 server coordinator write-timeout counter 增量。那是另一輪、另一設定與另一分母，不併入本輪，也不能據此認定逾時是 S4 獨有問題。現有證據沒有證明 SSD 或 SMT 是 root cause。

## 未覆蓋項目與限制

本輪使用 `commitlog_sync=batch` 和三副本 `CL=THREE` acknowledgement path。Scylla release 沒有已驗證的獨立 per-write fsync profile，因此沒有逐筆 fsync 比較，也沒有用 periodic 取代。這不是本矩陣四個未執行 trials 之一。

本 workload 每個 request 對單一 account partition 執行兩次 reads 與一次含兩個 statement 的 same-partition UNLOGGED batch。沒有執行跨 partition batch 或多個 wallet transactions 合併成單一 CQL batch 的 sweep。這不是四個遺漏 trials 之一。

本輪沒有對齊舊 RocksDB baseline 重跑。此項比較不屬於這 27 個 Scylla trials，也沒有由本輪資料得出引擎勝負。

三個 nodes 共用同一 host 和 SSD，I/O 未調優，也沒有隔離 OS/IRQ。有效重複數只有每 case 2 或 3，沒有足夠樣本估信賴區間或宣稱正式勝負、production SLA、穩態容量或跨引擎結論。每 account 最多 200 筆的短 workload 不代表長期 account history 容量。Group commit 與 fsync acknowledgement 契約保持；per-write fsync 仍未受支持或驗證。

## 後續安排與資料流程

本次先完成分析，不立即補測。若之後需要每個設定都有 3 個 valid trials，先分析 trial 023 的慢 replica 時間線；再另開一個 campaign，補跑 4 個未執行設定並獨立重現 S4/C12 失敗。保留本輪 failure，不把補測回填成原 run 的 27/27。若調整 deadline、I/O 或其他 profile，必須另建 profile 與統計，不與本輪混算。不可反覆重跑、只保留成功結果來洗掉失敗。

```text
Credit / Debit -> Service::submit -> account owner -> worker
  -> 2 SELECTs -> compute -> same-partition UNLOGGED BATCH
  -> 3 replicas commitlog fsync -> CL=THREE acknowledgement -> reply

timeout -> CommitOutcomeUnknown -> freeze / fail-closed
  -> drain -> verification -> owned cleanup -> formal_partial report
```
