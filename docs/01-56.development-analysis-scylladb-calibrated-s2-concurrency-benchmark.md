# 校準後單節點 Wallet 併發與 I/O 飽和測試：分析紀錄

日期：2026-10-13。需求與設計見 [01-54](01-54.raw-requirement-scylladb-calibrated-s2-concurrency-benchmark.md) 和 [01-55](01-55.development-design-scylladb-calibrated-s2-concurrency-benchmark.md)。

## 結論

本次兩個 case 均通過完整驗證與 cleanup。C=128 的先前基線限制可用併發。增加 worker 數至 C=256 和 C=512 後，吞吐提高，service DB queue 與端到端延遲下降；單次 LWT 延遲則上升。

C=256 到 C=512 的吞吐增益由前段 33.45% 降至 18.13%。S2 的兩個 Scylla reactor CPU 接近所配置 CPU 的 93%。這表示系統較接近 Scylla CPU/shard 限制，但本次沒有量到吞吐 plateau，也未證明硬體 CPU 上限或物理磁碟飽和。

本次 I/O queue delay 增加，代表 Scylla 內部 I/O 等待增加，不能單獨歸因於磁碟。Whole-device flush await 大致穩定，估計 queue 與 busy 下降。本次沒有持續物理磁碟飽和的證據。

若需要再擴測，可考慮固定 C=512 並增加 S。P 固定為 3 時，D 也會隨 S 增加；pool 大小因此是共同變因。本報告不自動新增測試。結果來自每案一次短測、單節點、共用 OS 磁碟，不代表 steady-state，也不外推至 RF3。

## 執行流程與限制

```text
Input Credit/Debit
  -> run_clients -> run_client -> Service::submit
  -> account owner lock / enqueue -> worker_loop
  -> process_job (cache compute) -> ScyllaStore::commit (conditional INSERT)
  -> batch fsync -> CL ONE ack -> publish cache on Applied -> reply
After all replies
  -> verify_all -> verify_account / verify_one_account -> cleanup
```

測試固定單節點 RF1、CL ONE 與 S=2。資料存放在同一 host 的共用 OS 磁碟。每個 C 值只測一次，量測窗有限，沒有信賴區間，也不是 steady-state 測試。此結果不能推論 RF3、production SLA 或多節點容錯。

本次沒有獨立逐筆 fsync profile，也沒有拆分 CQL、RF 或資料模型比較。Commitlog flush counter 和 host flush await 不是每交易一筆，也不是單筆 fsync latency。CPU、device、I/O queue 和 commitlog 指標應一起閱讀；它們不能單獨證明某項資源是唯一限制。

固定 P=3 增加 S 會同時增加總 data connections D。未來若調高 S，須把連線池變化列為共同因子。本報告不宣稱已達吞吐 plateau 或物理磁碟飽和，不自動擴測。
