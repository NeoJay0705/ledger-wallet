# batchsweep – requirements (confirmed by user)

Goal: find, per database and hardware limit, where RPS saturates as batch-max grows, with latency, so the user can choose an
acceptable latency afterwards. The tool does NOT pick an SLO; it reports the saturation point and the whole curve.

Fixed: 4,000,000 requests (100k accounts x 40), 256 queues = 256 connections 1:1, sample interval 250 ms, amount 1,
CPU4 (TiDB: 1 TiKV) and CPU8 (TiDB: 2 TiKV), no RF, durability gates unchanged. PG settings as in earlier txn runs
(wal_buffers=256MB, max_wal_size=8GB, track_wal_io_timing=on).
Variable: batch-max in 50, 100, 250, 500, 1000, 2000, 4000, 8000 (TiDB: 4000 then 6000 as a probe; 8000 only if 6000 passes;
a failure after GO ends that TiDB series and is recorded as the upper limit, with failure facts).
Cells: PG CPU4, PG CPU8, TiDB CPU4, TiDB CPU8 (4 series, one run per point, serial).
Saturation point = smallest batch whose RPS >= 95 % of the series' maximum RPS (reported with its p50/p95/p99/max).
Also report, per point: rps_request, duration, latency p50/p95/p99/max, windows, DB(TiKV)/tidb-server CPU, device flush await,
and flag points with device flush await > 2 ms (rerun once, keep both).
Replicate the 2 points around the saturation point of each series once more (noise check).
Pre-run gate (new): before EVERY run record 5 s of per-thread CPU idle; every logical CPU must be >= 90 % idle (user decision: 95 % was infeasible with the interactive pi session; agy/chrome closed) and no other
process > 30 % CPU, else wait up to 60 s and re-check, else abort that run (not silently continue). Evidence saved per run.
Reusable clean data (post orphan-kill): PG CPU4 4000 (txnpg4-bm4000-rerun), PG CPU4 8000 (txnpg4-bm8000-rerun client result +
txnpg4-bm8000 resources), TiDB CPU4 4000 (txntidb-c4-bm4000-v2), TiDB CPU8 4000 (txntidb-c8-bm4000-v2).
Old PG CPU8 artifacts (txn-bm4000-W256, -rep2, txn-bm8000-W256) are invalid (orphan CPU hogs) -> moved to artifacts/_invalid/ (not published)
after the new series exist. Nothing deleted without user consent. Existing programs unchanged; only new files.
Known disclosed limitation: with 4M fixed requests a large batch gives few windows per queue (4000 -> 4, 8000 -> 2).
