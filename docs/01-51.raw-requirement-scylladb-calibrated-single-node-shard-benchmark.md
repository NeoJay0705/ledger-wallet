日期：2026-10-12。

目標：執行校準後的單節點 Wallet shard 擴展測試。

需求編號：01。文件序號：51。
狀態：已授權；尚未執行。

本需求沿用 [01-48 memory-LWT RF3/CL3 雙 shard 需求](01-48.raw-requirement-scylladb-memory-lwt-rf3-s2-concurrency-benchmark.md) 與 [01-49 設計](01-49.development-design-scylladb-memory-lwt-rf3-s2-concurrency-benchmark.md) 中的 wallet profile。新測試使用一個 Scylla node。它先在實際 `/dev/sdb2` ext4 資料檔案系統執行 I/O calibration，再啟動 benchmark nodes。

此文件只定義一個 smoke 與兩個單次測試。這不是三節點 formal matrix，也不與 RF3/CL3 三節點結果直接比較。

## Calibration 與磁碟限制

Calibration 必須在新的 owned temporary directory 執行。該目錄必須位於實際 `/dev/sdb2` ext4 資料檔案系統。Runner 必須核對 mount、device 和檔案系統，並保存證據。

Calibration 工具的預期執行時間為 180 秒。外部 wall time 上限為 10 分鐘。Calibration temporary data 不得超過 32 GiB。Calibration 和後續 run 都必須保留至少 64 GiB 可用空間。

工具必須回報四個 raw capability 值。每個 node 的 budget 是對應 raw 值的 `floor(raw × 0.75)`。S=1 與 S=2 使用相同的 node budget。此計算不除以三個節點，也不代表 kernel 硬隔離或可保證 fsync latency。

若工具不支援 ext4、ext4 拒絕測試、mount/device 不符、時間超限、temporary data 超限，或剩餘空間不足，停止。不得格式化磁碟。不得改用其他 filesystem 或放寬門檻。

Scylla image 沿用 [01-48](01-48.raw-requirement-scylladb-memory-lwt-rf3-s2-concurrency-benchmark.md) 與 [01-49](01-49.development-design-scylladb-memory-lwt-rf3-s2-concurrency-benchmark.md) 的 pinned image。Rust 單節點支援合入後必須以本次 source 建立新的 release binary，不沿用舊 binary SHA。Runner 必須保存 compiled-source manifest 和新 binary SHA，並核對來源。Runner 也必須記錄 calibration tool、輸入屬性、輸出 hash、來源及 provenance。Runtime gate 必須核對注入的 read-only properties 與 calibration evidence hash。

## 固定 profile 與 workload

| 項目 | 固定值 |
|---|---|
| Scylla node 數 | 1 |
| Replication | RF=1、`durable_writes=true` |
| Wallet read/write CL | `ONE` / `ONE` |
| LWT serial CL | `LOCAL_SERIAL` |
| Wallet profile | `wallet-memory-lwt-v1` |
| Workload CQL | 每個 accepted request 一個 `INSERT ... IF NOT EXISTS` LWT；measurement 內零 SELECT |
| Scylla shards | S=1 或 S=2 |
| DB workers | C=128 |
| 每 shard pool | P=3 |
| Data connections | 單 node 時 `D=S×P` |
| Node CPU affinity | S=1 使用 CPU `0`；S=2 使用 CPU `0,1` |
| Service、load 與 monitor affinity | CPU `6,7,14,15` |
| Node memory | 8 GiB；cgroup limit 10 GiB |
| Accounts | 1,024 |
| Requests/account | 1,000，依序送出 |
| Requests/case | 1,024,000 |
| Repeats | 每 case 一次 |

所有交易使用 amount 1，Credit 與 Debit 交替。每個 client 收到目前 request 的 reply 後才送下一筆。同帳戶 owner lock、memory cache、LWT 和 fail-closed 行為保持不變。

沿用 dev mode 1、`io_setup=0`、overprovisioned 1、batch commitlog、fsync acknowledgement、timeouts 和 no-retry 行為。不得修改 CL、timeout、retry、CQL transaction path 或 Rust transaction 邏輯。Commitlog batch fsync acknowledgement 不是每筆一個獨立 fsync。

## 執行順序與成功條件

先執行 smoke：S=1、C=128、P=3、32 users × 1,000 requests。此 workload 需要足夠監控時間，讓 1 Hz required metrics 至少取得一筆 window sample。Smoke 必須完成 32 個 accounts、32,000 requests 與 ledger rows 的完整驗證及 owned cleanup。Smoke 只檢查生命週期和 profile，不列入 shard 效能比較。

Smoke 成功後依序執行兩個 full cases：S=1，然後 S=2。每個 case 使用 1,024 accounts × 1,000 requests，每 case 只執行一次。每個 case 使用 fresh owned node data。Calibration、smoke 或任何 full case 失敗時，停止後續階段。不得自動 retry。

Smoke 必須有 32,000 requests 全部 accepted、applied、replied，driver query delta 恰為 32,000，measured SELECT 為 0；32 個 accounts 與 32,000 筆 ledger rows 必須完整驗證。每個 full case 必須有 1,024,000 requests 全部 accepted、applied、replied，driver query delta 恰為 1,024,000，measured SELECT 為 0；1,024 個 accounts 與全部 ledger rows 必須完整驗證。所有階段的 errors、retries、request timeouts、connection timeouts 與 unknown outcomes 必須為 0。Source、binary 和 runtime calibration hashes 必須相符。Owned containers、network 和 data 必須 clean。

Unknown commit outcome 必須凍結該帳戶並 fail closed 全部 workload。保留錯誤、driver counters、partial verification 和 cleanup evidence。完成證據後只清理本次 owned data。不得將 unknown outcome 當作確定未提交。

## 解析限制

S=1 與 S=2 的總吞吐都是單節點總吞吐，不是單 shard 吞吐。S=2 會增加該 node 的 reactor 與 connection 數；node memory 固定，因此每 shard 可用 memory 會改變。RF1/CL1 單節點結果不能與 RF3/CL3 三節點結果直接作 scale 結論。
