## Qualification 順序與 gate

1. 讀取 Docker version/info，要求 cgroup v2；讀取 host storage identity、repo filesystem device 和 available memory。
2. Pull 官方 18.6 tag 作為解析來源，檢查 pinned repository digest、image ID 和 platform。Tag 更新或 digest/ID 不符即停止。
3. 為 run 建立 unique nonce、owner label、internal bridge 和 bind-data directory。Host parent mode 為 `0755`，由 official entrypoint 建立 PGDATA 權限。Container 不發布 host port，只附著到本 run internal network；qualification 專用 `trust` authentication 不得用於比較 workload。
4. PostgreSQL container 固定 CPU set `0,1`，memory limit 10 GiB、swap limit 等於 memory limit、無 CPU quota；四個 `--device-*` flags 都指定 `/dev/sdb` approved caps。PG18 mount 和 `POSTGRES_USER=postgres`、`POSTGRES_DB=walletbench`、`PGDATA=/var/lib/postgresql/18/docker` 以 inspect 驗證。進程先從 TCP loopback readiness gate 確認正式 server 已啟動，避免只連到 image entrypoint 的 temporary initialization server。
5. 讀取 container inspect `HostConfig` 和 server host PID 對應的 cgroup files。要求有效 CPU `0-1`、`memory.max=10737418240`、`memory.swap.max=0`、`cpu.max=max ...`、`io.max` 的 `8:16` 行與四個 approved caps 完全相符；不相符立即失敗。
6. 從 SQL 驗證 server version `18.6` / `server_version_num=180006`、`pg_is_in_recovery=false` 和全部 approved `SHOW` settings。Probe `pg_stat_io` WAL writes/write timing/fsync/fsync timing、`pg_stat_wal` bytes/FPI、`pg_stat_database` transaction counters、PG18 `pg_stat_checkpointer` counters 以及 `pg_stat_activity` wait data。
7. 建立暫時 qualification table，以 SQL 寫入 32 rows × 1 MiB payload（共 33,554,432 bytes），確認 row/byte totals，執行 `CHECKPOINT`，讀取 cgroup `io.stat` delta 與 host diskstats。要求資料 device 或 approved cap device 有非零 cgroup write bytes 和 I/O count。這只驗證寫入在限速 device path 可歸因，並不代表 Wallet throughput 或 transaction-level I/O。
8. 保存 logs 與 inspect，再停止、移除本 run 擁有的 container/network/data。Data cleanup 前驗證 owner/nonce、exact bind mount/path、PG18 layout 和 directory manifest；若清理 helper 失敗，保留尚不能安全清除的 path 並將 run 標記 failed。任何例外都在 `finally` 寫終態 `qualification.json` 和 `cleanup.json`，不留 `running` 狀態。

## 可下的結論與限制

Infrastructure-only run 證明 pinned PostgreSQL 18.6 image 能在指定 CPU/memory/swap/device cgroup profile 下啟動、讀回設定、提供 PG18 statistics，並讓 bounded buffered SQL write/checkpoint 的 cgroup I/O activity 出現在核准 whole-device。Live run 進一步證明 host-native tokio-postgres direct-IP route、frozen SQL migration 的實際 catalog/runtime gate、Wallet applied/replay/conflict/missing-account rollback/full verification、32×32 smoke 的完整結果、active-pool monitoring，以及 acknowledged rows 在 PostgreSQL process SIGKILL/restart 後仍符合 expected state。兩次 crash-test harness 前置失敗沒有提交 Wallet rows；它們和後續 pass attempt 各自保留。

這些 qualification 沒有執行 D=16/32/64 的 1,024,000-request calibration，沒有執行正式六個 Scylla/PostgreSQL full cases，也沒有測試電源故障或斷電耐久性。有限 smoke 的時間/RPS 不得充當 baseline、calibration 選擇或比較結論。短閉環 smoke 和 process restart 不證明 steady-state/hardware limit 或 power-loss durability；正式 campaign 仍須 root 完成 exact source/config/runner/hash review 和 final plan approval。
