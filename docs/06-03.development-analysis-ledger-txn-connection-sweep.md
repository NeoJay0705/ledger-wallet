# Connection sweep 測試報告：PostgreSQL vs TiDB，CPU4 / CPU8，connections 掃描

目的：在固定 batch-max（50、100）與 256 queues 下增加 client connections，量測 RPS 與 latency，找出各系列的飽和點。Latency 的可接受門檻由讀者自行選定，本報告不預設 SLO。

資料來源：`artifacts/connsweep-{pg,tidb}-c{4,8}-bm{50,100}.csv` 與各 attempt 目錄；選擇 effective primary、saturation、replicate 嚴格重用 `scripts/conn_sweep.py`。

## 2. 負載方式

- **資料：** 50,000 accounts × 40 requests = 2,000,000 requests；amount=1，transaction id 為新 UUID。
- **Queues / connections：** queue = `user % 256`，共 256 queues。每個測點使用 N 條資料連線（另有 monitor）；每條連線服務 `256/N` queues，round-robin 送出各 queue 的 windows；每連線同時一個 window in-flight，每 queue 至多一個 window in-flight，同 queue 依序處理。
- **Window：** 最多 batch-max 筆同一 queue 的請求構成一個 atomic transaction；每 window 只碰一個 TiDB region；TiDB 每表 256 個 pre-split regions、no RF，一 queue 對應一 region。PG 一條 SQL；TiDB pessimistic transaction 兩次 round trip。30 s per-window timeout。
- **Queue 數與 windows：** 50,000 × 40 按 256 queues 分配後，80 queues 各有 7,840 requests，176 queues 各 7,800。預期 windows = 40,016（batch 50）、20,048（batch 100），與 N 無關。逐一檢查所有 effective primary CSV `windows` 欄位：全部符合預期。
- **掃描網格：** CPU4：4、8、16、32、64、128、256；CPU8：8、16、32、64、128、256。256 是上限，因 queue 只有 256；不向上擴展。

### PostgreSQL 與 TiDB 差異（未補償）

- TiDB 一個 window 為 multi-statement、2 round trips，before/after 由 client 計算；PG 為單一 statement / round trip、由 DB 計算。
- TiDB 表有 shard 欄位，沒有 CHECK（TiDB 預設關閉）；兩者均保留 FK。
- TiDB 額外包含 tidb-server 與 PD；PG 沒有。Latency 是 window 送出至最後回應（TiDB 至 COMMIT），按 requests 加權。

## 3. DB 設定

| 項目 | PostgreSQL | TiDB |

| 持久化 | `fsync=on`、`synchronous_commit=on`、`full_page_writes=on` | raft-engine `enable=true`；每個 write batch sync；以 write/sync counter 差值檢驗（±1%） |

| 複本 | 單機 | no RF（`max-replicas=1`） |

| TiDB variables | – | pessimistic、1PC=1、async commit=1、FK checks=1、multi_statement_mode=OFF（client connection flag 允許 multi-statement） |

## 4. 監控與驗證方式

- **Sampling：** 250 ms；以 cgroup CPU/memory、主機 sdb diskstats、container network、client CPU/RSS 取樣，依 client measurement start/end 篩選。TiDB 另取 TiKV raft-engine durability 與 topology。
- CPU 以 cgroup usage 換算 cores / quota；memory 為 cgroup `memory.current` 最大值（含 page cache），client RSS 為最大值；sdb 列 write MiB/s、write IOPS、util、queue depth、flush await、write await。
- Idle gate：每次 launch 前各 logical CPU idle（含 iowait）至少 90%，同一 5 秒無其他 process 使用超過 30% 單核；最多等待 60 秒。每次測量都有 `<attempt>-idle.json`。
- Stall：flush await > 2 ms 則額外 rerun 一次，rerun 若 OK 取代 primary，兩列均保留。Sampler race 最多於新目錄重試兩次。
- **Latency：** 每 window 從送出至 COMMIT 回應，window latency 按其中 requests 加權，報 p50/p95/p99/max。
- **飽和定義：** fixed grid 上 effective-primary RPS 最大值的 95% 門檻，取最小 N；replicate 只跑飽和點及其下一個較低 grid 點，不改 primary 選擇。若 256 命中，標示 observed-grid saturation。
- **TiDB reclassified 樣本：** 26 筆 attempt 紀錄（含 replicate），其測量窗口開始時 tidb container cgroup io counters 空白，wrapper 因而標記 res-tidb non-formal。Driver 僅在 TiKV/PD formal 且 tidb CPU/memory samples 完整時接受；tidb CPU 對 † row 以 full-window counter 重算（3 個 formal attempt 驗證差異在 0.04% 內），不採用 `summary.json` 的 tidb CPU 值。

## 9. 限制與已知事件

- 每個 grid point 原則上單次 run；僅飽和點與下一低點 replicate，不能從單次結果推定穩態曲線。
- 總量 2M requests；高 connections 測點只需數秒，短 run 的取樣與雜訊影響較大；不可與此前 4M batch-sweep 直接比較。
- tidb-server 在 CPU4 / CPU8 都是 4 threads；client 固定 2 CPUs，tokio runtime 未配置；並有 SMT sibling sharing。
- TiDB failures / incomplete，以及歷史 stray incomplete attempts 均保留在第 7 節 CSV 列表；不納入 effective-primary。
- 無 TiKV per-thread profiling、per-stage latency、post-run region distribution 或 per-region load。
