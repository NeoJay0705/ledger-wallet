# Ledger R1 txn on TiDB (CPU=4 / CPU=8, no RF, pre-sharded) — Requirements (user-confirmed)

Goal name: ledger-txntidb. Source: user wants the R1 PostgreSQL batch-queue test (`txn_batch_pg`, `ledger-txnpg-*`) repeated on TiDB. Everything not listed here is identical to the PG R1 test (`ledger-txnpg-requirements.md`, `ledger-txn-requirements.md` DECISIONS, `ledger-txn-sql.md` semantics).

## Decisions (user)
1. Baseline = PG R1 (`txn_batch_pg`: probe, before/after, `existing`, `rejected:*`, FK kept, 5-column ledger).
2. CPU accounting: only TiKV is counted against the CPU budget (it is the storage/WAL engine, the PG-equivalent bottleneck). tidb-server and PD are NOT counted, but get their own CPUs, are sampled, and the report states whether tidb-server was saturated.
3. Sharding option B: both tables get a leading derived `shard` column = queue index (`user % queues`), clustered PK starts with it, and each table is pre-split into `queues` (256) regions, so one queue = one region.
4. Durability must have batch-fsync semantics (not periodic). TiKV raft-engine syncs every write batch; evidence from `raft_engine_sync_log_duration_seconds_count` vs `raft_engine_write_duration_seconds_count`.
5. Cells: TiDB `{cpu4, cpu8} x {batch-max 4000, 8000}` = 4 cells; plus 2 new PG R1 runs at CPU=4 (batch-max 4000, 8000). PG CPU=8 uses the existing artifacts (`artifacts/txn-bm4000-W256`, `txn-bm4000-W256-rep2`, `txn-bm8000-W256`).

## Topology / resources
| Profile | TiKV (counted) | tidb-server (not counted) | client | PD + sampler |
|---|---|---|---|---|
| CPU4 | 1 store, cpuset 0-3, quota 4 | cpuset 6-7,12-13 | 4-5 | 14-15 |
| CPU8 | 2 stores, each quota 4: cpuset 0-3 and 4-7 | cpuset 10-13 | 8-9 | 14-15 |
- no RF: PD `max-replicas=1`; at CPU8 the 256+256 regions are spread over the two stores (checked before GO).
- TiKV memory 8 GiB per store, block cache 2 GB (PG shared_buffers is 2 GB). Same host disk (sdb), same TiKV/PD/TiDB version v8.5.6, defaults otherwise (record effective config). tidb-server memory limit 16 GiB.
- CPU8 necessarily puts tidb-server/client on SMT siblings of TiKV cores (host has 8 physical cores); disclosed, same as the PG CPU8 runs.

## Workload (identical to PG R1)
100,000 accounts, 40 requests/user = 4,000,000 unique requests, amount 1, fresh UUIDs, 256 queues = 256 data connections 1:1 (+1 monitor = 257 sockets), queue = user % 256, round-robin order, up to `batch-max` requests per window, one atomic transaction per window, sampling 250 ms, single run per cell, stall rule as in ledger-bigbatch (re-run once if device flush await > 2 ms; keep both in report). No 5 % retry cell. Smoke-only flags `--retry-pct` / `--inject-rejects` exist to exercise `existing` / `rejected` on the real binary.

## Semantics per window (same R1 contract)
Dedupe (account,tx) keeping first, stable sort by account, then in ONE pessimistic transaction: lock+read account balances, probe existing ledger keys, classify (existing > invalid amount > unknown account > applied, as PG), compute before/after per account in input order, insert the applied ledger rows, write new balances, commit. Every request gets exactly one terminal outcome matched by (account, tx); a missing/unexpected/duplicate reply is an error. Any error/timeout (30 s) invalidates the run; no retry.
Known, disclosed differences from PG: no data-modifying CTE in TiDB, so a window is one transaction of several statements sent as TWO multi-statement round trips (packet 1 = `BEGIN PESSIMISTIC` + lock/read balances + probe; packet 2 = insert ledger + update balances + `COMMIT`); RPS(IO) = windows/s = transactions/s (decision L1: all-in-DB single round trip was tried and rejected: slower, plan scans, more tidb-server CPU); before/after is computed in the client; tables carry the extra `shard` column; no CHECK constraints (TiDB `tidb_enable_check_constraint` is OFF by default); latency = transaction duration (BEGIN..COMMIT) per request.

## Measurements
Same as PG R1 (RPS request/IO/applied-unique, latency p50/p95/p99, batch size, in-flight client/pool/server, CPU, memory, disk util/await, net bytes, client CPU/RSS) plus: per-store TiKV CPU, tidb-server CPU (% of its cpuset), per-store region/leader counts, TiKV raft-engine write/sync counters (count, bytes, sync seconds), effective TiKV/TiDB settings. Server in-flight = non-sleeping sessions in `information_schema.processlist`.

## Verification (necessary only)
Untimed after the run: per account balance == ledger count == 40, first before 0, `count(distinct before_balance)` == count, max after == balance, after == before+amount for all rows (with amount 1 this is the full chain), 100,000 accounts, sum balance == ledger rows == 4,000,000; outcomes: applied == 4,000,000, missing/unexpected/replay_mismatch 0. Before GO: each table has >= 256 regions, every region has exactly 1 peer, store region/leader balance at CPU8 within 40/60. Durability: sync count delta > 0 and equal (+-1 %) to write count delta. Wrapper: 257 sockets, resource placement, cleanup success.

## Out of scope
Multiple tidb-servers, TiDB tuning beyond the settings above, retry-5 % cell, Scylla, failover/crash, repeats beyond the stall rule.
