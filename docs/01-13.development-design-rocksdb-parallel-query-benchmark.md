# Tokio 並行 RocksDB 查詢 benchmark 設計

## 工作負載與比較方式

這個 benchmark 保留 `rocksdb_tokio_sequential` 作為既有 sequential baseline，另外新增平行查詢執行檔。每個 trial 使用 benchmark 共用的 RocksDB store，寫入相同的 10,000,000 筆 ledger workload，再以固定 seed Fisher–Yates 洗牌 `1..=iterations`，查詢每個 ledger transaction ID 一次。預設 batch size 為 2,048 和 4,096；每個 batch size 分別測試最多 1、2、4、8 個在途 query batches，每組預設重複 3 次。

每個 trial 建立唯一的新 RocksDB directory，沿用 sequential benchmark 的 options、WAL sync 寫入、key/value 編碼、write batches、持久狀態驗證、preflight、I/O 取樣、RocksDB counters 及 cleanup。寫入階段仍一次 await 一批，並維持相同的交易順序和 balance updates。只有查詢階段改為有界並行。

## 查詢排程與完整驗證

Harness 使用一個 current-thread Tokio runtime 和一個共享的 `Arc<DB>`。它以 `JoinSet::spawn_blocking` 提交 multiget 工作，最多維持設定數目的 batches 在途；在達到上限時收取一項完成工作，再提交下一項。此設定限制 benchmark 排入和執行的 query batches 數量，不會改變 Tokio runtime worker 數或 RocksDB background job 數。

每批工作攜帶固定 batch index、該批 transaction IDs 和 ledger keys。`batched_multi_get_cf` 的結果仍依該批原始 ID 順序逐筆解碼，並將每筆完整 `LedgerEntry` 與該 ID 對應的預期 entry 比對。完成訊息帶回原 batch index；主 runtime 允許完成順序不同於提交順序，並檢查 index 範圍、重複完成、所有預期 batches 完成，以及總驗證交易數。遇到工作失敗後停止新提交並收完已提交工作，讓所有 blocking calls 結束後才關閉 DB 和移除 trial directory。

## 延遲、吞吐與 CPU

`query_rps` 是完整驗證的 lookup 數除以 query phase wall time。Query phase 從第一批開始準備 keys，到最後一個成功結果由 JoinSet 收取為止。ProcessTime 與 phase wall time 在同一時間界線取樣，`query_cpu_core_equivalents` 為 process CPU seconds 除以 query wall seconds；它包含 runtime、RocksDB blocking threads 及 process 內其他 CPU work，不代表某一個 worker 的單獨用量。

`query_batch_submission_to_completion` 是每批呼叫 `spawn_blocking` 後至主 runtime 收到完成結果的時間，包含 blocking pool 排隊、RocksDB 呼叫、解碼驗證、worker 結束到 runtime 收取結果。它每批記錄一次，輸出 batch 數、平均值及 p50/p95/p99。`query_blocking_pool_wait` 是 blocking task 提交到 closure 開始執行的時間，也以每批一次計算。`query_batched_multi_get_call` 只量 RocksDB `batched_multi_get_cf` native call；不含 blocking pool wait、準備 keys、解碼、驗證或回到 runtime 的時間。

既有 `query_tx_latency` 維持 transaction-weighted 解讀：某 batch 的完整 latency 依該批交易數加權，包含 key 準備、提交、等待、native lookup、解碼驗證和完成確認。這項值不是每筆交易各自計時。`query_batch_prep` 單獨記錄 key 編碼與預期 ID 複製。這些分開欄位可直接比較 query 吞吐、批次提交到完成時間、blocking pool wait 及 RocksDB native call 時間。

## 系統與 RocksDB 觀測

每個 write 和 query phase 前均使用 sequential benchmark 的 strict idle preflight：預設 aggregate CPU busy 上限 10%、目標 block device busy 上限 5%，另外檢查 MemAvailable、free bytes、filesystem 類型，並拒絕無法讀取 CPU 或 disk busy 指標的情況。每次嘗試寫入 `<output-dir>/preflight.log`。並行設定的工作記憶體預估會按 batch size 和最大在途 batches 數量放大。各成功 trial 的 CSV 也包含兩階段 preflight 樣本和門檻。

CSV 沿用 sequential benchmark 的 process I/O counters、目標裝置 busy counter、RocksDB ticker/histogram/property snapshots 與 heartbeat lateness。Process I/O 是程序範圍；disk busy 是整個 block device 的活動；RocksDB counters 也可能包含該 phase 內的非同步 background work。它們是 phase 級觀測，不應解讀成某個 query batch 的成本。可用 `--diagnostic` 產生逐批 trace，檢視 worker thread、blocking wait、native call、validation 與 RocksDB PerfContext 指標。

## 執行與輸出

`cargo bench --bench rocksdb_tokio_parallel_query -- --help` 列出參數。可用 `--iterations`、`--repetitions`、`--batch-sizes`、`--max-concurrent-batches` 調整 workload；預設跑完整 10M workload 與 2x4 矩陣。只要降低 iterations、選擇單一 batch/concurrency 組合並縮短 `--preflight-observation-ms`，即可執行 correctness smoke。Preflight CPU/disk 預設值不可為 benchmark 成績而放寬。

CSV header 與成功 trial rows 輸出到 stdout；預設 preflight log 和暫存 trial DB 位於 `target/rocksdb-tokio-parallel-query/`。每個成功或錯誤 trial 在關閉 DB handles 後刪除自己的唯一 DB directory；preflight log 保留。既有 sequential benchmark 的執行檔與輸出保持獨立。
