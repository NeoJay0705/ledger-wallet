# ledger-connsweep — Design (rev 2, after review APPROVE-WITH-CHANGES)

## Changes (minimal, additive; defaults preserve current behaviour)
1. **Clients** `src/bin/txn_batch_pg.rs`, `src/bin/txn_batch_tidb.rs`: new arg `--connections N` (default = `--queues`; require 1 <= N <= queues). Open N data connections (+1 monitor) and spawn N workers (no `zip` truncation of the original per-queue workloads). Queue `q` is owned by connection `q % N`. A pure function builds each connection's merged window sequence: round-robin over its owned queues (window i of each queue, then i+1; exhausted queues skipped; unequal lengths allowed). Each merged window keeps its ORIGINAL shard (= queue index); TiDB uses that shard in BOTH packets (never the connection index, never derived from injected users). Setup gates (plan probe on queue 0 shard) unchanged. `data_connections` in result.json = N and `effective.connections` = N. Counters/batch-size stats stay per original window. With N == queues the sequence equals the old one.
2. **Wrappers** `scripts/batch_queue_run.py` (txn mode only), `scripts/txn_tidb_run.py`: new `--connections` (default = queues), forwarded to the client; socket census expects `connections + 1` (batch_queue_run.py:270, txn_tidb_run.py:286). Nothing else changes (TiDB region gate and store balance gate, PG `max_connections = max(300, queues+44)`).
3. **Driver** `scripts/conn_sweep.py` (new; `batch_sweep.py` untouched; imports `idle_gate`, `extract_row`, `classify_cause`, `should_flush_rerun`). Full invocation contract per attempt:
   - PG: `scripts/batch_queue_run.py <dir> --mode txn --cpus C --users 50000 --requests-per-user 40 --queues 256 --connections N --batch-max B --sample-interval-ms 250 --pg-conf wal_buffers=256MB --pg-conf max_wal_size=8GB --pg-conf track_wal_io_timing=on`.
   - TiDB: `scripts/txn_tidb_run.py <dir> --cpus C --users 50000 --requests-per-user 40 --queues 256 --connections N --batch-max B --sample-interval-ms 250`.
   - Attempt dir `artifacts/connsweep-<db>-c<C>-bm<B>-n<N>-a<k>`; idle gate evidence `<dir>-idle.json` before EVERY launched attempt (primary, rerun, replicate); CSV `artifacts/connsweep-<db>-c<C>-bm<B>.csv` (columns: conns, role, attempt_dir, status, exit, go_reached, cleanup, wall_s, duration_s, rps_request, p50_s, p95_s, p99_s, max_s, windows, db_cpu_cores, tidb_cpu_cores, flush_await_ms, client_cpu_cores, cause). No historical/4M rows are imported.
   - An attempt is OK only if: wrapper exit 0, cleanup success, client verification valid, effective workload in result.json equals the requested (users, requests-per-user, queues, connections, batch, total 2,000,000), flush value present, and the resource window is formal (`resource_window_formal` true; TiDB also durability gate passed).
   - **One authoritative selector** `effective_primary(rows)` used by run/resume/replicate/summarize/saturation: per connection count take the OK primary; if a flush rerun (flush await > 2 ms, max one) exists and is OK it replaces the primary; if the rerun failed the original stays but is flagged `flush>2ms, rerun failed` (visible in the report). Replicates are excluded from selection. Saturation = smallest conns with RPS >= 95 % of the max effective-primary RPS over the FIXED grid; if the curve has missing grid points it is reported incomplete and no saturation point is claimed; if the saturation point is 256 it is labeled "observed-grid saturation".
   - Run order per curve: full grid ascending (resume skips OK primaries, finishes pending flush reruns, skips completed replicates); sampler-race retry (max 2 fresh dirs); after the full grid, replicate the saturation point and its next-LOWER grid point once each (if the saturation point is the first grid point only that point; never a higher point). Cleanup residue/failure stops the campaign. Any other failure (including TiDB) is recorded and the sweep continues (each attempt uses fresh disposable resources).
4. **Report** `docs/06-03.development-analysis-ledger-txn-connection-sweep.md` generated by `scripts/conn_sweep_report.py` from CSV + attempt dirs (structure as `ledger-batchsweep-report.md`; additionally a client-bound flag when client CPU >= 85 % of its 2 CPUs, and tidb-server `*` when >= 85 % of its cpuset).

## Non-functional
- No new concurrency: one window in flight per connection; queues of one connection are sequential; shared state = existing atomics. `first_applied` keyed by (account, tx) is unaffected by merging.
- Totals derive from arguments (verification SQL, expected rows). With 50,000 users the queues are uneven (80 queues x 7,840 requests, 176 x 7,800); expected windows = 40,016 (batch 50), 20,048 (batch 100), independent of connections.
- TiDB: 256 pre-split regions/table and the CPU8 store-balance gate unchanged; tidb-server stays 4 threads; client keeps its 2-CPU binding and unconfigured tokio runtime (client CPU is reported to expose client-bound plateaus).
- Timeout 30 s per window unchanged.

## Verification (each item: why keep)
- Rust unit test of the real window merger (unequal queue lengths, exhausted queues, N == queues parity with old order, shard preserved per window, every request exactly once, per-queue order preserved) — the new core logic; wrong merging silently breaks order/shards. KEEP.
- Existing Rust client tests still pass — grouping must not regress ordering/retry/reject semantics. KEEP.
- Python tests: full argv contract for both DBs (incl. `--mode txn`, 250 ms, PG settings, `--connections`); wrapper->client forwarding and census `connections+1`; effective_primary (flush replacement, failed rerun, replicate exclusion, saturation changes after replacement, incomplete curve, 256 label, first-point replicate); resume/skip; sampler retry bounded; OK predicate (workload identity, formal resource window). KEEP: each prevents a silent invalid/misattributed result. Not required: re-running the unchanged wrapper test suites as a blanket item beyond what the change touches.
- Real smoke x2 (PG; TiDB at CPU8), multi-window (users 2000, requests-per-user 40, batch 50, queues 256, connections 4): result valid, `data_connections==4`, socket census 5, rounds >1 per queue, final remaining/inflight/busy 0, TiDB region/plan/store-balance/durability gates, cleanup. Retry/reject paths (`--retry-pct`, `--inject-rejects`) exercised once in the TiDB smoke only (outside the campaign). KEEP: end-to-end proof on the real binaries.
- Campaign acceptance: coverage audit of all 52 configurations (PG and TiDB: CPU4 7 conns x 2 batches = 14 each; CPU8 6 x 2 = 12 each); each selected point is OK per the predicate, has idle evidence, (TiDB) durability pass; failed/incomplete points listed explicitly. KEEP.
- Deleted: standalone full-size pilots (runtime comes from the first campaign points), "all CSV rows valid" (failure history is retained), separate "applied == total" check (already inside client validity).
