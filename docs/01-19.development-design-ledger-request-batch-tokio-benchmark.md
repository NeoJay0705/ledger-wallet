# Tokio 請求排程與批次佇列 benchmark 設計與結果

## 目的與範圍

`ledger_request_batch_tokio` 是獨立的 benchmark target，用來量測單一 Tokio worker 從 bounded `mpsc` queue 收集 request batch、呼叫非同步 handler、再以 per-request oneshot 回覆的成本。本階段只使用 opaque payload 和 deterministic echo handler；不包含 HashMap、RocksDB、gRPC、磁碟提交或 production ledger 邏輯。

可重用佇列實作位於 `benches/support/request_batch_queue.rs`。Handler 取得 owned `Vec<Payload>`，並須依原順序回傳等長的 `Vec<Reply>`。這個邊界可供後續 handler 在 future 中呼叫 `spawn_blocking`，同時保留同步 storage 操作與批次回覆的隔離。

## 工作負載與 CLI

預設每輪 10,000,000 個 request、50,000 個 user、50,000 個 coroutine，每個 coroutine 同時最多保留一筆 outstanding request。Runtime 固定使用 3 個 Tokio worker threads。Bounded queue 容量為 50,000；預設 batch size 為 2,048、第一筆 dequeue 後的 timeout 為 5 ms。Batch size 可設為 2,048 或 4,096；timeout 可設為 1、5、10 或 20 ms。`--iterations`、`--repetitions`、`--users`、`--coroutines`、`--sample-stride` 與 `--csv` 可調整工作量及輸出。

Coroutine `c` 使用 `user_id = c % users`，因此 coroutine 數可以大於 user 數。Request ID 由 coroutine index 開始，每次增加 coroutine 數；這會把 `0..iterations` 分割成互不重疊的序列。Handler 僅回傳 request ID 與由 request ID、user ID 算出的 deterministic opaque 值，不查詢或更新資料結構。

## 排程、deadline 與錯誤處理

`submit` 先等待 `mpsc::Sender::reserve()`，取得 permit 後再同步發布 request。Worker 每次成功 dequeue 第一個 request 時開始該 batch deadline；之後只在 batch 達上限、deadline 到期或 channel 關閉時 flush。唯一 worker 按 dequeue 順序呼叫 handler，並將 replies 依位置配回原 request。

正常關閉時，所有 sender drop 會關閉 channel；尚未滿批的尾端會以 `channel_closed` flush。Handler 回傳錯誤或 reply 數量不等於 request 數時，worker 對當前 batch 與已接受且仍排隊的 request 傳回錯誤，關閉並 drain channel，接著終止。Caller drop response handle 不會取消已接受的 request；worker 仍處理該 request。若 worker task panic 或被取消，oneshot receiver 會收到明確的 worker-stopped error。

## 時間邊界與統計方式

對每筆成功完成的 request，程式收集下列五段時間。各段使用同一組單調時鐘時間點，並在 request 完成時檢查五段總和等於 end-to-end duration。

| 欄位 | 邊界 |
| --- | --- |
| `enqueue_wait` | t0 開始 reserve 到 t1 reserve 成功；表示容量等待。 |
| `queue_wait` | t1 到成功 dequeue；t1 在同步 `permit.send()` 之前，因此這段也含 request 發布。 |
| `batch_wait` | 該 request dequeue 到 handler 開始；包含它在 active batch 中等待 flush 的時間。 |
| `handler_time` | handler 呼叫開始到 future 完成。每批共用的 wall interval 會記到批次內每筆 request，並非每筆獨立 CPU 時間。 |
| `response_wait` | handler 完成到 client 收到 oneshot reply；包含回覆派送及 client 喚醒時間。 |

`request_latency` 是 t0 到 client 收到 reply 的 end-to-end 時間。所有 stage 的 mean、count 與 nanosecond total 使用全體成功完成 request；程式逐筆驗證 additivity。Percentile 使用相同 deterministic sample：ID 0 加上 `splitmix64(request_id) % sample_stride == 0` 的 request；預設 stride 為 1,024。P50/P95/P99 使用 nearest-rank。不同 stage 的 percentile 是各自分布的統計量，不能相加；stage mean 則依全 request 的 nanosecond totals 相加。

Batch size histogram 是以每筆 reply 攜帶的 batch size 和 flush reason 彙整，並檢查每個 histogram bucket 的 reply 數可被 batch size 整除。結束時另檢查所有 histogram request 數、flush reason 數與 completed 數一致。ID verifier 用 atomic bitmap 拒絕重複 ID，並在結束時檢查 `0..iterations` 全部都有且只有一次回覆；每 coroutine 同時檢查回覆 ID 順序及 opaque 值。

ID bitmap 的 `fetch_or` 在每筆 reply 的 response observation timestamp 之後執行。它不計入該筆 end-to-end latency，但位於 process CPU bracket 內，並會延後該 coroutine 下一個 closed-loop request 的開始；所以 completed RPS 和 CPU seconds 包含 verifier 的成本。所有情境使用相同 verifier。

CSV 記錄 completed RPS、request latency 與五段 stage 的 mean/P50/P95/P99、樣本數、batch size/flush reason counts、ProcessTime CPU seconds/core equivalents，以及 benchmark I/O bracket 的 process 與 target-device counters。`request_wall_seconds` 從最早 request t0 到最晚 response observation；CPU wall bracket 從 start gate 放行到 worker join，因而略寬於 request wall interval。

## Preflight 與重現

每個 batch size/timeout/repetition case 開始前都呼叫既有的 `benches/support/ledger_preflight.rs`。Full runs 使用預設嚴格條件：3 秒觀察、最多等候 60 秒、CPU busy 上限 10%、target device busy 上限 5%、可用記憶體基準至少 128 MiB 加估算 working set、可用磁碟空間至少 1 GiB。Benchmark target 位於 ext4 `/dev/sdb2`。Preflight 不通過時 case 會停止，程式不放寬門檻。

Full runs 的命令、環境及實測彙整見 [bench results report](../benches/01-19.benchmark-results-ledger-request-batch-tokio.md)。Raw CSV 與完整 stdout/stderr log 保留在 ignored `target/`：

- `target/ledger-request-batch-2048-5ms.csv`、`target/ledger-request-batch-2048-5ms.log`
- `target/ledger-request-batch-4096-5ms.csv`、`target/ledger-request-batch-4096-5ms.log`
- `target/ledger-request-batch-timeout-matrix.csv`、`target/ledger-request-batch-timeout-matrix.log`

每個 full case 只執行一次；數字是此主機上的單次觀察，不代表統計顯著差異或 production 容量保證。Sampled latency percentile 及所有 mean/count 都保留於 CSV。
