# 帳戶記憶體狀態與單 CQL LWT Wallet 基準

## 目標

新增 `wallet-memory-lwt-v1` profile，評估帳戶狀態預載至記憶體後，以單一 conditional `INSERT ... IF NOT EXISTS` 保存每筆交易的做法。

此 profile 保留帳戶內循序處理、未知結果 fail-closed、單一共享 ScyllaDB Session、原有複本與一致性設定及 commitlog batch fsync 確認。它不代表效能已改善。效能結論須依實測結果。

## 交易與資料模型

交易請求只包含 `account_id`、`tx_id`、`operation` 及 `amount`。不使用 `transaction_at`。支援 Credit 與 Debit，並保存 InvalidAmount、InsufficientFunds、CreditOverflow 等業務拒絕結果。

表格以 `account_id` 為 partition key，`kind`、`tx_id` 為 clustering key：

```sql
PRIMARY KEY ((account_id), kind, tx_id)
```

`kind=0` 是帳戶 metadata sentinel row；`kind=1` 是 ledger row。`balance`、`version`、`write_clock` 是 static 欄位。Ledger 保存請求 body、outcome、交易後 balance、ledger version 及 logical write clock。Seed 的 `write_clock` 初值為 0。每筆新交易使用前值加 1，並以 checked arithmetic 檢查溢位。Logical write clock 是應用資料，獨立於 wall clock 和資料庫時間，不是 CQL write timestamp。

冪等鍵為 `(account_id, kind, tx_id)`。相同帳戶與交易 ID、相同 body 是 replay；body 不同是 Conflict。同一 `tx_id` 在不同帳戶互不衝突。

## 寫入與回覆

每筆新交易只送出一個 CQL statement：把 static 帳戶狀態和 ledger row 一起寫入 `INSERT ... IF NOT EXISTS`。該 statement 不使用 `USING TIMESTAMP`。Seed 也使用 LWT。設定 `LOCAL_SERIAL`；一般讀取與寫入 consistency level 仍分開設定並沿用 profile 明訂值。

若 LWT applied，只有在成功收到資料庫確認後才更新記憶體狀態並回覆。若未 applied，使用回傳的既有 row 判斷：相同 body 回傳原結果，不重寫 wallet row、不前進 cache，也不回退目前狀態；Paxos 內部仍可能寫入或 fsync。Body 不同回 Conflict。未 applied 回傳的 static state 必須符合目前 cache。較早 ledger row 的 `balance_after` 可以不同於目前值，因為該帳戶可能已有後續交易。資料庫狀態、ledger 或快取不一致時，回 Corruption 並 fail-closed。

LWT 會在 ScyllaDB 內執行 Paxos。單一 client CQL request 不代表資料庫只做一次內部工作，也不預設比原有多 statement 寫入更快。此 profile 移除一般 CQL BATCH；commitlog batch fsync 確認保持不變。Service transaction batch 與 commitlog batch 是不同概念。

## 帳戶狀態與併發

每個 trial 使用新 keyspace。服務 seed 後、measurement gate 開啟前，從資料庫預載該 trial 的帳戶狀態。預載併發上限為 `min(C, D)`，並在計時區間外完成。Measurement 不為每筆交易發出 SELECT。Unknown outcome 後的 process restart recovery 不在本 profile 支援範圍；即使 preload 可讀取非零狀態，也不得將它描述為 restart recovery 支援。

一個服務共享一個 ScyllaDB Session 與固定連線池。Worker 數 `C` 與 data connection 數 `D` 分別設定；不假設一條連線對應一個 coroutine。每個帳戶由單一 owner 循序處理。Owner 從狀態計算開始，持續到 conditional insert 確認、快取更新及回覆。不同帳戶可以並行。

LWT 對不同 `tx_id` 的陳舊記憶體狀態不提供應用層保護。本測試維持單一 owner，且不允許外部 writer。Restart recovery、多 service 寫入與 fencing 不在本 profile 範圍。

## 未知結果與清理

寫入 timeout、寫入錯誤，或寫入後無法解碼回應，都視為 CommitOutcomeUnknown。不得自動重試該交易。凍結該帳戶並停止全域新 admission；已接受工作須完成或確認結果。Caller cancellation 不得取消已接受的 worker 工作。

停止 admission 後 drain 已接受工作，再核對資料庫 ledger 與記憶體快照，最後依既有 ownership marker 清理本次建立的容器、網路與資料。任何不一致都使 trial 失敗。

## 固定環境與識別

保留既有三個隔離 ScyllaDB instances、pinned 2026.1.14 image、CPU affinity、SMT、replication factor、一般讀寫 consistency levels、commitlog 設定、監控、連線池稽核、strict preflight 與安全清理流程。除 `LOCAL_SERIAL` 與單一 LWT 寫入流程外，不改變固定環境設定。

報告須標記 `wallet_profile=wallet-memory-lwt-v1`、`account_state_source=memory`、`ledger_key=['account_id','kind','tx_id']`、`serial_cl=LOCAL_SERIAL`、`cql_requests_per_transaction=1` 及 `cql_statement_count=1`。Case ID 與報告須和歷史三 CQL profile 分組，不混算結果。

## 驗收與界線

先驗證 unit tests，再執行小型、由本次 trial 自有 namespace 的 live integration；如時間允許，包含 RF1/CL1 smoke。驗證同帳戶循序、跨帳戶並行、LWT 首次套用、同 body replay、不同 body conflict、持久化業務拒絕、overflow、unknown freeze、取消 caller 後仍完成已接受工作，以及 drain 後資料庫與快取一致。最終驗證須記錄完成比較的 cache account 數量。本次先完成實作與小型正確性驗證；10M 效能比較另列後續工作。本文件不記錄尚未執行的測試結果。

快取更新必須晚於成功 acknowledgement；未知結果必須 fail-closed。RF1 profile 沒有複本高可用性。沒有量測前不得宣稱此設計較快。
