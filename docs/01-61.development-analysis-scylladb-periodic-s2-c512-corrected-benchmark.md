3. 本次 runner 啟動並完成 workload，但外層 supervisor 將 profile object 當成含 `.valid` 的結構讀取，因欄位契約不符而留下 `case_failed`。這是結果彙整介面不匹配，不是測量期間的 service error。離線 reconciliation 確認已保存的 runner capture 與 profile 相符；原 job、run 與 case status 仍保留原始值，不把 outer job 改標為成功。

離線 reconciliation 使用 corrected supervisor copy，對既有 `ready_event` 以固定 S2/C512/P3/D6/N1/RF1/ONE/ONE profile 重新驗證，並與記錄的 profile object 做精確比對。Corrected validation、runner validation、observer validation 均為 valid，沒有 validation problems 或 observer errors。11 個 regression tests 與 py_compile 通過；frozen inputs 未變。這項結果只接受已保存的 measured capture，不改寫原始 job 狀態。Corrected validation SHA-256 為 `a22a1680eea6f84f153140e694846b50a5e756efd16392c739d74e60070e558c`。

```text
periodic configuration probe -> I/O readiness correction -> fresh strict preflight
  -> fresh node/runtime gates -> seed -> readiness -> one measured workload
  -> full verification -> cleanup -> offline outer-result reconciliation

run_clients -> run_client -> Service::submit -> owner lock / queue
  -> worker_loop -> process_job (cache compute)
  -> ScyllaStore::commit (single IF NOT EXISTS)
  -> LWT force_sync -> CL ONE acknowledgement
  -> publish cache -> reply
  -> after all replies: verify -> stop and inspect -> owned cleanup
```

## Interpretation limits

- 這是單次短測，沒有信賴區間，也不能代表 steady state、production SLA 或一般引擎勝負。
- Periodic LWT 仍同步執行 force-sync 路徑；本設定不等於沒有 fsync，也不保證禁止 group commit。普通 periodic write 的 acknowledgement 行為不能直接外推到 LWT。
- Diskstats、flush counters、Scylla queue metrics 和 per-request latency 使用不同計數單位及時間邊界。不可推算單筆 fsync latency，也不可把 counter delta 當成 request 數。
- 同一 host 與 device 承載 Scylla、runner 和其他 OS 工作。CPU、device 與 queue 觀察不能證明某一元件是唯一瓶頸。
- Binary 的 `durability_precondition.required_commitlog_sync` 仍記錄 batch，因 Rust binary 未變。Periodic 的實際設定以 frozen runner source、runtime config 和 pinned-release evidence 為準；本 case 是 diagnostic pilot，不是原 RF3/CL3 的 27-trial formal matrix。
- 完整 raw artifacts 保存在外部 archive；本文件引用的小型檔案、derived summaries 和來源索引見 [Scylla evidence package](../benches/data/scylla_wallet/README.md)。
