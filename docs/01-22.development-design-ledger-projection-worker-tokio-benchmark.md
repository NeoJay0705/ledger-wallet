# Tokio Ledger Projection Worker Benchmark

## Objective

Measure how the Tokio ledger source behaves when a single sequential projection worker reads committed ledger records in batches and applies them to a destination. The benchmark compares three phases against the same deterministic credit/debit workload:

1. Live durable writes with projection disabled as the control.
2. A complete durable prefill followed by measured projection catch-up.
3. Durable writes while the projection worker follows the committed sequence, then drains to the final sequence.

The full default workload is 50,000 accounts with 200 requests per account: 10,000,000 durable ledger records per case. The foreground uses batches of 4,096 transactions, checkpoint balance mode, a single shard namespace, and a four-worker Tokio runtime. Projection batches default to 256 records.

## Source ledger range API

`AccountStore::read_ledger_range(first_seq, max_records)` reads an inclusive contiguous range. It checks the latest-sequence metadata, performs the RocksDB reads and decoding on Tokio's blocking pool, preserves the store's keyspace prefix, and verifies each decoded record sequence against its ledger key. Missing, malformed, and sequence-mismatched records fail the request. The returned database-read duration excludes blocking-pool queue and async dispatch time so the benchmark can report both.

The API uses the existing transaction decoder and keyspace implementation. It does not define a second ledger codec.

## Projection destination model

The benchmark destination is an in-memory `HashMap<TransactionKey, ProjectedTransaction>` guarded by one mutex. It reserves capacity for the full expected key count before measured windows; that capacity reservation is excluded from measured latency, while hashing, inserts, and payload handling are included. Each batch is checked in full before any insert or watermark update. New records must begin at the next contiguous sequence; exact replays are accepted when both sequence and stored payload match. A key conflict or a gap leaves the prior state unchanged.

The destination is a measurement fixture only. Its in-memory projection sequence is not durable production progress: it has no persistence, restart recovery, retention, or garbage-collection behavior. `--projection-delay-ms` optionally adds an asynchronous per-batch delay before acquiring the destination lock; its default is zero.

## Worker behavior

The worker reads one range at a time, applies it, and advances only after a successful batch. Source reads use the account-store async API, which moves RocksDB calls to `spawn_blocking`; Tokio worker threads are not used for synchronous database calls. During live writes, a watch channel announces committed source heads. The worker waits on that channel while caught up, then drains after the writer closes it. Errors propagate through the worker join result, and the live case has an explicit cancellation signal for early worker failure.

## Windows and measurements

- **Control:** foreground transaction RPS uses the write-loop wall time. The measured I/O, CPU, and RocksDB window runs from the start of writes through checkpoint drain. Projection count and rate are zero; end lag equals the durable source sequence.
- **Catch-up:** the prefill occurs before the measured window. Foreground transaction count and rate are zero in this window. Projection RPS and all stage percentiles cover catch-up from sequence 1 through the final sequence. End lag records the initial backlog; peak lag is sampled every 5 ms.
- **Concurrent:** transaction RPS uses the write-loop wall time. The measured CPU, I/O, RocksDB, and projection window starts with the concurrent run and ends after checkpoint and projection drain. End lag is captured when foreground writes finish; peak lag is sampled every 5 ms.

Per projection batch, the report includes p50/p95/p99 and sample count for internal RocksDB read/decode time, in-memory mock apply time, actual async delay, dispatch/wait residual, and total batch time. It also reports deterministic sampled foreground transaction-handler p50/p95/p99 latency; a hash filter selects about one in 1,024 transaction IDs, and each selected transaction receives the full `handle_batch` elapsed time for the batch that contained it. The catch-up case has no foreground handler samples in its measured window. The residual is total elapsed time minus the measured read, actual delay, and apply durations. The catch-up case runs a second strict idle preflight after prefill and checkpoint drain, immediately before the measured window; that result is reported for the measured window.

The benchmark also records process CPU seconds and core equivalents, process and target-device I/O deltas, RocksDB ticker read/write deltas, WAL syncs/bytes, writes with WAL, flush bytes, compaction read/write bytes, stalls, peak RSS, DB size, and preflight observations. RocksDB ticker deltas are not equivalent to returned ledger payload or device bytes. The memory estimate reserves 256 bytes per projected record plus 768 MiB of headroom.

Latency percentiles are computed over all measured projection batches. Process CPU is process-wide, so the concurrent case includes both foreground and projector CPU. Device counters cover the filesystem device hosting the case directory.

## Preflight and cleanup

Every case runs the Linux idle preflight before workload execution. The free-space gate estimates 768 bytes per durable record plus the configured reserve; the available-memory gate estimates 256 bytes per projected record plus 768 MiB of headroom. Both estimates can be tuned through the CLI. A failed gate stops the case instead of shrinking the workload.

Each case gets a unique RocksDB directory. The account store is shut down and RocksDB handles are dropped before recursive cleanup on both success and handled failure paths. The benchmark writes its run log and result CSV under `target/ledger-projection-worker-tokio-trials` by default. Full-run archival data belongs under `benches/data/ledger_projection_worker/`; smoke output is not archived there.

## Commands

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --bench ledger_projection_worker_tokio -- --smoke
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --bench ledger_projection_worker_tokio
```

On the benchmark host, bindgen needs GCC 13's standard headers through `BINDGEN_EXTRA_CLANG_ARGS`; omitting this environment variable failed there because clang could not find `stdbool.h`. The executable also accepts explicit `--users`, `--waves`, `--projection-batch-size`, `--projection-delay-ms`, output-root, and preflight tuning flags. `--smoke` runs 200 users × 20 requests unless workload dimensions are explicitly supplied. The default command remains the full 10-million-record workload.
