# 單副本同步落盤 ScyllaDB Wallet 基準比較：需求

日期：2026-10-12。
目標名稱：單副本同步落盤 ScyllaDB Wallet 基準比較。
需求編號：01。文件序號：39。
狀態：RF1/CL1 單一 benchmark case 已授權；實作、驗證與執行狀態另行記錄。

本需求沿用 [01-31 ScyllaDB wallet benchmark 需求](01-31.raw-requirement-scylladb-wallet-benchmark.md)、[01-36 per-user worker 需求](01-36.raw-requirement-scylladb-per-user-worker-benchmark.md) 與 [01-37 設計](01-37.development-design-scylladb-per-user-worker-benchmark.md)。本 case 只變更 replication factor 與 wallet read/write consistency。其餘資料、worker、connection pool、commitlog、deadline、監控與清理契約保持不變。

## 目標與範圍

目標是評估單副本、CL=ONE 的 ScyllaDB wallet workload，同時要求成功 write acknowledgement 發生在該副本的 commitlog batch fsync 後。

只執行一個新 case：`RF=1`、`Read CL=ONE`、`Write CL=ONE`。不執行 CL/RF sweep，不改 DB in-flight 上限，不執行九 case 或 27 case matrix。本次 run 即使 trial 通過，也只代表此單一 custom case，不代表完整 formal matrix。

ScyllaDB 使用三個隔離 instance，並在三個 node 間按 partition 分布帳戶。每個帳戶在 RF1 下只有一份 replica。三個 instance 共用同一 host 和 SSD；它們不是三個獨立故障域。

## 固定 worker、連線與 workload

沿用 S4、每 node 每 shard `P=4`、`D=3*S*P=48` 條目標 data connections；每 node 16 條。服務使用 `C=50,000` 個 DB workers，50,000 users 與 workers 一對一。每個 account 固定路由到同 index 的 per-user worker。Workers 共用一個 Session，每 worker queue capacity 為 1，global admission capacity 為 50,000。Seed 與 verify concurrency 為 48。

Workload 為 50,000 users × 200 requests，共 10,000,000 筆交易。每帳戶初始 balance 為 100，每人以 amount 1 的 Credit 與 Debit 交替各 100 次。每個 request 必須 await reply 後才送下一筆。

沿用 wallet schema、single account owner lock、read/compute/commit 順序、兩個 SELECT 與一個 single-partition UNLOGGED BATCH。不得增加 LWT 或使用 authoritative balance cache。防重 key、replay、business rejection、version/write clock 及完整 ledger verification 沿用既有 wallet 規格。

## Consistency 與 durability

只有 RF 與 wallet read/write CL 改為 1：

| 設定 | 本 case |
| --- | --- |
| Keyspace replication factor | 1 |
| Wallet read consistency | `ONE` |
| Wallet write consistency | `ONE` |
| `durable_writes` | `true` |
| `commitlog_sync` | `batch` |
| `commitlog_use_o_dsync` | `false` |
| Write acknowledgement | commitlog batch fsync 後 |

RF1 只有一份 replica。Node 暫時離線時，該 node 上的 partitions 不可用；永久磁碟遺失時，沒有 peer replica 可復原資料。Commitlog batch fsync 的 ack 保護單一副本的本地 commitlog，不提供 RF3 的複本冗餘。

RF1/CL1 的讀取不會從其他 replica 讀到舊資料，因為該帳戶沒有另一份 replica。但 CL1 不支援多個 wallet service writer 的協調或 fencing。服務仍維持單 writer 與 account owner lock。

## 固定 server 與主機 profile

ScyllaDB 固定使用既有 2026.1.14 image `scylladb/scylla@sha256:333b9ab3a3214c7f98af100711c51df7f58964e8227e6d26050e889ebb216df1`。沿用既有 S4 CPU affinity 與 SMT 配置：node A CPUs 0,1,8,9；node B CPUs 2,3,10,11；node C CPUs 4,5,12,13；service/load/monitor CPUs 6,7,14,15。三個 instance 共用 host SSD。Server timeout、driver timeout、commitlog profile、strict preflight、required metrics、連線稽核及 owner-validated cleanup 均維持既有設定。

不得因 RF1 而修改 retry/speculation、timeout、CL contract、batch statements 或 acknowledgement path。未知 write outcome 必須保留為 `CommitOutcomeUnknown`；不得重送並假定未提交。

## 結果與比較限制

主要參考為最近一個相同 per-user worker、C=50,000、S4/P4/D48 的 RF3/R3/W3 run：`run-20261012T071303Z-a7f4b0a6`。該單一 trial failed，在 59.4758 秒 window 收到 1,886,870 replies、1,836,955 applied results 及 49,915 個 `CommitOutcomeUnknown`。它不是有效的成功性能 baseline；比較時必須明確標示其失敗狀態。

較早的 S4/C48/P4/D48 兩個 full-pass trials 可作輔助背景。它們使用 C=48、round-robin routing，且受測 binary 不同。不得把它們當作與 RF1 case 完全受控的比較，也不得只依 RF 差異歸因 throughput 或 latency 變化。

不得假定 RF1/CL1 能得到三倍效能。50,000 個 in-flight requests 也不保證通過。若 timeout 或錯誤發生，保留原始 error kind、driver/server 訊息、metrics、verification 與 cleanup evidence；不自動 retry，不調高 deadline，不改 CL，也不更換 workload。

本 case 必須完整驗證所有 50,000 個 accounts 與 10,000,000 筆 ledger rows。若 request、verification、required metrics 或 cleanup 有任一項失敗，該 case 標為 failed，不納入成功性能結果。
