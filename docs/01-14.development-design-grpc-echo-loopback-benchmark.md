# Tokio 同主機 gRPC Echo 基準測試

## 範圍

此基準測試量測同一主機上兩個 Tokio 程序之間的 unary gRPC echo 呼叫。Client 與 server 使用明文 IPv4 loopback 位址 127.0.0.1 通訊；parent 程序負責啟動、觀察並停止兩個 worker。測試不包含 ledger 工作負載、磁碟業務工作負載、TLS、外部請求來源、實體 NIC、RSS、實體鏈路速度，也不對實體網路作推論。

Protobuf service 與生成程式碼只供此基準測試使用。`benches/proto/grpc_echo.proto` 是 schema，`benches/support/grpc_echo_loopback.rs` 是檢查進版控的 tonic/prost 生成模組，使用 tonic-build 0.12 與 prost-build 0.13 產生。重新生成時，使用相同版本的 generator 對 schema 執行 protoc，並以產生的 `ledger.loopback.v1.rs` 取代檢查進版控的模組。生成碼保留在 bench 目錄，不讓其他 package build 依賴 protoc。`benches/grpc_echo_loopback.rs` 包含 parent、client、server 三種程序角色。Server 原樣回傳 request ID 與 payload，並附上 handler 進入及離開時的 CLOCK_MONOTONIC 時間戳。Client 會在每次連線初始化、warmup 與量測呼叫後檢查 ID 和每個 payload byte。

## 負載與 channel 配置

預設矩陣使用 128 與 4096 byte payload。每種 payload 都會先以固定 100 requests/second 執行 baseline，再依序測試 1、2、4、8、16、32、64、128、256 個 closed-loop coroutine。預設 warmup 5 秒、量測 20 秒、重複 3 次。

Baseline 建立一個獨立 tonic Channel；Client 複製的 generated stub 共用此 channel。預設 channel 數為 1。`--channels 2`、`4` 或 `8` 會明確建立彼此獨立的 channel；Parent 透過 `ss` 計算連到該 trial port 的 established TCP connection，數量不符就中止。只有在單一 channel 的結果顯示飽和，或多 channel 本身就是明確實驗目的時，才加入額外 channel。

Closed-loop 負載會維持恰好 C 個 request coroutine 執行。每個 coroutine 收到 echo response 後才送出下一次呼叫，因此同時未完成的工作不會超過 C。固定速率 baseline 以計時器依指定速率送出呼叫，並將未完成呼叫上限設為 256；錯過的 timer 時槽會計數，不會累積成突發負載。Client 宣告 ready 前會完成並排空 warmup 呼叫。量測的 issue window 結束後，Client 停止送出新請求並排空有限的未完成呼叫。`issue_window_s` 是從 ready 到停止送出的時間；`completion_window_s` 從 client phase 開始算到最後一個已排空的 response；`drain_s` 是停止送出到最後一個 response 完成的時間。Completed RPS 以完成呼叫數除以 `completion_window_s`，因此分子與分母使用相同時間範圍。

## 延遲與量測儀器

Client 在呼叫 generated client method 前記錄 t0，收到 response 後立即記錄 t3。Handler 進入時記錄 t1，回傳前記錄 t2。所有程序共用 Linux CLOCK_MONOTONIC 時鐘。每個 response 都必須符合 t0 <= t1 <= t2 <= t3，否則中止該 trial。

Measured client workers 會在各自的 coroutine 內累積延遲樣本；JoinSet 收回 worker 結果後，parent load future 再合併樣本計算分位數。Fixed-rate task 也透過 JoinSet 傳回單次樣本。每個 RPC completion 不會競爭共用 latency mutex。

基準測試會列出端到端延遲 (t3-t0) 及 t0-t1、t1-t2、t2-t3 各階段的 mean、p50、p95、p99、p99.9。t0-t1 和 t2-t3 包含 tonic/HTTP2 framework 工作、本機佇列與排程，以及 loopback transport；它們不是純網路傳輸時間。t1-t2 是 handler 執行時間，不代表 server 程序的全部成本。每個 request 都會記錄四個時間點。這個 instrumented 模式會增加 clock read、response 欄位與逐呼叫樣本收集成本，因此量到的是含儀器負擔的延遲。

Client 使用 cpu-time::ProcessTime 記錄 client phase 開始至最後 drain 完成的程序 CPU 時間。在最後 response 與所有 worker join 完成後，client 先記錄 CLOCK_MONOTONIC completion timestamp，再立即取 ProcessTime delta，兩者都在延遲樣本合併、排序與摘要前完成；Client core equivalent 以相同 completion window 作分母。heartbeat stop 在此 endpoint 發出，PHASE_END 隨即送出並 flush，然後才合併及排序延遲樣本。Parent 在送出 START 前及收到 PHASE_END 後讀取 server 的 `/proc` process CPU ticks；CSV 會記錄 parent wall window 及 sample 相對於 client CLOCK_MONOTONIC phase 邊界的正負 offset，以呈現控制訊息與取樣造成的時間差。Server core equivalent 以 parent sample wall window 為分母，不使用 client window。Process stat CPU ticks 受 USER_HZ 精度限制。這些值描述個別程序，不代表整台主機的使用率。

Client 與 server 的 Tokio runtime worker thread 數等於各自分配的實體核心數：預設 3/3，也可選 2/4 或 4/2。Client/server affinity mask 會包含每個分配核心的兩個 SMT sibling。Parent 在量測期間取樣各程序 RSS 與 `/proc/PID/io` counter，也記錄 loopback bytes/packets、目標 block device busy counter、整體與每核心 CPU tick。每核心 `softirq_pct` 是該核心 `/proc/stat` softirq tick 增量除以該核心總 tick 增量。約每秒執行一次 `ss -tinH` snapshot；CSV 記錄取樣到的 Send-Q、Recv-Q 最大值，各 trial diagnostic log 保留符合 trial port 的 socket/TCP_INFO 原始行。兩次取樣之間的 queue peak 可能不會被捕捉。

Client runtime 內有一個 1 ms Tokio heartbeat，記錄至最後 response 完成 endpoint 為止的 timer lateness；client 在該 endpoint 發出 stop 並 flush PHASE_END，之後等待 heartbeat task 結束，再計算延遲摘要及送出 RESULT。此基準測試只有一種 timing mode；heartbeat 與逐呼叫儀器都會套用於每個 trial。

## CPU 綁定

執行前會檢查主機 CPU 配置。CPU ID 0..7 必須是八個實體核心，8..15 必須分別是它們的 SMT sibling。預設 3/3 配置將 client 綁定到 0,1,2,8,9,10，server 綁定到 3,4,5,11,12,13。實體核心 6、7 與 sibling 14、15 不分配給 benchmark worker，留給 monitor 與 OS 活動；Parent monitor 由主機排程。`taskset` 負責綁定 workers，Parent 透過 `/proc/PID/status` 檢查各 worker affinity，並記錄 CPU mask。主機拓樸不符或綁定失敗時會中止。

`--cpu-layout 2/4` 與 `--cpu-layout 4/2` 是明確指定的替代配置，總共仍使用六個實體核心，並讓核心 6、7 不分配給 workers。只有當預設 trial 的程序 CPU 資料顯示有調整 CPU 分配的研究問題時，才比較這些配置。

## 閒置前置檢查與輸出

每個 trial 開始前先取樣 3 秒閒置狀態。預設門檻為整體 CPU busy 不超過 10%、目標 block device busy 不超過 5%、MemAvailable 至少 512 MiB。觀察開始與結束時，benchmark port 都必須沒有使用。每次觀察期間的背景 loopback 流量上限為 1 MiB 與 RX/TX 合計 4096 packets；有限門檻可容許無關的少量主機流量，同時偵測繁忙的本機網路。每次嘗試及門檻結果都會追加至 `preflight.log`。不符合門檻時會重試，直到 `--preflight-timeout-ms`（預設 60 秒）到期後中止。CPU、disk 或 loopback counter 無法讀取時也會中止。

每次執行都會在 `--output-dir`（預設 `target/grpc-echo-loopback`）下建立唯一目錄，不會覆寫既有結果。目錄包含 `results.csv`、`run.txt`、前置檢查嘗試紀錄，以及每個 trial 一份原始診斷 log。CSV 包含各階段延遲分布、速率與時間範圍、client/server 程序 CPU 與 RSS、程序 I/O counter、loopback counter、TCP queue 取樣、CPU 配置與前置檢查證據。

Smoke 範例：

```sh
cargo bench --bench grpc_echo_loopback -- --payload-sizes 128 --concurrencies 1 --modes closed --channels 1 --warmup-seconds 0.2 --seconds 1 --repetitions 1 --output-dir target/grpc-echo-loopback-smoke --preflight-observation-ms 3000 --preflight-timeout-ms 60000
```

只有本機程式 smoke check 可以縮短 preflight observation；benchmark 執行時請使用預設 3 秒。不要為了取得結果而放寬 CPU 或 disk 門檻。
