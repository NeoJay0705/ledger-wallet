# Tokio 多分片 Ledger Pipeline 基準測試設計：S2／S4 與 RocksDB 配置

## 目的與範圍

本文件定義新的 `ledger_pipeline_sharding_tokio` 基準測試，用來比較 2 與 4 個 shard，以及共用單一 RocksDB 或每個 shard 使用獨立 RocksDB 的組合；每個 shard 使用相同的 transaction-index 查詢設定 `Chunked { group_size: 256, max_in_flight: 4 | 8 }`。完整 pipeline 會在前景請求期間同時執行 projector、watermark 與 safe GC。

正式矩陣只有 S2、S4 及下表八種組合，每種組合執行三個輪替順序的 repetition，共 24 個 fresh trials。每個 trial 執行 10,000,000 筆 client request，因此完整矩陣共 240,000,000 筆。此工作不重跑 S1，也不加入其他 shard 數或查詢 concurrency；本設計不以兩個 concurrency 點宣稱已找到飽和點。

Benchmark 已實作並完成本次正式驗證；矩陣結果與限制見 [canonical report](../benches/ledger_pipeline_sharding_tokio_report.md) 及 [run archive index](../benches/data/ledger_pipeline_sharding/run-1790925219743034498/evidence_archive.md)。新 target 使用獨立的 `benches/ledger_pipeline_sharding_tokio.rs`，重用既有 pipeline helper 的請求、projection、watermark、safe-GC 與 recovery 語意；helper 抽取保留既有 benchmark 行為，新 target 另加 logical request ID、shard ID 及 per-batch/per-shard 遙測，既有 target 的預設值、行為與報告不變。

## Client 負載、路由與序列

每個 trial 固定 50,000 個全域使用者 coroutine，每位使用者依序送出 200 筆 request，同時最多一筆 outstanding，共 10,000,000 筆。Credit 與 debit 各占 50%，amount 為 1，history 為 0。所有 request 使用固定全域 logical IDs；依 `account_id % S` 將帳戶路由至 S 個 shard，故同一帳戶的操作順序不變。使用者、request 與 seed 依 shard 均分。

計時前，每位使用者在其所屬 shard 執行三筆 seed：credit 100、credit 1、debit 1。Seed 不計入 client window；負載前後每位使用者餘額皆為 100。每個 shard 有獨立的 sequence namespace，無論 shard 共用 DB 或各用 DB 都相同。預期 S2 每 shard 最終 sequence 為 5,075,000，S4 每 shard 為 2,537,500；跨 shard sequence 數合計為 10,150,000。不同 shard 之間不建立全域交易順序。

每 shard 各有一個 bounded request queue；各 queue 容量由全域 50,000 拆分，即 S2 每個 25,000、S4 每個 12,500。每 shard 最大 batch 為 2,048 筆，第一筆 dequeue 後最多等待 5 ms 組批。50,000 個 coroutine 各最多一筆 outstanding request，queue slots 總量也是 50,000；此閉迴路負載主要量 buffered backlog 與 pipeline，不代表持續超出 queue capacity 時的 enqueue backpressure 性能。餘額使用 `PerBatch`。每個前景 batch 的 ledger、transaction index、變更餘額及 latest sequence 必須由同一個啟用 WAL、`sync=true` 的原子 WriteBatch 持久化，成功後才發布記憶體狀態。

每 shard 的 index 查詢 group size 固定為 256，`max_in_flight` 為 P4 或 P8。此上限套用在每個 shard 的前景 batch；全域同時可提交的查詢群組理論上限為 `S × P`（S2/P4 為 8、S2/P8 與 S4/P4 為 16、S4/P8 為 32）。這不是 Tokio async worker 數或 CPU core 數。整個 process 固定 4 個共用 Tokio async workers；blocking pool 使用沿用的 Tokio 設定。每個 child 共用 RocksDB default Env，LOW/HIGH thread pools 設為 6/2；這是共用 Env 的設定，不是實際活動 thread 數或 CPU 配額。每 DB 的 `max_background_jobs` 另依資源表設定。記錄 per-batch 與 per-shard 可觀測的已提交／未收集群組峰值及實際執行 query jobs 峰值；現有 metrics 不提供全域同時 peak，因此全域實測 peak 記為 NA，不把 per-shard peaks 相加。

## 背景工作與儲存配置

所有 shard 在測量及結算期間都啟用既有 projector、watermark 與 GC 路徑。每 shard projector batch 為 256；watermark tick 為 100 ms、retention 為 500 ms；GC batch 為 256。有進展時 GC 持續 catch up 並 yield；受阻或無工作時 sleep 100 ms。沿用 producer 提供且同一次請求內不變的 `transaction_at`，以及既有 admission／batch gate、projection durability 與 safe-GC safeguards，不加入 application-level WAL。測量期間 fresh request 的 `transaction_at` 在 admission 前立即產生，進入 queue 後不再改變。

共用 DB 配置在同一 RocksDB 中以 shard namespace 隔離 ledger、transaction index、餘額及 sequence；獨立 DB 配置為每 shard 一個 DB。所有 DB 位於同一 filesystem。兩種配置的總 configured resource budgets 固定如下：

| DB 配置 | DB 數 | 每 DB write buffers | 每個 write buffer 大小 | 每 DB block cache | 每 DB `max_background_jobs` | 配置合計 background jobs |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 共用 DB | 1 | 2 | 64 MiB | 128 MiB | 8 | 8 |
| S2 獨立 DB | 2 | 2 | 32 MiB | 64 MiB | 4 | 8 |
| S4 獨立 DB | 4 | 2 | 16 MiB | 32 MiB | 2 | 8 |

總 configured write-buffer budget 為 128 MiB，總 configured block-cache budget 為 128 MiB，`max_background_jobs` 的配置總額為 8。每個值按 DB 數與兩個 write buffers 平分。每個 child 的 RocksDB default Env 共用 LOW=6、HIGH=2 thread pools；所有 DB 共用這兩個 pool，不能把 pool 設定解讀為每 DB 各有一份。這些設定不是 process RSS 上限、硬性 active-thread 上限或 CPU 配額；RocksDB flush／compaction 的最低工作需求及 native Env 都可能影響實際活動。記錄各唯一 DB 的 RocksDB counters 及背景活動。獨立 DB 的每 DB memtable 較小，可能增加 flush 頻率；共用 DB 使用同一 WAL 寫入協調，獨立 DB 則各有 WAL 並增加 DB metadata。這些差異是本矩陣中 DB 配置的一部分。

CPU affinity 沿用程序繼承值，不為 shard、Tokio、blocking pool 或 RocksDB thread pin CPU。主機有 8 個 physical cores 與 16 個 logical processors，但本 benchmark 不保留或專屬配置其中 4 個 CPU 給 Tokio workers。不得將 process CPU 總量拆稱為各 shard CPU，也不得僅由 CPU core equivalents 推論 physical-core 飽和。

## 前置檢查、公平性與量測範圍

Run setup、trial setup 與測量開始前執行 strict preflight：觀察 3 秒，CPU busy 不高於 10%，目標裝置 busy 不高於 5%，最多等待 60 秒；同時檢查依全矩陣與 trial 狀態估算的記憶體及磁碟需求和 reserve。不得放寬門檻以取得結果。報告記錄每次 preflight 的觀察值、等待時間、可用資源及需求估算。

所有 trial 使用相同全域負載、queue／batch 參數、worker 數、background 設定、查詢 group size、總 configured RocksDB buffers/cache/background jobs，以及同一 filesystem。S2/S4 的 per-shard 負載依 shard 數均分。Shared 與 dedicated DB 的 RocksDB 設定依上表平分總額。記錄各 shard 的實際 request、seed、batch、query group、sequence 與 backlog 數，讓負載及進度是否均分可被檢查。

Global start barrier 釋放前啟動 client window 計時；window 結束於最後一個 reply 返回。Reply 在前景原子 sync WriteBatch 成功、memory publish 完成且結果被 client 觀測後返回，不逐筆等待 projection 或 GC。client RPS 為 10,000,000 除以此 global client wall。另報各 shard 在同一 global window 內完成的 request 數與每 shard RPS。不要把各 shard 的 RPS 當成不同時間窗口來相加或比較。Settlement 包括 background catch-up/drain；workers 收集後，finalizer 依 shard 順序執行最後 watermark 與 safe GC。有限 10M load drain rate `10,000,000 / (client_wall + settlement_time)` 受這項 settlement/finalizer 政策影響，不代表 concurrent GC worker 容量或 steady-state capacity。

Request latency 依全域 logical request ID 的 deterministic hash stride 64 抽樣。每個 trial 將所有 shard 的原始 request latency samples 合併後，以 nearest-rank 計算全域分位數並記錄樣本數；不得先算 shard percentile 再平均。另列各 shard 的分布作負載診斷。每 shard 全部 batch metrics 及 lookup-group metrics 都保留；projector、watermark、GC 保留 stage summaries 與 background time series。每 trial 有 36 個固定 stage identities：request 7 個、index batch/group 17 個、projector 4 個、watermark 4 個、GC 4 個；沒有事件的 stage 記 count=0、量值為 NA。Request/index raw stage samples 沒有逐筆 completion timestamp，不補造時間；background event 以實際完成時間分類，client-window CSV 只納入不晚於最後 reply 完成的事件。Settlement 只記總耗時與最終 progress，不提供 post-window 逐段 CPU、IO 或 latency。

CPU 與 CPU µs/request 是 client window 內整個 child process 的 CPU delta，包含 Tokio、blocking pool、RocksDB native 與 background threads，不包含 settlement CPU，也沒有 per-shard attribution。4 個 async workers 不是 4 CPU quota；host 有 8 physical cores／16 logical processors。CPU、process IO、device IO、progress 與 RocksDB counters 保留相對 client end 的 offset，但 IO 計時邊界不同：Process/device/RocksDB IO 起點在 seed 與 measurement preflight 後、queue/background setup 與 client tasks spawn 前，終點在 last reply 後。Target 是 logical mounted partition `sdb2`（8:18），counter 包含主機其他 IO，並非 per-file/per-shard 或全部 physical disk 的精準歸因。Process/device counters 各取一次；RocksDB stats 依 unique DB 取一次，共用 DB 不乘 shard 數，dedicated DB 才合計不同 DB。WAL sync 是觀測值，RocksDB 可能協調同 DB 的並行同步 WriteBatch，不假定 sync 數等於 batch 或 shard commits 數。Native operation durations 可重疊。VmHWM/RSS 在 client end 附近按 `storage_sample_offset` 讀取；涵蓋 startup 與 seed，為截至讀取時的 process lifetime peak，不包含後續 settlement、recovery 或 artifact-writing peak。DB bytes 則在 recovery/integrity 驗證與關閉 unique DB 後、刪除 scratch 前量得。

每 trial 的 request、batch、group 及背景指標均附樣本數或事件數。三個 repetition 的比較先保留 trial 級數值，再報各 trial 結果的 median、min、max；每 trial 的 request percentile 在 trial 內由 nearest-rank 得出，再彙整三個 trial percentile 的 median/min/max。不得跨 trial 合併原始 latency samples，也不得平均不同 trial 的 percentile。

## 結算與正確性閘門

Client end 時在背景 workers 仍運作下，逐 shard 讀取 latest sequence、source durable projected sequence、destination sequence、watermark、GC prefix 及 backlog。需符合 seed sequence 不高於 source projected sequence、不高於 destination sequence、不高於 latest sequence；GC prefix 不得超過其 durable projection 與餘額 coverage。Client end 的 source、destination 與 latest 允許有 backlog，需分別報告，不得以單一合併值替代。

Settlement 單獨計時，包括 background catch-up 與 drain。Background workers 收集後，finalizer 依 shard 順序執行最後 watermark 與 safe GC；因此 finite drain rate 受有限 settlement/finalizer 政策影響，不代表 concurrent GC worker 容量或 steady-state throughput。每 shard 最終都必須滿足 source durable projected sequence、destination sequence 與 latest sequence 相等。Boundary timestamp `W` 是時間戳，與 ledger sequence 使用不同單位；驗證 `W` 等於保存的 watermark/boundary，並以 companion `target_sequence` 確認 boundary ordinal 不超過 durable projected sequence。GC prefix 不得超過 boundary target sequence，且 projection 與 durable balance coverage 均須涵蓋此安全連續 prefix，並符合 retention。不得為了清空資料而強制 compaction。對各 shard close/reopen RocksDB 前，先關閉所有 source clones 及 unique DB handles；共用配置只 reopen 該唯一 DB 一次，dedicated 配置各 DB reopen 一次。重新掛接相同的 in-memory `MockDB` instances，驗證所有 shard namespace、sequence、seed/history 與每位使用者最終餘額。

`MockDB` apply 成功依既有測試契約視為 durable，close/reopen 驗證重用相同 instance；此流程不代表真實外部 projection DB 的程序 crash 或斷電 durability。若前景寫入、背景工作、reply、integrity 或必要 metrics 失敗，trial 必須 fail closed，不產生可用的效能結果。停止 client 並阻止新工作，釋放或解除會阻塞的 fence，排空本 trial 擁有的 async workers、query groups、blocking closures 與 native IO 後，才能 close 或刪除 DB。不得刪除仍有開啟 handle 的目錄。正常成功或已完成 drain 的失敗路徑，只清理由本 run 擁有的 DB／scratch；若發生非預期取消或無法確認 workers/handles 已停止，保留 scratch 以免刪除仍開啟的 DB。原始 logs 與 CSV archive 保留。
