# batchsweep – design and tasks (rev 2, after review: APPROVE-WITH-CHANGES, all changes applied)

New files only: scripts/batch_sweep.py, scripts/test_batch_sweep.py, artifacts/sweep-imports.json (import mapping, data).

## Wrapper contract (fixed args)
Both wrappers: positional output dir that must NOT exist, plus `--cpus C --users 100000 --requests-per-user 40 --queues 256
--batch-max N --sample-interval-ms 250`.
PG only (scripts/batch_queue_run.py): `--mode txn` and `--pg-conf wal_buffers=256MB --pg-conf max_wal_size=8GB --pg-conf track_wal_io_timing=on`.
TiDB (scripts/txn_tidb_run.py): no --mode / --pg-conf. (PG defaults would otherwise be 1M requests / 1000 ms sampling.)

## Attempts (immutable) and status
Each wrapper execution is an attempt with its own new dir `artifacts/sweep-<db>-c<C>-bm<N>-a<k>` and a role: primary,
flush_rerun, replicate. Never reuse a dir. An attempt is OK iff wrapper exit == 0 AND cleanup.json status == success AND
summary.json parses (valid=true). Failures (no summary, or cleanup residue) are recorded in the CSV with exit/GO-reached/cause and
carry no metrics. Cleanup residue stops the campaign before the next benchmark. Resume state comes from the CSV, never from
"summary.json exists".
Primary row per batch = first OK primary attempt; if its flush await > 2 ms, the flush_rerun (one only) becomes the primary and
the flagged first attempt stays listed. Replicates never change the primary; they are reported beside it.

## Known tooling race
A wrapper exit caused by monitor.Sampler `client proc ... Permission denied /proc/<pid>/io` at client exit (cause=sampler) is a tooling
defect, not a result: the driver retries it in a fresh attempt dir (max 2 extra) and it never counts as a TiDB terminal failure; failed
attempts stay in the CSV.

## Imported (reused) points – explicit, with provenance, flagged `imported`
artifacts/sweep-imports.json maps series+batch to sources; extraction supports (a) summary.json, (b) result.json + a separate
resource-summary.json. Approved imports: PG c4 4000 = txnpg4-bm4000-rerun/summary.json; PG c4 8000 = txnpg4-bm8000-rerun/client/result.json
(client numbers) + txnpg4-bm8000/resource-summary.json (resources; approved exception); TiDB c4 4000 = txntidb-c4-bm4000-v2/summary.json;
TiDB c8 4000 = txntidb-c8-bm4000-v2/summary.json. Imports yield CSV rows (idle evidence: "unavailable (historical, approved)"; not fabricated).

## Idle gate (inside batch_sweep.py; before EVERY new attempt)
Sample /proc/stat twice 5 s apart: per logical CPU idle% = (idle+iowait)/total. Per-process CPU = delta (utime+stime) of
/proc/<pid>/stat over the SAME 5 s interval (not ps %CPU). Pass iff every logical CPU >= 90 % idle (relaxed from 95 by user after quitting agy/chrome; interactive pi session ~10 % remains) and no process > 30 % of one CPU,
excluding only the driver's own PID and its checker threads/children (not Python processes in general). On fail: wait and re-check
for up to 60 s, then abort that attempt (row status gate_failed, evidence kept). Evidence `<attempt dir>-idle.json` (per-CPU idle,
top 5 processes by delta CPU computed over ALL processes). Pure function `evaluate(cpu_idle, proc_cpu, min_idle=90, max_proc=30)`.
`batch_sweep.py --idle-probe` runs the gate once and prints it: used BEFORE the campaign to prove the thresholds are achievable on this
host (background tools pi/agy/chrome use ~5-10 %). If repeatedly failing: stop and ask the user (quiesce or change the requirement);
never relax silently.

## Series driver
`batch_sweep.py run --db pg|tidb --cpus 4|8 [--batches ...]` serial, in ascending order; default batches 50,100,250,500,1000,2000,
4000,8000 (TiDB: 50..4000, then 6000, then 8000). Per point: skip if the CSV has an OK primary (incl. imported); else gate -> wrapper
(timed with wall clock) -> row. Flush await > 2 ms -> one flush_rerun. PG: a failed point is recorded as incomplete and the series
continues. TiDB: setup-phase failure (before GO: topology/socket/gate) is recorded and the point is retried by a fresh attempt
only by explicit re-invocation; a post-GO failure ends the series permanently (also on resume), recorded with the cause
(memory 8176 / timeout / sampler / cleanup distinguished from failure.txt, client/invalid.json); 8000 runs only after a valid 6000.
`batch_sweep.py replicate --db .. --cpus .. --batches a,b` adds replicate attempts in fresh dirs (a = saturation point,
b = its predecessor in the grid, or its successor if it is the smallest point).
`batch_sweep.py summarize [--prefix ..]` prints markdown per series: batch, windows, rps_request, duration, p50/p95/p99/max s,
db(TiKV) cores, tidb-server cores, flush await, flags (imported, flush_rerun, replicate RPS beside primary, incomplete), and the
observed-grid saturation point = smallest batch whose primary RPS >= 95 % of the series' maximum primary RPS (if it is the largest
tested batch it is labelled observed-grid saturation, not a proven plateau). Replicate differences are reported as stability notes.
CSV `artifacts/sweep-<db>-c<C>.csv` columns: batch, role, attempt_dir, status, exit, go_reached, cleanup, wall_s, duration_s,
rps_request, p50_s, p95_s, p99_s, max_s, windows, db_cpu_cores, tidb_cpu_cores, flush_await_ms, imported, cause.

## Field mapping (summary.json; null/missing never becomes 0 – a missing flush await is flagged and blocks "OK")
| value | PG | TiDB |
|---|---|---|
| duration, rps | duration_s, rps_request | same |
| latency (s) | latency_us.{p50,p95,p99,max}/1e6 | same |
| windows | outcomes.windows | outcomes.windows |
| DB CPU cores | resource_summary.means.db_cpu_core_equivalents | resource_summary.tikv_cpu_cores_mean |
| tidb-server cores | n/a | resource_summary.tidb_cpu_cores_mean |
| flush await ms | resource_summary.means.device_flush_await_ms | resource_summary.device_means.device_flush_await_ms |
