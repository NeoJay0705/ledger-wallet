本設計沿用 [01-42 memory-state LWT 需求](01-42.raw-requirement-scylladb-memory-lwt-benchmark.md) 和 [01-43 memory-state LWT 設計](01-43.development-design-scylladb-memory-lwt-benchmark.md)。不改 Rust service、store、schema、transaction path 或 retry/deadline contract。本工作只定義四個 run profiles、每 case 的 strict preflight、結果驗收及停止規則。

## Case matrix

固定 `S=1`，worker count `C` 代表 DB worker 數與應用層 in-flight 上限。`P=ceil(C/50)` 是每 node、每 shard 的 data connection target，`D=3×S×P` 是三個 node 的 target 總數。

| Case | S | C | P | D | Users | Requests per user | Total requests |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 128 | 3 | 9 | 1,024 | 1,000 | 1,024,000 |
| 2 | 1 | 256 | 6 | 18 | 1,024 | 1,000 | 1,024,000 |
| 3 | 1 | 512 | 11 | 33 | 1,024 | 1,000 | 1,024,000 |
| 4 | 1 | 1,024 | 21 | 63 | 1,024 | 1,000 | 1,024,000 |

每個 case 各執行一次。各 case 使用新 keyspace 和新 owned node data。不要把四個 case 合併為一個 run 後只做一次 gate；strict preflight 必須在每一個 case 啟動前獨立通過。本次不新增或執行 live integration/fault tests，不執行 RF1、S4、額外 repeats 或其他 pool 組合。

## Strict preflight 與啟動

Runner 的 `formal` mode 綁定舊有 27-case matrix，不用它啟動這四個 custom cases。Target-only supervisor 在每次呼叫既有 `strict_formal_preflight` 後，才用 `pilot` mode 啟動單一 case。不得複製或放寬 gate 條件。Preflight 輸入包含該 case 的正式 workload estimate、目前 output filesystem 與既有 host CPU、memory、device 及 disk samples。

每 case 使用以下命令形狀，並將 `C`、`P` 分別替換成 matrix 中的一組固定值：

```bash
python3 benches/scylla_wallet.py \
  --mode pilot \
  --shards 1 \
  --workers C \
  --per-shard-pool P \
  --worker-routing round-robin \
  --users 1024 \
  --requests-per-user 1000 \
  --repeats 1 \
  --skip-build
```

Supervisor 保存每 case 的 strict preflight、argv、source/binary hashes、PID、開始與結束時間、runner status、trial ID 和 cleanup status。若 preflight 不通過，不建立 cluster。若 trial failed、relaxed、invalid 或 cleanup dirty，不啟動後續 cases，也不 retry。

## Runtime profile 與 workload 驗證

啟動後核對三個 node、pinned image `scylladb/scylla@sha256:333b9ab3a3214c7f98af100711c51df7f58964e8227e6d26050e889ebb216df1`、ScyllaDB `2026.1.14` release、`S=1`、RF3、`durable_writes=true`、read/write CL `THREE`、LWT serial CL `LOCAL_SERIAL`、`commitlog_sync=batch`、`commitlog_use_o_dsync=false`，以及 write acknowledgement 發生於 commitlog batch fsync 後。再核對所選 pool target、schema agreement、`system.clients` control/data client 分類、pool-ready event 與 before/after connection audits。

沿用三 node CPU affinity：node A=`0`、node B=`2`、node C=`4`；service/load/monitor=`6,7,14,15`。維持既有 pinned image、commitlog 設定與 deadlines。不要假定 batch window 有固定等待時間；不將 commitlog flush count換算為每 request fsync。

每個 case 在 measurement gate 前 seed 1,024 accounts 並 preload cache。Measurement window 中，1,024 個 users 各送 1,000 個 amount 1 的 Credit/Debit alternating requests。每個 client 等待目前 request reply 後才送下一筆。Round-robin worker routing 不改變 account owner lock；同帳戶交易仍依序計算和提交。

預期結果是每帳戶 1,000 筆 `Applied`、最終 balance 100、version 1,000、logical clock 1,000，且恰有 1,000 ledger rows。總計 1,024,000 replies、applied results 和 ledger rows。`verify_account` 的每帳戶 1,000 row 上限不變；逐帳戶核對 cache、static state、完整 ledger 與總數。

## 驗收、metrics 與停止規則

每 case 必須同時符合以下條件才能記錄為 `passed`：

| 面向 | 驗收值 |
|---|---|
| Strict gate / required metrics | 全部有效 |
| Effective profile | RF3、read/write `THREE`、serial `LOCAL_SERIAL` |
| Pool | 實際 target 為 `D=3×S×P`，audit 無 mismatch |
| Requests | 1,024,000 accepted、applied、replied |
| Driver accounting | 1,024,000 queries；0 measurement SELECT |
| Errors | 0 errors、retries、request timeouts、connection timeouts、unknown outcomes |
| Verification | 1,024 accounts 與 1,024,000 ledger rows 全部符合預期 |
| Cleanup | 本 trial owned containers、network、data 全部 clean |

儲存 window metrics 包括 E2E RPS、p50/p95/p99、CPU、process I/O、pool min/max/samples、CQL peak、busy/idle workers，以及每 node/shard 的 commitlog flushes、bytes、cycles、allocations 和 pending metrics。失敗時保留最先錯誤、driver counters、raw server metrics、已接受請求的結果統計、錯誤樣本、partial verification 和 cleanup evidence。

Paxos 和 commitlog group commit 可能有額外內部操作。一次 client CQL LWT 不等於單次 Paxos 寫入或每 request fsync。Commitlog counters 用於觀察 node/shard 工作量，不證明單筆交易各自完成一次 fsync。

`C`、`P` 同時依公式改變。即使四 case 全部通過，也只能報告這四個配置組合在單次 1,024,000-request window 的結果。不能推導單獨增加 worker 或連線數的因果效應，也不能宣稱穩態、統計顯著或 27-case formal 完成。

## Execution flow

```text
input
  -> run_clients
  -> run_client (one account; await reply before next request)
  -> Service::submit
  -> account owner lock
  -> worker_loop (round-robin shared worker pool)
  -> process_job
  -> read cached AccountState and compute next result
  -> ScyllaStore::commit
  -> one conditional INSERT ... IF NOT EXISTS
  -> LOCAL_SERIAL / regular CL=THREE / acknowledgement
  -> publish cache after Applied acknowledgement
  -> reply

after all replies
  -> drain service
  -> verify 1,024 account states and 1,024,000 ledger rows
  -> keep CLI session open for runner connection/socket audit
  -> release finish gate
  -> CLI exits and closes Session
  -> cleanup only this trial's owned resources
  -> write case and run reports

failure, invalid result, or unknown outcome
  -> stop launching later cases
  -> preserve partial evidence
  -> wait for owned cleanup
  -> report the case as failed; do not retry
```
