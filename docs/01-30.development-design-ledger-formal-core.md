本文件定義可嵌入應用程式使用的 Rust ledger library，以及供本機啟動、停止核心的 CLI。核心直接持有本機 RocksDB，不連接 gRPC 或外部資料庫。現有 benchmark 可保留原始報告和量測來源；新 benchmark 必須呼叫共用核心實作，不能把新程式碼描述成歷史測得的 artifact。

## 目標與邊界

第一版抽取已由 benchmark 驗證過的交易儲存、bounded queue、admission、pipeline 和歷史投影原語，建立可從 Rust library 和本機 CLI 使用的正式核心。交易正確性、重啟恢復、資源有界和失敗時的明確行為優先於宣稱吞吐量或飽和能力。

第一版只提供單機、單一幣別、`u64` 最小貨幣單位的帳本。可設定 shard 數，以及各 shard 共用一個 RocksDB 或各自使用 RocksDB。持久化格式會記錄 shard 數、路由版本和儲存拓樸；現有資料不支援啟動時改 shard 數或改 layout，也不執行 resharding。

範圍外包含 gRPC、外部資料庫 connector、跨 shard 原子交易、複寫、認證、多幣別、匯率和業務帳戶建立流程。注入式歷史儲存介面讓未來 connector 能遵守同一契約，但 mock 或測試 fixture 不等於 production connector。

## 模組責任

Rust crate `ledger_wallet` 目前公開下列 module。`account_store` 位於 `storage` 之下；library API 與 CLI 都使用同一個 pipeline。

| 模組 | 責任 |
| --- | --- |
| `storage` | RocksDB 開啟、schema／layout 驗證、原子同步批次、恢復與關閉。 |
| `storage::account_store` | 帳戶餘額、交易索引、退款狀態及每 shard 最新 sequence 的一致性操作。 |
| `batch_queue` | 容量有界的交易入口、批次收集、逾時 flush 與背壓。 |
| `admission` | 歷史邊界 fence、歷史查詢和新交易入列之間的協調。 |
| `pipeline` | 分片 worker、批次處理、儲存提交、記憶體發布和回覆。 |
| `history` | 可注入、具明確 durability capability 的非同步歷史儲存介面及投影協調。 |
| `config` | 可設定項、保守預設、跨 shard 共用資源預算和持久化格式識別。 |
| `error` | 帶操作脈絡的型別化錯誤與結果未知狀態。 |
| `metrics` | 固定集合的計數器、時間統計、階段分位數和背景進度觀測。 |

主要公開型別為 `ledger_wallet::Pipeline`、`PipelineConfig`、`PipelineError`、`Transaction`、`TransactionKey`、`TransactionStatus`、`TransactionReceipt`、`BalanceReceipt`、`PipelineStatus`、`HistoryStore`、`HistoryDurability` 及 `MockHistory`。`HistoryStore` 是 object-safe async trait；呼叫者需為每個 shard 傳入一個實作。

CLI 只負責載入設定、檢查本機資源、建立／啟動／停止核心及呈現狀態。交易行為由 library 共用實作；CLI 不另寫一套 ledger 邏輯。

## 交易與查詢契約

### 支援的操作

- Credit、Debit 和 Refund 使用整數 `u64` 最小貨幣單位，第一版只有一種幣別。
- Refund 只可成功退回同一帳戶的一筆成功 Debit；同一筆成功 Debit 最多成功退款一次。
- Balance 查詢直接讀取核心的餘額狀態，不經交易 queue，也不建立帳戶。
- 核心沒有帳戶業務建立 API。不存在的帳戶查詢餘額回傳 `0`。
- 對不存在帳戶的第一筆新交易，不論交易最後是成功或業務拒絕，都要在原子提交中建立需要的零餘額狀態和該交易的耐久結果。重播該 key 時回傳原結果，不再次套用交易。
- 缺少帳戶的 balance query 回傳 `0`，不進 queue，也不建立持久化帳戶記錄。

交易 key 為：

```text
(account_id, tx_id, producer_transaction_at_unix_microseconds)
```

時間戳由 producer 提供且提交後不可變。相同 key、相同交易內容是 replay，回傳已保存結果且不配置新 sequence；相同 key、不同內容是 conflict。改變時間戳即形成另一個 key；client 必須保存並重用第一次提交的完整 key，不能把改時間戳當作同一請求的重試。

第一個被核心接受的該 key 會得到明確耐久結果，即使結果是例如餘額不足的業務拒絕。業務拒絕和儲存／協定錯誤是不同類別：前者是已提交、可重播的交易結果；後者不能偽裝成交易結果。

## 分片、佇列與批次

分片由 `account_id % S` 決定。同一帳戶固定落在同一 shard，各 shard sequence 各自遞增；對外識別 sequence 必須連同 shard 一起使用，不能把不同 shard 的 sequence 當成全域次序。Shard 數和路由版本在首次建立資料時保存，重新開啟時必須相符。

同一帳戶依核心接受的 queue 順序序列化。不同並行呼叫的實際接受順序由排程和 queue 決定，核心不承諾等於 caller 發起的牆鐘先後。不同帳戶可並行處理。

第一版保守預設如下：

| 項目 | 預設 |
| --- | --- |
| shard 數 | 1 |
| DB 拓樸 | 所有 shard 共用 DB |
| Tokio async worker threads | 4 |
| 共用 blocking worker 上限 | 32 |
| bounded MPSC transaction queue | 全域 50,000 筆，確定性分配至各 shard，所有 shard 容量總和維持 50,000 |
| accepted／in-flight 請求 | 全域 50,000 筆 |
| batch 收集上限 | 每 shard 2,048 筆 |
| 首筆 dequeue 後 flush timeout | 5 ms |
| transaction index lookup | 每組 256 keys、最多 4 組並行，之後依批次順序套用 |
| history I/O concurrency | 全域 4 |
| source storage batch concurrency | 全域 4 |
| admission／response／history operation timeout | 5 秒／30 秒／5 秒 |
| history retention | 60 秒 |
| retention／watermark tick | 1 秒 |
| projector 與 GC 單次工作上限 | 256 筆，持續追趕；有進度時讓出執行權，被阻擋時等待 100 ms |
| shutdown timeout | 30 秒 |
| RocksDB write buffer／block cache 預算 | 各 128 MiB，全程序共用；dedicated DB 會按 shard 數分配 |
| RocksDB background jobs 預算 | 全程序 8 |
| startup minimum free disk／MemAvailable | 512 MiB／256 MiB；設為 0 只停用對應啟動門檻 |

本機 CLI 建立 Tokio runtime 時使用 4 個 async worker 和最多 32 個 blocking worker。Library 不建立或持有 Tokio runtime，呼叫端負責提供 runtime；這兩個執行緒數不是 `PipelineConfig` 的欄位。

Shard 數、共用／獨立 RocksDB、queue、批次、timeout、history concurrency、in-flight 數和 blocking work 都須有界且可設定。Queue 容量是全域 50,000 筆，依 shard 數確定性分配；每 shard 的 2,048 是 batch 收集上限，並非 queue 容量。需要同時設定全程序資源預算；shared DB 和 dedicated DB 都不能藉由 shard 數增加而讓所有 shard 各自重複取得完整的全域上限。表中的預設是保守起點，不是由現有 benchmark 證明為最佳值，也不是飽和容量保證。完整 library 欄位見 `PipelineConfig`；CLI 可覆寫的啟動設定列於下方。

完整核心 benchmark 的預定固定 workload 為 50,000 users × 每 user 200 筆，共 10,000,000 筆；amount=1 且 Credit／Debit 各半。50,000 是 benchmark workload 的帳戶數，不是執行期固定帳戶限制；正式核心不預先建立或限制在這些帳戶。

## RocksDB 提交與恢復

每個新交易批次透過 RocksDB 同步 WAL `WriteBatch` 原子保存該批交易 ledger record、交易索引、退款 marker、所有 touched balance，以及該 shard 的 latest sequence。第一版不另加一層 WAL。只有同步 WriteBatch 成功後，核心才發布記憶體餘額／交易狀態並回覆已提交結果。

每批保存該批觸及的動態餘額是第一版正式核心的餘額模式。既有 checkpoint benchmark 的歷史模式與報告保留作原樣比較資料，不代表新核心提供該模式；新核心不提供動態 checkpoint 模式。

持久化識別至少包含 schema version 1、routing version 1、shard count、shared／dedicated layout 和相關模式。Service identity 為 OS 隨機產生的 16 bytes；建立或更新 metadata 後同步父目錄。每 shard 的 history destination identity 會先持久化，之後才允許保存 durable projector progress；重開時缺少 identity、destination 不一致或覆蓋範圍不符都 fail closed。

開啟時先檢查設定和 DB metadata，再做 RocksDB recovery 及 ledger、索引、sequence、餘額等一致性檢查。metadata 缺失、版本不支援或拓樸不一致時停止啟動，不推測或自動遷移。第一版不支援 resharding。

正常程序結束不得刪除正式資料。Benchmark 每個 trial 只能建立和清除自己專屬且唯一的 scratch 目錄；不得清除其他 run 或正式資料目錄。

## 歷史投影、watermark 與安全 GC

`history` 提供 object-safe async interface。能力需明確區分 durable 和 volatile，並涵蓋每 shard 身分及進度、連續且冪等的 apply、精確 key 查詢、內容衝突／不存在辨識和退款狀態查詢。Durable backend 必須在同一個原子、耐久操作中保存歷史 row、相關退款狀態和連續 progress；progress 只能涵蓋已完整提交的無缺口前綴。`apply` 成功後的精確讀取必須提供 read-after-write 一致性，不能由落後副本回傳查無資料、舊 row 或未更新的退款狀態。這項一致性也適用於 source GC 之後：歷史 row 或退款證據一旦由 source 清除，目的端不得因 replica lag 暫時查不到。未來真實 connector 必須實作並證明同一組 durability、讀取一致性與覆蓋範圍契約。

投影順序為：將一批來源 ledger 套用到目的端、同步保存來源的 projected sequence、最後通知 watermark 管理者。若目的端 apply 成功後、來源進度同步前程序中斷，重啟會重播該批；目的端必須接受相同內容的冪等 apply。

測試／benchmark 的 in-memory Mock history 是 volatile。它可由仍保留的 source ledger 重建投影視圖，但不得將記憶體中的 projected sequence 或 watermark 偽裝成 durable 狀態，也不得因此執行正式歷史 GC。若重開 source 時已有 durable history progress、已發布 W 或 GC prefix，就必須注入正確的 durable 歷史目的端並驗證其覆蓋來源所需資料；另一個具有相同高 watermark 的目的端仍不足以證明資料一致或完整。Durable destination 必須在套用後可一致讀回 row 與退款狀態，GC 依賴的歷史資料不能只存在於尚未同步的 replica。測試用 durable fixture 只驗證契約，不構成 production external DB connector。

Watermark 使用單調遞增候選值 `now - retention`。發布候選值時，先安裝 `[W, C)` 歷史路由 fence，等待已進入 fence 的 request guard 排空，擷取來源 sequence，等 projector 追至該 sequence，再同步保存候選 W 與配對 sequence，最後才發布新邊界。`transaction_at < W` 的請求必須走歷史查詢：精確命中回傳歷史結果，查無資料則回傳 expired／rejected，不執行新交易；`transaction_at == W` 屬新交易邊界。W 和其配對 sequence 必須一起持久化和恢復。

GC 只刪除連續、符合所有條件的前綴：交易時間嚴格早於已發布 W、來源投影進度耐久覆蓋該 sequence、餘額 coverage 足夠、ledger record 與 transaction index 一致有效。刪除 ledger、index、符合條件的退款 marker 及 GC prefix 必須放在同一同步批次。第一筆不符合條件的資料會停止前綴回收，即使後續 timestamp 較舊亦然。退款防重證據在安全 GC 後仍須可透過耐久 history 查得。

GC 在沒有 durable history backend 時停用。它只管理應用程式自己的 ledger/index/refund records 和 GC prefix，不管理 RocksDB WAL、SST、metadata 或外部檔案。RocksDB logical delete 不等於實體空間已回收；第一版不保證 compaction 或即時釋放磁碟空間。

## 歷史儲存失敗與提交語意

錯誤使用帶操作脈絡的型別，不以解析舊內部字串推斷類別。至少區分：已提交的業務拒絕、相同 key 不同 body 的 conflict、入列接受前 timeout、接受後 caller 結果未知、RocksDB/storage 失敗、history 暫時失敗、history 永久 conflict/corruption 和生命週期錯誤。

- 接受前 timeout 表示沒有接受該請求，client 可用相同 key 重新送出。
- 接受後 caller cancellation 或 timeout 不會撤銷已接受工作；caller 的結果是 unknown。交易繼續執行，client 必須以原交易 key 重試以取得已保存結果。
- 一旦同步儲存操作已開始，取消 task 或 shutdown deadline 不會中止已啟動的 `spawn_blocking` mutation。
- Storage error 或核心 panic 後停止接受新交易並呈現 unhealthy 狀態；不回覆偽造成功結果。
- History 暫時錯誤只作有界重試；耗盡後明確進入 degraded 狀態並凍結相關 projection progress。
- History 永久 conflict 或 corruption 停止投影；不得假造進度或 watermark 以繼續 GC。

Shutdown 先停止新入口，排空已接受交易和已開始的 I/O，等待健康投影到要求的停止點，join 背景工作，再關閉 DB。若超過呼叫者 deadline，已開始的 storage mutation 仍會完成或回報錯誤；生命週期狀態必須可觀察，且不可在仍有 worker 或 handle 使用 DB 時刪除其目錄。

## 啟動檢查、生命週期與資源觀測

Runtime startup 檢查必要資料目錄可用、可用資源符合設定、DB metadata 和 recovery/integrity 狀態有效。Linux startup 會拒絕 tmpfs／ramfs，並檢查 data directory filesystem 的可用空間與 MemAvailable；預設門檻為 512 MiB 和 256 MiB，CLI 或 library config 設為 0 可停用該項啟動檢查。這些是啟動 admission 門檻，不是執行期間的容量保證或 memory／disk lifetime cap。若必要條件不符，啟動失敗並提供操作脈絡。Benchmark 的 idle preflight 是 harness 的外部前置工作，不放進 library pipeline。

健康狀態至少可看出入口是否接受請求、每 shard 提交／投影／watermark／GC 進度、history 是否 degraded、背景工作是否停止，以及 shutdown 是否完成。Metrics 使用固定上限的 counters、histograms 和 gauges；不累積無界逐請求 raw samples。每 stage 保留最多 4,096 筆 deterministic uniform reservoir，p50/p95/p99 使用 nearest-rank 計算且只描述該 sample；count、sum 和 max 涵蓋完整觀測流，snapshot 另外輸出 average。Library 的 1／10／60 秒 RPS window 計入已返回的 `submit` 與 `balance` 呼叫，包括回傳 error 的呼叫；被 caller 取消、尚未返回的呼叫不會計入。這個 RPS 不是 durable commit RPS。

Stage 的觀測單位不同：request、enqueue、queue、batch wait、response 是 per observed request；batch、index read、apply、sync publish、projector、watermark、GC 是 per batch／operation。`batch_wait` 是 dequeue 到 handler 開始的時間，不包含 handler 內等待全域 storage permit 的時間。`batch` 是每批儲存處理 wall time，從取得全域 storage permit 後開始，至 `handle_batch_with_index_lookup` 返回為止，包含 index lookup、apply 和 sync publish；因此它與 index read／apply／sync publish 計時重疊。各階段觀測範圍不同，不構成可相加還原 caller 端到端 latency 的非重疊分解。CLI 與新 benchmark 實際輸出 process CPU、process read/write bytes、benchmark 的 target-device I/O 和 stage timings；沒有從 duration 推算 per-stage CPU／file attribution，也不宣稱有 RocksDB native counters。Process 與 device I/O 為總量，device counters 可能包含其他程序的 filesystem activity。

不同階段或窗口的 latency percentile 不能相加；各自分布重疊。Process 和 device I/O counters 不是 per-request 或 per-shard 歸因。除能說明明確同一計時範圍外，不把這些總量直接分配到單一交易。

## 共用核心與 benchmark 證據

正式 library、local CLI 和新 `ledger_core_pipeline` benchmark 共用 `src` 核心實作；benchmark 只建立 workload、量測和報告，不維護另一份交易或儲存邏輯。核心聚焦驗證涵蓋公開 API 的 replay/refund、RocksDB reopen、schema/layout mismatch、取消與 shutdown、volatile history 防護、durable fixture 錯誤、apply／progress 間中斷恢復和歷史查詢覆蓋。

新 `ledger_core_pipeline` workload 預設為 50,000 users × 每 user 200 筆，共 10,000,000 筆；每 user 的 Credit／Debit 各半、amount=1。Benchmark 以固定 async runtime 呼叫公開 library API，驗證每筆交易都回傳 Applied；headline RPS 是已驗證 Applied transaction 數除以 foreground workload wall time。Shutdown／drain 時間另外列出，不併入該 headline。`--smoke` 預設使用 100 users × 每人 20 筆，並放寬／停用 idle preflight 限制，只用於正確性檢查，不能當作 idle host 或性能結果。Benchmark 預設在 `target/ledger-core-pipeline-trials` 建立各 run 專屬 scratch 目錄，正常清除僅限於該 run。

Full workload 的 idle preflight 門檻為 CPU busy ≤10%、target disk busy ≤5%，最多等候 60 秒；10M workload 至少要求 MemAvailable 8 GiB、free disk 16 GiB。較短的非-smoke workload 依 transaction 數線性縮放這兩項資源門檻，下限分別為 256 MiB 和 512 MiB。這些是 benchmark 啟動前 idle admission 門檻，不是容量保證。`--smoke` 將 CPU／disk busy 上限放寬至 100%、資源門檻設為 0，輸出 `smoke_relaxed=true` 和 `correctness-and-wiring-only` scope；smoke 不代表 idle host 或性能測量。

Benchmark 的每次結果列出 git HEAD、worktree dirty 狀態及受測核心／benchmark／Cargo source files 的 SHA-256；dirty worktree 的 SHA 和狀態清單是該次 source identity 的一部分。歷史 benchmark 報告及 artifacts 保留原測量程式碼、參數和來源 identity，不因抽取共用核心而重新標記為新核心結果。歷史數據只能作歷史背景，不能宣稱新程式碼已達到舊報告的數值。

Benchmark 使用每 shard 一個 volatile `MockHistory`。因此該 workload 不建立 durable watermark，也不會執行實際 history GC；它的吞吐數字不代表 durable projection／GC 的負載能力。Benchmark 執行前的 idle preflight 在 pipeline 啟動與 workload 計時之外執行。

本輪驗證沒有執行完整 10M benchmark。benchmark 結果也不能單獨證明最佳預設、穩態容量、飽和點或 production readiness；這些結論需要相符的 workload、資源、source identity 和量測證據。

## 驗收範圍與排除項目

本版驗收項目與契約如下；已執行的聚焦驗證命令和限制記錄於實作與驗證章節：

- 相同完整 key/body 的重播回傳原結果且 sequence 不變；相同 key 不同 body 衝突；更換 timestamp 視為不同 key。
- 同帳戶成功 Debit 最多退款一次；業務拒絕亦耐久重播；餘額查詢不入 queue，缺少帳戶回傳零。
- commit 的 ledger/index/refund state/touched balance/latest sequence 同步原子恢復；close/reopen 後結果一致。
- shard identity、schema、routing version、shard count 和 DB layout 不相符時拒絕開啟。
- 接受前 timeout 與接受後結果未知可區分；已開始 mutation 不被 caller cancellation 或 shutdown deadline 假性取消。
- volatile history 不得宣稱 durable progress、不得推進 real watermark/GC；durable history fixture 覆蓋錯誤時 fail closed。
- apply 成功但來源 progress sync 前中斷會安全冪等重播；watermark fence 的 `< W`、`== W` 邊界正確；GC 停於首個不合格 sequence，退款防重狀態仍可查。
- Shutdown 停止入口、排空已接受／已開始工作、join worker 並關閉 DB；正式資料不在正常結束時刪除。
- metrics 與所有背景佇列／in-flight work 有界；文件記錄其量測範圍與限制。

第一版不涵蓋 replication、cross-shard transaction、gRPC、外部 DB connector、auth、multi-currency、帳戶業務建立、快照與 resharding。它們不能被測試 fixture 或本機 CLI 的存在推論為已支援。

## 公開 API、CLI 與 benchmark 命令

Rust library 的主要入口為：

```rust
let pipeline = Pipeline::open(config, histories).await?;
```

`PipelineConfig::new(data_dir)` 建立預設設定；`histories` 必須依 shard 順序各提供一個 `HistoryStore`。服務提供 `submit(Transaction)`、`credit`、`debit`、`refund`、`balance`、`status`、`metrics`、`shutdown` 和 `wait_closed`。交易業務拒絕以 `Ok(TransactionReceipt { status: ... })` 回傳，基礎設施／協定錯誤以 `PipelineError` 回傳；`TransactionReceipt` 含 shard、sequence、status、balance 和 replay flags。API 不設帳戶數量上限，也沒有顯式 account-create API。呼叫者需讓 Tokio runtime 存活到 service 關閉；`shutdown` timeout 後仍應等待 `wait_closed`，再釋放 runtime 或資料目錄。

本機 binary `ledger-wallet` 啟動時開啟 source store，並從 stdin 接受下列命令；輸入 `shutdown`、EOF 或 SIGINT 會要求 graceful shutdown：

```text
credit ACCOUNT TX_ID TX_AT_US AMOUNT
debit ACCOUNT TX_ID TX_AT_US AMOUNT
refund ACCOUNT TX_ID TX_AT_US AMOUNT DEBIT_TX_ID DEBIT_TX_AT_US
balance ACCOUNT
status
shutdown
help
```

CLI flags 是 `--data-dir PATH`、`--shards N`、`--db-layout shared|dedicated`、`--min-free-disk-bytes N` 和 `--min-available-memory-bytes N`。`ledger-wallet --help` 會列出同一份用法。可在 repository 使用下列命令啟動預設單 shard/shared DB：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo run --locked --bin ledger-wallet -- --data-dir ./ledger-data
```

CLI 目前為每 shard 注入 volatile `MockHistory`，沒有 durable external history connector；source ledger 可本機持久化，但 CLI 不提供跨重啟的 durable historical lookup／GC 保證。需 durable history 的應用程式應由 library 注入真正符合前述契約的 backend。CLI 啟動預設 4 個 Tokio async worker、最多 32 個 blocking worker。

下列 release-profile 命令會執行預設 full 10M workload；它未在本輪驗證中執行。Smoke 驗證命令和結果列在下方，使用 test profile 且只驗證 correctness/wiring：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --locked --bench ledger_core_pipeline
```

該 `BINDGEN_EXTRA_CLANG_ARGS` 路徑是此 Ubuntu host 的 GCC 13 include path；其他環境應替換成相符的 GCC include path。`--help` 支援 `--users N`、`--requests-per-user N`、`--shards N`、`--db-layout shared|dedicated`、`--output-root PATH`、`--smoke` 和 preflight timeout／observation／最低記憶體與磁碟參數。Smoke 僅為 correctness/wiring check；不執行 full 10M workload，也不提供性能基準聲明。

驗證內容涵蓋交易 replay/refund、動態帳戶與 atomic storage/reopen、schema/layout/source identity fail-closed、volatile history safeguard、durable fixture projection/watermark/GC、history failure 耗盡後凍結 progress、metrics bounded reservoir，以及取消和 shutdown。`formal_crash_recovery` 在 Linux child process 寫入同步 source commit 並輸出測試 IPC marker 後送 SIGKILL；parent 重開並以相同 key/body replay。這是 process crash／lost reply 測試，不是 power loss、kernel crash、磁碟故障或斷電 durability proof。Durable history fixture 只測試介面契約，仍不構成 production external DB connector。

All-target compile 已由下列命令通過（只編譯、不執行所有 target）：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo test --locked --all-targets --no-run
```

Correctness smoke 使用 default test profile，實際命令為：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo test --locked --bench ledger_core_pipeline -- --smoke --users 64 --requests-per-user 4 --shards 2 --db-layout shared
```

該次共驗證 256 transactions（128 credits、128 debits）、2 shards、shared DB，最終 shard sequences 為 `[128, 128]`；輸出 `smoke_relaxed=true`、scope 為 `correctness-and-wiring-only`，preflight 通過。`batch_wait` stage 記錄 256 個 per-request observations，p50 約 6.12 ms、p95 約 6.39 ms、p99 約 6.47 ms。這些是 debug/test-profile correctness smoke 的接線／指標驗證，不是性能結果。Run 專屬 scratch 已清除，output root 無殘留；沒有保存 benchmark log/archive。Smoke 使用 volatile history，不觸發 durable watermark／real GC；本輪未執行 full 10M workload，也不能據此宣稱飽和能力、production readiness 或 benchmark performance。新 benchmark 產物應保留輸出中的 git HEAD、dirty worktree 狀態及 source SHA-256 作為測量來源識別。
