# 分析：PostgreSQL 冪等帳本交易批次測試結果

需求 [03-01](03-01.raw-requirement-pg-ledger-txn-batch-benchmark.md)、設計 [03-02](03-02.development-design-pg-ledger-txn-batch-benchmark.md)、原始資料與重現方式 [`benchmarks/pg-ledger-txn`](../benchmarks/pg-ledger-txn/README.md)（`results/`）。

## 1. 條件
單機、PostgreSQL 18.6、8 CPU（DB 容器 cpuset 0–7，client CPU 8–9，sampler CPU 14–15）、8 GiB 容器記憶體、`shared_buffers=2GB`、`wal_buffers=256MB`、`max_wal_size=8GB`、`fsync/synchronous_commit/full_page_writes=on`、`track_wal_io_timing=on`。主機：AMD Ryzen 7 3700X（8 核／16 執行緒）、62 GiB RAM、Ubuntu 24.04、kernel 6.17、Docker 29.1；資料位於單顆消費級 SATA SSD（CT1000BX500，I/O scheduler `mq-deadline`），與主機作業系統共用同一顆。工作量：100,000 帳號 × 40 筆 = 4,000,000 個新請求，256 queue／連線，一個視窗一個 statement。

## 2. 正確性
所有採用與停頓的 run 都通過：`applied = 4,000,000`、ledger 4,000,000 筆、10萬帳號餘額皆為 40、before/after 鏈無缺口無分叉、`missing = unexpected = replay_mismatch = 0`、`wal_stats.settled = true`、0 次 checkpoint、`wal_buffers_full = 0`。重送 cell 的 200,000 筆重送全部回傳原本記錄，ledger 筆數不變。Smoke（含 512 筆注入的拒絕請求）也通過。**沒有發生 `23505`／`40P01`**（`statement_retries = 0`），所以 SQL 重試路徑沒有在資料庫上實際執行過。

## 3. 吞吐、延遲與資源（每格 1–2 個有效樣本）
完整數字見 README 表與 `results/summary.csv`。

| Cell | rps_total（run） | 備註 |
|---|---|---|
| 視窗 4000 | 195,047 / 204,926 | 兩次相差 5% |
| 視窗 8000 | 262,134 | 另一次磁碟停頓（126,183），不採用 |
| 視窗 8000 + 5% 重送 | 259,833（新套用 247,460） | 另一次磁碟停頓（157,716），不採用 |

監控摘要（正常 run）：DB CPU 7.27–7.43 核（91–93%）、client CPU 0.26–0.39 核（可用 2 核）；裝置寫入 105–137 MiB/s、write IOPS 110–168、write await 3.5–6.4 ms、flush await 0.37–0.50 ms、磁碟 util 26–31%；WAL 988–1048 MB；平均每次 fsync 1.34–1.36 MB（視窗 4000）、2.15–2.24 MB（視窗 8000）；DB cgroup 記憶體最大 5.9–7.6 GiB（含 page cache，逼近 8 GiB 上限，不是 PG 行程記憶體）；client RSS 最大 0.5–0.95 GiB。每秒 RPS 呈波浪狀（同一批視窗大致同時完成）。

延遲是請求為權重的 statement 執行時間（視窗 4000：p50 約 4.4–4.6 s、p99 約 7.9 s；視窗 8000：p50 約 6.3–6.8 s、p99 約 10.2–10.9 s），不含 queue 等待，不是 end-to-end 延遲，並隨視窗增大而增加，所以不同視窗之間以 RPS 比較。

## 4. 觀察與解讀
1. **DB CPU 是主要限制。** 正常 run 的 DB CPU 達 91–93%，磁碟 util 約 30%、flush await 低於 1 ms，client CPU 遠低於配額。（這是由計數器推論，沒有取樣等待事件。）
2. **5% 重送沒有看到吞吐損失：** 總 RPS −0.9%、新套用 RPS −5.6%（皆在約 10% 雜訊內；只有一個有效樣本）。
3. **視窗 4000 比視窗 8000 慢：** 每個請求的 DB CPU 約 36–38 µs（視窗 4000）對 27.7 µs（視窗 8000）。原因**未查明**。已排除一個假設：每個 statement 的固定成本——單連線在 10 萬帳號／10 萬筆 ledger 上執行同一 SQL，10 筆約 1.7 ms、100 筆約 3.5 ms、1000 筆 23–56 ms、4000 筆約 112 ms、8000 筆 210–245 ms，4000 與 8000 的每筆成本都約 28 µs。未測試的候選：256 個視窗同時進行時對帳號列／頁面的競爭；起始時視窗同時啟動（視窗 4000 的第一段 RPS 只有約 74–78k）。
4. **磁碟停頓：** 6 個 run 中 2 個停頓（flush await 4.5／5.8 ms、util 62–75%、DB CPU 降到 49–56%、RPS 126k–158k），即使每次事前檢查磁碟閒置（寫入 < 1 MiB/s、`Dirty` < 5 MB）都通過；原因未知（假設與共用磁碟有關）。停頓的 run 保留作為證據，不用於結論。
5. 準備好的 statement 每個連線只執行 2–4 次（視窗 8000／4000），所以保持 custom plan；PG 預設 `plan_cache_mode=auto` 於第 6 次執行才可能改用 generic plan。這些 run 不代表 generic plan 的效能。

## 5. 與較早基準的關係
較早的 batch-queue 版本（舊 SQL：3 欄 ledger、`ON CONFLICT DO NOTHING`、不回傳任何記錄、單一 INSERT 加餘額更新）用同一套 wrapper、同樣的設定與 4 M 請求，視窗 4000 為 252,391 RPS、視窗 8000 為 263,065 RPS（原始資料不在本 repo，數字引用自先前的量測報告）。對比：視窗 8000 沒有可分辨的差異（262.1k 對 263.1k，−0.4%，雜訊內）；視窗 4000 低約 19–23%，原因未知（見上）。這**不是等價比較**：新 SQL 每筆多做探測、before/after 計算、回傳記錄，client 另做去重／排序／解析；新 SQL 的 WAL 較少（988–1048 MB 對先前 1112–1171 MB）且每次 fsync 較小，原因未調查。

## 6. 限制
- 每格只有 1–2 個有效樣本，無變異估計；8000 與重送 cell 各只有一個有效樣本。
- 共用的消費級 SATA SSD 有停頓，原因未知；client／sampler 與 DB 共用 SMT 兄弟核，影響未量；未取樣等待事件與實際執行計畫。
- 新容器 volume 的 WAL 初始化寫入（約 1 GB 的 `init` context）包含在量測視窗內。
- 每帳號只有一個 executor，沒有量到跨連線的鎖競爭、`23505`／`40P01` 重試或多 client 實例。
- 延遲不含 queue 等待；T3 的實際視窗最大 8,422 筆（`--batch-max` 限制新請求數）。
- 只有 PostgreSQL；ScyllaDB 的 CQL 僅記錄於設計文件，尚未實作或量測。
- 重送在較後的視窗送出，資料庫只看到「晚到的重送」，沒有同時競爭同一 key 的案例。
