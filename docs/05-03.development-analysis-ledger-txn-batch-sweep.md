# Batch sweep 測試報告：PostgreSQL vs TiDB，CPU4 / CPU8，batch-max 掃描

目的：在固定硬體（CPU4、CPU8）與固定並行度（256 queue = 256 連線）下，把 batch-max 從小掃到大，量測 RPS 與 latency，找出各情境的飽和點。可接受的 latency 由讀者自行選定，本報告不預設 SLO。

資料來源：`artifacts/sweep-<db>-c<C>.csv`（每次執行一列）與各 attempt 目錄 `artifacts/sweep-<db>-c<C>-bm<N>-a<k>/`。需求與設計見 `docs/05-01.raw-requirement-ledger-txn-batch-sweep.md`、`docs/05-02.development-design-ledger-txn-batch-sweep.md`。

## 2. 負載方式

- **資料：** 100,000 個帳戶，每個帳戶 40 筆請求，共 **4,000,000 筆**請求，amount 固定為 1，transaction id 為新產生的 UUID。
- **並行度：** 256 個 queue，對應 256 條資料連線（1:1），另加 1 條 monitor 連線，共 257 個 socket（wrapper 在 GO 前以 socket 普查確認）。
- **queue 分配：** `user % 256` 決定 queue；同一帳戶的請求都在同一個 queue，依序處理。每個 queue 約 15,625 筆請求。
- **window（批次）：** 每個 queue 從自己的請求中依序取最多 `batch-max` 筆組成一個 window，一個 window 是一個原子交易；window 內先去重（account, tx）並依帳戶排序。每個連線同時只有一個 window 在途（封閉迴路）。因 4M 請求固定，window 總數 ≈ 4M / batch-max（batch 50 為 80,032 個，batch 16000 為 256 個；batch 大於每 queue 的 15,625 筆時等於整個 queue 一個 window）。
- **每筆請求的終態：** `applied` / `existing` / `rejected:invalid_amount` / `rejected:unknown_account`；missing、unexpected、重複回覆都視為錯誤。本次掃描為純新請求，`applied` = 4,000,000。
- **逾時：** 每個 window 30 秒（per window，不是整個 run）。任何錯誤或逾時使該 run 無效，不重試。
- **掃描的 batch-max：** 50、100、250、500、1000、2000、4000、8000；PG 另外探測 12000、16000；TiDB 另外探測 6000，6000 成功才試 8000。

### PostgreSQL 的交易寫法

每個 window 一條 SQL（單一往返）：CTE 內以 `unnest` 展開輸入，探測已存在的 ledger、驗證帳戶與金額、`UPDATE accounts` 並以 window function 算出每筆的 before/after、`INSERT INTO ledger`，回傳每筆結果（`docs/04-02.development-design-ledger-txn-tidb.md`）。表結構：`accounts(account_id uuid PK, balance)`、`ledger(transaction_id, account_id, amount, before_balance, after_balance, PK(account_id, transaction_id), FK, CHECK)`。

### TiDB 的交易寫法

TiDB 沒有 data-modifying CTE，因此每個 window 是一個悲觀交易，用 **2 次往返**送出（multi-statement）：

- 封包 1：`BEGIN PESSIMISTIC`、`SELECT account_id,balance FROM accounts WHERE shard=S AND account_id IN (...) FOR UPDATE`、`SELECT ... FROM ledger WHERE (shard,account_id,transaction_id) IN (...)`（探測 existing）。
- client 分類每筆請求（existing > invalid amount > unknown account > applied）並算出 before/after。
- 封包 2：`INSERT INTO ledger ...`（僅 applied）、`INSERT INTO accounts ... ON DUPLICATE KEY UPDATE balance=VALUES(balance)`、`COMMIT`。
- 每個 window 2 次往返；summary 的 `round_trips` = 2 × windows（例：batch 50 為 160,064 = 2 × 80,032）。
- UUID 存成 `BINARY(16)`，以 `x'<32 hex>'` 字面值送出。
- 表結構：兩張表主鍵最前面加 `shard = queue 編號`（clustered）：`accounts(shard, account_id, balance, PK(shard, account_id))`、`ledger(shard, account_id, transaction_id, amount, before_balance, after_balance, PK(shard, account_id, transaction_id), FK(shard, account_id) -> accounts)`。FK 有實際執行（負向測試要求 error 1452）。
- 預切 region：兩張表各預切 256 個 region（`SPLIT TABLE`），一個 queue 對應一個 region；PD 設 `max-replicas=1`（no RF）與 `max-merge-region-size/keys=0` 避免合併。

### 與 PG 的差異（已揭露，未補償）

- TiDB 一個 window 是多個 statement、2 次往返，before/after 在 client 計算；PG 是單一 statement、單一往返、DB 內計算。
- TiDB 表多一個 `shard` 欄；沒有 CHECK 約束（TiDB 預設關閉）；FK 都保留。
- TiDB 另有 tidb-server 與 PD 兩個元件，PG 沒有。
- 兩者的 latency 都是 window 從送出到最後一個回應（TiDB 含 `BEGIN` 到 `COMMIT`）。

## 3. DB 設定

## 4. 監控與驗證方式

### 4.1 取樣

- 取樣間隔 **250 ms**，每個容器各有一個 sampler（`scripts/monitor.py`，各容器在 `res-*` 目錄，PG 在 attempt 根目錄 `resources.csv`），跑在獨立綁核（14-15）上，從 GO 開始、client 結束為止，之後依 client 回報的測量窗口（measurement start/end）過濾；summary 的 `resource_window_formal` 標示資源窗口是否有效（本報告的 attempt 均為 true）。
- **CPU：** 讀容器 cgroup v2 的 `cpu.stat`（usage_usec 差值），換算成核心等價數與佔配額的百分比；TiDB 另外記錄 tidb-server、PD 的 CPU，tidb-server 佔其 4 執行緒 cpuset ≥ 85% 時標為飽和（`*`，即 tidb-server-bound）。
- **記憶體：** cgroup `memory.current` 的最大值（含 page cache）；client 記錄 RSS 最大值。
- **磁碟：** 讀主機 `/proc/diskstats` 的 sdb：寫入 MiB/s、寫 IOPS、`util %`、平均 queue depth、write await（毫秒/次）、flush await（毫秒/次）；另有容器 cgroup `io.stat` 的讀寫量。
- **網路：** 讀容器網路命名空間的 `/proc/<pid>/net/dev`，取 rx、tx 的 MiB/s 平均與最大值（PG 的資料庫容器、TiDB 的 tidb-server 與各 TiKV 容器；PD 不取）。
- **client：** CPU、RSS、執行緒數、每秒的完成請求數、在途請求、忙碌連線、server 端非 sleeping session 數（PG 為 `pg_stat_activity`，TiDB 為 `SHOW PROCESSLIST`）。
- **TiDB 專屬：** 每個 TiKV 的 raft-engine write/sync 次數、bytes、sync 秒數（run 前後 metrics 差值）；TiKV 的 region 與 leader 數、每表 region 數、peer 數（`information_schema.tikv_*`，計時前記錄）。

### 4.2 latency 的定義

由 client 量測，**每個 window 一次**：計時從送出第一個封包之前（去重與排序完成後）開始，到最後一個封包（TiDB 含 `COMMIT`）的回應收完。window 內每筆請求都記同一個值（以請求數加權），存成 HDR histogram（`latency.hdr`）。不含 client 內部的等待與去重。因為 256 條連線一直滿載，latency 約等於 256 × batch ÷ RPS（Little's law），會隨 batch 近似線性上升。

### 4.3 RPS 的定義

`rps_request` = 4,000,000 ÷ 計時時間（GO 到最後一個 window 完成）；`rps_io` = windows/s（TiDB 為每秒交易數）。報告只以 `rps_request` 比較。

### 4.4 執行前後的驗證（每個 attempt）

- 執行前（GO 之前）：257 個 socket 普查；資源配置（cpuset、NanoCpus、記憶體）與預期一致；TiDB 另驗證每表 ≥ 256 個 region、每個 region 恰好 1 個 peer、CPU8 兩台 store 的 region 與 leader 各占 40–60%、FK 負向測試（error 1452）、Q1/Q2 的執行計畫須為 `Batch_Point_Get` 且無 `TableFullScan`。
- 計時後（不計時）：每個帳戶 balance = ledger 筆數 = 40；before_balance 不重複、最大 after = balance、每列 after = before + amount；100,000 個帳戶、balance 總和 = ledger 列數 = 4,000,000；outcomes 為 applied = 4,000,000、missing / unexpected / replay_mismatch = 0。
- TiDB 另驗證持久化：raft-engine sync 次數與 write 次數差值 > 0 且總和差在 ±1% 內（所有 attempt 通過）。
- 清理：`cleanup.json` 須為 success，無殘留容器、網路、volume。

### 4.5 測試前的環境閘門與流程

- **idle 閘門（每次新 attempt 之前）：** 讀 `/proc/stat` 5 秒，每個邏輯 CPU 的閒置率（含 iowait）須 ≥ **90%**，且沒有任何其他程序在同一 5 秒區間用超過 30% 的單核（以 `/proc/<pid>/stat` 的 CPU 差值計算；只排除 driver 自己）。不合格時等待並重測，最多 60 秒，仍不合格就中止該 attempt。證據存為 `<attempt>-idle.json`。原本設計為 95%，因互動式 `pi` session 常駐約 10% 而無法達成，使用者決定放寬為 90%（並關閉了 agy 與 chrome）。沿用的 4 個資料點（PG CPU4 的 4000 與 8000、TiDB CPU4 與 CPU8 的 4000）早於此閘門，沒有 idle 證據。
- **stall 規則：** 磁碟 flush await 平均 > 2 ms 時，primary 補跑一次（`flush_rerun`），補跑的結果取代該 batch 的 primary，兩筆都保留。
- **replicate：** 每個系列在飽和點附近補跑數個點，只作為雜訊對照，不改變飽和點。
- **sampler 競態：** `monitor.Sampler` 在 client 結束時偶爾讀 `/proc/<pid>/io` 失敗（Permission denied），wrapper 判為失敗；driver 在新目錄自動重試（最多 2 次），失敗的 attempt 保留在 CSV；TiDB wrapper 另外容忍結束前 2 秒內的此錯誤並記錄於 `sampler-tolerated-errors.json`。
- **飽和點定義：** primary RPS 達該系列最大 primary RPS 的 95% 的最小 batch；若剛好是最大測試 batch，稱為「網格上的飽和點」，不代表已出現平台。

## 6. Region 分布（TiDB，計時開始前記錄）

- 每個 TiDB attempt：`accounts` 與 `ledger` 各 256 個 region，peer 數不等於 1 的 region 為 0（無 RF）；總 region 數 577（含系統表等其他 region）。
- CPU4：單一 store，577 個 region、577 個 leader，所有 attempt 相同。
- CPU8：兩台 store 的 region 與 leader 數相同，比例都落在 49.2%–50.8%（例：288/289、292/285、293/284），遠在 40–60% 的閘門內。CPU8 的 wrapper 在建表前固定等待約 125 秒，讓 PD 平衡 region；早期一次 2-store 驗證在 120 秒內只平衡到 83.9% / 16.1%，被閘門擋下，因此改為固定等待。
- 一個 queue 對應一個 region（shard = user % 256）。**沒有量**的部分：run 結束後的 region/leader 分布、每個 region 的實際負載與各 store 的資料大小。

## 8. 觀察（事實）

- **PG 吃滿 CPU：** 各 batch 的 DB CPU 為 CPU4 的 83–99% 與 CPU8 的 90–97%，磁碟 util 約 19–46%、flush await 約 0.4 ms，網路與 client CPU 都很低；PG 的上限落在 DB CPU，RPS 隨 batch 增加直到整個 queue 一個 window（16000）仍在上升。
- **TiDB CPU8 沒有比 CPU4 快：** batch 500 為 67.6k 對 66.9k。兩者的 tidb-server 都只有 4 執行緒；batch ≤ 500 時 tidb-server 為 81–98%（250 與 500 在 CPU8 為 98% 與 96%），TiKV 為 3.3–4.2 核，屬 tidb-server-bound。batch ≥ 1000 時 tidb-server 降到 57–82%、TiKV 降到 2.4–3.1 核，平台的瓶頸**沒有量到**（無 TiKV 各 thread 的使用率）。
- **TiDB 的 latency 受 30 秒逾時限制：** 4000（CPU4 與 CPU8 的 replicate）、8000（CPU4）、6000（CPU8）逾時失敗；沿用的 4000 資料 max 為 27.1 與 29.9 秒。tidb-server 記憶體隨 batch 增加（1.6 → 14.6 GB，6000 時已逼近上限）。調查 batch 8000 的記憶體（`artifacts/txntidb-mem*`）顯示 256 個含 8000 筆字面值 SQL 的連線同時存在時，tidb-server heap 達 13–18 GB，EXPLAIN ANALYZE 追蹤的每條 statement 只有數 MB，因此記憶體主要在未追蹤的 parse/plan 結構；關閉 GC tuner、GOGC=50、解除上限、32g 容器都未能跑完。
- **磁碟暫停造成雜訊：** flush await > 1.5 ms 的點（PG CPU4 的 2000、PG CPU4 的 4000 replicate、PG CPU8 的 2000 第一次、TiDB 的 1000 與 2000）RPS 或尾端 latency 異常，例如 PG CPU8 的 2000 第一次為 117.0k（3.7 ms），補跑為 214.0k。replicate 差異：PG CPU4 的 4000 為 −21.9%（有磁碟暫停）、8000 為 −0.4%。
- **持久化：** 所有 TiDB attempt 的 raft-engine sync 次數與 write 次數差距均在 1% 內；TiKV 每個 store 都有正的差值。
- **同 batch、同 CPU 的 PG 與 TiDB：** batch 500，PG CPU4 為 89.3k、p99 2.94 秒，TiDB CPU4 為 66.9k、p99 2.60 秒；PG CPU8 為 138.4k、p99 1.72 秒，TiDB CPU8 為 67.6k、p99 2.57 秒。資料上無法判定 TiDB latency 較長的原因，只能指出它每個 window 多 2 次往返與較多 statement。

## 9. 限制與已知事件

- 每個點單次 run（飽和點附近有 replicate），中間 batch 的雜訊（尤其磁碟暫停）可達 ±20%，曲線不保證單調。
- 4M 請求固定：大 batch 每個 queue 只有 1–4 個 window，樣本少且起始為同步突發；小 batch 的總時間較長。
- 沿用的 4 個資料點（PG CPU4 的 4000 與 8000、TiDB CPU4 與 CPU8 的 4000）早於 idle 閘門，當時 agy 與 chrome 正在執行；PG CPU4 的 8000 的資源數據來自第一次 run，client 數據來自補跑（兩者 RPS 相差 0.1%）。
- 測試期間曾有兩個無關的孤兒程序（各約 99% CPU）在跑，已由主 implementation task 在最終量測前停止；先前的 PG CPU8 舊結果（`txn-bm4000-W256`、`-rep2`、`txn-bm8000-W256`）受其影響，已被本次資料取代並移到 `artifacts/_invalid/`。早期失敗的 run 目錄（`txntidb-c4-bm4000`、`-c4-bm8000(-v2)`、`-c8-bm4000`、`-c8-bm8000`、`txnpg4-bm4000`、`txntidb-mem*`、`txntidb-smoke*`）保留作為證據，不是結果。
- client 的 monitor 查詢由 `information_schema.processlist`（會載入完整 SQL 文字）改為 `SHOW PROCESSLIST`；PG 的第一個 8000 run 是在該 sampler 競態出現前完成，其餘 PG run 發生 3 次競態並由 driver 重試。
- 沒有量：TiKV 各 thread（raftstore、apply、grpc）的 CPU、window 內各階段（Q1/Q2/INSERT/COMMIT）的時間、run 結束後的 region 分布與每個 region 的負載。
