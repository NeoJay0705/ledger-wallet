## 技術邊界

同一個 CPU shard 不是交易邊界。
自動分配表示使用 ScyllaDB 與 driver 的資料路由，不使用 account_id % S 來假定 CPU shard 位置。Scylla CPU shard 數與應用邏輯 shard 數分開設定。改變 CPU shard 數可能需要重啟及資料重新分配，須依固定版本確認。本輪比較 fresh trials 的固定 S1/S2/S4 配置；在線擴縮容不列入本輪驗收。
建議將同人的 balance、ledger 與必要的防重證據放在同一 table 的同一 partition。
每人單一 partition 的代價是 ledger 隨歷史交易持續增長，熱帳戶也會集中負載。此次 200 筆／人的有限負載不能證明長期容量。若未來以時間切 partition，當前 balance 與跨時間 ledger 的原子範圍會改變，須重新設計。本輪不得為了分散熱點而把同人的必要變更拆成未受保護的多 partition 寫入。
每次交易以單一 partition mutation 或單一 partition CQL BATCH 提交必要變更。
此方案取得該次寫入的原子性與 isolation。
它不自動提供任意 read-modify-write 的序列化，也不提供跨人的 SQL transaction。
分開執行的多次 SELECT 不形成同一個讀取 snapshot。
多個服務程序的本機鎖不能保證同人只有一個寫入者。
參考：[ScyllaDB data definition](https://docs.scylladb.com/manual/stable/cql/ddl.html)、[CQL BATCH](https://docs.scylladb.com/manual/stable/cql/dml/batch.html)。

CL 與 fsync 是不同條件。
建議使用單一 DC、RF=3、一般寫入 CL=THREE。
在這個固定拓撲內，THREE 與 ALL 都要求三個 replica 回覆。
建議 balance、dedupe 及驗證讀取也使用 THREE。
三個 node 都須啟用 durable_writes，並使用該固定版本支援的 commitlog_sync=batch。
這個 commitlog 設定也適用於應用程式的非 batch case。
periodic 模式可能在 fsync 前回覆，不符合本需求。
Commitlog group commit 可能讓多次交易共用一次 fsync。
不得假設 fsync 數等於 request、CQL BATCH 或 replica commit 數。
開始 bench 前須核對三個 node 的生效設定、keyspace RF、prepared statement CL 與 driver policy。
必須固定 ScyllaDB 版本、image digest、Rust driver 版本及實際生效的 commitlog 設定。
不能只依設定文件假設 commitlog_sync_batch_window_in_ms 可用。官方設定說明仍提到此欄位，但本輪核對的 master db/config.cc 與 db/commitlog/commitlog.cc 未見此設定被使用。後續設計須核對受測 release 的設定註冊與執行路徑，再以 metrics 或 trace 驗證。
目前核對的 master 路徑在 batch_cycle() 等待前次 I/O，期間允許多個 allocation 合併。這不表示一定每筆一次 fsync，也不表示有可設定的固定等待 window。
此處 master 證據只供需求評估，不構成受測 release 的行為保證。
參考：[Consistency levels](https://docs.scylladb.com/manual/stable/cql/consistency.html)、[Commit log settings](https://docs.scylladb.com/manual/stable/reference/configuration-parameters.html)、[ScyllaDB config source](https://github.com/scylladb/scylladb/blob/master/db/config.cc)、[Commitlog source](https://github.com/scylladb/scylladb/blob/master/db/commitlog/commitlog.cc)。

## Commitlog 與 worker／connection scaling

依使用者最新修訂，服務端的主比較是 worker／connection scaling。固定總請求數，改變 DB worker coroutine 數 C，並要求資料 connection pool 總數等於 C。
本文件中的 client coroutine、account owner、DB worker、physical connection 與 Tokio runtime worker thread 是不同概念。
服務組批、CQL BATCH 與 commitlog group commit 仍須分開記錄。改變 C 本身不表示改變 CQL batch 大小或 fsync 模式。
所有正式 case 保存相同資料，使用相同的單人原子性、RF/CL 與 fsync 後 ack。
不能以 periodic 當作符合契約的非 batch fsync。
不能以 global in-flight=1 宣稱逐筆 fsync；它同時改變並行度，也不能排除背景或其他 shard 的 log activity。
先核對固定 release 是否提供可獨立控制的同步模式。沒有就報告限制，量測可觀察的 requests、partition mutations、commitlog syncs 及其分布。
增加 C 的任何收益都由量測確認，不預設它會減少 fsync 或 round trips。每個 C case 維持相同的單次 CQL 內容、batch 筆數／bytes 上限及收集等待政策。

### CQL 送出方式的設計評估

下列三種方式只保留作為先前要求的協定與取捨評估，不是新增三倍的必要正式矩陣。
主比較選定一種 CQL 送出政策後保持不變；不將 C 與 CQL batch size 同時改動。
不同 partition 的單一 request 能否一起提交之原子邊界仍依下表及後續錯誤處理要求驗證。

| 服務送出方式 | 行為 | 評估重點 |
| --- | --- | --- |
| Independent | 每筆交易提交同人 balance 與 ledger 的單 partition mutation／CQL BATCH；不同人可並行。 | 保留原子性。可利用 driver 的 shard-aware routing 與 connection multiplexing。 |
| Partition-grouped | 服務收集多筆 request，按 table/partition 分組。每組各自提交，組間受全域 in-flight 限制。 | 同 partition 多筆可一起保存 ledger 與最終 balance；每筆結果及 version 仍須正確。若每人只有一筆 outstanding，通常無法把同人多筆交易合併。 |
| Mixed-partition CQL BATCH | 單一 CQL request 內含不同人的 mutations，先按 table/partition 整理 statements。作獨立實驗 profile。 | 同 partition 的變更可原子套用；不同 partition 不形成共同 transaction 或 snapshot。成功回覆涵蓋整個 CQL request，失敗時不得推論各 partition 均未提交。 |

Mixed-partition profile 建議使用 UNLOGGED，因本輪沒有跨人整批原子需求。
這是後續設計需驗證的比較方案，不代表已實作。
跨 partition UNLOGGED 可能部分套用；同人必要資料仍須在同一 table/partition mutation 內。
LOGGED BATCH 增加 batchlog 成本，提供跨 partition 最終完成保證，不提供跨 partition isolation；本輪不將它作為預設優化。
不能巢狀包 CQL BATCH。外層 mixed request 必須展開必要 statements 並保留同 partition 的原子範圍。
同一 batch 內若多次更新同人 balance，不依 CQL statement 列出順序計算結果。
先按 account 順序計算每筆結果，只提交正確的最終 balance，或使用經驗證的 write timestamps/version。
原子提交也保存各筆 ledger 結果，且 owner 持續持有同人順序控制。
跨 partition batch 只經一個 coordinator；不同 partition 可能位於不同 CPU shards，需要轉送。RF=3 時三個 node 都有 replicas，仍不能消除 shard 路由及 fan-out 成本。
同 partition 不保證一定只有一次 fsync；同 shard 不保證共同 transaction。
Mixed request 結果未知時，停止所有被該 request 包含的 account，不能只停止其中一人。
CQL BATCH 使用筆數及 encoded bytes 雙重上限。不得放大 guardrail 以套用舊 2,048 筆的設定。
服務收集上限與等待時間另定，Independent 不加入收集等待。
每種方式記錄 logical transactions、CQL requests、partition mutations、實際 batch size/bytes、flush reason、in-flight peak、latency 與 commitlog syncs。
參考：[CQL BATCH](https://docs.scylladb.com/manual/stable/cql/dml/batch.html)、[Rust driver batch performance](https://rust-driver.docs.scylladb.com/stable/statements/batch.html)。

### Coroutine 與 connection 的 1:1 定義

固定總 logical requests N。沿用前述 workload 預設時，N=10,000,000，client coroutine=50,000。
DB worker 數記為 C。Client coroutine 數不隨 C 改變，也不直接等同 DB connections。
Account owner 保留同人完整 read-modify-write 順序，不與 DB worker 數或實體 connection 身分混同。
每個 DB worker 同時最多一個 workload CQL request 在等待回覆；read 完成後才發出下一個 read 或 write。
DB worker 不在內部啟動未受限制的並行 CQL futures。全域 workload CQL in-flight 上限為 C。
Driver retry、speculative execution、paging、prepare、health check 與監控流量另列；不能把它們當作不存在。
正式 case 的 prepare 與連線建立在量測前完成。讀取語句須有界，避免隱含 paging 改變操作數。
每次 CQL request 包含 B 筆 logical transactions 時，同時被提交的 logical transactions 可達 C×B；因此 CQL in-flight 與 logical transaction in-flight 分開記錄。
C 是並行上限，不是保證每一刻都有 C 個 request，也不是 CPU thread 數。

使用者已確認：DB worker 數與目標資料 connection pool 總數採 1:1，並使用共用 Session。
多個 DB workers 共用一個 Arc<Session>，由 driver 按 token／shard 選擇 connection。
不要求每個 worker 獨占或固定綁定某條 physical connection。
Rust driver 的一條 connection 可以 multiplex 多個 requests；總數相等不保證各 worker 使用不同 connection，也不保證每條 connection 只有一個 in-flight。
應用程式的全域 workload CQL in-flight 上限仍為 C。
不能用建立 C 個 Session 假裝只有 C 條 connections；每個 Session 會建立自己的 node／shard pool，還有 control connections。
本輪不需要獨占連線 adapter。Account owner 的順序控制及已確認的 fsync 後 ack 契約維持不變。

### 可對齊的連線配置候選

採用共用 Session 與 PerShard(P) 時，三個 node 各 S 個 shards 的資料連線目標為 3×S×P。
要讓資料連線數等於 C，需 P=C/(3×S)，且 P 是正整數。
為了在 S1/S2/S4 比較相同的 C，建議候選測點使用 C=12/24/48。
這些是後續設計的候選點，不是已確認的最佳值或飽和點。

| 每 node shards | C=12 時 P | C=24 時 P | C=48 時 P |
| --- | --- | --- | --- |
| S1 | 4 | 8 | 16 |
| S2 | 2 | 4 | 8 |
| S4 | 1 | 2 | 4 |

C 不是 3×S 的整數倍時，PerShard 無法直接產生相同總數；不得靜默四捨五入。
PerHost 可作替代評估，但不保證各 shard 連線均勻，不能當作完全等價配置。
Control、metadata、監控、初始化及重連連線不計入 C；實際分類及總數另行記錄。
量測前驗證目標資料連線都已建立，並記錄 measurement window 中實際 connections 與 in-flight。
Target pool size 不是瞬間實際總連線數的硬保證。不能僅依設定值宣稱已達成 1:1。
若正式 trial 期間連線配置不符或發生重連，標記失效，不混入完整正常矩陣。
C 個 workers 與 C 條資料連線同時變動，結果稱為 worker／connection scaling。
增加 C 可增加並行 I/O 與 commitlog 合併機會，也會增加 socket、memory、排程、queue wait、tail latency 與 overload 成本。
先做獨立 pilot，確認候選 C 能形成有效比較，然後凍結正式測點、batch policy 與 error policy。
參考：[Session best practices](https://rust-driver.docs.scylladb.com/stable/connecting/connecting.html)、[PoolSize](https://docs.rs/scylla/latest/scylla/client/enum.PoolSize.html)。

以下名稱是預定函式責任，不代表現有程式已有這些函式。

```text
Fixed clients / fixed N requests
  -> validate_request()
  -> sequence_account_owner(account_id)
  -> enqueue_ready_db_work()
  -> C DB worker coroutines
       -> await one CQL operation
       -> C target data connections
       -> 3 Scylla nodes (S shards each)
  -> wait_for_durable_result()
  -> release_account_owner()

Unknown write result
  -> freeze_affected_accounts()
  -> invalidate_trial()
  -> drain_and_cleanup_owned_resources()
```

C 條資料連線是總數 1:1 的目標；DB workers 共用 Session，由 driver 選擇 connection，不要求獨占綁定。Owner 在需要多個 DB 操作時，持續保留同人順序控制直到完整交易完成。

## 狀態與 sequential

「不存狀態」定義為服務不保留權威 balance、ledger、dedupe 或 durable recovery log。
服務仍須保留有界 queue、同人排程、連線與 in-flight 工作。
同一 account 的所有 caller 進入同一 owner 排程。Owner 持有順序控制直到成功 ack、明確業務拒絕或未知結果凍結。
Account owner 的順序保證獨立於 DB worker／connection 的 1:1 對應方式。CQL connection multiplexing 不能提供這段 read-modify-write 的隔離。
帳戶 owner、全域 queue 與實際 DB operations 均須有界，並定義取消及 shutdown 時的資源回收。
Batch 不能造成跨 owner 等待死鎖。多 owner 的保留與放行政策由設計明確定義。
每次計算所需的 balance 與防重證據由 Scylla 讀取。
在同人的順序控制範圍內，完成讀取、驗證、原子提交及結果處理。
同人有未知提交結果時，不得繼續執行下一筆 read-modify-write。
不能僅依 client 每人一筆 outstanding，宣稱服務已實作 sequential。
驗證須包含多個 caller 同時提交同一 account。
排程資料結構及全域儲存 concurrency 必須有上限。
服務重啟或舊 writer 接手的安全契約必須與性能結果一起列出。
若採一般 CQL last-write-wins，須定義單調 write timestamp/version，防止舊寫入覆蓋新 balance。
交易的 producer transaction_at 不等於資料庫的 write timestamp。
目前正式核心的完整交易 key 是 (account_id, tx_id, transaction_at)。
若保留該 key，重試必須沿用相同 key/body；相同 key 不同 body 必須回傳 conflict。
成功 replay 也必須符合 fsync 後 ack 的契約。若原交易提交結果未知，僅以 SELECT 看到 ledger，不能單獨證明三個 replica 的 fsync 已完成。恢復流程須建立可驗證的耐久確認，且不得重寫舊 balance 以覆蓋後續交易。具體機制在實作設計前確定。
參考：[正式核心設計](01-30.development-design-ledger-formal-core.md)。

## CPU affinity 與公平性

本輪只讀盤點：8 個 physical cores、16 個 logical CPUs。
CPU 0..7 與 8..15 分別共用相同的 8 個實體核心。
目前允許 affinity 為 CPU 0..15。
舊 01-29 bench 使用 4 個 Tokio workers，未固定各 thread affinity。
舊服務 shard 數不代表專屬 CPU core 數。

CPU 規劃固定每個 node 的 physical core pool，再隨 S 啟用 logical CPUs。下表是後續設計的明示配置預設。

| 每 node shards | Node A CPUs | Node B CPUs | Node C CPUs | 服務／負載／監控共用 pool |
| --- | --- | --- | --- | --- |
| S1 | 0 | 2 | 4 | 6,7,14,15 |
| S2 | 0,1 | 2,3 | 4,5 | 6,7,14,15 |
| S4 | 0,1,8,9 | 2,3,10,11 | 4,5,12,13 | 6,7,14,15 |

三個 node 分別使用 cores 0/1、2/3、4/5 的 pool。Core 6/7 保留給服務、負載產生器與監控。
S1 未啟用的 DB CPUs 保留，不移給其他 benchmark 角色。
S2 到 S4 是每 node 在相同兩個 physical cores 上啟用 SMT，不是 physical cores 倍增。
服務／負載／監控共用兩個 physical cores，必須量測各自 CPU 與瓶頸。這個 pool 可能限制 DB 可收到的負載。
OS、IRQ 及其他程序不會只因 benchmark affinity 就自動隔離。記錄干擾及實際 thread affinity。
啟動前重新核對 CPU topology；若與本輪盤點不符，重新產生配置，不盲用上述 CPU IDs。
不得把同一個 core 的 SMT siblings 當作互不干擾的 physical cores。
S1 到 S2 增加有效 physical DB CPU；S2 到 S4 啟用 SMT，結果包含 CPU 增量，不能宣稱固定 CPU 下的純軟體效益。
每 case 必須記錄 cpuset、SMT 關係、Tokio workers、Scylla shards、memory budget、driver connections 與全域 in-flight 上限。
Scylla memory 不得隨 case 自動吞用全部主機記憶體。
同機三個 node 仍共用磁碟、kernel 與主機故障域。
三份 fsync 不等於三份獨立硬體耐久副本。
不得把這個結果描述為跨機 network 或 fault-tolerance benchmark。

本輪磁碟可用空間約 44 GiB；這是一次性觀察值，不是容量承諾。
正式 preflight 須估算三副本、commitlog、SSTables、compaction 暫存及 artifact 所需容量，另留 reserve。
舊 CPU busy 10% 門檻不能直接套在已啟動的 Scylla polling reactors 上。
須分開記錄啟動前主機閒置與啟動後 reactor idle baseline。
儲存空間不足、背景 I/O 未穩定或配置不符時停止 trial。
不得靜默放寬門檻。

## 監控要求

| 範圍 | 指標與解讀 |
| --- | --- |
| Client | 同一量測窗的 logical request RPS、成功／replay／拒絕／conflict／未知結果數、latency p50/p95/p99/p99.9/max 與 sample count。尾端樣本不足時標示限制。 |
| Service | Queue wait、admission/backpressure、同人等待、batch wait/build、DB read/decode、計算、DB write await、reply、in-flight peak、DB worker C、busy/idle workers、worker queue wait、event-loop heartbeat 及 missed ticks。 |
| CPU/Memory | Service、load generator、每個 node 與監控程序的 CPU、CPU microseconds/request、RSS、peak RSS、context switches。另報總量與計時邊界。 |
| Storage | Process I/O、共用 device I/O、disk busy、bytes/request、commitlog bytes/sync count/sync duration、memtable flush、compaction、stall 或等價 backlog。指標依固定版本確認。 |
| Scylla | 每 node／shard 的 requests、CPU/reactor utilization、queue/backlog、cache、memory、timeouts、overload、dropped requests、replica/coordinator latency。不能用 reactor polling CPU 單獨推論飽和。 |
| Network | Client-to-node 與 node-to-node 流量、目標及實際資料連線數、control connections、worker/connection mapping（若可取得；無法取得時標示 unavailable）、driver retries、speculative execution、rerouting。Loopback traffic 與 physical NIC traffic 分開。 |
| Correctness | 每人最終 balance、ledger count/content、交易順序／version、完整 key 防重、replay 不新增記錄、所有成功 ack 的交易均可讀回。 |
| Artifact | 每 trial 原始資料、參數、版本、source hashes、dirty worktree、執行順序、錯誤、cleanup status。 |

不存在的 RocksDB counters 不得假造為 Scylla 指標。
若未啟用 projection、watermark 或 safe GC，相關舊指標標示 N/A 並說明範圍。
每 trial 先計算自己的分位數，再彙整各 trial 的 median/min/max。
不得平均各 shard 的 percentile，也不得將不同 stage 的 p99 相加。
共用裝置指標只計一次，不將三個 node 觀察到的同一 device counters 相加。
CPU 與 I/O 的 window、取樣偏移及監控成本須列入報告。
必要監控缺失時，trial 不可標為可用正式結果。

## 錯誤處理要求

| 情況 | 必要行為 |
| --- | --- |
| Admission 前拒絕或 timeout | 明確回傳未接受；不提交 DB mutation。 |
| DB write timeout、斷線、服務取消或 reply 遺失 | 結果為未知。不得回報確定未提交，不得換 key 重試，不得直接重新加減 balance。 |
| 未知交易查無 ledger | 不足以證明不曾提交；舊寫入仍可能在進行。同人維持停止狀態，直到安全核對或 fail closed。 |
| Driver retry/speculation | 一般 read-modify-write 的主測試建議關閉寫入自動重試及 speculative execution。若啟用，須先證明 mutation 冪等且不會覆蓋較新 balance。 |
| 相同 key、相同 body | 回傳原結果，不再次修改 balance 或配置新 version。 |
| 相同 key、不同 body | 回傳 conflict。不得覆寫原交易。 |
| 餘額不足、溢位或非法金額 | 保存可重播的拒絕結果。不得只回傳暫時錯誤。 |
| 任一 node 不可用 | RF=3/CL=THREE 下停止成功 ack。不得降級 CL 以完成 bench。未知結果另計。 |
| Balance 與 ledger 不符、缺成功交易或順序倒退 | Trial 失敗。保留診斷資訊，不發布效能勝負。 |
| Node/服務 crash 後重啟 | 核對所有已確認成功交易；未知交易可已提交，但必須符合 balance/ledger invariants。Process crash 測試不等於斷電證明。 |
| 清理失敗 | 回報未清理路徑及失敗原因。結果標示 infrastructure failure，不宣稱資料已清除。 |

Fault injection 與正式性能 trial 分開。
不將錯誤重試後的成功吞吐混成無錯誤 baseline。
跨 node 的單 partition atomicity 不等於同一時刻所有副本可見。

## 驗證與清理

每個 trial 使用新的 owned cluster data 或可證明等價的 fresh storage。
Seed、warm-up、計時窗、drain、讀回驗證與 cleanup 分開記錄。
Finite closed-loop workload 的 RPS 不是 steady-state capacity，也不代表已找到飽和點。正式報告須保留這項限制。
建議在正常完成後停止負載、等待本輪 in-flight 結束，核對全部資料，再停止本輪服務及 node。
確認所有本輪程序與 handles 已停止後，刪除本輪的 data、commitlog、hints、cache 及自有 volume。
僅刪除本輪 manifest 記錄的 owned resources。
不得清除既有叢集、使用者資料或 benchmark archive。
只執行 DROP/TRUNCATE 不代表磁碟資料已清除。
失敗路徑也須嘗試安全關閉與清理。
若不能確認程序已停止，先保留資料並明確回報；後續完成關閉後再清理。
原始 logs、CSV、設定、source hashes 及 cleanup audit 保留。

## 預定 execution flow

下列名稱是預定函式責任，不代表現有程式已有這些函式。
實作設計凍結前，不以此圖宣稱實作完成。
CQL 送出政策在 worker scaling 矩陣內固定。C 個 workers 共用 Session，資料連線目標總數為 C，不要求獨占綁定。
Mixed case 的未知結果會凍結該 CQL request 包含的所有 account；正式 case 均使用受測 release 已驗證的同步 commitlog 設定。

```text
Client request(key, body)
  |
  v
validate_request()
  |
  v
admit_bounded() --> rejected before acceptance
  |
  v
sequence_account_owner(account_id)
  |
  v
dispatch_to_db_workers(C; fixed CQL policy)
  |
  v
read_account_and_transaction(CL=THREE)
  |
  +--> existing same body --> confirm_replay_durability() --> saved reply
  +--> existing other body --> conflict
  |
  v
compute_wallet_result()
  |
  v
build_mutations_grouped_by_partition()
  |
  v
submit_one_cql_at_a_time_per_worker(CL=THREE)
  |
  +--> replica node A: commitlog -> fsync -> ack
  +--> replica node B: commitlog -> fsync -> ack
  +--> replica node C: commitlog -> fsync -> ack
  |
  +--> uncertain --> stop_account() -> reconcile_or_fail_closed()
  |
  v
reply_after_three_durable_acks()
  |
  v
release_account_sequence()

Trial end
  -> stop_admission()
  -> drain_in_flight()
  -> verify_balance_and_ledger()
  -> stop_owned_processes()
  -> remove_owned_storage()
  -> write_cleanup_audit_and_report()
```

## 驗收條件

1. 已確認決策 D01 至 D07 與使用者補充一致；1:1 採共用 Session 與總數相等語意。正式矩陣前另凍結版本及設計參數。
2. 每個人保持獨立 partition。所有同人必要變更在同一原子提交範圍內。
3. 三個 replica 在 fsync 後回覆。服務收到要求的三份成功回覆後才回成功。
4. 固定總請求數及 CQL 送出政策，比較不同 C 的 DB workers 與 C 條目標資料連線。不存在的逐筆 fsync 模式明示不支援。
5. Sequential 由服務驗證，不依賴 benchmark client 的發送模式。
6. CPU affinity、SMT、memory、driver concurrency 及共用磁碟限制可稽核。
7. Trial 有完整監控、correctness gate、錯誤分類及 cleanup audit。
8. 完整矩陣通過後才發布正式結論；smoke 及 partial run 明確標示。
9. 本輪先交付需求評估，不修改服務、不部署 ScyllaDB、不執行 bench。

本輪記錄：使用者已確認：接受 SMT；只做 Credit/Debit；所有正式 case fsync 後 ack；單一服務、account owner sequential。多個 DB workers 共用一個 Arc<Session>，不要求 worker 獨占連線。

使用者後續修訂：服務端固定請求數，變動 DB worker coroutine 數，connection pool 數與 DB workers 採 1:1。先前獨立 sweep connections per shard 的主矩陣建議由此取代。

使用者最終確認：共用 Session 可以；不要求 DB worker 獨占實體連線。需求範圍確認完成。
