## 固定工作負載

| 項目 | C=256 | 條件式 C=512 |
|---|---:|---:|
| Node count / RF / wallet CL | 1 / RF1 / read-write ONE | 相同 |
| Shards / P / D | S=2 / P=3 / D=6 | 相同 |
| Workers / in-flight bound | C=256 | C=512 |
| Worker ratio / routing | worker:C 1:1 / round-robin | 相同 |
| Users / requests per user | 1,024 / 1,000 sequential；每位 user 收到 reply 後再送下一筆 | 相同 |
| Accepted request target | 1,024,000 | 1,024,000 |
| Operations | 512,000 Credit + 512,000 Debit | 相同 |
| CPU / memory | node `0,1`; service/load/monitor `6,7,14,15`; node 8 GiB; container 10 GiB; no CPU quota | 相同 |
| Pool target | 每 shard P=3，總 D=6 | 固定 D=6，不隨 C 變動 |

Keyspace 使用 RF1 與 `durable_writes=true`。Wallet read/write CL 為 `ONE`，serial CL 為 `LOCAL_SERIAL`。沿用 memory cache 與同 partition 單 conditional insert LWT。Measurement 中不應有 SELECT。Commitlog 使用 batch sync，`O_DSYNC=false`，成功回覆等待 write CL 的 fsync acknowledgement。不得將 batch fsync 說成每 request 一次 fsync。

S=2 基線來自 01-53 的 C=128 single-repeat diagnostic case。該基線不重新執行。C=256 case 完成後，job supervisor 讀取 Rust result、observer analysis 和保存的 Prometheus evidence，對基線比較四個 continuation gates：RPS 至少 1.10 倍、E2E p99 最多 2 倍、LWT p99 最多 2 倍、I/O observer 與 metric collection 有效。每一 gate 都必須保存實際值、baseline 值、limit、pass/fail 和決策理由。只有 supervisor 可依此決定是否啟動 C=512；unchanged runner 只執行一個指定 case 並保存該 case evidence。這些是 continuation controls，不是統計測試或服務目標。

## Runner、observer 與 supervisor 流程

1. 驗證 frozen source、binary、runner 與 budget SHA。重新執行 strict preflight。需要可用空間 `max(64 GiB, estimated bytes)`、CPU busy ≤10%、device busy ≤5%、available memory ≥32 GiB、AIO gate 通過與三個連續 passing samples。
2. 啟動 `benches/scylla_io_observer.py`，確認 process ready、disk identity 正確，並開始帶單調時鐘和 UTC timestamp 的 1 Hz samples。Observer 在 workload window 前啟動，於 case cleanup 後停止；保存 exit status、最大 sample gap、reset/parse errors 和原始 samples。
3. 建立單一 fresh owned node。確認 CPU affinity、8 GiB memory、10 GiB container limit、I/O properties runtime load、AIO、commitlog 和 keyspace RF/CL。以受限 setup concurrency seed/preload，且不把 setup 納入 measured window。
4. 啟動 Rust CLI，執行 S2/C256、1,024×1,000。Window 為第一個 client 實際開始前到最後一個 reply，包含 admission、owner、DB queue 和 commit latency。所有操作依照 existing Wallet service。
5. 完成 drain。先全量比對 memory cache、account static state 和 ledger。保存 Rust result 與既有 raw Prometheus scrape。停止 node，核對 ownership 後只清除本 case data/network；停止 host observer，分析 diskstats 與保存的 Prometheus samples，再保存 cleanup 和 analysis evidence。
6. Job supervisor 讀取 C=256 的完整 evidence。只有 case 無任何問題且四個 continuation gates 全 pass，supervisor 才啟動新的 unchanged runner process 執行 fresh owned C=512 case。若 strict validation、correctness、observer、cleanup 或其他 mandatory gate 失敗，supervisor 停止 campaign，不自動 retry。若 C=256 case 本身通過但 continuation gate 未全通過，supervisor 寫出 skip reason，不執行 C=512。

S1/S2/C=128 baseline 不屬於本次 campaign。不得新增 smoke 或重新 calibration。Observer 每個 case 必須明確標出 `ready`、`started`、`stopped`、`exit status` 和 samples 文件；runner 不可以從一個空檔推定 0 latency 或 0 flush。

## I/O observer 設計

Observer collector 是 read-only host process，使用 Python 標準 library 讀取 `/proc/diskstats`、`/sys/dev/block` 和 `/sys/class/block`。它不得使用 shell 寫入 sysfs，不得執行 benchmark、fsync probe 或額外 HTTP scrape。每秒將原始 counter JSON record append 至該 case 的 observer JSONL，並即時 flush。Record 至少含：

- UTC timestamp、monotonic timestamp、sample sequence 和 observer PID。
- Partition identity：`8:18`、`/dev/sdb2`、sysfs parent；whole identity：`8:16`、`/dev/sdb`。
- Partition 與 whole 的原始 diskstats 欄位，分別保存，不合併或相加。
- Whole-device 原始 flush count/time、read/write sectors/operations/time、I/O in-progress、busy milliseconds 和 weighted-I/O-time counters。
- Parse status、counter reset flag、identity validation 和與上一筆的 sample gap。

Observer analyzer 從 raw diskstats samples 計算 read/write rates、average queue、busy percentage 和 whole-device flush await。Counter delta 除以兩筆有效 sample 的實際 elapsed time。Whole-device flush count delta 為 0 時，flush await 為 `N/A`。原始 counter 與 derived values 分開保存。Counter decrease 或 identity mismatch 使 observer validity 失敗。最大 sample gap 必須 ≤2.5 秒。Observer early exit、missing sample/required metric、counter reset、file write error 或 invalid identity，均使 case invalid，且禁止 C=512。

Scylla metrics 使用既有 per-node Prometheus scrape。Runner 只保存 raw Prometheus samples，不增加 HTTP scrape，也不解析 counter。Observer analyzer 從保存的 raw samples 取每個 node、shard、class=`main`/`commitlog` 和 data mountpoint 的 total ops、delay、exec counters，再產生 start/end、delta、elapsed 和 window mean。任何必要 metric 缺漏、reset 或解析錯誤都使 case invalid。外部 host observer、Scylla metric analyzer 和 process monitor 是不同資料來源；報告要分開呈現。

Whole device 的 flush await 是 host block layer 統計，不是 wallet request 的 fsync latency。partition 和 whole device counters 可能包含相同 I/O，不可相加。高 disk busy 不能單獨證明 device saturation；要一起檢查 throughput、queue depth、Scylla commitlog class、service CPU、DB queue、LWT latency 和 errors。

## Result、verification 與 audit

Rust result 必須保留既有成功要求：attempted/accepted/replied/applied 各 1,024,000；operation 各 512,000；1,024 cache accounts 和 1,024,000 ledger rows 全量驗證；measured SELECT=0；driver query delta=1,024,000；driver errors/retries/connection/request timeouts 與 unknown errors 為 0。D 固定 6，pool sampler min/max/after-last-reply 都是 6；worker busy/current/peak 不超過 C。失敗時 result 保留原始 error samples、server/driver counters、partial verification 和 cleanup status。

Runner 必須保留：job launch/freeze manifest、每 case strict preflight、node inventory、source/binary/budget hashes、observer stdout/stderr、observer raw JSONL、observer analysis、Prometheus raw samples、runtime profile validation、Rust events/result、latency/stage histograms、driver counters、per-shard commitlog counters、process/device samples、verification、continuation gate 與 ownership cleanup audit。Job supervisor 必須保留 C=256 gate evaluation 及 C=512 launch/skip decision。每一個 case 使用全新 owned data。Cleanup 不得刪除無法確認 owned 的資源。

## 流程圖

```text
Campaign
  validate source/binary/runner/budget hashes
  -> strict preflight (3 consecutive passes)
  -> start 1 Hz host I/O observer
  -> create fresh node -> validate runtime AIO/I/O/commitlog profile
  -> bounded seed/preload -> run C=256 workload
  -> drain -> full wallet verification -> stop/inspect/clean node
  -> stop observer -> validate host + Scylla counter evidence
  -> observer analyzer derives diskstats and Scylla metrics
  -> supervisor compares with C=128 baseline and evaluates 4 gates
  -> supervisor starts C=512 once, or saves skip decision and stops

Wallet request
  run_clients -> run_client -> Service::submit
  -> owner lock + enqueue -> worker_loop -> process_job/cache compute
  -> ScyllaStore::commit (one conditional INSERT LWT)
  -> batch fsync -> CL ONE acknowledgement
  -> publish cache on Applied -> reply

After all replies
  verify_all -> verify_account / verify_one_account -> owned cleanup
```

只有全量正確性、必需 metrics、I/O observer、hash 與 cleanup 都通過的 case 才能列為通過。C=512 的 skip 是有效 continuation decision，不是失敗 case，也不表示 C=256 達到長期飽和。此次診斷只測一個 Scylla node 和共享主機裝置，不能推斷多故障域、RF3、steady-state 或 production SLA。
