## Profile 與 gate 驗證

唯一啟動的 case 使用 1,024 個 accounts，每個 account 預期 1,000 筆 amount 1 的 Credit/Debit 交替交易，初始 balance 100，總計預期 1,024,000 requests。沿用 ScyllaDB 2026.1.14 pinned image、RF3、read/write CL `THREE`、LWT serial CL `LOCAL_SERIAL`、`wallet-memory-lwt-v1`、每 accepted request 一個 conditional LWT、0 measured SELECT、commitlog batch、`commitlog_use_o_dsync=false` 及既有 deadline/no-retry profile。

這個 case 的 runtime、schema、strict preflight、required metrics、source/build correspondence、pool、socket audit 與 cleanup 驗證通過。CLI 因 storage failure 以 exit 1 結束，因此 final CLI profile validation 缺失或無效，正確性驗證未通過。

`S=2`，每 node 兩個 shards；`C=128`、`P=3`，每 node 預期 6 條 data connections，總計 `D=18`。Before/after connection audit 均觀察到 18 條 data connections、每 node 6 條，無 mismatch，socket window 穩定。Measured CQL in-flight peak 與 workers busy peak 均為 128；drain 後 workers idle。

預先核對的 CPU affinity 在 runtime 成立：node A shards 為 CPU `0,1`，node B 為 `2,3`，node C 為 `4,5`；每個 node 的兩個 reactor threads 均符合指定 CPU。Service、load、monitor 使用 CPU `6,7,14,15`。`lscpu` 核對實體核心配置。每 node memory profile 為 8 GiB，cgroup limit 為 10 GiB。三個 instance 共用同一 host 與 SSD。

## 儲存資源設定與 I/O 診斷

三個 Scylla log 都記錄沒有設定 `--io-properties` 或 `--io-properties-file`，並指出可用 `scylla_io_setup` 產生 I/O properties。實際啟動參數為 `developer-mode=1`、`io-setup=0`、`overprovisioned=1`；沒有 CPU quota 或 blkio limits。Host inventory 顯示三個 instance、作業系統及 commitlog 共用同一顆 CT1000BX500SSD1，掛載於 `/dev/sdb2` ext4 root filesystem。既有本機 profile 刻意不作 device autotune；runtime gate 驗證啟動設定，不代表已校準儲存裝置。Scylla 文件說明 `scylla_io_setup` 會產生 `io.conf` / I/O properties，但未設定這些 properties 本身不能證明它是本次失敗的唯一原因。[Scylla I/O setup 文件](https://docs.scylladb.com/manual/stable/getting-started/system-configuration.html)；[既有本機 profile 設計](01-32.development-design-scylladb-wallet-benchmark.md)。

同一 host device 的 1 秒 interval samples 顯示，measurement offset 約 137–141 秒時 device busy 為 96.6–97.7%、write await 為 0.50–0.51 ms、寫入約 91–97 MiB/s。Offset 約 143–151 秒時 busy 升至 99.9–100%；連續 write-await samples 為 71.01、78.37、93.69、85.66、87.01、73.37、96.54、93.21、127.77 ms，而寫入約 1.1–2.3 MiB/s。這與失敗前儲存延遲惡化同時發生。

這些 device 數值由 interval 差值計算：write await = `Δwrite_ms / Δcompleted_writes`，寫入 MiB/s = `Δwritten_sectors × 512 / Δtime / 2^20`，busy = `Δbusy_ms / (Δtime × 10)`。它們是整顆 host device 的聚合資料，包含其他 host I/O，不能當成每筆 wallet operation 的 fsync 延遲或歸屬證據。

三份 node log 在約 12:58:01–12:58:03 UTC 記錄 `system.paxos` CL ONE 收到 0/1 timeout，之後 client CAS write 出現 CL THREE 收到 2/3 的錯誤。這提供錯誤先後的觀測，但沒有證明 timeout 的底層機制。S1/C512 失敗窗口最後 5 秒也觀察到 device busy 約 100%、write await 2.71、21.01、21.21、25.28、24.97 ms，寫入約 29.37、14.26、7.52、9.33、5.70 MiB/s。I/O properties 未設定的警告也出現在已通過的 S1/C128 與 S1/C256，因此警告本身不能解釋 S2/C128 失敗。S1 的相似 device 訊號支持優先檢查 shared-storage path，但不足以證明兩次錯誤有相同根因。

目前沒有 CPU、記憶體或 commitlog 耗盡的證據：reactor CPU mean 為 A shard 0/1 `46.9439/47.898%`、B `47.6867/47.4941%`、C `43.8853/44.0392%`，各 reactor peak 均不超過 `81.862658%`；1 Hz sampling 不能排除短暫 stall。每 node cgroup 平均約使用 2 核中的 `0.949/0.951/0.891` 核，`nr_throttled` delta 為 0。所有 shard 的 `malloc_failed=0`，三 node `oom_killed=false`，memory.current peak 為 `2.211/2.229/2.205 GiB`。Commitlog pending allocation 為 0、blocked memory 為 0、flush-limit-exceeded 為 0，pending flush 最大值為 1–2。

根據目前證據，已確認 I/O properties 設定缺口，且失敗前觀察到儲存延遲明顯惡化；優先懷疑 shared SSD / I/O 排程路徑，但尚未證明缺少 properties 是唯一根因。CPU 或記憶體耗盡目前沒有證據。後續若要重測，先校準實際掛載的儲存裝置、分配三個 node 共用的 IOPS / bandwidth budget，並在 runtime 確認載入的 I/O properties；profile 確認後再 gated 重跑 S2/C128。這是待議的下一步，尚未執行，也不能保證能消除此錯誤。不變更 CL、timeout 或 retry，也不改動 NVMe format、mount 或 host 全域設定。

## 清理與結論

唯一啟動 case 的 owned cleanup 為 clean：三個 containers 已移除、network 已移除、三份 owned data 已移除，`errors=[]`、`retained_data=[]`。Job 在 case 失敗後停止，C=256/512/1,024 未啟動，沒有自動重試。

一次 S2/C128 失敗不能說明增加 shard 導致失敗，也不能建立 RF3 capacity 結論。同一 C/P 下，S2 對 S1 會使每 node reactor 數及每 node/cluster data connections 加倍；每 node memory 固定，故每 shard 可用 memory 減少。兩者共享 host SSD，profiles 不是單一變數對照。

下一步先檢查保存的 CAS timeout、node、I/O 與 Paxos 證據，再決定是否重測或繼續後續 C。不要自動變更 CL、deadline 或 retry policy，也不要把未知結果當作確定未提交。

## ASCII execution flow

```text
input
  -> run_clients -> run_client (wait for each reply)
  -> Service::submit -> account owner lock
  -> worker_loop (round-robin shared pool) -> process_job
  -> cached state compute -> ScyllaStore::commit
  -> one conditional INSERT ... IF NOT EXISTS
  -> LOCAL_SERIAL / regular CL=THREE / acknowledgement
  -> publish cache after Applied acknowledgement -> reply

after replies
  -> drain service -> verify cache, static state and ledger
  -> keep CLI Session open for runner connection/socket audit
  -> release finish gate -> CLI exits and closes Session
  -> cleanup owned containers, network and data -> report

unknown outcome or invalid case
  -> freeze account and fail closed globally
  -> settle accepted work and retain partial evidence
  -> stop later cases -> cleanup owned resources -> report without retry
```
