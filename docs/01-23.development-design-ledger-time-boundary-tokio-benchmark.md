# Tokio 單 shard 交易時間分界與安全發布 benchmark 設計

## 範圍

此 benchmark 使用既有 `AccountStore` 與 bounded request batch queue，以單一 Tokio runtime、單一 RocksDB shard，量測交易時間分界的安全發布及舊時間歷史查詢。歷史目的端為 process 內的 `MockProjectionStore`。這是可重複執行的 benchmark/test harness，不是 production storage 實作；沒有 GC、外部 DB、跨 process 恢復或多 shard 保證。

程式分為幾個可獨立檢視的部分：

- `ledger_time_boundary.rs`：admission gate、guard/fence、contiguous projection progress、從 `AccountStore` sequence range 讀取並投影的 background worker、watermark manager 和舊時間查詢路由。
- `ledger_projection_worker.rs`：mock projection destination 的 apply、range query 與歷史查詢；查詢能區分 exact hit、conflict、not found 與實際錯誤。
- `ledger_account_store.rs`：沿用既有交易 batch 寫入，並在 RocksDB metadata namespace 持久化 watermark。
- `ledger_time_boundary_benchmark.rs`：固定工作負載、資源 preflight、計時、CSV/log、trial cleanup 及預設完整結果 archive。

## Admission、fence 與發布順序

時間戳使用 Unix microseconds，`W` 是目前已發布 watermark，候選值為 `C = max(0, now_us - retention_us)`。候選必須大於目前 `W` 才開始發布。

- `transaction_at < W`：走歷史 mock lookup。這些請求不屬於候選 fence 的 commit drain。
- `W <= transaction_at < C`：尚未 admission 的 request 等待 fence 完成；已取得 commit admission 的 request 由 guard 計數追蹤。
- `transaction_at >= C`：繼續走新交易 commit，不受此 fence 阻擋。

Commit guard 隨 accepted payload 進入 batch queue，完成後轉入 oneshot reply。caller 只有在觀察到回覆時才會釋放 guard；若 caller 在 enqueue 後取消，reply channel 所擁有的 guard 會在 receiver 關閉時釋放，不能提早讓 watermark manager 誤判交易已完成。歷史請求不會 enqueue。

Watermark manager 每隔一秒提出候選 `C`。發布步驟有固定順序：

1. 在 gate 安裝 `[W, C)` admission fence。
2. 等待這個範圍內已接受的 commit guards 全部釋放。
3. 此時讀取 AccountStore 最新 sequence 作為 target。
4. 等 projector 的 contiguous sequence 追到 target；投影失敗或逾時會使此輪失敗。
5. 透過 blocking pool 將 `C` 寫入 RocksDB metadata，使用同步 WAL write。
6. metadata 寫入成功後，才將 gate 的 in-memory `W` 發布為 `C` 並解除 fence。

候選失敗時，guard lease 取消 fence、維持舊 `W`，錯誤傳回 benchmark 並終止 trial，不進行無限重試。Manager 收到 shutdown 時會完成已開始的 advance（直到發布或回報錯誤）後再停止，避免取消非同步等待後，背景 `spawn_blocking` WAL 寫入晚於 fence release 完成。

## 持久化界線與恢復限制

Watermark metadata 使用 account-store 既有 DB namespace；測試以共享 RocksDB database 的不同 shard namespace 驗證隔離及 durable roundtrip。這不代表舊歷史 destination 可恢復：`MockProjectionStore` 是 volatile 的，benchmark 沒有把完整 projection 持久化，也沒有在 restart 時重建投影後安全載入舊 watermark。故此持久化步驟只驗證安全發布順序，不能解讀為 restart-safe historical lookup、GC 或 production durability 保證。

## 工作負載與資料分布

預設建立 50,000 個 user 與 50,000 個 coroutine，一個 coroutine 固定服務一個 user；收到前一筆回覆才送下一筆。每個 user 執行 200 requests，四個 case 各有 10,000,000 個 measured requests，old mix 為 0%、1%、5%、10%。一個 user 的 200 slots 透過 `(request_index * 37 + splitmix64(user) % 200) % 200` 排列；37 與 200 互質，因此每個 user 的每輪都剛好包含 `old_pct` 個 hit、`old_pct` 個 miss，其餘為 fresh commit，hit/miss 分散在 request positions。全 workload 的取樣依 `splitmix64(logical_id) % sample_stride == 0`，預設 stride 64；程式確認每個有 old traffic 的 case 都有 hit 與 miss latency samples。

每個 user 只有一筆實際 projector 產生的 seed transaction（`tx_id=0`）。Old hits 重複使用這 50,000 個 keys，old misses 使用唯一 absent keys；因此不能將它視為大型歷史 keyspace 的隨機存取分布。Fresh workload 全是 amount=1 的 credit。每個 case 完成所有 client replies 後，benchmark 在 `client_wall` 結束之外逐一檢查全部 user 的記憶體餘額，預期為 `1 + requests_per_user * (100 - old_pct) / 100`；任何帳戶不符即令 case 失敗。

Runtime 有 4 個 worker threads。Commit queue 容量 50,000、batch size 2,048、timeout 5 ms；projector batch size 256。歷史 lookup 使用預設 10 ms 非同步合成延遲。每個 case 在建立 RocksDB/mock projection 及 seed 前、以及 measured window 前各執行嚴格 idle/resource preflight；不因 preflight 未通過而降門檻或省略 case。

## 計時與報告解讀

`client_wall` 從 client coroutine 開始送 measured request 到最後一筆 reply 被觀察為止，用於 fresh/old/total completed RPS。`settled_wall` 與 process CPU seconds 涵蓋 measured start 到 projector drain、manager/queue/projector/store 停止及其量測 checkpoint。每 request 記錄 overall、admission、enqueue、queue、batch、handler、response；old request 另記 lookup span。CSV 也記錄 projection/watermark stage percentile、process 及目標裝置 I/O、RocksDB WAL/flush/compaction/stall 計數、preflight、RSS 與 DB 大小。各 stage percentile 分別計算，不可相加；程式沒有 per-request residual/scheduler-staging span。

測試涵蓋嚴格 `< W` 邊界、active/queued/cancelled request drain、projection lag、durable write ordering、持久化錯誤時舊 `W` 不變，以及 hit/miss/conflict/not-found。完整預設 benchmark 若完成四個 case 才寫 canonical CSV/log。非預設參數不會覆寫該 archive。單次 case 的 RPS 僅為該次描述性量測，不能用不同 mix 的一次執行宣稱因果差異。若 `fenced_admissions=0`，代表量測窗口內沒有 admission 等待 fence，不是 contended fence 的效能樣本。
