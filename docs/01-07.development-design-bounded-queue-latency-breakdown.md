# Bounded Queue latency breakdown subdevelopment

## 目的

在既有 `bounded_queue_hashmap` 同步 pipeline benchmark 中，逐筆量出完整 request latency 的四段來源，說明 send/receive 呼叫或 batch map update 本身很短時，為何完整 pipeline latency 仍可能較長。保留 01-06 的原始 harness 指標與設計；本文件只補充逐筆 latency 分解。

## 同一 request 的邊界

所有時間點都使用 request ID 對應的同一筆 `Instant`，並以半開區間相減：

| 時間點 | 定義 |
| --- | --- |
| t0 | Producer 開始嘗試 blocking send；沿用 `Request.started_at`。 |
| t2 | Worker 的 `recv` 或 `recv_timeout` 成功返回時，立即取一次時間。 |
| t3 | 該 batch 的 HashMap 更新開始前，使用現有 batch active timer 的起點。 |
| t4 | 該 batch 全部 HashMap 更新及本地 response staging 完成、response channel send 尚未開始時，使用現有 batch active timer 的終點；同批 response 共用此時間。 |
| t6 | Collector 收到該 response 時；沿用 `response_received_at`。 |

分解為四段：

| 指標 | 定義 | 含義 |
| --- | --- | --- |
| `submit_to_dequeue` | t2 − t0 | 含 Producer 的 blocking send 及 request queue 內等待，不能解讀為純 queue wait。 |
| `batch_wait` | t3 − t2 | 該筆 dequeue 後等待 batch 開始更新的時間。 |
| `batch_service` | t4 − t3 | 每筆都承擔整個 batch 的 map update 與 response staging 時間；此值不等於舊的 active ns/item。 |
| `response_delivery` | t6 − t4 | 含 worker 的 response send 阻塞、response queue 等待及 collector 取出 response。 |

同一筆的四段首尾相接，故其 nanoseconds 總和必須精確等於 t6 − t0。每輪四段的 count 都必須等於 N；任一段 count 不符或四段 `total_nanos` 總和不等於 pipeline latency 的 `total_nanos`，benchmark 以錯誤結束。此等式使用整數 nanosecond 累加，不比較浮點平均值。

`sync_channel` 沒有公開訊息精確成功入列的 timestamp，且 receiver 可在 `send` 返回前拿到訊息，因此不能把 send 返回時間設為 t1 並切出不重疊的 enqueue 與 queue-wait 兩段。既有 producer `send` 呼叫 latency 仍保留作獨立指標，不加入此四段。

## 計量與抽樣

Worker 每次成功 receive 只取一次 t2，並將它與 request 一起保存至 batch。Flush 時用現有 active timer 的起訖取得 t3/t4；同批所有 response 共用 t4。Collector 收到 response 時取得 t6。逐筆記錄使用已保存的 t0/t2 和 batch 共用 t3/t4 計算，不在 batch active timer 中為每筆再讀取時鐘。原有 batch active timer、flush 次數、RPS、CPU 等輸出維持可用。

四段 mean 都以 `LatencyAccumulator` 累積完整 N 筆真實 duration，並輸出 count、sample count 及 total nanoseconds。四段的 p50/p95/p99 沿用相同、起跑前建好的 `SamplePlan`，按 request ID 選出同一批樣本並使用 nearest-rank。預設 stride 為 1024；stride=1 時每筆取樣。跨輪摘要逐欄輸出各輪值的中位數，並標示每輪的整數總和驗證結果。

逐筆四段可加總，所以四段平均值（以 total nanoseconds / N 計算）應加總為完整 pipeline 平均值；各段 p50/p95/p99 是各自排序後的分位數，並非同一筆的分段值，不能直接相加推算完整 latency 分位數。`batch_service` 讓該 batch 的所有筆都承擔 batch 整體耗時；舊的 `map_update_avg_ns_per_item` 則是 batch active time / N，意義不同，兩者都保留。

## 輸出與相容性

每輪和跨輪摘要輸出四段各自的 mean、p50、p95、p99、count 和 sample count，以及 breakdown/pipeline 的 total nanoseconds 與驗證狀態。完整矩陣報告另外列出 16 個情境四段 latency，統一以微秒呈現，並保留原有 throughput、enqueue/dequeue call、batch、flush 與 CPU 表格。

加入 t2 和 t6 timestamp、四個 accumulator 更新與 t4 傳遞會改變 benchmark 的計量成本，因此新版完整矩陣結果不能直接與舊版報告數值比較。新數據代表加入此分解後的量測版本。報告仍只執行每情境一輪，沒有輪間變異估計；百分位數依 deterministic sample plan 抽樣。

## 驗證

依序執行 `cargo fmt --check`、`cargo check --benches --locked`、完整 16 組短矩陣、涵蓋 tail/full flush 的邊界短跑，以及預設每組 10,000,000 筆的完整 16 組矩陣。每輪驗證 response ID/count、map 最終狀態、四段 count=N 及四段總和精確等於 pipeline total nanoseconds。

完整設計沿革見 [01-06 bounded queue HashMap benchmark](01-06.development-design-bounded-queue-hashmap-benchmark.md)，實測數據見 [benchmark report](../benches/bounded_queue_hashmap_report.md)。
