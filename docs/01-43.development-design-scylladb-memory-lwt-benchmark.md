# 帳戶記憶體狀態與單 CQL LWT Wallet 基準

## 狀態與範圍

本文件定義 `wallet-memory-lwt-v1` 的實作與驗證邊界。結果文件保留為 `docs/01-44`，不得在執行驗證前填入測試結果。

本 profile 只改變帳戶狀態來源和每筆交易的 CQL 寫入方式。它使用預載的帳戶狀態和一個 conditional `INSERT ... IF NOT EXISTS`。它不改變已確認的 ScyllaDB cluster、一般讀寫 consistency levels、CPU profile、commitlog batch fsync 確認、strict gate 或 cleanup 契約。

## Schema 與一致性設定

使用每帳戶單一 partition，主鍵如下：

```sql
PRIMARY KEY ((account_id), kind, tx_id)
```

`kind=0, tx_id=0` 是 metadata sentinel；`kind=1` 是 ledger。`balance`、`version` 與 `write_clock` 為 static 欄位。Ledger 欄位保存 operation、amount、outcome、balance_after、ledger_version 與 ledger_write_clock。Seed 的 `write_clock` 初值為 0。每筆新交易（包括持久化的業務拒絕）以 checked arithmetic 計算 `previous_write_clock + 1`；溢位時不得送出該寫入。Logical clock 獨立於 wall clock 與資料庫時間，不是 CQL timestamp。Request、ledger、verify API 均不含 `transaction_at`。

Logical write clock 是 wallet row 的資料欄位。不得把它轉成 CQL timestamp。條件寫入與 seed 都使用 LWT，不附 `USING TIMESTAMP`。使用 `LOCAL_SERIAL` serial consistency；一般讀與寫 CL 使用既有 profile 的明確設定。Pool、keyspace RF、tablets 與既有來源稽核維持不變。

每筆交易使用一個 CQL statement，在同一個 partition row 寫入 static state 與 ledger row：

```sql
INSERT INTO wallet (...static state..., ...ledger fields...)
VALUES (...)
IF NOT EXISTS
```

不得以普通 CQL BATCH 包住此 statement，也不得拆成多個 CQL request。LWT 內部的 Paxos 往返不計為額外 client statement。Commitlog batch fsync 設定維持原值；它與 wallet transaction 的 CQL batch 是不同機制。

## Seed、預載與交易流程

每個 trial 使用新 keyspace。Seed 在 measurement gate 前執行，使用 LWT 建立 metadata sentinel 和初始帳戶狀態。Seed 後逐帳戶載入 `AccountState`，並建立有限帳戶集合的 owner 與 cache。預載併發限制為 `min(C, D)`。全部預載及必要驗證完成後才開啟 gate。計時交易路徑不執行 SELECT。Unknown outcome 後的 process restart recovery 不支援；即使 preload API 能讀取非零狀態，也不得視為支援 restart recovery。

單一 service 持有共享 `Arc<Session>`。`C` 表示 worker 和應用層最大 in-flight 上限；`D` 表示實際固定 data connections。兩者分開配置及稽核，不推定一個 worker 對應一條連線。

每個帳戶只有一個 owner。Owner 依序從快取讀取目前狀態、計算下一狀態與結果、送出 LWT，並等候資料庫 acknowledgement。成功套用後才發布新狀態至 cache，然後回覆 caller。不同帳戶可以並行處理。

```text
input
  -> run_clients
  -> run_client
  -> Service::submit
  -> account owner lock
  -> worker_loop
  -> process_job
  -> read cached AccountState and compute outcome / next state
  -> ScyllaStore::commit
  -> one kind=1 INSERT ... IF NOT EXISTS
  -> LOCAL_SERIAL Paxos / regular write CL / acknowledgement
  -> publish cache after Applied acknowledgement
  -> reply

unknown write result or invalid response
  -> freeze account and fail admission closed
  -> drain accepted work
  -> compare ScyllaDB ledger with cached snapshot
  -> cleanup owned resources
  -> report failed trial
```

服務流程使用 `Service::submit`、`worker_loop`、`process_job` 與 `ScyllaStore::commit`。所有 worker 共用 `Arc<Session>`；worker 數不代表 socket 數。

## LWT 結果處理

對新 key，依 cache 計算新的 static state 和 ledger 結果，放進同一個 `INSERT IF NOT EXISTS`。新的交易包含成功交易及業務拒絕。業務拒絕不改 balance，但依 wallet version 與 logical clock 契約保存拒絕結果。

若 `[applied] = true`，在 acknowledgement 成功且回應可解碼後發布 cache 狀態並回覆結果。若寫入已送出，但 timeout、driver error 或 response decode error 使結果不確定，回 `CommitOutcomeUnknown`，凍結帳戶並 fail-closed；不得猜測沒有提交，也不得重送。

若 `[applied] = false`，不重寫 wallet row，也不前進 cache；Paxos 內部仍可能寫入或 fsync。比對同一冪等鍵的已存 body。相同 body 回傳原本已 durable 的 ledger 結果，並保留目前較新的 cache/static state；不得用舊 ledger 的 `balance_after` 覆寫目前 balance、version 或 clock。未 applied 回傳的 static state 必須符合目前 cache。較早 ledger 的 `balance_after` 與目前 balance 不同是合法情況，前提是 static state 與 cache 一致且該帳戶已有後續交易。不同 body 回 Conflict。若既有 ledger 與 static state 或 cache 關係違反不變量，回 Corruption 並凍結該帳戶。

冪等鍵是 `(account_id, kind=1, tx_id)`。相同 `tx_id` 在不同 partition 獨立。LWT 條件檢查指定 ledger row 是否存在；Paxos 共識在 partition 範圍執行。它不驗證另一個 `tx_id` 所依賴的 cache state 是否最新。因此本 profile 必須維持單 service、單帳戶 owner 及禁止外部 writer。跨 process recovery、multi-service write 與 fencing 均不在本次範圍。

## 取消、失敗與完成驗證

成功 enqueue 是 admission 線性化點。Caller 在此後取消，不會取消已接受的 worker 工作。Shutdown 先停止 admission，再 drain worker，最後以資料庫 ledger 和已確認的 cache snapshot 驗證帳戶。Unknown outcome、Conflict 或 Corruption 不得被轉成成功結果。

驗證需覆蓋相同 body replay 不改 wallet row、不前進 cache 且不回退 cache；此項不要求 Paxos 內部 fsync 數為零。另驗證不同 body conflict、拒絕交易持久化、不同帳戶可並行、同帳戶循序、u64 overflow、未知結果凍結，以及取消 caller 後完成 accepted work。Live integration 使用新建且由 trial ownership marker 管理的 keyspace；只清理本 trial 擁有的資源。最終 verify 必須記錄實際完成比較的 cache account 數量及預期數量，並確認 ledger 與 cache 的一致性。小型 live validation 如時間允許可加 RF1/CL1 smoke；不因此放寬 strict gate。Cleanup 後保留驗證與 ownership evidence。

本次先完成 unit tests、build/format checks 及小型 owned live integration；如時間允許，包含 RF1/CL1 smoke。10M 效能比較另列後續工作。測試失敗時保留錯誤、driver counters、metrics、驗證結果與 cleanup evidence；不得藉由改 timeout、retry 或 CL 讓結果通過。

## Metrics 與分組

每個 case 必須輸出並核對：

| 欄位 | 固定值或定義 |
|---|---|
| `wallet_profile` | `wallet-memory-lwt-v1` |
| `account_state_source` | `memory` |
| `ledger_key` | `['account_id','kind','tx_id']` |
| `serial_cl` | `LOCAL_SERIAL` |
| `cql_requests_per_transaction` | `1` |
| `cql_statement_count` | `1` |
| pool target | 獨立記錄 `D`，以實際連線數稽核 |
| worker / in-flight target | 獨立記錄 `C` |

Seed 和預載發生在 measurement gate 外，必須標出其操作和併發數。LWT 的內部 Paxos 活動不應描述成單一內部操作。新 profile 的 case ID、metadata 和彙總資料須與歷史三 CQL profile 分開，避免將不同協定放在同一組比較。

## 取捨與限制

此設計以每帳戶記憶體狀態減少計時區間中的讀取，但需要明確的單一 owner、acknowledgement 後才發布 cache，以及未知結果時 fail-closed。LWT 的 Paxos 成本仍需實測。沒有測量資料前，不宣稱較快。

RF1 沒有 replica failover；唯一副本所在節點不可用時，其資料不可用，永久磁碟遺失也沒有其他副本可恢復。採用本 profile 不改變這項限制。
