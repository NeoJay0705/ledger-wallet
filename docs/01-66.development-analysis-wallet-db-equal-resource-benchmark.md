## 固定條件與執行路徑

每個案例只啟動一種 DB。Database CPU affinity 為 `0,1`，container memory 為 10 GiB，無額外 swap，也不設 CPU quota。兩種 DB 使用相同 Docker I/O caps，裝置為 `/dev/sdb` (`8:16`)：read 403,631,184 B/s、write 152,226,096 B/s、read 24,497 IOPS、write 23,500 IOPS。資料 filesystem 是 `/dev/sdb2` (`8:18`) ext4。Service、client、monitor 使用 CPU `6,7,14,15`。DB CPU 0、1 是兩個不同的 physical core（siblings 為 8、9）；service 使用兩組 SMT siblings：6/14 和 7/15。

Scylla 使用單一 node、S=2、RF=1、durable_writes=true、read/write CL ONE、serial CL LOCAL_SERIAL、P=3、D=6、batch commitlog、O_DSYNC=false、node memory 8 GiB，並保留 calibrated I/O budget（SHA-256 `12bf0b79c4520ca6d00183ca14b87d321b9221b687cc6e889619876f5b87b2bf`）。PostgreSQL 使用 pinned Official Image 18.6：`docker.io/library/postgres@sha256:afc7e2d441324c0388fa80c3d24f733b4194a4eb7f47dd8ee2b08eb1a24a647c`；正式 pool D=16。PostgreSQL 設定如下：shared_buffers=2GB、work_mem=4MB、maintenance_work_mem=256MB、autovacuum_work_mem=64MB、max_connections=100、fsync=on、synchronous_commit=on、full_page_writes=on、wal_sync_method=fdatasync、commit_delay=0、wal_level=replica、checkpoint_timeout=5min、max_wal_size=1GB、autovacuum=on、track_io_timing=on、track_wal_io_timing=on。

Workload 使用 C=512、queue capacity 50,000、1,024 users × 1,000 requests，共 1,024,000 筆操作；Credit 和 Debit 各 512,000 筆，amount=1，每個 account 同時只有一筆未完成 request。先執行 PG D=16/32/64 calibration，再從達到最高有效 RPS 95% 的設定中選最小 D。之後執行六個全新 full cases：Scylla／PG／PG／Scylla／Scylla／PG，各三次。

    input
      -> Service::submit (接收請求 / account-owner lock；回覆前持續持有 lock)
      -> worker queue (工作佇列)
      -> worker_loop -> process_job (讀取 cache / 計算)
      -> WalletStore::commit
      -> { ScyllaStore::commit: 在同一 partition 執行單一條件式 INSERT IF NOT EXISTS
         | PostgresStore::commit: 獨占借用 pool connection
           -> wallet_commit 的 implicit transaction (ledger INSERT + account UPDATE)
           -> query_one 收完回覆，直到 ReadyForQuery }
      -> 收到 durable acknowledgement
      -> process_job 發布 cache
      -> worker reply (工作回覆)
      -> Service::submit 回覆
      -> 全部 requests 完成後：full verification -> owned cleanup

PG client 只送出一個 prepared statement call；資料庫在 implicit transaction 內執行 ledger INSERT attempt 和 account UPDATE 兩個 writes。這與 Scylla 同 partition LWT 不同。Client 等 durable acknowledgement 後才發布 cache。PG SQL latency 不含 pool wait；E2E latency 和 RPS window 含 pool wait。各階段的 percentiles 是巢狀量測值，不可相加。全部 requests 結束後才做 full verification 和 cleanup。RPS window 從第一個 client request 到最後一個 reply；setup、seed、verification、checkpoint/drain 和 cleanup 都在 window 外。

## 結果範圍與持久性

本結果只適用於固定的單節點測試條件。RPS 是整個 DB 節點／server 的吞吐量，不是 Scylla 每個 shard 的吞吐量。三次結果用於觀察波動，未提供長期效能或統計顯著性保證。

PG 使用 fsync=on、synchronous_commit=on、full_page_writes=on、wal_sync_method=fdatasync；Scylla 使用 durable_writes=true 與 batch commitlog ack。這些設定描述軟體要求的 flush 契約，不能視為已驗證斷電保存。Scylla batch ack 不代表每筆請求各做一次 fsync。先前的 PG SIGKILL／restart 測試只涵蓋該 process crash 情境，不涵蓋斷電或硬體故障。

這些 1,024,000 筆的短期閉環測試不能證明 steady-state 容量或硬體上限。若要評估長期 checkpoint／compaction 成本，需另做長時間測試；本次等資源比較基準已完成。Git 內精簡證據包的檔案清單、逐檔 SHA-256、封存驗證與解壓重算命令見[證據索引](../benches/data/wallet_db_compare/run-20261013T124123Z-3216cf07f3/README.md)；完整 runner/case JSON、monitors、qualification 與 launch records 只保存在該 README 記載的本機 raw archive。
