# 設計：PostgreSQL 冪等帳本交易批次測試

需求見 [03-01](03-01.raw-requirement-pg-ledger-txn-batch-benchmark.md)；程式碼與資料見 [`benchmarks/pg-ledger-txn`](../benchmarks/pg-ledger-txn/README.md)。

## 1. Schema（`sql/schema.sql`）
```sql
CREATE TABLE accounts(account_id uuid PRIMARY KEY, balance bigint NOT NULL DEFAULT 0);
CREATE TABLE ledger(
  transaction_id uuid NOT NULL,
  account_id     uuid NOT NULL REFERENCES accounts(account_id),
  amount         bigint NOT NULL CHECK (amount > 0),
  before_balance bigint NOT NULL,
  after_balance  bigint NOT NULL,
  PRIMARY KEY (account_id, transaction_id),
  CHECK (after_balance = before_balance + amount));
```

## 2. 每視窗一個 statement（`sql/txn_batch.sql`）
參數 `$1` 帳號 `uuid[]`、`$2` tx id `uuid[]`、`$3` 金額 `bigint[]`；結果欄位 `status, transaction_id, account_id, amount, before_balance, after_balance`。步驟：
1. `input`：`unnest(...) WITH ORDINALITY`，`ord` 保留輸入順序。
2. `probe`：`LEFT JOIN ledger`，每筆只探測一次，判斷是否已存在並帶出原記錄。
3. `valid`：新單、金額 > 0、帳號存在。
4. `agg` → `upd`：每個帳號只更新一次餘額（`balance + sum`），回傳起始餘額。
5. `calc`：`起始餘額 + sum(amt) OVER (PARTITION BY acc ORDER BY ord) - amt` 得到每筆 before。
6. `ins`：純 `INSERT`（不用 `ON CONFLICT`）。
7. 最後把 `applied`、`existing`（回傳**原本儲存**的 before/after，不是目前餘額）、`rejected:invalid_amount`、`rejected:unknown_account` 以 `UNION ALL` 合併。

性質（`scripts/sql_functional_test.py` 驗證，標註者為獨立審查時另外實測）：
- 重送回傳原記錄；重送金額不同也回傳原金額；重送不改餘額。
- before/after 鏈依**輸入順序**（`ord`），不是 tx id 順序；結果列沒有保證順序，需以 `(account, tx)` 對應回請求。
- 同一個 statement 輸入內有重複的新 key → `23505` 並整個回滾（餘額不變），所以 application 必須先去重。
- 另一個 session 同時插入相同 key（審查實測）→ 該 statement 以 `23505` 失敗，連同餘額更新一起回滾；重試後得到 `existing`。這是不使用 `ON CONFLICT DO NOTHING` 的原因：被略過的列仍會被算進 before/after 與餘額。
- 兩個 session 以不同順序持有重疊帳號（審查實測）會 `deadlock detected (40P01)`；對輸入排序不能保證 `UPDATE` 的鎖順序，所以靠「每帳號單一 executor」避免，並在 client 對 `23505`／`40P01` 重試（最多 3 次）。

## 3. Client（`src/bin/txn_batch_pg.rs`）
- 啟動：建 schema、插入帳號、建立 256 條連線（每條 prepare 同一個 statement）+ 1 條 monitor 連線；寫 ready 檔並等待 GO 檔，確保取樣先就位。
- **工作量產生（確定性，tx id 為 UUID v4）**：`queue = user % queues`，queue 內 round-robin，一個視窗 = `--batch-max` 個**新**請求。`--retry-pct P`：每個 queue 重送 `round(n·P/100)` 筆，來源均勻分佈在所有非最後視窗的新請求，並附加在**下一個視窗**新請求之後（所以重送一定走 DB `existing` 路徑，不會被視窗內去重吸收）。`--inject-rejects`：每個 queue 在第一個視窗多一筆未知帳號與一筆金額 0 的請求（僅 smoke 使用）。
- **視窗處理**：依 `(account, tx)` 去重保留第一筆（重複者共享 canonical 的結果；canonical 若被拒絕，重複者維持同樣的拒絕）→ 依帳號穩定排序（保留帳號內輸入順序）→ 送出一個 statement → 對 `23505`／`40P01` 重試 → 以 `(account, tx)` 對應每個回傳列；canonical key 集合與回傳 key 集合必須一一對應（`missing`／`unexpected`／重複 key 都使 run 失敗）。
- 對於重送的請求，比較回傳的 `existing` 與先前 `applied` 的記錄（`replay_mismatch`）。
- 延遲計時只包住 query await（含 SQL 重試）；以請求為權重記錄（每個請求記錄其視窗的 statement 時間）。
- 量測結束與 WAL 快照之後，才用單一 SQL 驗證：帳號數、每帳號 ledger 筆數、餘額、before/after 鏈（`lag(after_balance) OVER (PARTITION BY account_id ORDER BY before_balance)`，因金額為正所以以 before 排序有效）、`sum(balance)`；4 M 筆約 6 秒，所以放在量測視窗之外。

## 4. Wrapper（`scripts/batch_queue_run.py`）
建立有標籤的拋棄式容器／volume／network、`--cpuset-cpus`、記憶體上限、固定的 PG 參數（`shared_buffers=2GB`、`fsync`、`synchronous_commit`、`full_page_writes` 為 on，不能被 `--pg-conf` 覆蓋）；`taskset` 綁定 client 與 sampler；以 250 ms 取樣 cgroup CPU／記憶體／IO、裝置 `/proc/diskstats`、網路；結束後清理並確認無殘留。

## 5. 驗證項目（為何列、為何不刪）
| 項目 | 為何列出 | 為何不刪 |
|---|---|---|
| 每個請求一個終態回覆、key 一一對應 | 去重／對應路徑可能悄悄漏掉回覆 | DB 總數正確並不代表呼叫者拿到結果 |
| `existing` 與原記錄一致（含重送金額不同） | R1 要求回傳原內容 | 計數無法偵測內容被替換 |
| 每帳號 count／sum／餘額／before-after 鏈 | 單看加總無法發現錯誤的歷史餘額 | 這是新增的 before/after 需求 |
| 拒絕案例無變更（smoke） | 正式 cell 不會走到，只有 smoke 能證明 | 否則拒絕路徑未經真實 binary 驗證 |
| 生效設定、`wal_stats.settled`、視窗數 | 確保量測的是預期的組態與區間 | wrapper 本身不檢查這些 |
| 診斷（checkpoint、`wal_buffers_full`、fsync 大小、await） | 使用者要求的量測 | 只作診斷，不作正確性門檻 |

## 6. ScyllaDB（僅記錄，未實作／未量測）
同一契約下，每個帳號一個條件式 BATCH（同一 partition）：
```cql
CREATE TABLE ledger(account_id uuid, transaction_id uuid, balance bigint static, amount bigint,
  before_balance bigint, after_balance bigint, PRIMARY KEY(account_id, transaction_id));
BEGIN BATCH
  UPDATE ledger SET balance = :new WHERE account_id = :acc IF balance = :old;
  INSERT INTO ledger(account_id, transaction_id, amount, before_balance, after_balance) VALUES(:acc, :tx1, :a1, :b1, :f1) IF NOT EXISTS;
  -- 同帳號每個請求一個 INSERT ... IF NOT EXISTS
APPLY BATCH;
```
在 Scylla 2026.1.14 的實測：條件式 BATCH 不能跨 partition（`BATCH with conditions cannot span multiple partitions`）；若有任一條件失敗則整組不套用，並回傳目前餘額與已存在的列（原內容）；剔除已存在者、以回傳餘額重算 before/after 後重送；成功時回傳的 static 列是**舊餘額**，client 要快取自己送出的新餘額；帳號不存在時回傳全 null。因此與 PostgreSQL 不等價之處：原子單位是每帳號而不是整個視窗、全域 tx_id 唯一性無法強制、已存在的 tx 需要額外一次往返。
