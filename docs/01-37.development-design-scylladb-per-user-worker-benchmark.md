# 單帳戶 Worker 與固定連線池 ScyllaDB 基準評估：開發設計

日期：2026-10-12。
目標：實作 [01-36 單帳戶 Worker 與固定連線池 ScyllaDB benchmark 需求](01-36.raw-requirement-scylladb-per-user-worker-benchmark.md)。
需求編號：01。文件序號：37。
狀態：設計範圍已確認；實作與單元測試進行中。

本設計只增加一個 per-user worker routing 模式與固定 PerShard pool 參數。既有預設模式維持原行為。資料模型、交易 statements、consistency、durability、timeouts、strict preflight、monitoring 與 cleanup 沿用 [01-32 ScyllaDB wallet benchmark 設計](01-32.development-design-scylladb-wallet-benchmark.md)。實作與測試依本次使用者授權執行。Live case 啟動前須完成下列驗證與 root review。

## 執行範圍

本次只準備及執行 `S=4, C=50,000, P=4` 的一個 custom workload。每 node 16 條 data connections，三 node 目標合計 `D=48`。CLI 明確指定：

```text
--per-shard-pool 4
--worker-routing per-user
```

未提供 `--per-shard-pool` 時，既有預設仍計算 `P=C/(3*S)`。未提供 `--worker-routing` 時，既有 round-robin routing 保持不變。新增參數不得改變舊 case 的設定結果。

`C` 與 `D` 分開記錄。C 是 DB worker 數與應用層 in-flight 上限。D 是 pool 的目標 data connection 數。Pool setup 使用單一共享 `Arc<Session>` 和 PerShard 設定；實際 D 必須從 session readiness 與 `system.clients` audit 驗證，不能只以設定值作證。Control connections 不計入 D。

## Per-user worker routing

建立 C=50,000 個 dedicated DB workers。對此 workload，`account_id` 為 `0..49,999`，並固定送到相同 index 的 worker。此映射不使用 round-robin，也不以連線作為帳戶 owner。

每個 worker channel 的 queue capacity 為 1。Global admission semaphore 上限為 50,000，permit 從接受工作起持有至 reply/settlement，並包含 queued 與 active jobs。Acceptance 仍依既有 service linearization point 判定。不可只因取得 permit 就回報 request accepted。

保留每個 account 的 owner lock 和 frozen flag。Worker 在完整交易期間持有 request 所需的 owner guard；caller cancellation 不取消已 accepted 的 job。相同 account 的交易必須 sequential。若有多個 caller 同時提交相同帳戶，lock 仍負責序列化。

每個 worker 同時最多執行一個 job。交易內兩個 SELECT、decode、compute 與一個 BATCH await 依序完成。Workers 共用同一 `Arc<Session>`；driver 將工作送到 48 條目標 data connections。此設定不保證 worker 與實體 connection 一對一。

## 固定 storage path

每筆交易沿用目前 implementation 的兩個 SELECT 與一個 single-partition UNLOGGED BATCH。Batch 固定兩個 statements，估算 encoded size 維持低於 1 KiB。不得改成 mixed-partition batch、LWT、counter、額外 SELECT 或改變 durability path。

同一 ScyllaDB wallet table、keyspace replication、schema agreement、metadata sentinel、ledger key/body/outcome/version/clock、replay 耐久確認與 unknown-commit handling 全部沿用既有設計。Wallet read/write/replay/verify 繼續使用 CL=THREE；三個 nodes 繼續使用 `durable_writes=true` 與 `commitlog_sync=batch`。Driver retries 與 speculation 關閉。沿用既有 driver、server read/write deadlines 和 120 秒 shutdown deadline，不覆寫或延長。

任何 write error 若無法證明未提交，回傳 `CommitOutcomeUnknown` 並 freeze account。Trial fail closed；後續新 request 不再寫入。不得更換 key、降低 CL 或自動 retry。錯誤樣本保存原始 driver error text，而非只保存 fail-closed 衍生訊息。

## Seed、verify 與量測窗

計時前以 concurrency `min(C,D)=48` 建立 50,000 個初始 balance=100 的帳戶。建立成功後再開始完整 workload。計時外完整 verify 也以最多 48 個並行帳戶工作執行。

每個 user 發送 200 個 request。Credit 與 Debit amount=1 交替，每筆 await reply 後再送下一筆。全 case 預期 10,000,000 logical transactions、30,000,000 application CQL operations，以及每個 account 200 個 ledger rows。成功後每個 account 的 balance 為 100、version 為 200。

Seed、pool readiness、`system.clients` pre-audit、verify 和 cleanup 均在 measurement window 外。量測從既有共同 start barrier 到最後一個 caller reply。記錄實際 request/reply count、stage latency、worker busy/idle、queue/admission wait、CQL in-flight current/peak、worker queue capacity、service RSS/CPU、Scylla metrics 和 driver counters。

若 workload failure 或 timeout，保留各 error kind 的原始 driver 訊息及 server error/timeout counters。需要區分 `CommitOutcomeUnknown`、後續 fail-closed `NotAccepted` 和 driver request error。不可只以 runner exit code 或總 error count 代替原始 error evidence。

## Scylla pool、CPU 與資源 profile

固定 `S=4`, `P=4`。每 node 每 shard 目標四條 data connections；每 node 合計 16，三 node 合計 48。Runner 依 session ID 對 `system.clients` 結果分類 data 與 control connections，並在 measurement 完成後再稽核。任何 data connection count、每 node 分布或 pool readiness 不符合 48 的 trial 不得開始或不得判為有效。

沿用固定 image `scylladb/scylla@sha256:333b9ab3a3214c7f98af100711c51df7f58964e8227e6d26050e889ebb216df1` 和現有 S4 runtime profile。各 node process 使用：

| Role | CPU affinity |
| --- | --- |
| Scylla node A | 0,1,8,9 |
| Scylla node B | 2,3,10,11 |
| Scylla node C | 4,5,12,13 |
| Service、load generator、monitor | 6,7,14,15 |

每 node 仍是兩個 physical cores 和四個 SMT threads。Nodes 共用同一 host 和 SSD。不得將三個 nodes 描述為獨立故障域，也不得將 S4 threads 當作四個 physical cores。

C=50,000 會建立大量 workers、waiters、guards 與 admission slots。必須記錄 service RSS peak、process CPU、context switches、heartbeat lag、queue latency、CQL in-flight peak 和每 worker busy/idle 數。監控要檢查 CPU、記憶體、disk、commitlog、timeout、overload、connection pool 及 cleanup evidence。若 strict formal preflight 不通過，停止且不建立 cluster。

## 實作與啟動 gate

先完成以下檢查，逐項保存輸出：

1. 增加及執行 per-user worker routing 單元測試，並確認 round-robin 預設模式沒有行為改變。
2. Build 獨立 Scylla wallet crate；固定 binary 與 source hashes。
3. 執行 CLI dry-run。核對 `C=50,000`、`P=4`、`D=48`、`S=4`、worker mapping、queue capacity 和單一 workload 的完整 argv/config。
4. 對照 source、CLI、runner config、pool readiness/audit 與本文契約。由 root review 完成後才啟動 live case。
5. 執行既有 strict formal preflight。必須對實際 output filesystem 連續三次通過 CPU busy ≤10%、device busy ≤5%、available memory ≥32 GiB、available disk ≥32 GiB 且不低於容量估算，以及既有 AIO headroom。不得放寬 gate 或清除非 owned 資料。

Preflight 通過後只執行一次下列 custom formal case：

```bash
python3 benches/scylla_wallet.py \
  --mode formal \
  --shards 4 \
  --workers 50000 \
  --per-shard-pool 4 \
  --worker-routing per-user \
  --users 50000 \
  --requests-per-user 200 \
  --repeats 1 \
  --skip-build
```

不得啟動九-case matrix，不得增加重試。若初次 run 結果未知，保留該結果並交由 root 決策；不得自行重建相同 workload。

## 驗收與報告

Case pass 須符合所有 workload、pool、driver、metrics、ledger verify 和 cleanup gates。預期 50,000 個 users 都完成 200 次 reply，10,000,000 個 ledger records 均逐帳戶核對。結果同時列 RPS、latency 分位數、各 stage、connection pool min/max/sample count、CQL in-flight peak、driver query/error/retry/timeout deltas、Scylla timeout/overload counters、CPU、memory、device I/O 和 cleanup status。

Runner 將單 case `--mode formal` 保留為 `formal_partial`，exit code 1。報告可寫「單 case trial passed」或「單 case trial failed」，不得寫「完整 formal benchmark passed」。

與既有 `S4/C48/P4` 的比較只用前兩次 valid trials median：RPS `9176.983178`、p99 `25.425870847` 秒。新舊 case 的 worker 數和 routing 同時不同。比較只描述兩個 profile 的結果，不作純 worker scaling 的因果結論。

完整結果放到後續文件。保存 run config、source/binary hash、strict preflight、dry-run、worker/pool audit、原始 error samples、metrics、全 ledger verification 與 owner-validated cleanup artifacts。若 case 未完整通過，保留 partial/failure 狀態，不納入有效性能比較。

## 執行流程

```text
input
  -> run_clients
  -> run_client
  -> Service::submit(account owner lock)
  -> dedicated per-user worker
  -> SELECT static state
  -> SELECT ledger key
  -> compute
  -> single-partition UNLOGGED BATCH through shared Session (48 data connections)
  -> CL=THREE / fsync-backed acknowledgement
  -> reply
  -> next request

write outcome unknown
  -> freeze account and fail closed
  -> stop new work
  -> drain accepted work
  -> verify accounts and ledger
  -> owner-validated cleanup
  -> report failure or partial result
```
