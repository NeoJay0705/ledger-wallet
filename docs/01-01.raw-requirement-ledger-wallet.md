下面整理成目前這版架構的完整基準，假設 **一個 tx_id 只修改一個人的 balance**，並且採用：

* DB：歷史 tx dedupe
* LSM：DB projection 尚未追上的 gap index
* WAL：交易 durability / recovery source
* Memory：account balance
* 不使用 Recent Tx Memory Index

---

# 1. 核心需求

```text
Transaction {
    tx_id
    account_id
    delta
    payload_hash
}
```

核心約束：

```text
1. 一個 tx 只修改一個 account 的 balance

2. 同一 account 的 transaction 必須序列化
   避免 concurrent balance race

3. 同一 tx_id 不可重複執行

4. Request 高流量，以 batch 處理

5. WAL 採 batch append + fsync
   降低 fsync 次數

6. Balance 主要存在 memory

7. Projection DB 永久保存歷史 transaction

8. Request 進交易服務之前會先查 Projection DB

9. DB pre-check 必須同時取得當下的 projection watermark

10. LSM 只保存：
    DB 尚未完整 projection 的 tx_id

11. WAL 是 durability / recovery log

12. DB / LSM / balance snapshot 都有各自 progress watermark
```

---

# 2. Idempotency Key

如果 tx_id 只保證 account 內唯一：

```text
Idempotency Key
=
(account_id, tx_id)
```

這是最簡單的模型。

如果：

```text
tx_id 必須 global unique
```

那還需要額外的 global tx-id ownership/dedupe 層。

以下先假設：

```text
(account_id, tx_id)
```

為唯一 key。

---

# 3. Account Sharding

因為每筆 transaction 只修改一個 account：

```text
shard =
hash(account_id) % N
```

例如：

```text
Alice
  TX1
  TX2
  TX3
   │
   ▼
Account Shard 17
```

同一 account 永遠由同一 shard 處理。

因此：

```text
TX-A: Alice -80
TX-B: Alice -50
```

不會同時操作 Alice 的 balance。

而是：

```text
TX-A
 ↓
TX-B
```

序列執行。

# 4. Storage Responsibility

整體 responsibility：

```text
                ┌─────────────────────┐
                │ Projection DB       │
                │                     │
                │ Historical tx-id    │
                │ permanent history   │
                └─────────────────────┘


                ┌─────────────────────┐
                │ LSM                 │
                │                     │
                │ DB projection gap   │
                │ recent tx-id index  │
                └─────────────────────┘


                ┌─────────────────────┐
                │ Primary WAL         │
                │                     │
                │ durability          │
                │ recovery            │
                └─────────────────────┘


                ┌─────────────────────┐
                │ Account State       │
                │                     │
                │ current balance     │
                │ Memory              │
                └─────────────────────┘
```

簡單說：

```text
DB
= 舊資料

LSM
= DB 尚未追上的資料

WAL
= recovery

Memory
= current balance
```

# 5. Projection DB 資料結構

Transaction table：

```text
TransactionRecord {
    account_id
    tx_id

    payload_hash

    wal_lsn

    delta
    result

    created_at
}
```

建議：

```text
UNIQUE(account_id, tx_id)
```

另外有：

```text
ProjectionState {
    projection_lsn
}
```

`projection_lsn = 10000` 的定義必須是：

> 所有 WAL LSN <= 10000 的 transaction，都已經 durable projection 到 DB。

必須是 **contiguous watermark**。

不能：

```text
9998 ✓
9999 ✗
10000 ✓

projection_lsn = 10000    // 錯
```

只能：

```text
projection_lsn = 9998
```

---

# 6. DB Pre-check

Request 進交易服務前：

```text
Incoming Request
      │
      ▼
Projection DB
```

必須在同一個 consistent snapshot 裡取得：

```text
lookup(account_id, tx_id)

+

projection_lsn
```

例如：

```text
TX123 = NOT FOUND
projection_lsn = 9000
```

然後送進 Transaction Service：

```text
Request {
    account_id
    tx_id
    delta

    payload_hash

    db_checked_lsn = 9000
}
```

`db_checked_lsn` 的意思是：

> DB 已完整包含所有 <= 9000 的 transaction，而且在這個 snapshot 中沒有看到這個 tx_id。

---

# 7. DB Pre-check Hit / Miss

如果 DB：

```text
FOUND
```

直接回：

```text
previous result
```

不必進 Transaction Service。

如果 DB：

```text
MISS
```

不能表示：

```text
這一定是新 transaction
```

因為 DB projection 可能落後 WAL。

所以：

```text
DB miss
→ 帶 db_checked_lsn
→ 進 Transaction Service
```

---

# 8. LSM 的資料結構

LSM key：

```text
(account_id, tx_id)
```

value：

```text
TxIndexValue {
    wal_lsn
    payload_hash
    result
}
```

例如：

```text
(Alice, TX123)
    →
{
    wal_lsn: 10321,
    payload_hash: ABC,
    result: SUCCESS
}
```

LSM 不需要保存所有歷史 transaction。

它只 cover：

```text
DB projection watermark
<
LSN
<=
WAL committed head
```

---

# 9. LSM 內部

典型：

```text
                 RAM

            Mutable MemTable
                   │
                   ▼
           Immutable MemTable

              ASYNC FLUSH
                   │
                   ▼

                 DISK

                L0 SST
                   │
             ASYNC COMPACTION
                   ▼
            L1 / L2 / L3
```

`LSM.WriteBatch()` 成功 return：

```text
資料已進 LSM read path
```

通常已存在：

```text
MemTable
```

所以立即：

```text
Get / MultiGet
```

可以看到。

不需要等 SST flush。

---

# 10. 為什麼不需要 Recent Memory Index

目前設計採：

```text
WAL fsync
 ↓
LSM WriteBatch
 ↓
LSM visible
 ↓
Return
```

所以 committed transaction 在 return 前一定已經：

```text
DB
OR
LSM
```

其中之一可查。

因此不用另外：

```text
RecentTxMap
```

去 cover WAL → LSM gap。

代價是：

```text
LSM WriteBatch latency
```

會進 request synchronous path。

如果 LSM stall：

```text
request 也會 backpressure
```

這反而比 RAM queue 無限制膨脹容易控制。

# 11. Request Batch Flow

完整同步流程：

```text
Incoming Batch
      │
      ▼
┌───────────────────────────┐
│ 1. Batch-local dedupe     │
│                           │
│ HashSet / HashMap         │
│ Memory                    │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 2. Route by account_id    │
│                           │
│ hash(account_id)          │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 3. Account shard          │
│                           │
│ serialize same account    │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 4. LSM MultiGet           │
│                           │
│ Historical gap dedupe     │
│ RAM + Disk                │
└─────────────┬─────────────┘
              │
            MISS
              │
              ▼
┌───────────────────────────┐
│ 5. Validate DB watermark  │
│                           │
│ db_checked_lsn            │
│ vs                        │
│ lsm_gc_lsn                │
└─────────────┬─────────────┘
              │
              ▼
        safe / recheck DB
              │
              ▼
┌───────────────────────────┐
│ 6. Prepare balance        │
│                           │
│ read current balance      │
│ validate                  │
│ calculate new balance     │
│                           │
│ NOT visible yet           │
│ Memory                    │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 7. Primary WAL            │
│                           │
│ batch append              │
│ fsync                     │
│ Disk                      │
└─────────────┬─────────────┘
              │
         COMMIT POINT
              │
              ▼
┌───────────────────────────┐
│ 8. LSM WriteBatch         │
│                           │
│ synchronous visibility    │
│ → MemTable                │
└─────────────┬─────────────┘
              │
              ▼
┌───────────────────────────┐
│ 9. Publish balance        │
│                           │
│ Memory                    │
└─────────────┬─────────────┘
              │
              ▼
        Return success
```

# 12. Step 1：Batch-local dedupe

例如 batch：

```text
Alice / TX1
Bob   / TX2
Alice / TX1
Carol / TX3
```

先在 memory：

```text
HashMap<(account_id, tx_id), request>
```

得到：

```text
Alice / TX1
Bob   / TX2
Carol / TX3
```

避免同 batch duplicate 重複查 LSM。

---

# 13. Step 4：LSM Dedupe

LSM：

```text
MultiGet([
    Alice/TX1,
    Bob/TX2,
    Carol/TX3
])
```

如果：

```text
TX1 → HIT
```

比較：

```text
payload_hash
```

相同：

```text
return previous result
```

不同：

```text
TX_ID_CONFLICT
```

如果：

```text
MISS
```

還不能立刻判斷為新交易。

因為有可能該 transaction 已被從 LSM GC 到 DB。

所以需要：

```text
db_checked_lsn
```

---

# 14. DB Watermark 與 LSM GC Watermark

Service 維護：

```text
lsm_gc_lsn
```

它的意思是：

> <= lsm_gc_lsn 的 tx-id 已經允許不存在於 LSM，因為 responsibility 已轉移到 DB。

收到：

```text
db_checked_lsn = 9000
```

目前：

```text
lsm_gc_lsn = 8500
```

則：

```text
9000 >= 8500
```

DB pre-check 足夠新。

LSM miss 可以安全表示：

```text
NEW
```

---

如果：

```text
db_checked_lsn = 8000
lsm_gc_lsn     = 8500
```

則：

```text
8000 < 8500
```

存在：

```text
8001 ~ 8500
```

的 blind spot。

因此必須：

```text
recheck DB(account_id, tx_id)
```

如果 DB：

```text
FOUND
→ duplicate
```

如果：

```text
MISS
→ new
```

# 15. Dedupe Decision

完整邏輯：

```text
LSM lookup
    │
    ├── HIT
    │     │
    │     ├─ same payload
    │     │      → previous result
    │     │
    │     └─ different payload
    │            → conflict
    │
    └── MISS
          │
          ▼
 db_checked_lsn >= lsm_gc_lsn ?
          │
       ┌──┴──┐
      YES    NO
       │      │
      NEW     ▼
          Recheck DB
              │
         ┌────┴────┐
       FOUND      MISS
         │          │
     duplicate     NEW
```

# 17. WAL

WAL record：

```text
WalRecord {
    lsn

    account_id
    tx_id

    payload_hash

    old_balance_version
    new_balance

    result
}
```

Batch：

```text
WAL Batch N

LSN 10001 Alice/TX1
LSN 10002 Bob/TX2
LSN 10003 Carol/TX3
...
```

執行：

```text
append batch
+
fsync
```

成功後：

```text
COMMITTED
```

這是不可逆的 commit point。

---

# 18. WAL Commit 後

順序：

```text
WAL fsync success
        │
        ▼
LSM WriteBatch
        │
        ▼
LSM visible
        │
        ▼
publish account balance
        │
        ▼
return success
```

重要 invariant：

```text
任何 client 看得到成功的 transaction
→ WAL 一定 durable
→ LSM 一定可以 dedupe
```

# 19. Async Projection DB Flow

另外一條：

```text
Primary WAL
     │
     ▼
Projection Worker
     │
     ▼
DB transaction rows
     │
     ▼
advance projection_lsn
```

例如：

```text
LSN 10001 ✓
LSN 10002 ✓
LSN 10003 ✓
```

才能：

```text
projection_lsn = 10003
```

如果：

```text
10002 尚未完成
```

即使 10003 已寫：

```text
projection_lsn
```

也不能超過：

```text
10001
```

# 20. LSM GC

如果：

```text
DB projection_lsn = 10000
```

代表：

```text
LSN <= 10000
```

已經全部存在 DB。

這些 tx-id 在 LSM 就不需要了。

因此：

```text
LSM GC target = DB projection_lsn
```

LSM 可以 async expire/delete：

```text
wal_lsn <= 10000
```

的 index records。

完成後：

```text
lsm_gc_lsn = 10000
```

注意：

```text
db_projection_lsn
```

和：

```text
lsm_gc_lsn
```

不是同一個值。

例如：

```text
DB projection = 12000
LSM GC        = 10000
```

完全正常。

---

# 21. LSM GC 不使用 TTL

這個架構不需要：

```text
保留 7 天
30 天
60 天
```

因為 retention 是 state-driven：

```text
DB 已 durable cover
→ LSM responsibility 結束
→ 可 GC
```

也就是：

```text
LSM size
≈
transaction rate
×
DB projection lag
```

而不是：

```text
LSM size
≈
所有歷史交易
```

# 22. LSM 自己的 Physical GC

另外還有 LSM engine 本身：

```text
L0
 ↓
L1
 ↓
L2
```

的 compaction。

例如：

```text
SST-A
SST-B
SST-C
   │
   ▼
SST-D
```

SST-D durable 後：

```text
delete SST-A/B/C
```

這是：

```text
physical file GC
```

跟：

```text
tx-id logical GC
```

不同。

# 23. Balance Snapshot

Balance 在 memory，WAL 不可能永久保存。

所以要定期建立：

```text
BalanceSnapshot {
    accounts...
    checkpoint_lsn
}
```

例如：

```text
checkpoint_lsn = 9000
```

表示：

> <= 9000 的所有 balance mutation 都已經 reflected 在 durable balance snapshot。

Restart：

```text
load balance snapshot @9000
        │
        ▼
replay WAL >9000
```

---

# 24. WAL GC

WAL GC 跟 LSM GC 是不同概念。

WAL 能不能刪，要看所有依賴 WAL recovery 的 consumer。

目前至少：

```text
Balance Snapshot
Projection DB
```

所以：

```text
wal_gc_lsn =
    min(
        balance_checkpoint_lsn,
        db_projection_lsn
    )
```

例如：

```text
WAL head               = 15000

DB projection_lsn      = 13000

Balance checkpoint_lsn = 11000
```

則：

```text
wal_gc_lsn = 11000
```

只有：

```text
segment.end_lsn <= 11000
```

的 WAL segment 可以刪除。

---

# 25. 為什麼 LSM 不一定阻擋 WAL GC

LSM 是：

```text
DB projection gap index
```

如果：

```text
DB 已 projection 到 13000
```

LSM 中：

```text
<=13000
```

本來就可以刪。

因此只要 LSM 能從：

```text
DB + remaining WAL
```

恢復，就不一定要把：

```text
lsm durable_lsn
```

放入 WAL GC safe point。

例如：

```text
DB projection = 13000
WAL retained  = >11000
```

LSM crash 後可以：

```text
DB responsibility <=13000
+
rebuild LSM from WAL >13000
```

這會比要求 LSM 自己永久 durable 更簡單。

---

# 26. Crash Recovery

假設：

```text
DB projection_lsn      = 13000
Balance checkpoint_lsn = 11000
WAL head               = 15000
```

restart：

### Balance

```text
load balance snapshot @11000
        ↓
replay WAL 11001~15000
```

### LSM

LSM 只需要 cover：

```text
DB projection_lsn < LSN <= WAL head
```

也就是：

```text
13001 ~ 15000
```

可以直接從 WAL rebuild：

```text
WAL 13001~15000
      ↓
LSM WriteBatch
```

所以 LSM 完全是 disposable derived state。

# 29. 最核心的 correctness invariants

整個系統可以濃縮成這六條：

```text
1.
同一 account 的 transaction 必須序列化。

2.
Balance mutation 只有在 WAL fsync 成功後才能 publish。

3.
成功回 client 前：
transaction 必須已進 WAL，而且 LSM 已 visible。

4.
DB pre-check MISS 必須攜帶 db_checked_lsn。

5.
只有：
db_checked_lsn >= lsm_gc_lsn
且 LSM MISS
才能直接判定 NEW。

否則必須重新查 DB。

6.
WAL GC 必須等：
DB projection
以及
Balance snapshot
都 durable cover 該 LSN。
```

這版的核心其實可以濃縮成一句：

```text
DB = historical dedupe
LSM = projection gap dedupe
WAL = durability/recovery
Memory = current balance
Watermark = 各層之間安全移交 responsibility 的依據
```

而且在這個模型下，**不需要 Recent Tx Memory Index，也不需要靠 TTL 決定 LSM 或 WAL 的 GC。**
