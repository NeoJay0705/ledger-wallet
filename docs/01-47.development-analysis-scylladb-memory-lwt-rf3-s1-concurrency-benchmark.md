# ScyllaDB Wallet 記憶體狀態 LWT：RF3/CL3 單 shard 並發與連線池掃描結果

## 結果狀態

## 測試條件

每個 case 使用 1,024 個帳戶，每個帳戶送 1,000 筆交易，總計 1,024,000 筆。每筆金額為 1，Credit 與 Debit 交替；每個 client 等待本筆回覆後才送下一筆。初始餘額為 100。

三個隔離 ScyllaDB instance 使用 pinned 2026.1.14 image。`S=1`、RF3、read/write CL=`THREE`、LWT serial CL=`LOCAL_SERIAL`。Wallet profile 為 `wallet-memory-lwt-v1`：seed 後在 gate 前 preload 帳戶狀態；measurement 內每個交易使用一個 `INSERT ... IF NOT EXISTS` LWT，沒有 measured SELECT。Commitlog 設定為 batch、`commitlog_use_o_dsync=false`；沿用既有 timeout、commitlog batch fsync acknowledgement 與 cleanup 條件。三個已啟動 case 的 runtime、schema、strict preflight 與 required metrics 驗證均通過。完整 CLI profile 和正確性驗證只有 C=128、C=256 通過；C=512 的 CLI 因 storage failure 以 exit 1 結束，CLI profile validation 缺失或無效，case 結果如後文所述。

`C` 是 worker 與 application CQL in-flight 上限。`P=ceil(C/50)` 是每 node、每 shard 的 data connection target；`D=3×S×P` 是全 cluster 的 data connections。三個 case 的 pool 都 ready 且穩定：9、18、33 條連線，分別符合 target；無 connection mismatch。Measured CQL peak 與 workers busy peak 分別為 128、256、512；workers 在 drain 後 idle。Worker routing 是 round-robin；帳戶 owner lock 保持同帳戶交易循序。每 case global admission capacity 是 50,000。

Node reactor affinity 經 runtime 證據核對為 A=CPU 0、B=CPU 2、C=CPU 4；service、load 與 monitor 使用 CPU 6、7、14、15。Scylla reactor 與 client 程序的 affinity 證據保存在各 trial 的 `reactor-affinity.json`、`runner-affinity.json` 及 `proc/samples.jsonl`。

## 執行流程

```text
input
  -> run_clients
  -> run_client (one account; await reply before next request)
  -> Service::submit
  -> account owner lock
  -> worker_loop (round-robin shared worker pool)
  -> process_job
  -> read cached AccountState and compute next result
  -> ScyllaStore::commit
  -> one conditional INSERT ... IF NOT EXISTS
  -> LOCAL_SERIAL / regular CL=THREE / durable acknowledgement
  -> publish cache after Applied acknowledgement
  -> reply

after all replies
  -> drain service
  -> verify account cache, static state and ledger
  -> keep CLI session open for runner connection/socket audit
  -> release finish gate; CLI exits and closes Session
  -> cleanup owned containers, network and data
  -> write case and matrix reports

write timeout or unknown outcome
  -> freeze account and fail closed globally
  -> stop admitting new work; settle accepted requests
  -> preserve partial verification and error evidence
  -> stop later cases; cleanup owned resources; report without retry
```

## 通過 case 的測量結果

以下只列完整通過、正確性驗證有效的兩個 case。每組只有一次 measurement。

| C / P / D | Requests（accepted / applied / replies） | RPS | E2E p50 / p95 / p99 | DB queue wait p99 | service process CPU |
|---|---:|---:|---:|---:|---:|
| 128 / 3 / 9 | 1,024,000 / 1,024,000 / 1,024,000 | 5,505.46 | 163.578 / 309.854 / 468.189 ms | 438.567 ms | 46.100 s |
| 256 / 6 / 18 | 1,024,000 / 1,024,000 / 1,024,000 | 4,638.42 | 145.621 / 568.852 / 1,027.080 ms | 876.610 ms | 44.066 s |

兩個 case 均有 1,024,000 筆 driver queries、0 measured SELECT、0 driver errors/retries/request timeouts/connection timeouts。1,024 個帳戶及 1,024,000 筆 ledger rows 全數與 cache/static state 驗證相符。

在這兩個單次觀測中，C=256 的 RPS 比 C=128 低約 15.75%，E2E p99 約為 2.19 倍。C 與 P 同時改變，且只有一次重複；這不能隔離 worker 或 connection 的因果效果，也不代表穩態性能。

Admission wait 與 account wait 的 p99 在通過 case 約為 0.3–0.4 微秒；DB queue wait p99 則為 438.567 ms 和 876.610 ms。這些 stage histogram 描述本次 window，不能外推到其他配置。

## C=512 失敗窗口

| 項目 | 觀測值 |
|---|---:|
| Measurement 時間 | 110.116334257 s |
| accepted / attempted / replies | 586,283 / 586,283 / 586,283 |
| applied | 585,259 |
| errors | 1,024：510 `commit_outcome_unknown`、514 `not_accepted` |
| driver query delta / errors / retries / request and connection timeouts | 585,769 / 510 / 0 / 0 / 0 |
| verification | 1,024 accounts compared；0 accounts 符合完整 1,000-request 預期；585,769 ledger rows returned；`complete=false`, `valid=false` |

Bounded `error_samples` 記錄 ScyllaDB 的 CAS write timeout：CL THREE 收到 2 個回覆，要求 3 個。Driver request timeout、connection timeout 與 retry counter 都是 0。`first_error` 是 fail-closed 後的 `not_accepted` 訊息，不代表最早發生的錯誤；失敗原因依據是 `commit_outcome_unknown` 的原始 storage error sample 和 driver error counter。

`accounts_verified=0` 表示沒有帳戶符合這個 case 的完整 1,000 筆預期，不表示沒有逐帳戶檢查。驗證遍歷 1,024 個 cache 帳戶並記錄 1,024 個不符合預期的項目；`ledger_rows_seen=585,769` 是驗證讀取到的 row 數，不是整個 Scylla ledger 的總數。未知提交可能已寫入 DB，而 cache 只保留最後確認的狀態。沒有證據顯示已確認回覆的交易遺失；這份驗證不能宣稱完整 workload 正確性通過。

C=512 的回覆吞吐與 latency 都是失敗窗口中的部分值，沒有列入通過 case 的效能表，也不能與前兩組作效能比較。C=1,024 因 fail-fast 未啟動；本次沒有重試。

## 清理與結論

三個已啟動 case 都完成 owned containers、network、owned data 清理；各 `cleanup.json` 均為 `clean`、`errors=[]`、`retained_data=[]`。Post-stop inspection 中部分 container exit code 為 137；C=512 的 node C 亦如此。這是停止清理階段的狀態，`OOMKilled=false`，不能據此推斷 workload 期間發生 OOM 或 crash。

兩個通過 case 顯示配置從 C=128/P=3/D=9 增至 C=256/P=6/D=18 時，application admission/account wait 仍很小，但 DB queue、E2E p95/p99 上升，RPS 下降。C=512 的 CL THREE CAS timeout 觸發 unknown/fail-closed，說明本次 C=512 的並發設置未能完成完整 case；這不證明唯一根因是 worker 數或連線數。

下一步應先檢查保存的 CAS timeout、node、I/O 與 Paxos 指標，再決定是否重測或啟動 C=1,024。不要自動改 CL、deadline 或 retry policy。這份 pilot 沒有完成四組掃描，也沒有形成 27-case formal 結果。
