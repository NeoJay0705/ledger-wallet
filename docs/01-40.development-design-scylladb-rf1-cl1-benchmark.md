此 case 沿用 [01-37 per-user worker 設計](01-37.development-design-scylladb-per-user-worker-benchmark.md)。只改 replication factor 與 wallet read/write consistency。它不修改既有 RF3 預設，也不改資料模型、交易流程、worker、pool、fsync acknowledgement、timeout、監控或 cleanup。

## CLI 與 profile

CLI 與 runner 增加以下選項：

| Option | Default | 本 case |
| --- | ---: | ---: |
| `--replication-factor` | 3 | 1 |
| `--read-cl` | 3 | 1 |
| `--write-cl` | 3 | 1 |

三個參數只接受 1 至 3。`read-cl` 與 `write-cl` 不可高於 replication factor。Numeric CL 轉為 driver 與 profile metadata 使用的 canonical consistency string：1=`ONE`、2=`TWO`、3=`THREE`。Keyspace metadata 的 replication factor 保存為整數。原有預設仍是 RF3/THREE/THREE。

Runner 必須把 RF、read CL 與 write CL 寫入 run config、trial config 和 startup record。啟動後要核對實際 keyspace replication factor 為 1，並確認 readiness event 與 final profile 都記錄 RF1/ONE/ONE。不能只依 CLI argument 或單一 consistency 設定位置認定 profile 有效。

RF1 是獨立 custom profile。所有有效 case 要求、runtime evidence 與結果報告都必須顯示 `RF=1, read=ONE, write=ONE`。Schema/system metadata bootstrap 可沿用既有 bootstrap policy；wallet seed、load、replay、verify 的 CL 都使用指定 read/write profile。

## 固定 workload 與 storage path

只執行一個 workload：S4、C=50,000、P=4、D=48、per-user routing、50,000 users × 200 requests、一次 repeat。每帳戶初始 balance=100，Credit/Debit amount=1 交替各 100 筆。每筆 request await reply 後，該 user 才送下一筆。

單一 service 共用 Session。Account owner lock、每 worker queue capacity 1、global admission 50,000、setup/verify concurrency 48 與 worker routing 均沿用既有 per-user profile。Data connection pool 目標維持每 node 16 條，整體 48 條，不隨 RF 改變。Control connections 另行分類。

每筆交易仍執行兩個 SELECT、compute 和一個含兩個 statements 的 single-partition UNLOGGED BATCH。讀取使用 CL=ONE；batch write 使用 CL=ONE。仍使用 `durable_writes=true`、`commitlog_sync=batch`、`commitlog_use_o_dsync=false`。Success acknowledgement 必須在唯一 replica 的 commitlog batch fsync 後。保留既有 fixed ScyllaDB 2026.1.14 image 與 driver/server deadlines。

Seed 建立 50,000 個 RF1 帳戶。完整 verify 檢查各帳戶 static state 及 200 個 ledger rows。Seed 與 verify 的最大併發數為 48。未知 write outcome freeze account，並觸發全域 fail-fast：停止新 work，settle 已接受工作，再執行 verification、owned cleanup 和結果報告。Driver retries/speculation 保持關閉。

## 主機、failure semantics 與監控

三個 Scylla instances 使用 pinned image `scylladb/scylla@sha256:333b9ab3a3214c7f98af100711c51df7f58964e8227e6d26050e889ebb216df1`（release 2026.1.14）、S4 affinity 與同一 SSD。CPU affinity 沿用：node A CPUs 0,1,8,9；node B CPUs 2,3,10,11；node C CPUs 4,5,12,13；service/load/monitor CPUs 6,7,14,15。三個 instance 是同機共用裝置，不是獨立 fault domains。

RF1 下每個 partition 只有一個 replica。該 node 離線時，對應 partition 沒有其他 replica 可服務；磁碟永久遺失時，沒有 peer copy 可恢復。CL1 acknowledgement 和 commitlog fsync 保護單一副本，但沒有 RF3 的 replica fault tolerance。此 profile 仍只支援單一 service writer；CL1 不提供跨 service writer coordination。

沿用既有 strict formal preflight，不放寬容量、CPU、device、memory 或 AIO gates。Required metrics、pool readiness 和 before/after connection audit 都必須有效。報告記錄 worker count、CQL in-flight peak、pool min/max/sample count、RPS、latency、CPU、RSS、disk、commitlog、Scylla errors/timeouts、driver queries/errors/retries/timeouts、verification 和 cleanup。

Server-side CL1 write timeout 與 driver request timeout 分開報告。所有未知結果記錄原始 driver error sample 和 server metrics。不得因 RF1/ONE 調整 timeout、增加 retry 或把 error 窗口當成功 throughput。

## 驗證與單次執行

Live case 前完成 Rust tests、format check、release build、Python tests/compile、CLI dry-run、source/binary hash snapshot 與 profile/source correspondence。Root review 完成後，才執行單次 case。strict preflight 不通過時不建立 cluster。

執行命令：

```bash
python3 benches/scylla_wallet.py \
  --mode formal \
  --shards 4 \
  --workers 50000 \
  --per-shard-pool 4 \
  --worker-routing per-user \
  --replication-factor 1 \
  --read-cl 1 \
  --write-cl 1 \
  --users 50000 \
  --requests-per-user 200 \
  --repeats 1 \
  --skip-build
```

這是單一 `custom_workload` case。即使 trial 通過，run 仍是 `formal_partial`，不能稱為 27-case formal pass。只執行一次。未知結果、timeout 或驗證失敗後不自動重試，不更改 timeout/CL，不另跑 CL matrix，也不改成 C=48。

## 比較規則

主要對照是 RF3/R3/W3 per-user case `run-20261012T071303Z-a7f4b0a6`。它同為 S4/C50,000/P4/D48，但 trial failed：1,886,870 replies、1,836,955 applied、49,915 `CommitOutcomeUnknown`，量測 59.475756915 秒。不可把它當作 full-pass throughput baseline。

較早的 S4/C48/P4/D48 round-robin n=2 full-pass 數據只能作輔助背景。該比較同時改變 RF/CL、C、routing 與 binary。不可把不同 profile 的差異解讀為 RF1 單一因素的因果效果，也不可假設 RF1 帶來三倍效能。

## 執行流程

```text
input
  -> run_clients
  -> run_client (per user; await reply before next request)
  -> Service::submit (account owner lock)
  -> worker_loop
  -> process_job
  -> ScyllaStore::load
  -> SELECT static state
  -> SELECT ledger key
  -> compute
  -> ScyllaStore::commit
  -> single-partition UNLOGGED BATCH
  -> RF1 / CL=ONE / unique replica commitlog fsync acknowledgement
  -> reply
  -> next request

write outcome unknown
  -> freeze account / global fail-fast
  -> stop new work and drain accepted jobs
  -> verify
  -> cleanup owned containers, network and data
  -> report result
```
