# Tokio sequential RocksDB ledger benchmark 設計

## 工作負載與鍵值格式

Benchmark 預設每個 trial 寫入 10,000,000 筆交易；batch size 64、256、1,024、2,048、4,096 各跑 3 次，每次使用新 DB。所有 key 放在一個 RocksDB default column family，以 `L + tx_id`、`B + user_id`、`G:latest-ledger-seq` 分別表示 ledger、latest balance 與全域 ledger sequence。

Ledger value 固定 42 bytes，依序存放 `tx_id`、`user_id`、direction、outcome、amount cents、post-balance cents 及 sequence。Outcome 使用明確的 `Applied` code；一次成功寫入的 ledger record 表示該交易已原子套用。

交易以一為起點編號，`user_id=(seq-1)%100000`，`user_round=(seq-1)/100000`。每個 user 有 100 rounds；偶數 round 是 credit，奇數 round 是 debit。每筆固定 100 cents，所以 debit 不會令餘額低於零；完整 10M workload 結束時所有餘額歸零。每個 user 在每輪只收一筆交易，因此交易依序輪流走訪 100,000 個 users。Smoke run 可用較小 `--iterations` 測試 workload 的前綴。

每批只建立一個 RocksDB `WriteBatch`。批次內含全部 ledger values、該批每個受影響 user 的最後餘額，以及該批最後一個全域 sequence。遇到同一 user 多次時，批次只寫入一筆最終 balance key。`WriteOptions.sync=true` 且 WAL 維持啟用；程式逐批 await blocking-pool 工作，確認 `DB::write_opt` 成功後才提交對應的 in-memory balance updates，再開始下一批。任一時刻只有一批 write 在途。

## Runtime、階段與延遲

Harness 使用帶 time driver 的 current-thread Tokio runtime，並在 write 和 query phase 各執行一個 1 ms heartbeat task。RocksDB write 和讀取呼叫都交給 Tokio blocking pool；主執行緒逐批 await，所以工作順序固定且不會排入多批並行寫入。Heartbeat lateness 顯示 runtime event loop 何時再次 poll timer，不會單獨指出延遲來源。

Write phase 從第一批開始建立 entries 和 `WriteBatch` 前開始，到最後一批寫入成功且 in-memory balances 更新後結束。`write_batch_build` 包含 entry 產生、balance 計算與 RocksDB `WriteBatch` 編碼；`write_db_write_opt_call` 只計時 blocking thread 內的 `DB::write_opt` 呼叫。整批 transaction latency 從 build 開始到 in-memory commit 完成，包含 blocking-pool dispatch/queue 與返回主 runtime 的時間。每批 latency 值依批內交易數重複加權，輸出的 transaction-weighted mean 與 nearest-rank p50/p95/p99 由此計算；它描述每筆交易所屬批次的完成時間，不是每筆交易各自的獨立計時。

Write RPS 是實際寫入交易數除以 write phase wall time。ProcessTime 記錄整個 benchmark process 的 CPU time，包含 current-thread runtime 與 RocksDB blocking/background threads；CPU wall time 使用相同 phase window。程序 I/O counter 與 target device busy milliseconds 在 phase 邊界附近讀取，OS 裝置 busy counter 是該裝置的全域活動，不會只歸因於本程序。

Write 完成後，程式在量測窗外讀回最新 global sequence 和所有已觸及 users 的持久餘額，逐項與 in-memory balances 比對。之後關閉所有 writer DB handles，重開同一 trial DB，再做 query idle preflight。Query phase 不刻意呼叫任何 warming lookup；每筆 query ID 來自事先以固定 seed Fisher–Yates 洗牌的 `1..=iterations`。重開 DB 本身可能讀取 manifest、options 等 metadata，RocksDB file cache 和 OS page cache 也可能保留 write phase 的頁面，因此「reopen」不表示 OS cold cache。

Query 使用 `DB::batched_multi_get_cf`，一次查詢同一 default column family 的 batch 個 ledger keys，輸入為 deterministic shuffled sequence，所以 `sorted_input=false`。`query_batch_prep` 計時將 ID 編成 RocksDB keys 並複製該批期望 IDs；`query_batched_multi_get_call` 只計時 blocking thread 內 multiget 呼叫；`query_decode_validate` 計時解碼與完整欄位比對。整批 transaction latency 從 key prep 開始到 blocking-pool 結果返回，涵蓋 prep、dispatch/queue、multiget、decode/validation 及回到 runtime 的時間；其 mean、p50/p95/p99 同樣以每批交易數加權。Query RPS 使用全部成功驗證的 ledger lookups 除以整個 query phase wall time。

## RocksDB 與系統指標

RocksDB statistics 使用 `StatsLevel::ExceptDetailedTimers`。CSV 記錄 write/query 各自 phase 前後 `Options::get_ticker_count` 的差值：`WalFileSynced`、WAL bytes、`WriteWithWal`、flush bytes、compaction read/write bytes 及 stall microseconds。這些 ticker 共用該 DB statistics 狀態並涵蓋其內部 background work；compaction 或 flush 是非同步的，因此不能將 byte/count 差值解讀成某一批或某一筆交易的單獨成本。WAL sync counter 是 RocksDB ticker 回報值，不是硬體快取或斷電後資料完整性的獨立證明。

CSV 另輸出從該 DB options 建立後累計的 WAL sync 與 write stall histogram 摘要，以及 phase 後讀取的 `num-immutable-mem-table`、flush pending、running flushes、compaction pending、running compactions、pending compaction bytes、write stopped、delayed write rate 與 background error properties。Histogram 是 RocksDB 摘要而非本 harness 的逐批 latency。Properties 若 binding/RocksDB 沒有提供會留空；數值是讀取瞬間的 gauge。

每個 write 和 query phase 前都檢查 filesystem 類型、free bytes、MemAvailable、process RSS、aggregate CPU busy 與 target block device busy；無法確認 disk busy 或 CPU busy 時直接失敗，不產生該 trial CSV row。tmpfs、ramfs、devtmpfs 會被拒絕。Write preflight 以每筆 160 bytes 的 estimated live footprint 乘 4 作寫放大空間預留，再加預設 1 GiB free reserve；這是保守規劃門檻，不是實際 RocksDB 空間上限。Query preflight 仍要求 free reserve，以保留背景 flush/compaction 空間。兩階段 preflight 每次嘗試都寫入 `<output-dir>/preflight.log`，也會輸出到 stderr。CSV header 和每個成功 trial row 輸出到 stdout。

Query ID vector 在第一個 write preflight 前配置。啟動記憶體檢查將 10M 個 `u64` IDs、100k 個 balance slots、最大 batch working set 及預設 headroom 納入；每個 phase preflight 另確認最小可用記憶體及該批工作空間。

成功或錯誤退出時，程式先關閉 RocksDB handles，再刪除該 trial 專屬的唯一 DB directory；output directory 與 preflight log 保留。它不會清理其他 trial 或使用者檔案。

## CLI 與短 smoke

預設矩陣共 15 個 trial，包含 5 種 batch size、每種 3 次，每 trial 10M write 與 10M shuffled lookups。用 `--iterations`、`--repetitions`、`--batch-sizes` 及 `--output-dir` 縮小或調整工作量；iterations 上限是完整 10M workload。Preflight 門檻可用 `--preflight-*` 調整。

建置需要 libclang/bindgen 與可用的 C/C++ build toolchain。此 Ubuntu 開發主機上，bindgen 的 Clang header search 找不到 GCC 標準 include，因此命令需設定 `BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include'`。這個 include path 依賴該主機的 GCC 安裝位置；其他環境應改用當地對應目錄。完整預設矩陣命令如下：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench rocksdb_tokio_sequential
```

完整命令會啟動 15 個 trial、各 10M writes 和 10M lookups。預設矩陣已完成，實測數據見 [Tokio sequential RocksDB benchmark 報告](../benches/rocksdb_tokio_sequential_report.md)；短 smoke 命令仍可用來快速驗證程式路徑。

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench rocksdb_tokio_sequential -- \
  --iterations 512 --repetitions 1 --batch-sizes 64 \
  --output-dir target/rocksdb-tokio-smoke \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --preflight-max-cpu-pct 100 --preflight-max-disk-busy-pct 100 \
  --preflight-min-mem-bytes 16777216 --preflight-free-reserve-bytes 1048576
```

診斷 trace 的短 smoke 至少用 2,048 batch；例如 4,096 筆可涵蓋 write/query 各兩個 batch：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench rocksdb_tokio_sequential -- \
  --iterations 4096 --repetitions 1 --batch-sizes 2048 --diagnostic \
  --output-dir target/rocksdb-tokio-diagnostic-smoke \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --preflight-max-cpu-pct 100 --preflight-max-disk-busy-pct 100 \
  --preflight-min-mem-bytes 16777216 --preflight-free-reserve-bytes 1048576
```

Short smoke validates the code path and persistence checks only; it is not a result for the default 10M matrix. This document defines the harness; full matrix measurements are in the linked benchmark report.
