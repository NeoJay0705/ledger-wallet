# Tokio Ledger 投影進度持久化、重啟恢復與安全 GC

## 範圍

本階段在既有單 shard `AccountStore` 與 Tokio ledger projector 上加入可恢復的投影進度、與 sequence 綁定的交易時間 watermark，以及 RocksDB ledger/index/refund marker 的安全清理。獨立 benchmark 比較 GC 開關與 per-batch/checkpoint balance persistence 的四種組合。既有 `ledger_time_boundary_tokio` 的行為及數字保持不變。

這是 benchmark/test harness 的儲存契約，不是 production 外部資料庫實作。目的端 `MockProjectionStore` 保留在 process 記憶體；測試模擬 source RocksDB close/reopen 時會保留同一個 mock instance。設計假設「目的端 apply 成功」代表目的端資料已耐久。這個假設支援 source 端 apply 後、進度 sync 前的重播測試，但不代表 mock 可承受 process crash，也不代表真實外部 DB 的 crash durability。

## Source 端耐久進度

- Projector 由 `M:projected-seq + 1` 開始，依連續 ledger sequence 讀取 source。
- Projector 先將 batch 套用至 idempotent destination，再以 RocksDB sync WAL WriteBatch 推進 `M:projected-seq`，最後才通知 watermark manager。apply 成功但進度 sync 失敗時，重啟會重播該 batch；目的端必須接受完全相同的冪等重播。
- `M:projected-before` 與 `M:projected-before-seq` 在同一個 sync WriteBatch 寫入。第一個值是嚴格歷史路由邊界 `W`；第二個值是發布該邊界前已 drain 且已投影的 source sequence。
- 重開 source 後，先確認恢復的歷史 destination progress 不小於 RocksDB 的 projected sequence，再恢復 W。destination 不存在、落後、metadata 不完整或前進方向倒退時 fail closed。
- 舊的 timestamp-only W API 保留給 01-23 stage；缺少 sequence 配對的舊 metadata 不可用於恢復路由或 GC。

## Safe GC

GC 只會在下列條件全部成立時刪除一筆 record：

1. `transaction_at < W`，其中 W 與 drain sequence 已同步持久化。
2. record sequence 不大於 source 已 sync 的 `projected_seq`。
3. record sequence 不大於 balance coverage：per-batch mode 使用 `latest-seq`。每個改變餘額的 ledger batch 已把 latest sequence 和 touched balance keys 放在同一個同步 WriteBatch；不存在的 balance key 代表零餘額。checkpoint mode 使用已發布 checkpoint manifest 的 sequence。
4. ledger 與 transaction index 互相一致，record 解碼有效。

GC 使用耐久連續前綴 `M:gc-prefix-seq`，不為每個 sequence 寫 tombstone。單一同步 WriteBatch 刪除該次連續前綴的 ledger/index/可清理 refund marker，並更新 prefix。若下一筆 record 不符合 W 或任何 coverage guard，GC 停在該筆並回報 blocked sequence。即使後面的 timestamp 較舊也暫不清除；這是保守的空間回收 tradeoff，避免假設 transaction timestamp 隨 sequence 單調遞增。重啟 integrity scan 允許 prefix 內已刪除記錄缺席，仍嚴格驗證 prefix 之後每一筆 record 和 index。

成功套用的退款其 marker 只會在該退款本身也通過 safe-GC 條件、並於同一個刪除 batch 移除時清除。若舊 debit 已 GC，新的退款驗證會查歷史 destination 的 debit/used state；一般仍留在 source 的 debit/marker 走 RocksDB 本地路徑。GC 需要已安裝且 progress 足夠的歷史 destination。RocksDB `Delete` 是邏輯刪除；benchmark 不強制 compaction，也不把 logical bytes 當成已回收的實體檔案空間。

## Benchmark 固定工作負載

新執行檔為 `ledger_safe_gc_tokio`，預設四個 case 依序為 GC off/on × per-batch/checkpoint。每 case 使用 50,000 個帳戶與 50,000 個 Tokio coroutine，每個 coroutine 發出 200 個 request，共 10,000,000 個 request。每個 200-slot block 以 `splitmix64(account_id) % 200` 為 offset，再用乘數 37 做固定排列：10 筆精確歷史命中、10 筆歷史未命中、180 筆新 credit。每 case 因此有 9,000,000 個新 commit，另加每帳戶 3 筆 seed，共 150,000 筆。

GC 開/關與兩種 balance mode 共用 seed keys、命中/未命中分布、queue/batch/projector/retention/watermark/lookup-delay 參數。新交易的 `transaction_at` 在呼叫 admission route 前以目前 Unix microseconds 產生；固定 retention 是從這個交易時間起算，watermark 每 100 ms 嘗試推進至 `now - retention`。預設 retention 為 500 ms。GC eligibility 使用嚴格 `< W`。Watermark fence、durable projection sync 和 GC 都在 client 測量窗口內執行。

GC worker 每次同步寫入最多處理一個有界 batch。只要連續 prefix 前進，就在 batch 間 `yield_now`，讓 commit 與 projector task 執行；遇到 eligibility blocker 或 prefix 無進度才等待固定 GC poll interval。這避免以固定 tick 限制回收速度，也避免 blocker 前忙等。client wall 結束附近會記錄 `gc_backlog_records_near_client_end = latest_seq - gc_prefix_seq`；這個數包含受 W、投影或餘額 coverage guard 阻擋的 record，不等同全數已具備刪除資格。

客戶端 RPS 只以 10M request 的 coroutine wall time 計算。CPU process time 在 client wall endpoint 立即取樣。Projection、GC 和 watermark 每個操作都記錄完成時間，只納入 `completed_at <= client_end` 的操作；這些 stage 的 read/apply/progress sync/scan/delete build/sync write/fence wait/projection wait/persist/total latency 會以 ns 輸出 p50/p95/p99 與 sample count。sample count 為 0 表示該 stage 沒有操作，與 latency 為 0 分開表示。

GC prefix 與剩餘 sequence backlog 是 client endpoint 附近讀取的 RocksDB 原子狀態，不能與背景 GC 完成事件在同一瞬間原子快照；輸出會標為 `near_client_end`。Process/device I/O counter 與 RocksDB 統計、DB bytes 在 client endpoint 後取樣，summary CSV 以 microseconds 記錄各自的取樣 offset；這些累計 counters 的短尾端包含在 offset 內。Seed/setup、projector settle、最終 watermark/GC sweep、source close/reopen、integrity scan 與所有帳戶 balance 驗證都不列入 client RPS。Client 之後的 catch-up/final sweep 不會算進 per-operation GC/projector/watermark latency。DB size 是窗口結束附近的 RocksDB 檔案大小，logical deletes 不代表檔案已因 compaction 縮小。

Benchmark 在建立每個 case 前，以及 seed/setup 完成後、開始量測前，檢查 CPU/device idle、可用記憶體和磁碟空間。任何量測或驗證失敗時不建立完整 default archive；只清除該次執行自己擁有的 trial DB 目錄。完整預設四個 case 全部通過後，才建立 raw CSV/log archive。`--smoke` 和客製 workload 不產生 canonical archive。

```sh
cargo bench --bench ledger_safe_gc_tokio -- --help
cargo bench --bench ledger_safe_gc_tokio -- --smoke
cargo bench --bench ledger_safe_gc_tokio
```

完整 benchmark 需 Linux `/proc`、可讀 `/proc/diskstats`、非 volatile filesystem、足夠記憶體與磁碟空間。Smoke 是縮小使用者數的功能驗證，不能作為完整 workload 的效能結果。

## 回歸測試

`tests/ledger_safe_gc.rs` 覆蓋 apply 成功但 progress sync 失敗、GC sync 中斷前後、checkpoint manifest lag、strict W 邊界、亂序 timestamp 阻塞連續 prefix、refund marker 壽命與 GC/reopen 後防止重複退款、歷史 destination 不存在/落後時 fail closed、GC prefix 外的缺失 ledger corruption、以及共享 RocksDB namespace 隔離。另須回歸執行 `ledger_account_store` 與 `ledger_time_boundary` 測試，確保新 stage 沒改變既有 stage 行為。
