# Tokio 單 shard Ledger Pipeline Index 查詢設定與整合基準測試

## 目的與範圍

本文件定義 `ledger_pipeline_tokio` 的 transaction index 查詢設定，以及沿用既有 `ledger_index_lookup_tokio` runner 的完整 pipeline 整合 profile。目標是讓 Plan A 的分組與並行設定可由 pipeline CLI 選擇，並量出前景持久化與 projector、watermark、checkpoint、GC 同時執行時的成本。此 profile 是獨立比較設計；既有 foreground lookup 的六種 mode × 三次 repetition 正式矩陣與結果維持不變。尚未完成的試跑不得寫成正式結果。

`AccountStore::handle_batch` 保持既有預設入口及行為。Pipeline queue 可使用已驗證的 `IndexLookupConfig` 指定該次批次的 lookup。Pipeline 預設採 `Chunked { group_size: 256, max_in_flight: 4 }`，Tokio runtime 預設為共享 pool 的 4 個 async worker。CLI 提供 `--index-lookup point_get|whole_batch_multiget|chunked`、`--index-group-size N`、`--index-concurrency N`；chunk 大小有效範圍為 1..=2048，最大 in-flight 群組數為 1..=8，由既有 `IndexLookupConfig` 驗證。明確指定 group size 或 concurrency 時，只能搭配 `--index-lookup chunked`；若 lookup 為另外兩種 mode，明確傳入這兩個參數會被拒絕，未明確傳入的預設值不會觸發拒絕。這些 pipeline 預設與下文固定的正式比較 profile 分開：正式 profile 明確指定三種案例，不以 pipeline CLI 預設替代 baseline。

## 前景批次與一致性

維持 Plan A：在單一前景批次內以共享 `Arc<DB>` 查詢 transaction index；此索引只用於交易冪等性判斷，非 ledger sequence。`whole_batch_multiget` 與 `chunked` 使用 default column family 的原生 `batched_multi_get_cf`，設定 `sorted_input=false`，並由 Tokio `spawn_blocking` 執行查詢。Chunked 模式限制已提交但尚未收集的群組數。收齊結果後，必須驗證群組識別、範圍、項目數、重複及遺漏，並還原至請求原始位置；所有結果驗證完成以前不得套用該批任何交易。`point_get` 保留逐筆 Get 後立即套用的既有順序。

從批次讀取狀態與 sequence snapshot 開始，直到查詢、順序套用、同步寫入及記憶體發布完成，持續持有同一個 AccountStore batch gate；它也負責與 GC 序列化。對外時間與 sequence 契約維持不變。交易仍按原始順序套用，保留 staged-map 優先、精確重複重播餘額與 sequence、不相同內容的同 key 衝突、同帳戶操作順序，以及 refund 查詢原目標的既有語意。兩種模式都以單一啟用 WAL 且 `sync=true` 的 `WriteBatch` 寫入 ledger、transaction index 與 latest sequence；`PerBatch` 另在同一批寫入有變更的餘額。`Checkpoint` 模式保留原有前景 ledger/index/sequence commit 和記憶體發布，再由背景 balance checkpoint 建立 checkpoint/progress 覆蓋，供 GC 判定安全範圍。

呼叫端取消 await 不會取消已接受的工作。Coordinator 必須持有 admission guard，直到提交與 head publication 完成。查詢失敗後停止提交新群組並排空已啟動工作；整批失敗，不得部分提交或錯誤回覆成功。真實 RocksDB write error 的 durable outcome 可能不確定，該 trial 立即視為 fatal，停止後續寫入。Production 若要重試相同 key，須先 close/reopen 並 reconcile durable state；`FailSyncWrite` 測試僅代表原生寫入呼叫前的注入故障，不代表斷電復原保證。

## 完整 pipeline 工作負載

每個正式 trial 使用新的 child process、Tokio runtime 及 RocksDB 目錄，固定一個 shard、`PerBatch` 餘額模式、4 個共享 async workers、50,000 個使用者 coroutine、每位使用者 200 筆請求（每人同時最多一筆 outstanding），合計 10,000,000 筆請求。Credit／debit 精確各半，金額均為 1，history 為 0；queue 容量 50,000、batch 上限 2,048，第一筆 dequeue 後最多等候 5 ms 組批。Blocking pool 與 RocksDB internal pools 沿用預設設定，CPU affinity 沿用繼承值，不另行 pin thread。

每位使用者在計時前依既有 seed handler 執行 credit 100、credit 1、debit 1，合計 150,000 個 seed sequence。計時負載開始及結束時餘額都應為 100；預期最終 latest sequence 為 10,150,000。測試啟用 projector、watermark 與 GC：projection batch 256，watermark tick 100 ms、retention 500 ms，GC batch 256。GC 有進展時連續 catch up 並 yield；受阻或無工作時 sleep 100 ms。Seed 先投影至 destination，再設定初始 durable watermark。

`MockDB` destination 的 apply 成功依測試契約視為 durable，close/reopen 檢查重用同一 instance。這只驗證本 benchmark 的 mock 契約，不能當作真實資料庫或程序／斷電後持久性的證據。Checkpoint/snapshot 與 history 路徑屬相容性正確性檢查，不增加到以下正式效能矩陣。

## 正式比較矩陣

沿用既有 `ledger_index_lookup_tokio` benchmark target 與 runner，`--profile foreground_persistence` 是預設 profile，維持原有六種 mode × 三次 repetition 的 foreground 矩陣；`--profile integrated_pipeline` 選擇本文件定義的完整 pipeline 矩陣。完整矩陣每種設定重複 1、2、3，共 9 個 fresh-process trials；每個 repetition 輪替 mode 執行順序。每個 trial 執行上述 10,000,000 筆負載，合計 90,000,000 筆。

| Profile mode | 查詢設定 |
| --- | --- |
| `point_get` | 逐筆 Get 基準 |
| `chunked_256_p4` | 每組 256 keys，最多 4 個已提交且尚未收集的群組 |
| `chunked_256_p8` | 每組 256 keys，最多 8 個已提交且尚未收集的群組 |

Foreground-only lookup 正式報告中，`chunked_256_p4` median 為 84,817.870 RPS、2.589715 CPU cores；`chunked_256_p8` 為 98,578.103 RPS、3.495190 CPU cores。P8 的前景吞吐量約高 16%，平均 CPU 約高 35%。因此完整 pipeline 以 P4 作為起始預設，保留較多 CPU 空間供背景工作；此結果不代表已證明 P4 是最優設定。背景投影、GC、blocking pool、原生 WAL 與 compaction 可能競爭資源，不能由 foreground-only 報告推算整合 RPS；正式比較必須同輪含 `point_get`、P4、P8。

Runner 可使用 `--profile`、`--smoke`、`--validate-only`、`--modes`、`--repetitions` 與 `--output-root`；未指定 profile 時使用 `foreground_persistence`。未明確指定 `--modes` 時依 profile 選擇預設矩陣；`--validate-only` 只列出排程，不做 preflight 或建立 trial。完整正式命令：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --locked --bench ledger_index_lookup_tokio -- --profile integrated_pipeline
```

`--modes` 僅接受此 profile 支援的精確名稱；`integrated_pipeline` 支援 `point_get`、`chunked_256_p4`、`chunked_256_p8`，其他 mode 會被拒絕。`--repetitions` 接受 `1,2,3` 中不重複的 repetition 身分，是要執行的編號，不是數量。只有三種 mode 與三個 repetition 全部執行才算完整矩陣；子集須標為 partial。

若完整 runner 已完成所有 trials，但 canonical report 輸出階段失敗，可用 `--report-only RUN_DIR` 從保留的 archive 重建報告，不重跑 runtime benchmark：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --locked --bench ledger_index_lookup_tokio -- --profile integrated_pipeline --report-only benches/data/ledger_pipeline_index_lookup/run-<ID>
```

`--report-only` 必須明確指定 `--profile`，且 `RUN_DIR` 必須是該 profile 預設 archive root 下直接存在的完整 run 目錄；拒絕 parent-directory traversal、非直屬目錄與不存在的路徑。此模式會驗證完整正式矩陣、manifest 與 per-trial artifacts 後重產 canonical report，並寫入 `report_recovery.txt`。它不得搭配 `--smoke`、`--modes`、`--repetitions`、`--internal-trial`、`--trial-mode`、`--trial-output`、`--validate-only` 或 `--output-root`。Recovery 不重寫原始 `run_metadata.txt` 的 runner status；原始 run 若在報告階段失敗，仍須記錄為失敗，即使完整 trial matrix 已通過驗證。

## 前置檢查、計時與量測

正式 run root、每個 trial setup，以及 seed 完成後的 premeasurement 都執行 strict preflight：觀察 3 秒，CPU busy 不高於 10%，目標裝置 busy 不高於 5%，最多等待 60 秒，並確認預估負載與 reserve 所需 RAM、磁碟空間。Runner 不提供放寬這些門檻的參數。Smoke 使用相同百分比門檻、100 ms 觀察，每個 trial 為 200 users × 200 requests（40,000 requests），執行相同 9 個 cases；由於小型負載常使每個批次只有一個 lookup 群組，smoke 只能檢查 runner 與正確性流程，不能證明正式負載下的群組平行度。Smoke 預設輸出根目錄為 `target/ledger-pipeline-index-lookup-smoke/`；明確指定的 smoke output root 也必須位於 `target/`，並拒絕 path traversal 與 symlink escape。Smoke 或 partial run 不會更新 canonical report。

Client wall window 從 client start barrier 釋放前開始，到最慢請求收到 reply 為止；seed、preflight、settlement、recovery 與 integrity 不在窗口。Client-end source projection、destination、latest sequence 及 GC prefix 在背景 workers 執行期間分開取樣；需滿足 `seed_seq <= source_projected_seq <= destination_seq <= latest_seq`，不要求 client-end 的 source 與 destination 相等。分別報告 `latest_seq - source_projected_seq` projection backlog，以及 `latest_seq - gc_prefix_seq` GC backlog。最終 settlement 必須使 durable projected sequence、destination sequence 與 latest sequence 相等，再推進最終 boundary，並只回收符合條件的連續舊 prefix；retention 為 500 ms，因此完成時不要求刪除所有 ledger rows。Close/reopen 後驗證餘額皆為 100、sequence 為 10,150,000、boundary target 不超過 durable projected sequence，且 projection 覆蓋 GC prefix。

每個 trial 輸出 24 個 stage summaries；含 request admission、enqueue、queue、batch、handler、response、total，批次及 lookup-group 指標，並新增 `batch_gate.wait`。Request latency 使用 deterministic hash stride 64 抽樣，各 trial 以 nearest-rank 計算分位數並記錄樣本數；批次及 lookup 群組保留全部觀測。`batch_gate.wait` 與 queue/worker `dispatch.wait` 分開記錄。批次另量 key preparation、lookup `query.wall`、順序套用與建構、sync WriteBatch、memory publish；群組記錄 blocking-pool wait、native MultiGet、decode 與 submit-to-collection。每 trial 前景 captured batch metrics 的交易數總和必須為 10,000,000。並行群組的 native 工作時間會重疊，不能與 query wall 相加或由兩者相減推算歸因。

背景指標分別保留 projection read/apply/progress sync，GC scan/delete/write，watermark 與 snapshot 成本，以及 retained records。整體輸出 RPS、整個 child process 的 CPU core equivalents、CPU µs/request、process RSS peak、RocksDB IO/WAL flush/compaction/stall、程序 IO 與目標裝置 busy/IO，並註記相對 client window 的取樣 offset。CPU clock 在 start barrier 前重設，於最慢 reply 後讀取；CPU 使用此 client window 內 whole-process CPU time delta，涵蓋所有程序 threads，但不含 setup/seed。RSS peak 涵蓋 process startup 與 seed。RocksDB/WAL 統計涵蓋同一 DB 的前景與背景寫入，會受 projection、watermark 與 GC 活動影響，各 mode 的 WAL sync 數及 bytes 不保證相同，也不假定等於 foreground-only 的 batch 計數。這些數值不提供 per-file、syscall 或 per-thread CPU 歸因，也不宣稱是裝置以外的物理 IO 量。

## 輸出、清理與完成條件

完整新 profile 的原始封存根目錄為 `benches/data/ledger_pipeline_index_lookup/run-<run-id>/`，canonical 報告為 `benches/ledger_pipeline_index_lookup_tokio_report.md`。每個 trial 另保留 `ledger_index_lookup_trial_summary.csv`、`ledger_index_lookup_trial_batches.csv`、`ledger_index_lookup_trial_stages.csv`、`ledger_index_lookup_trial_metadata.txt`、`ledger_pipeline_summary.csv`、`ledger_pipeline_stages.csv`、`ledger_pipeline_background.csv`、`ledger_pipeline_index_lookup.csv` 及 child stdout/stderr；run 根目錄保留 `ledger_index_lookup_summary.csv`、`ledger_index_lookup_stages.csv`、`trial_manifest.csv` 與 `run_metadata.txt`。Pipeline 背景 raw stages/events/log 分別使用 `ledger_pipeline_stages.csv`、`ledger_pipeline_background.csv`、`ledger_pipeline_run.log`。報告中的相對連結須以封存目錄為基準正確解析。成功或已處理失敗後，須先排空查詢工作並 drop store/DB handles，再只清理由本次 trial 擁有的 DB 與 scratch；保留所有既有 archive 與報告。

只有完整 9-trial run 完成且 manifest、stage/background 輸出、settlement、recovery 與 integrity 全部通過後，才可更新 canonical 報告並寫入正式結果。Smoke、partial run 或中斷的正式 run 僅能留作對應 raw artifact，不得呈現為完整正式比較。
