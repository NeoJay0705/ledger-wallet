# Tokio 單分片交易批次並行 Index 查詢與前景持久化效能對照測試

## 目的與範圍

本文件定義新的 `ledger_index_lookup_tokio` 基準測試設計，用來比較單分片帳本在前景交易批次中查詢 transaction index 的不同方式，並觀察它們對前景持久化路徑的影響。本文中的 transaction index 專指供交易冪等性判斷使用的索引，不是 ledger sequence key。本文是設計規格，不代表實作、冒煙測試或正式 18 次試跑已完成。

Plan A 僅在同一個前景交易批次內，透過共享的 `Arc<DB>` 對多組 transaction index key 執行有界並行讀取。`whole_batch_multiget` 與 `chunked_256_p*` 先收齊並驗證該批查詢結果，再依原始順序逐筆套用交易；`point_get` 則保留逐筆 transaction index Get 後立即套用的順序。各模式最後都以單一 `WriteBatch` 和 `sync=true` 寫入啟用 WAL 的 RocksDB；只有寫入成功後才發布記憶體狀態。不得跨多個提交批次預先查詢或累積交易。

基準測試使用獨立命名的 `ledger_index_lookup_tokio` wrapper 與支援 runner，經由窄介面接入既有前景持久化流程。舊有預設 benchmark CLI、演算法及封存結果維持原有語意。查詢模式在每次 invocation 開始時明確指定並保持不變，不在批次執行期間動態切換。

## 固定負載與矩陣

比較下列六種模式，每種模式執行三次，共 18 個全尺寸子程序試跑；每次試跑包含 10,000,000 筆交易，總計 180,000,000 筆。每次 repetition 會輪替模式執行順序，以降低固定先後順序造成的偏差。每個 trial 使用全新的子程序、Tokio runtime 與資料庫。

| 模式 | 查詢方式 | 已提交且尚未收集的查詢群組上限 |
| --- | --- | ---: |
| `point_get` | 沿用逐筆交易 `Get`，查詢後立即進入原有套用迴圈 | N/A；逐筆 Get，不建立查詢群組 |
| `whole_batch_multiget` | 每批至多 2,048 個 key，一次批次 MultiGet | 1 |
| `chunked_256_p1` | 每組固定 256 個 key | 1 |
| `chunked_256_p2` | 每組固定 256 個 key | 2 |
| `chunked_256_p4` | 每組固定 256 個 key | 4 |
| `chunked_256_p8` | 每組固定 256 個 key | 8 |

所有模式共用一個 Tokio runtime，固定設定 `worker_threads(4)`；此數值與 blocking lookup group concurrency 分開計算。表中的群組上限計算已提交但尚未收集的查詢群組；另行記錄實際正在執行的 blocking query closure 數量。這兩種數量含義不同，也都不等同於 CPU core 數。各 trial 沿用相同 inherited CPU affinity，不為不同角色另行 pin thread，並維持預設 blocking pool 與 RocksDB pool 設定。

全尺寸負載固定使用 50,000 個使用者／coroutine，每個使用者送出 200 筆請求，共 10,000,000 筆；每個使用者同時最多有一筆 outstanding request。所有請求進入單一 shard，credit 與 debit 各占 50%，金額均為 1，history 為 0。效能負載不包含 refund 或 balance query。餘額計算固定使用 `PerBatch` mode；佇列容量為 50,000，最大批次大小為 2,048。批次收集 timer 從第一筆 dequeue 並進入批次時開始，最多等待 5 ms 收集更多請求；這不是等待第一筆 dequeue 的 timeout。

Seed 使用未修改的預設 handler：每位使用者先執行三筆交易，即 credit 100、credit 1、debit 1，共 150,000 個 sequence。效能負載開始與結束時每位使用者餘額都應為 100；最後 sequence 應為 10,150,000。

測量及結算期間不得啟動 projector、watermark 或 GC worker。Projector 與目的端 durable sequence 的邊界維持 150,000；預期 GC prefix 為 0，並保留 10,000,000 筆未投影 backlog。Projection destination 使用記憶體中的 `MockDB`；依其契約，成功 apply 即視為 durable，close/reopen 使用同一個 instance。本設計不據此宣稱真實外部資料庫或程序崩潰後的持久性。

## 演算法與一致性

持有相同的 `AccountStore` batch gate，從餘額與 sequence snapshot 開始，直到 transaction index 查詢、交易套用、持久化及記憶體發布完成。依交易原始位置編碼 transaction index key。`point_get` 保留逐筆 Get 與 decode；`whole_batch_multiget` 對整批 key 執行一次 MultiGet；`chunked_256_p*` 對各組 key 執行 MultiGet。兩種 MultiGet 模式都使用 default column family 的 `batched_multi_get_cf`，並傳入 `sorted_input=false`。Chunked 模式以有界 `JoinSet::spawn_blocking` 執行讀取與 decode；群組可依不同順序完成，但每個回傳結果都必須驗證群組識別、範圍、重複或缺失項目及結果長度，並還原到原始位置。

`whole_batch_multiget` 與 `chunked_256_p*` 必須在套用該批任何交易前完成並驗證所有查詢；`point_get` 維持每筆 transaction index Get 後立即套用的原始逐筆順序。transaction index 查詢回傳 `None` 是正常的未命中；讀取錯誤、decode 錯誤、資料損毀或 key 不相符均使整個批次失敗。即使預取結果為 `None`，同批次 staging map 仍優先；相同交易的精確重複會重播餘額與 sequence 而不建立新 sequence，不同內容的同 key 交易則回報衝突。同帳戶交易保持原順序。共用 handler 中的 refund 行為維持以原序列方式查詢原目標，正確性不變，但 refund 不納入本效能負載。

查詢結果可供該模式使用後，按原始順序套用交易及 sequence，再由單一同步 `WriteBatch` 寫入 ledger、transaction index、latest sequence 與有變更的餘額；WAL 保持啟用且 `sync=true`。只有整個持久化寫入成功後，才發布對應的記憶體狀態。

實作相容性：為使用原生 `batched_multi_get_cf`，default column family 必須明確開啟，並使用從既有 RocksDB options 複製的同一份設定，以維持原有資源預算。同批次對已持久化或歷史 debit 執行第二次 refund 時，必須透過 staged-refund check 發現並拒絕重複退款；保留既有 amount/status validation 的優先順序。

## 錯誤處理與取消

遇到第一個錯誤後停止提交新的查詢群組，並等待所有已啟動的 blocking read 完成後，才釋放 gate 或清理資料庫。任何查詢故障都使整個 trial case 失敗。Prefetch 模式尚未套用任何交易；`point_get` 若已對先前記錄計算 batch-local 暫存狀態，須丟棄該狀態。任何模式均不得提交批次、發布記憶體狀態或回覆成功。

注入的 `FailSyncWrite` 發生在呼叫原生 `WriteBatch` 前；此測試只能證明這種 prewrite 故障不會呼叫原生寫入、不會發布記憶體狀態或回覆成功。真實 RocksDB write error 的 durable outcome 可能不確定。基準遇到任何寫入錯誤都將整個 trial 判為 fatal 並 teardown，不再執行一般寫入。Production 若要重試相同 key，必須先 close/reopen 並 reconcile durable state；不得宣稱同一個 in-memory store 可安全續跑，也不宣稱此測試驗證了實體斷電復原。

新 handler 一旦開始執行，就由持有 store、gate 與工作項目的 async coordinator 負責完成及排空工作，即使呼叫端的 awaiter 被取消也一樣。請求已被佇列接受後，即使其 response receiver 被丟棄，所屬批次仍繼續執行。不得對已開始的 blocking write 設定會取消該寫入的 timeout。舊有預設公開 handler 的取消契約不變。

## 指標語意

RPS client window 從釋放 client 前一刻開始，到最慢的一筆 reply 返回時結束。Seed、preflight、settlement、recovery 與 integrity 工作均不計入此窗口。CPU 取對應 benchmark endpoint 的程序讀值，並保留時間 offset；保留 IO 與 RocksDB snapshot offset，並註記最後 reply 之後的 tail 活動。

每筆請求記錄 admission、enqueue、queue、batch、handler、response 及 total 的 p50、p95、p99。使用 deterministic hash 對約 1/64 請求抽樣，並記錄各統計值的樣本數；分位數使用 nearest-rank 計算。

在 `whole_batch_multiget` 與 `chunked_256_p*` 中，新增每批的 key preparation、query phase wall、sequential apply/build、同步 `WriteBatch` 及 memory publish 分段。Query phase wall 從 key preparation 前開始，直到所有查詢結果完成驗證。另按查詢群組彙整 blocking-pool wait、native Get 或 MultiGet、decode 與 submit-to-collection 時間。並行群組的工作時間總和不等於 phase wall；join wait 與 native/decode 時間有重疊，故不得用相減或相加分位數推算歸因。

`point_get` 保持原始 Get/decode 與 apply 交錯的流程，報告累計呼叫工作時間；不存在獨立的 prefetch phase 時標示為 N/A。不得把 baseline 改成先逐筆預取再套用。新入口共用 supervisor 與選擇性 instrumentation 的額外成本須記錄；舊 benchmark 預設不啟用昂貴的逐請求 tracing。

記錄並核對 reads、hits、misses、查詢群組總數、最多已提交但尚未收集的群組數，以及實際同時執行的 blocking query closure 數；本負載預期有 10,000,000 個 unique miss。這兩項並行計數分別描述待收集工作與正在執行的 blocking 工作，均不代表 CPU core 數。另記錄 CPU core equivalent、CPU microseconds/request、RSS、程序 IO、目標裝置 IO、WAL sync bytes、flush、compaction 與 stall。預設不宣稱提供 per-file 或 syscall tracing。

## 隔離與 preflight

正式試跑前須通過嚴格 preflight：觀察至少 3,000 ms（預設 3 秒），CPU 使用率不高於 10%，目標裝置 busy 不高於 5%；preflight 最長等待 60 秒，且必須確認既有流程所需的儲存空間與記憶體保留量足夠。每個 trial 使用新的子程序、runtime 與資料庫，沿用相同 CPU affinity 並記錄 host metadata。不得為取得結果放寬門檻。

`--smoke` 執行同一組 18 個 mode/repetition cases，每 case 使用 200 個使用者、每人 200 筆請求（共 40,000 筆），stride 為 1；觀察時間為 100 ms，但仍套用相同嚴格百分比門檻，輸出根目錄須在 `target/` 下。`--validate-only` 只列出矩陣，不建立資料庫。CLI 必須拒絕未知 mode、為零的 chunk 或 concurrency，以及其他無效參數。只選部分 cases 時，結果必須標記為 partial，不得標示為完整 18-case 結果，也不得覆寫 canonical report。

## CLI 產物與清理

預設輸出根目錄為 `benches/data/ledger_index_lookup/run-<id>`；正式報告路徑為 `benches/ledger_index_lookup_tokio_report.md`。保留 CSV summary、stages、精簡的 per-batch traces（每 trial 約 4,883 筆）、manifest、metadata、logs 與 report。避免輸出龐大的逐請求事件，以 per-group distribution 彙整取代。

成功完成或已處理失敗並排空工作、釋放 handle 後，清理由本次 trial 擁有的資料庫、preflight 暫存資料及大型中間檔；不得刪除先前產生且不屬於本次 run 的資料。

全尺寸命令：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --locked --bench ledger_index_lookup_tokio
```

冒煙命令：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' cargo bench --locked --bench ledger_index_lookup_tokio -- --smoke --output-root target/ledger-index-lookup-smoke
```

CLI 支援 `--modes`、`--repetitions`、`--output-root`、`--smoke` 與 `--validate-only`。`--modes` 接受以逗號分隔的精確 mode 名稱：`point_get`、`whole_batch_multiget`、`chunked_256_p1`、`chunked_256_p2`、`chunked_256_p4`、`chunked_256_p8`。`--repetitions` 接受以逗號分隔且不重複的 repetition 編號 `1`、`2`、`3`；這些值代表要執行的 repetition，不是 repetition 數量。完整矩陣包含六種 mode 與 repetitions 1、2、3；篩選後的部分矩陣標示為 partial，且不可覆寫 canonical report。

## 驗證與限制

實作後須驗證六種策略結果等價，涵蓋同帳戶 credit/debit 順序，以及 persisted、同批次與跨查詢群組的重複及衝突；也須驗證同批次對已持久化或歷史 debit 的第二次 refund 會由 staged-refund check 拒絕，且 amount/status validation 優先順序不變。Missing index 是正常情況；損毀值、key mismatch、讀取失敗、task panic、缺少或重複回傳項目及越界群組均須在提交前失敗。另驗證最大 in-flight 上限、最後不足 256 筆的群組、錯誤後工作排空、batch gate 序列化、`FailSyncWrite` prewrite injection 在呼叫原生 `WriteBatch` 前失敗且不發布記憶體，以及 awaiter 取消時批次仍正確完成並發布。Queue error 必須使受影響的 queued replies 失敗。

close/reopen recovery 與 integrity 檢查須確認每位使用者餘額為 100、效能負載包含 5,000,000 筆 credit 與 5,000,000 筆 debit、最後 sequence 為 10,150,000，且背景工作維持未啟動。MockDB 的同 instance close/reopen 結果不能外推為真實外部資料庫的崩潰復原保證。

先前正向的平行 LEDGER HIT lookup benchmark 不足以證明 transaction index MISS 或小型 256-key 群組會加速。本測試也不代表真實 projection、外部資料庫或完整 pipeline 的效能。正式比較須在同一輪包含原始 `point_get` baseline；三次重複只提供描述性 median、min、max 及各 trial 分位數，不把分位數跨 trial 平均或 pooled，也不宣稱因果顯著性。正式 18-case run 的前置驗收條件為實作完成且 smoke 驗證通過。
