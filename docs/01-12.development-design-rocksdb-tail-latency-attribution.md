# RocksDB 大批次尾延遲歸因設計

## 使用方式

`rocksdb_tokio_sequential` 的 `--diagnostic` 旗標為 write 和 query 每個 batch 記錄一列 trace，只接受 batch size 2,048 或 4,096。預設 workload、summary CSV、10M transaction validation、preflight 與 trial DB cleanup 維持原行為。診斷只應用於大批次尾延遲調查；不要把診斷模式的 latency/throughput 當成一般模式量測結果。

每個成功 trial 在 `<output-dir>/rocksdb-tokio-sequential-<trial>-<timestamp>.trace.csv` 建立一份 trace。程式在量測期間只把數值列留在記憶體；等 query 驗證完成、RocksDB handles 關閉且 trial DB directory 清除後，才一次寫出 trace。任何 phase 或驗證失敗都不會輸出該 trial trace。完成後 stderr 會報告 trace path、row count 和 DB cleanup 結果。

## 欄位與可加總延遲

每列目前含 47 欄：`phase`、1 起算的 `batch_index`、`item_count`、`batch_total_ns`、`build_or_prep_ns`、dispatch/worker/native/decode/await 各階段、native call 的 worker thread CPU/resource delta、worker OS thread ID、worker CPU，以及 RocksDB PerfContext 指標。Write 的 build 階段從 batch 開始算到 blocking dispatch；query 的 prep 階段同樣涵蓋 batch 開始到 dispatch。完整延遲從該 batch 開始，到 write 更新 in-memory balances 或 query 結果返回為止。

延遲區段依相鄰 `Instant` 邊界切分：

```text
batch_total_ns = build_or_prep_ns
               + dispatch_to_worker_start_ns
               + worker_setup_ns
               + native_call_ns
               + decode_validate_ns
               + worker_post_call_ns
               + worker_finish_to_await_resume_ns
               + await_resume_to_ack_ns
```

Trace 同列輸出 `component_sum_ns` 和 signed `residual_ns = batch_total_ns - component_sum_ns`，方便確認欄位能重建總延遲；正常值應為 0。Query 的 `worker_post_call_ns` 包含 native call 結束後到 validation 開始之間的少量工作，以及 PerfContext 收集；該時段不與 `decode_validate_ns` 重疊。

`worker_thread_id` 是 Linux OS TID，`worker_cpu_id` 是 blocking closure 剛開始時 `sched_getcpu` 回報的 CPU。CPU 欄位是單點取樣；thread 在 batch 執行中可能被 OS 移到其他 CPU。

`native_call_thread_cpu_ns` 在同一個 blocking closure 內以 `CLOCK_THREAD_CPUTIME_ID` 緊貼 `write_opt` 或 `batched_multi_get_cf` 前後取樣，表示該 worker thread 在 native call 區間消耗的 CPU 時間。`native_call_ns` 的 wall clock 區間也包住這些取樣，因此 CPU 值應不大於 native wall；極小差異可能來自兩種 clock 的取樣解析度。計時或讀取 `RUSAGE_THREAD` 失敗、counter 倒退，或 thread CPU clock 未前進時，該 trial 會回報錯誤而不輸出 trace，不會用 0 代表讀取失敗。`native_call_voluntary_context_switches`、`native_call_involuntary_context_switches`、`native_call_minor_page_faults` 和 `native_call_major_page_faults` 是同一區間的 `RUSAGE_THREAD` delta；這些事件本來就可能是 0。

## RocksDB PerfContext

診斷模式在每個 write/query `spawn_blocking` closure 內設定 RocksDB `PerfStatsLevel::EnableTime`，reset 該執行緒的 `PerfContext`，執行本批 native operation，並在同一 closure 讀回 metrics；不會跨 worker 執行緒讀取 thread-local context。Write 欄位含 WAL time、memtable time、write delay 和 write pre/post-process time。Query 欄位含 block cache hits、block reads/bytes/read/checksum/decompress time、multiget bytes、index/filter block time、memtable lookup time/count、output-file lookup time、Bloom hit/miss counts、user-key comparison count、new table block iterator time、block seek time、table lookup time，以及 DB mutex lock 和 condition wait time。時間欄位以 ns 命名，計數與 bytes 欄位分別為事件數和位元組數；不適用的 read/write metrics 留 0。這些 PerfContext 指標在本批呼叫前 reset 並於呼叫後、同一 closure 內讀取。此 thread-local snapshot 對應本批同步呼叫，不含 RocksDB background thread latency 的逐批歸因。

## p99.9

Trace 可用 `item_count` 對 `batch_total_ns` 做 transaction-weighted nearest-rank 分位數。將 batch 依 `batch_total_ns` 遞增排序，p99.9 的 rank 為 `ceil(sum(item_count) * 0.999)`；累加 item count 後，第一個累積值達到該 rank 的 batch latency 即為 p99.9。這和 summary CSV 將每批 latency 按該批 transaction 數加權的 percentile 語意相同。

診斷會啟用 RocksDB perf timers、每批讀取 PerfContext 並保存每批 trace row，這些工作會增加量測成本；用短輪次找出延遲落在哪一階段，再以一般模式做正式比較。

## Smoke 命令

4,096 transactions 搭配 2,048 batch 會在 write/query 各產生兩列：

```sh
BINDGEN_EXTRA_CLANG_ARGS='-I/usr/lib/gcc/x86_64-linux-gnu/13/include' \
  cargo bench --bench rocksdb_tokio_sequential -- \
  --iterations 4096 --repetitions 1 --batch-sizes 2048 --diagnostic \
  --output-dir target/rocksdb-tokio-diagnostic-smoke \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --preflight-max-cpu-pct 100 --preflight-max-disk-busy-pct 100 \
  --preflight-min-mem-bytes 16777216 --preflight-free-reserve-bytes 1048576
```

Smoke 應產生 4 筆 trace rows；每列新增的 native thread CPU 和 PerfContext 欄位應有數值，`native_call_thread_cpu_ns` 應不大於 `native_call_ns`（容許極小 clock 解析誤差），`component_sum_ns` 應等於 `batch_total_ns`、`residual_ns` 應為 0，worker TID/CPU 欄位應有值。stderr 的 `db_cleanup=complete` 表示 trial database 已刪除；output directory 只保留 preflight log 與 trace CSV。
