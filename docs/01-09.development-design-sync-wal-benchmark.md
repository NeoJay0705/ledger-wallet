# 同步 WAL 持久性 benchmark 設計

## 目標

此 benchmark 衡量單一同步 writer 將固定大小交易批次寫入檔案後，以 `File::sync_all` 確認持久性所需的 throughput 與 latency。它使用分段檔案、frame checksum、目錄同步，以及完整 recovery 驗證。它不使用 Tokio、transaction processor 或背景 writer。

## 固定 workload

預設每輪寫入 10,000,000 筆預先產生並在所有情境重用的 128-byte 記錄。LSN 與 transaction ID 從 1 開始嚴格遞增；帳戶 ID 以 100,000 個值循環；signed cents 依記錄序號交替 debit 與 credit。記錄產生在量測外，且不更新餘額。預設 batch size 為 64、256、1,024、2,048、4,096，每組 3 輪。這些情境使用 1 GiB rotation threshold；另有 batch size 4,096、256 MiB threshold 的 3 輪情境。

`--iterations`、`--repetitions`、`--batch-sizes`、`--rotation-bytes` 可縮小工作量或選擇情境。未提供 `--rotation-bytes` 時使用上述預設矩陣；明確提供時，會對所選 batch size 與 rotation threshold 做笛卡兒積。Benchmark 輸出 CSV 到 stdout，預設 WAL 暫存位置是 `target/wal-sync-benchmark/`。

## WAL 格式與 durability

每個 frame 包含 magic、格式版本、header 長度、record 長度、record 數、payload 長度、首筆 LSN、整批固定長度 records，以及包含 CRC32、frame 長度與結尾 magic 的 trailer。CRC 使用 table-driven CRC32。每個 batch 完整寫入同一個 segment，絕不跨 segment 拆分。

成功回覆一個 batch 前，writer 對 segment 呼叫一次 `sync_all`。完整批次與 final partial batch 都遵守相同規則。寫入、檔案同步、目錄同步或 segment 建立有任何錯誤時，writer 進入 failed 狀態，該輪不輸出成功結果。若 `sync_all` 回報錯誤，實際持久狀態不確定；程式不會把該批標記為 durable。

Segment 在整批寫入後若累計 bytes **大於** threshold，writer 會在下一批開始前建立新 segment。因此觸發 threshold 的批次留在舊 segment，segment 不會在 batch 中途輪替。新 segment 檔案建立後先同步 run directory 以持久化檔名，再寫批次；檔案 `sync_all` 成功後才承認該批 durable。Segment 名稱為 `segment-000000.wal` 等連續序號。

Recovery 依 segment 序號讀取 frame，檢查 frame header、版本、長度、checksum、trailer、record bytes 與連續 LSN。Frame payload 上限為 64 MiB；超過此界限的批次會在寫入前被拒絕。只允許最後 segment 的不完整尾 frame 被截斷；較早 segment 的不完整 frame、完整 frame checksum 錯誤、序號缺口或資料缺口都會失敗。Benchmark 量測停止後 recovery 驗證恰好全部輸入 records，再刪除本輪唯一 run directory 中的 `.wal` 檔。Recovery 驗證與清理不列入 throughput 或 latency。

## 指標

Durable RPS 是 records 除以第一個 batch handoff 至最後一次成功 durability acknowledgement 的 wall time。每筆記錄 latency 是完整 batch handoff 至該批 durability acknowledgement 的時間；該批所有 records 共用此觀測值。mean 使用所有 records 的累積 nanoseconds，p50/p95/p99 使用 `splitmix64(index) % stride == 0` 的 deterministic sample，並固定納入第一筆以避免短輪次空樣本。分位數採 nearest-rank。

CSV 也包含 batch、write、file sync、directory sync、segment open、rotation latency 的 count、total、mean 與 p50/p95/p99；實際 frame bytes、records/batches/segments、file sync 次數、directory sync 次數、recovery 時間、ProcessTime CPU 秒數與 CPU core equivalents。Linux 上另外記錄 `/proc/self/io` 量測前後值與 target block device `/proc/diskstats` busy time。若無法將 WAL 目錄映射到可讀取的 block device stats，preflight 會失敗且不輸出 benchmark 數字。

## Preflight 與隔離

每輪執行前檢查目標 filesystem 與可用空間、`MemAvailable`、程序 RSS、整體 CPU utilization 及 target block device busy。若無法將 WAL 目錄映射到可讀取的 `/proc/diskstats` 裝置，preflight 會失敗且不輸出 benchmark 數字。`tmpfs`、`ramfs` 與 `devtmpfs` 會被拒絕。預設觀察窗 3 秒，CPU 上限 10%、disk busy 上限 5%，最多等候 60 秒。可用 `--preflight-*` 調整觀察時間、等待時間、百分比門檻、額外記憶體 headroom 與 free-space reserve；檢查仍會執行。Free-space reserve 預設為 `max(預估 WAL bytes 的 25%, 1 GiB)`。未達門檻時繼續等待；timeout 時失敗且不輸出該輪 benchmark 數字。

輸出 base directory 若不存在，程式逐層建立目錄並同步每個新目錄的 parent，以持久化新目錄項目；每輪建立獨立、唯一的 run directory 後，也會同步它的 parent。這些目錄準備與同步都在第一個 WAL batch handoff 前完成，不計入 durable throughput 或 latency。新 WAL segment 檔名仍在每批寫入前同步 run directory，這項同步會計入 benchmark 指標。成功與錯誤路徑都只刪除該輪目錄中的 `.wal` 檔及該空目錄，不對 benchmark base directory 或其他資料做遞迴清除。

## 驗證範圍

Recovery tests 以一般檔案操作模擬 final segment 的 torn tail 與完整 frame checksum corruption，並檢查 recovery 的截斷或錯誤結果。這些測試沒有實際斷電、強制 power-cycle 或硬體故障；目前也沒有實測在斷電後由特定 filesystem 與儲存裝置保留 `sync_all` 結果。因此 benchmark 驗證 WAL 格式與 recovery 邏輯，不構成實際斷電測試。

短 smoke 範例：

```sh
cargo bench --bench wal_sync -- \
  --iterations 10000 --repetitions 1 --batch-sizes 1024 \
  --rotation-bytes 104857600 \
  --preflight-observation-ms 50 --preflight-timeout-ms 5000 \
  --preflight-max-cpu-pct 100 --preflight-max-disk-busy-pct 100 \
  --preflight-min-mem-bytes 16777216 --preflight-free-reserve-bytes 1048576
```

完整預設矩陣刻意不列入日常 smoke command；它會寫入總計數億筆記錄並執行 18 輪 durable storage 測量。
